## Decisions

- **D1. No reset signal (M2, L12; coordinator decision).** A cooldown ends only at its stored end, the reported reset time or the default. The contract's overview, section 5, the cooldown test of section 9, section 10, and the `account-pool-port` requirement "Cooldown bounds" drop the reset signal. `reset-time` stays: it is the port's optional reset time on a `limit` event, which sets the cooldown's end.
- **D2. The usage window is the pool's (M1, L13; coordinator decision).** The pool configuration sets a usage window length per harness plugin, a positive whole number of minutes, as an installation setting that an `installation-owner` sets. A usage report stores `windowEndsAt` as the database time at which the control plane applies it plus that length; without a length the end is unknown and the report clears `usage`, so the tie-breaker skips the slot, as it skips an ended window. The record keeps its `SlotUsage` shape, so no type changes: the observed time is folded into the stored end. The tie-breaker of section 4.2, its selection test in section 9, and both specs say "derived window". The contract sets no range and no default for the length; item 12 adds the setting and its validation.
- **D3. No plugin query outside a session (M4).** The pool never asks a harness plugin anything; the worker's harness host is the only caller of a plugin.
  - *Mechanism.* The add-slot command checks a slot's mechanism against the admitted pairs of harness plugin and mechanism that the control plane already keeps for deliveries (contract section 7.1). The item that admits a pair checks that the plugin declares the mechanism, and the port still refuses an undeclared mechanism at every session start with `invalid`.
  - *Health.* A slot becomes `unhealthy` from a session's own report: a turn failure `authentication` or a start or resume failure `forbidden`. It becomes `healthy` again only when a rotation switches it to a new credential, which section 8.1 already does; an operator who judges a failure transient rotates the slot to the same text.
  - *Alternatives.* (a) The worker reports its plugins' `capabilities` at admission (G3 item 27) and the control plane caches them: rejected, because it widens item 27, ties the pool to the fleet, and lets workers with different plugin versions disagree. (b) The control plane loads the plugin package to read `capabilities` or check a credential: rejected, because that is the query that M4 forbids and puts harness code in the control plane. (c) A probe session to check a credential: rejected, because it consumes the subscription and needs a run, a worker, and a reservation. (d) An operator command that marks a slot healthy: not added, because no finding asks for a new command and a rotation already restores health; item 12 or the owner may add it later.
  - No owner decision is needed: the choice adds no command, no port, and no setting beyond D2, and it keeps ADR 0005 decision 8.
- **D4. The slot of a signal (L5).** A signal or failure names no slot; it belongs to the session of one attempt, whose reservation records the one selected slot in `providerCredentials`. The control plane applies it to that slot by compare-and-set; item 18 relays it from the worker with its attempt, which section 10 now names.
- **D5. After a limit (L1).** Section 4.4 step 3 no longer promises a continuation "as soon as" a slot is eligible: each later placement try repeats the steps, and the tries follow the G2 fair order and backoff, so the work continues at the first try after a slot is eligible.
- **D6. Session invariant owner (L2).** Capacity reservation section 10 says that G2 item 7 delivered the per-task invariant and that G3 item 4 must establish the per-session one, as the account pool contract section 3.2 already says. The `capacity-reservation` living spec names no plan item and no reset signal, so it has no delta.
- **D7. Order and status (L10, L11).** The contract and the `account-pool-port` requirement "Slot store compare-and-set" say code-unit order, the order of the `"C"` collation, as `byCodeUnits` and the capacity contract do. The status line says the contract was reviewed and merged, and that the follow-up changes of G3 item 0 align it.
- **D8. Other documents.** `docs/architecture.md` named "load, limit, and reset signals"; it now names the port's `usage`, `limit`, and `reset-time` signals. ADR 0005 ("report load, limits, and resets") is an accepted decision record and stays; its resets are the reset times. The `docs/g3-plan.md` row of item 3 describes merged work and stays. `docs/contracts/git-workspace.md` also says code point order; it is outside this change's capabilities and is listed in verification.

## Risks

- A usage report applied late gets a later window end than the provider's, by the relay delay; the window length bounds the error, and an ended window only skips the tie-breaker.
- A credential rejected for a transient provider fault keeps its slot `unhealthy` until an operator rotates it; the pool falls back to its other slots and harnesses meanwhile.
