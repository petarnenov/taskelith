## Context

`PlacementService` (`apps/control-plane/src/application/placement-service.ts`) runs a pass every 5 s over at most `PLACEMENT_BATCH` (100) waiting tasks, in the rotation order of `fairWaitingOrder`, each in its own transaction. `#offer` kept offering after the first decline for lack of fleet capacity; the `RotationCursor` (`packages/modules/scheduling/src/domain/fair-order.ts`) ignored those later offers, so the cursor stayed before the declined project, but a slot that freed during the pass went to the first later task of the read, of a project after the declined one. `advance-placement-rotation-cursor` recorded this as review pass 3, L2, with the candidate fix of ending the pass at that decline; `placement-backoff-preserves-rotation` (pull request #344) kept it out of scope (open point 2) and made a fleet capacity decline keep the task's wait.

## Analysis

- **Where the cursor ends.** The cursor rule is unchanged: it moves only by the offers before the first fleet capacity decline, to the project of the last of them placed, else of the last of them, else it stays. Ending the pass there makes no offer after the decline, so the cursor ends exactly where it ended before, and the next read starts after it. Between the cursor and the declined project lie only projects whose offers in the pass were declined for their own reasons, and projects with no further task in the read; the declined project's task is offered before any task of a project after it in the rotation, so the next free slot follows the rotation.
- **No placement the contract promises is lost.** A decline for lack of fleet capacity means every candidate declined for a reason about the worker and the last one for a fleet reason (`reserveOnCandidate` tries each candidate on a worker reason), or quarantine, or no candidate. The candidates do not depend on the task (`tx.workers.candidates()`), worker eligibility does not depend on the task, every G2 task requests `DEFAULT_ATTEMPT_REQUEST` with no hard control, and the worker checks come before the quota checks (contract section 4 step 3 before step 4; section 13 "Check order"). Placements in the pass only take capacity, and an attempt ended by a rejecting reason held none. So a task after that decline finds no room either, unless capacity frees during the pass, and that capacity is exactly what the rotation assigns to the declined project.
- **Own declines continue.** Quotas, provider concurrency, `control-not-enforceable`, a backing-off retry, a rejecting or standing reason, a task that no longer waits, and a failure without a reason are the task's own: the pass goes on, so one project's limits never hold the others (contract section 12, "One project's retry loop ..."; requirement "Project rotation", scenario "Many blocked projects").
- **What the contract promises.** Section 5 bounds a pass by the batch ("at most"); nothing promises that a pass reaches the tasks after a fleet capacity decline. The only cost is that a slot freeing during a pass is placed by the next pass, at most one pass interval (5 s) later.
- **Alternatives considered.** Continuing the pass but offering a freed slot back to the declined project first would need a second read or a retry within the pass, with the same result one pass earlier at more complexity; re-reading after every placement is costlier. Ending the pass is the smallest rule that keeps the rotation exact.

## Decisions

- **End the pass at the first fleet capacity decline.** `#offer` leaves its loop (`break`) when `isFleetCapacityDecline(outcome)` is true, after `cursor.ranOutOfCapacity()`. It answers the placements so far and the cursor as before.
- **No settle for that decline.** `#settle` is no longer called for a fleet capacity decline, so its early return for one was removed; the task's wait stays unchanged as `placement-backoff-preserves-rotation` decided, and the existing test `a fleet capacity decline keeps the failure count of an own-reason backoff` still holds.
- **The cursor keeps its guard.** `RotationCursor.ranOutOfCapacity()` stays as the domain rule and is still called: the service now makes no later offer, so its guard against later offers no longer changes the result, but the cursor's own contract and tests (`packages/modules/scheduling/test/resource-admission.test.ts`) keep it.
- **Both stores.** The rule lives only in the service's loop; `InMemoryPlacementQueue` and `PostgresPlacementQueue` answer the same read as before and need no change. The unit tests run over the in-memory queue; the integration test runs the freed slot through `PostgresDatabase`.
- **Contract first.** Capacity reservation contract sections 5 and 13, operational targets section 1, and the `execution-placement` requirement "Project rotation" changed in their own commit before the code.

## Known limit: placement transactions of a full fleet

`placement-backoff-preserves-rotation` recorded (open point 1) that a full or quarantined fleet costs up to `PLACEMENT_BATCH` (100) rolled-back placement transactions every 5 s, about 20 per second, and that no load test measured it. With this change a pass makes at most one placement transaction that a fleet capacity decline rolls back, and no offer after it. The offers before it are tasks that end, stand, back off, or are placed for reasons checked before the worker (a rejecting request check of section 13 "Check order", a backing-off retry, a task no longer waiting); each such task leaves the reads until it is due again or for good. In a quarantined installation every task's first check fails, so each pass makes one transaction. The unit test `a full fleet costs one placement transaction per pass` (`apps/control-plane/test/placement-service.test.ts:396`) checks one transaction for three waiting tasks on a full fleet; it failed with three before the change. No load test was run; the cost per pass is bounded by reasoning and that test, not measured.

## Risks

- A slot that frees during a pass is placed one pass later (up to 5 s) instead of at once by a later task of the same read.
- The rule relies on a fleet capacity decline of one task implying the same for every later one. That holds while all requests are equal and eligibility does not depend on the task, as in G2; per-task requests or hard controls must revisit it, as `FLEET_REASONS` (`packages/modules/scheduling/src/domain/capacity-reasons.ts`) already notes for the classification itself.
- The classification still sees only the last candidate's reason (`advance-placement-rotation-cursor`, review pass 2, L4).
