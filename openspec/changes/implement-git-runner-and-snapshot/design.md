## Context

G3 item 16 implements the Git workspace contract (`docs/contracts/git-workspace.md`) with the pinned `git` CLI of G3 plan decision D3 (a), in sub-changes 16a to 16e (`docs/g3-plan.md`, row 16). 16a settled the contract, the `git-workspace-port` spec, the port, the fixture hooks, the conformance suite, and the test double ([16a design](/openspec/changes/archive/2026-10-28-align-git-workspace-adapter-contract/design.md), D1 to D12). This is 16b: the adapter's local operations, `prepare`, `inspect`, `snapshot`, `remove`, and `sweep`, with the pinned client, its environment, the rewrite of `.git/config`, and the crash points. The coordinator first briefed 16b as primitives only and then, on 2026-10-28, made the plan row the authority (proposal, "Scope correction").

Inputs read at `dev` `1c73e1a7`: the contract (all sections), `openspec/specs/git-workspace-port/spec.md`, the archived 16a change, `packages/modules/workspace` (domain, ports, suite, double, and tests), `docs/g3-dependencies.md` section 4, `packages/testing/src/crash-points.ts`, and the adapter packages `postgres`, `data-root`, and `worker-journal` for the package conventions.

## Decisions

1. **Placement.** A new private workspace package `@taskelith/git-workspace` under `packages/adapters/git-workspace`, matching the review checklist's glob `packages/adapters/**/git*`. It depends on `@taskelith/workspace` for the port, the domain rules, and the contract values, on `@taskelith/data-root` for the durable record write (`replaceFileAsync`, `syncPathAsync`), and on the kernel and `@taskelith/execution` for types; process spawning and file system details stay in the adapter. It imports `node:child_process`, so the boundary check treats it as worker-only. It uses Node.js built-ins only, so no third-party dependency is added.
2. **Gate before construction.** `GitWorkspaces` takes a `VerifiedGitClient`, which only `verifyGitClient` (`VerifiedGitClient.verify`) creates after `git --version`, run in `/` with the built environment, printed exactly the pin's version (`checkGitClient`). A client that cannot start fails the gate as `git-client-mismatch` too. The class holds a private field (`#verified`), which makes the type nominal, so no object literal with a `runner` passes for one, and a type test with `@ts-expect-error` proves it (pass 2, L2); so "the adapter runs no Git before the gate" holds at compile time; the worker's refusal to start on that failure is the wiring of 16e. A test pin is a recording wrapper of the host's `/usr/bin/git` with that Git's own version string, so the tests run on any host; the mismatch is tested with `git version 2.56.0` and a missing path.
3. **Runner.** `GitRunner.run` spawns `pin.path` (never a `PATH` lookup) with `env` set to exactly `gitConfigEnvironment(credential?.authorization)`, whose built environment holds `GIT_NO_REPLACE_OBJECTS=1` since pass 1, so no replace ref under `refs/replace/` changes an object Git reads, plus `NODE_V8_COVERAGE: undefined`: Node copies its own `NODE_V8_COVERAGE` into a child's environment unless `env` names it, and a variable named as undefined is left out, so the child gets exactly the built environment also while the worker collects coverage. So nothing of the worker's environment is inherited, and the header is in the environment of the one process that names a credential. In 16b only the clone does; every other process gets no header. Standard input is always a pipe, closed at once when no input is given, so Git never waits on the worker's terminal. A process that cannot start is `unavailable`; a non-zero exit stays an exit code, and `succeeded` turns it into a failure of the code the caller names (`unavailable` for the clone, `internal` for local Git).
4. **Scrubbing.** `credentialForms` gives every non-empty form of the command's credential, however short: the secret, the `Authorization` value, its parts after the scheme, and the base64 of each. It is the adapter's own redaction; the suite's `sensitiveValues`, which skips forms shorter than 8 characters against false findings, stays a conformance heuristic (pass 1, finding 4). Both captured streams of a process that carries a credential are scrubbed in one pass, longest form first, so no replacement is matched again: standard error as text, standard output as latin1 text, one character per byte, so every other byte survives. A process without a credential, such as the `cat-file` of a snapshot, keeps its standard output exact (pass 1, finding 3).
5. **Configuration rewrite.** `writeRepositoryConfig` creates `.git/config.taskelith-<random>` with `O_CREAT | O_EXCL | O_NOFOLLOW`, writes `repositoryConfigText` of the record's object format (`repositoryformatversion = 0` for SHA-1; `1` and `extensions.objectformat = sha256` for SHA-256), and renames it over `.git/config`. The rename replaces a symbolic or hard link the agent left there instead of writing through it, which matters most where the agent and the worker are one account (macOS). With it, `resetRepositoryFiles` deletes `.git/info`, whose `exclude`, `attributes`, and `grafts` Git reads beside the tracked files, so no ignore rule the agent wrote there hides untracked work from `inspect` and `remove` (coordinator decision B2). An operation does both once, after the checkout checks and before its first Git call; its later Git calls follow without any agent process in between, because a reclaimed checkout is closed to the execution (contract section 2). Contract section 7 now says "once per operation, before its first Git call" (coordinator decision B3).
6. **Checkout checks.** `checkCheckoutSafety` uses `lstat` and `readdir` only, with names and paths as bytes (`encoding: 'buffer'`), so a directory whose name is not UTF-8 is walked as itself, not as a decoded name that does not exist (pass 1, finding 6). Since pass 2, `.git` may hold only directories and regular files, so a FIFO, socket, or device that would block a Git process at `open` is refused like a link (M1); an entry named `.git` in any case is refused below the top, and at the top unless it is `.git` itself, because Git refuses `.GIT` in a path and APFS finds it as `.git` (L4); and only `ENOENT` or `ENOTDIR` from `lstat` means absent (`entryAt`, `isPresent`), so any other error rejects and becomes `unavailable`, never an absent hand-off record, operation marker, or redirection, or an unsafe checkout (L1): the checkout and `.git` are directories of the worker's uid, `.git` holds no `commondir`, no `objects/info/alternates`, and no symbolic link at any depth, and no entry named `.git` exists below the top. Each failure is `precondition-failed` with reason `unsafe-checkout`. They run once per operation, after the workspace record and the hand-off record are read, so the order of section 9 holds: `not-found`, `workspace-handed-off`, `unsafe-checkout`, then `workspace-dirty`.
7. **Prepare.** After the refusals that need no Git (the head's repository, `checkRemoteTransport` with the composed policy, and `checkCredentialScope`), `prepare` creates `.staging-<name>/` (`0710`) exclusively, so a concurrent prepare of the same attempt fails with `conflict`, and the checkout directory with mode `2700` before the clone writes into it. The clone is `git clone --no-checkout --quiet --origin origin -- <remote> <checkout>`, started in `/` with the header (`WS1`). It then reads the object format, rewrites `.git/config` before any further Git call, so the clone's own remote settings never act, resolves the start from the clone's `refs/remotes/origin/` (the task branch, else the base branch; or the `at-head` commit and its tree, `not-found` or `head-mismatch`), checks it out on the task branch with `--no-track` or detached, and writes the workspace record durably. The rename into place (`WS2`) refuses an existing workspace atomically, as `ENOTEMPTY` or `EEXIST`, so the existing-workspace check comes last, as section 9 orders it. A refusal deletes the staging entry; a crash leaves it for `sweep`.
8. **Record after the clone.** The record holds the clone's object format, which is known only after the clone, so it is written after the clone and the checkout of the target, still inside the staging entry. Contract sections 2 and 3 now say so (coordinator decision B3); nothing reads a staging entry, and `sweep` deletes it after a crash.
9. **Status.** `inspect` first lists the index with `git ls-files --stage -z` (`parseIndexEntries`) and writes every entry anew from its mode, object, stage, and path with `git update-index -z --index-info` (`indexInfo`). A new entry has no stat data, so Git compares the file's content; no assume-unchanged or skip-worktree flag, with which `git status` skips a file (pass 1, finding 2); and `add_index_entry` invalidates the cache tree on its path, which `diff-index --cached` otherwise trusts for a whole directory. So neither forged stat data after a change of the same size (pass 2, H2) nor a forged cache tree over a staged change (H3) hides work; this replaces the flag clearing of pass 1. Then `indexMatchesTree` compares the merged entries with the verified head tree (D10): any added, changed, or removed file, link, or gitlink makes the workspace `modified`, so a gitlink added to the index alone, which `--ignore-submodules=all` and the untracked scan skip, never hides a directory of work (H1); a conflicted path is left to the status. Then it runs `git status --porcelain=v2 -z --branch --untracked-files=all --ignore-submodules=all`, parsed by `parsePorcelainStatus` into the head, the branch (null when detached), and entries whose paths stay bytes. The parser checks every field before a path, the `XY` code, the submodule state, the modes, the object names, and the rename score, refuses an empty path, and requires `branch.oid`, an object name or `(initial)`, and a non-empty `branch.head` (pass 1, finding 10). `modified` comes from a changed (`1`) or renamed (`2`) entry, which covers the index and the working tree, `untracked` from `?`, and `operation-in-progress` from an unmerged entry (`u`) or one of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, `rebase-merge`, `rebase-apply`, or `sequencer` in `.git`; `off-branch` from the record's task branch. The brief asked for `decodeGitPath` on status paths; the parser keeps them as bytes instead, because section 9 lets only `snapshot` refuse a name that is not UTF-8, and decoding there would make `inspect` and `remove` fail on such an untracked file. `decodeGitPath` decodes the paths and link targets of the snapshot.
10. **Snapshot from verified objects (decision Q1 b).** Git checks no object's bytes against its name when it reads them, so a pack, loose object, or multi-pack-index the agent added could give an existing name other bytes (pass 2, H4). `readHeadTree` therefore reads the head commit, then each level of trees, and `#snapshotTree` the blobs, with `git cat-file --batch` (`parseBatchObjects`, which requires, in the requested order, one header `<object> <type> <size>` each with the requested type, a decimal size without sign or leading zero, that many bytes, and nothing after the last, pass 1, finding 9), and `readVerified` checks that each body hashes to its name as `<type> <size>\0` and the body, in the record's object format (`objectName`); otherwise the operation fails with `internal`. The commit's first line names the tree (`parseCommitTree`); `parseTreeObject` reads a tree's entries, `<mode> <name>\0<raw name>`, refuses a mode that is not octal without a leading zero or not a tree, file, link, or gitlink, and canonicalizes a file's mode as Git does (`100755` when the owner may execute, else `100644`). `git ls-tree` is no longer used (it replaced pass 1, finding 11's parser). The head tree that `inspect` reports is this verified one, so `rev-parse <commit>^{tree}`, which could read a forged object, serves only `prepare` on the fresh clone. With `GIT_NO_REPLACE_OBJECTS=1` no replace ref acts (pass 1, finding 1), and `core.commitGraph=false` and `core.multiPackIndex=false` keep Git's own reads, such as the status's view of the head tree, off a forged commit-graph or multi-pack-index. A blob forged in a pack, with its loose object deleted, fails the snapshot; a forged commit-graph root tree changes nothing (tests "an object whose bytes do not hash to its name fails the snapshot" and "a forged commit-graph never changes what status reads"). A regular file's mode is canonicalized as Git does (`100755` when the owner may execute, else `100644`). `snapshotTree` refuses a gitlink first, then decodes every name and link target, then refuses a name that Git refuses in a path and a duplicate path with `unsafe-tree-path` (D16), so the order of section 9 holds; `encodeHeadSnapshot` builds the bytes. Nothing uses `git archive`.
11. **Crash points.** `GitWorkspaceCrashPoint` names `WS1` to `WS4` with `.before` and `.after`; tests pass the harness's `CrashPoints` with the action `throw`, production `NO_CRASH_POINTS`, as the postgres adapter does. `WS4` is reached both by a removal and by `sweep` for each removing entry. `WS5` to `WS10` belong to the hand-off and the reclaim (16d).
12. **Test composition.** The fixture serves a local bare repository over Git's dumb HTTP protocol from a static Node.js file server on `127.0.0.1`, which a clone can use, with the policy `https-or-loopback-http`; it counts requests as remote calls and keeps their `Authorization` headers. The smart-HTTP server that the push and the credential checks need is 16c's. The pinned client is a Perl wrapper that records each process's arguments, process identifier (kept by `exec`), working directory, exact environment, and the configuration of the repository Git finds from that directory, then runs `/usr/bin/git`; Perl is used because a shell adds variables such as `PWD` to the environment it would record. Native helpers run `/usr/bin/git` directly with their own environment, so they are never recorded.
13. **Deferred conformance cases.** `test/conformance.test.ts` runs every case of `WORKSPACE_CONFORMANCE` and skips, with the reason "sub-change 16c" or "16d", the 15 cases that call `push`, `readRemoteHead`, `handOff`, or `reclaim`; the provider's methods for those reject loudly, so a case that reaches one fails. Since pass 1 no test file of the adapter removes `NODE_V8_COVERAGE` from its own environment, so the Git process checks see the child environment that production gets, and a runner test sets the variable and requires the exact built environment (finding 5). A test checks that every skipped name is a case of the suite. The adapter's own tests cover what those cases check of the local operations: the snapshot, the staged-and-reverted refusal, the unsafe checkouts, the planted settings, and the Git process checks, through `gitProcessProblems`, which `@taskelith/workspace` now exports.
14. **Error handling.** Every contract refusal is a kernel `Result` with its code and reason. `prepare`, `inspect`, `snapshot`, and `remove` run inside `failingFileSystemAsUnavailable`, which turns a Node system error, one with a string `code` and `syscall`, into `unavailable` with only those two, and lets anything else reject, so a simulated crash stays a crash (pass 1, finding 7). `prepare` applies it to the build and to the rename into place, and deletes the staging entry after any failure, so a fault before the rename, such as `EIO` from `rename`, leaves no entry (pass 2, L3). A failure after the rename, which can only be the directory sync, fails the prepare with `unavailable` and keeps the ready workspace, which `list` reports and the attempt can use; the alternative, success, would hide an I/O error, and a retry would get `conflict` either way (contract section 3). A malformed workspace record is `internal`, never an absent workspace; only `list` and `sweep`, which the contract lets reject, reject on a fault. A revision lookup returns `Result<string | undefined>`: exit code 1 of `rev-parse --verify --quiet` is a missing revision, any other outcome a failure, so a failed lookup never reads as a missing task branch and never falls back to the base branch (pass 1, finding 8). A crash leaves the staging entry for `sweep`. A concurrent removal that finds the workspace already renamed succeeds.

15. **Index caches (author self-check fix after pass 1).** `git status` trusts an untracked cache in the index while a directory's stat data match, and an agent can forge one: renaming a cached untracked name to a tracked one hid the file from `status --untracked-files=all`. `core.untrackedCache=false` is therefore the last command-scope setting before the header (`GIT_COMMAND_SCOPE_SETTINGS`, contract section 7), appended so the earlier settings keep their positions; pass 2 appended `core.commitGraph=false` and `core.multiPackIndex=false` after it (D10). `core.fsmonitor` needs no such setting: Git runs a monitor only from `core.fsmonitor` in configuration, which the rewrite, the absent system and global files, and the built environment leave unset, and with the monitor disabled Git drops the index's `FSMN` extension without applying its valid bits, so `core.fsmonitorHookVersion` has no effect either. A check on the host Git confirmed it: a hook that reported no change hid a modified file, and after the rewrite the same index showed it.

16. **Unsafe tree paths (pass 2, M2).** A tree object can hold any name, and `hash-object -t tree --literally` writes one that Git's own commands refuse, such as `..`, `.git`, or a name twice. No existing reason fits: `non-utf8-path` is about encoding, `gitlink-in-tree` about content. A new reason, `unsafe-tree-path`, joins `WORKSPACE_FAILURE_REASONS` and contract sections 9 and 10. `isSafeTreeName` in the port follows Git's `verify_path` for one name with its NTFS rule (`.git` or `git~1`, any case, then dots, spaces, or a `:` stream) and HFS+ rule (`.git` with ignorable code points removed); `encodeHeadSnapshot` refuses such a name and a path that is both a file and a directory, after its gitlink and UTF-8 checks, so the test double refuses them too, and the adapter's `snapshotTree` adds the exact duplicate, which a map cannot hold.

## Coordinator decisions (Niki, 2026-10-28)

- **B1, crash points.** 16b covers `WS1` to `WS4` with crash tests; `WS5` to `WS10` go to 16d, as G3 plan row 16 orders.
- **B2, `.git/info`.** 16b deletes `.git/info`, `exclude` and `attributes` among it, together with the `.git/config` rewrite (D5), with a fail-before test and the scenario "Planted ignore rule"; contract section 7 says so.
- **B3, contract amendments.** Contract sections 2 and 3 say that `prepare` writes the workspace record after the clone, inside the staging entry (D8); section 7 says that the Git directory checks and the rewrite run once per operation, before its first Git call (D5), and the built environment names `GIT_NO_REPLACE_OBJECTS=1` and keeps out a variable the runtime adds, such as `NODE_V8_COVERAGE`. The decision named a test exception for that variable; the runner keeps it out in production instead (D3), so the contract needs none. The living requirements "Git directory safety" and "Git configuration scope" are modified to match.
- **Untracked cache (author fix before pass 2).** The coordinator asked to close the untracked-cache gap that the pass 1 report listed (D15).
- **Pass 2, M3.** The coordinator authorized amending the contract sections that 16b implements: section 9 now lists `unavailable` for a file system fault and `internal` for a malformed record, unreadable Git output, or an object that does not hash to its name.
- **B4, hand-overs.** The clone's umask `0007` and the execution group go to 16e; a time limit for Git processes goes to 16c.

## Risks

- The clone does not force `fsync` of Git's objects (`core.fsync` is not among the command-scope settings), so a power loss right after `WS2.after` could leave a ready workspace with lost objects; a process crash cannot.
- No Git process has a time limit; a remote that stops answering holds a prepare until the transport fails. 16c, which adds the remote operations, decides a bound (B4).
- The clone runs with the worker's umask, not `0007`, and the checkout keeps the worker's primary group; 16e wires the execution group and the umask (B4).
- The checks walk the whole working tree once per operation; a large checkout costs a walk per `inspect`.
