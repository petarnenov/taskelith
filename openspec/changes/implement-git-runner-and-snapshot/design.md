## Decisions

1. **Placement.** A new private workspace package `@taskelith/git-workspace` under `packages/adapters/git-workspace`, matching the review checklist's glob `packages/adapters/**/git*`. It depends on `@taskelith/workspace` for the port, the domain rules, and the contract values, on `@taskelith/data-root` for the durable record write (`replaceFileAsync`, `syncPathAsync`), and on the kernel and `@taskelith/execution` for types; process spawning and file system details stay in the adapter. It imports `node:child_process`, so the boundary check treats it as worker-only. It uses Node.js built-ins only, so no third-party dependency is added.
2. **Gate before construction.** `GitWorkspaces` takes a `VerifiedGitClient`, which only `verifyGitClient` (`VerifiedGitClient.verify`) creates after `git --version`, run in `/` with the built environment, printed exactly the pin's version (`checkGitClient`). A client that cannot start fails the gate as `git-client-mismatch` too. The type makes "the adapter runs no Git before the gate" hold at compile time; the worker's refusal to start on that failure is the wiring of 16e. A test pin is a recording wrapper of the host's `/usr/bin/git` with that Git's own version string, so the tests run on any host; the mismatch is tested with `git version 2.56.0` and a missing path.
3. **Runner.** `GitRunner.run` spawns `pin.path` (never a `PATH` lookup) with `env` set to exactly `gitConfigEnvironment(credential?.authorization)`, so nothing of the worker's environment is inherited, and the header is in the environment of the one process that names a credential. In 16b only the clone does; every other process gets no header. Standard input is always a pipe, closed at once when no input is given, so Git never waits on the worker's terminal. A process that cannot start is `unavailable`; a non-zero exit stays an exit code, and `succeeded` turns it into a failure of the code the caller names (`unavailable` for the clone, `internal` for local Git).
4. **Scrubbing.** Standard error is scrubbed of every form that `sensitiveValues` gives for the command's credential (the secret, the `Authorization` value, its parts after the scheme, and the base64 of each, longest first), and only scrubbed text reaches a failure message. Standard output is returned as bytes and never put into a message: it is the data that the adapter parses, such as blob contents, and scrubbing it would change a snapshot's bytes. The brief asked to scrub "every captured stdout/stderr line"; this design scrubs every captured line that can leave the adapter, and keeps parsed data exact. `sensitiveValues` skips forms shorter than 8 characters, as the suite's checks do.
5. **Configuration rewrite.** `writeRepositoryConfig` creates `.git/config.taskelith-<random>` with `O_CREAT | O_EXCL | O_NOFOLLOW`, writes `repositoryConfigText` of the record's object format (`repositoryformatversion = 0` for SHA-1; `1` and `extensions.objectformat = sha256` for SHA-256), and renames it over `.git/config`. The rename replaces a symbolic or hard link the agent left there instead of writing through it, which matters most where the agent and the worker are one account (macOS). An operation rewrites the file once, after the checkout checks and before its first Git call; its later Git calls follow without any agent process in between, because a reclaimed checkout is closed to the execution (contract section 2), which is how the 16a double reads "before each Git call".
6. **Checkout checks.** `checkCheckoutSafety` uses `lstat` and `readdir` only: the checkout and `.git` are directories of the worker's uid, `.git` holds no `commondir`, no `objects/info/alternates`, and no symbolic link at any depth, and no entry named `.git` exists below the top. Each failure is `precondition-failed` with reason `unsafe-checkout`. They run once per operation, after the workspace record and the hand-off record are read, so the order of section 9 holds: `not-found`, `workspace-handed-off`, `unsafe-checkout`, then `workspace-dirty`.
7. **Prepare.** After the refusals that need no Git (the head's repository, `checkRemoteTransport` with the composed policy, and `checkCredentialScope`), `prepare` creates `.staging-<name>/` (`0710`) exclusively, so a concurrent prepare of the same attempt fails with `conflict`, and the checkout directory with mode `2700` before the clone writes into it. The clone is `git clone --no-checkout --quiet --origin origin -- <remote> <checkout>`, started in `/` with the header (`WS1`). It then reads the object format, rewrites `.git/config` before any further Git call, so the clone's own remote settings never act, resolves the start from the clone's `refs/remotes/origin/` (the task branch, else the base branch; or the `at-head` commit and its tree, `not-found` or `head-mismatch`), checks it out on the task branch with `--no-track` or detached, and writes the workspace record durably. The rename into place (`WS2`) refuses an existing workspace atomically, as `ENOTEMPTY` or `EEXIST`, so the existing-workspace check comes last, as section 9 orders it. A refusal deletes the staging entry; a crash leaves it for `sweep`.
8. **Record after the clone.** The record holds the clone's object format, which is known only after the clone, so it is written after the clone, still inside the staging entry. Contract section 3, step 1, lists the record before the clone; as nothing reads a staging entry and `sweep` deletes it after a crash, the order inside it is not observable. The report to the coordinator lists this as a wording difference.
9. **Status.** `inspect` runs `git status --porcelain=v2 -z --branch --untracked-files=all --ignore-submodules=all`, parsed by `parsePorcelainStatus` into the head, the branch (null when detached), and entries whose paths stay bytes. `modified` comes from a changed (`1`) or renamed (`2`) entry, which covers the index and the working tree, `untracked` from `?`, and `operation-in-progress` from an unmerged entry (`u`) or one of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, `rebase-merge`, `rebase-apply`, or `sequencer` in `.git`; `off-branch` from the record's task branch. The brief asked for `decodeGitPath` on status paths; the parser keeps them as bytes instead, because section 9 lets only `snapshot` refuse a name that is not UTF-8, and decoding there would make `inspect` and `remove` fail on such an untracked file. `decodeGitPath` decodes the paths and link targets of the snapshot.
10. **Snapshot from objects (decision Q1 b).** `git ls-tree -r -z --full-tree <commit>` lists the tree with byte paths (`parseTreeListing`); `git cat-file --batch` reads each blob once by its size (`parseBatchObjects`), so any byte survives. A regular file's mode is canonicalized as Git does (`100755` when the owner may execute, else `100644`). `snapshotTree` refuses a gitlink first and then decodes, so a tree with both reports `gitlink-in-tree`, as section 9 orders it; `encodeHeadSnapshot` builds the bytes. Nothing uses `git archive`.
11. **Crash points.** `GitWorkspaceCrashPoint` names `WS1` to `WS4` with `.before` and `.after`; tests pass the harness's `CrashPoints` with the action `throw`, production `NO_CRASH_POINTS`, as the postgres adapter does. `WS4` is reached both by a removal and by `sweep` for each removing entry. `WS5` to `WS10` belong to the hand-off and the reclaim (16d).
12. **Test composition.** The fixture serves a local bare repository over Git's dumb HTTP protocol from a static Node.js file server on `127.0.0.1`, which a clone can use, with the policy `https-or-loopback-http`; it counts requests as remote calls and keeps their `Authorization` headers. The smart-HTTP server that the push and the credential checks need is 16c's. The pinned client is a Perl wrapper that records each process's arguments, process identifier (kept by `exec`), working directory, exact environment, and the configuration of the repository Git finds from that directory, then runs `/usr/bin/git`; Perl is used because a shell adds variables such as `PWD` to the environment it would record. Native helpers run `/usr/bin/git` directly with their own environment, so they are never recorded.
13. **Deferred conformance cases.** `test/conformance.test.ts` runs every case of `WORKSPACE_CONFORMANCE` and skips, with the reason "sub-change 16c" or "16d", the 15 cases that call `push`, `readRemoteHead`, `handOff`, or `reclaim`; the provider's methods for those reject loudly, so a case that reaches one fails. A test checks that every skipped name is a case of the suite. The adapter's own tests cover what those cases check of the local operations: the snapshot, the staged-and-reverted refusal, the unsafe checkouts, the planted settings, and the Git process checks, through `gitProcessProblems`, which `@taskelith/workspace` now exports.
14. **Error handling.** Every contract refusal is a kernel `Result` with its code and reason. A file system fault that is not a refusal, such as an unreadable or malformed workspace record, rejects the promise, as `list` and `sweep` do by contract, and is never reported as an absent workspace. A failed prepare deletes its staging entry before it returns; an exception, such as a simulated crash, leaves it for `sweep`. A concurrent removal that finds the workspace already renamed succeeds.

## Risks

- The clone does not force `fsync` of Git's objects (`core.fsync` is not among the command-scope settings), so a power loss right after `WS2.after` could leave a ready workspace with lost objects; a process crash cannot.
- No Git process has a time limit; a remote that stops answering holds a prepare until the transport fails. 16c, which adds the remote operations, decides a bound.
- The clone runs with the worker's umask, not `0007`, and the checkout keeps the worker's primary group; the execution group and the umask are wired with the hand-off in 16d and 16e.
- The checks walk the whole working tree once per operation; a large checkout costs a walk per `inspect`.
