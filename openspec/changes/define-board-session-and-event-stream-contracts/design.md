## Decisions

Where a source is silent, the change takes the minimal shape and records it here with the source it relies on.

1. **One document, version 0.2.0.** The operations go into `control-plane.openapi.json` (architect answer 1). They add paths and schemas and change none of 9a's, so `make contract-compatibility` finds no breaking change; the minor version still rises, as the brief asks, so that a client can tell the documents apart, and the title drops "access", which no longer covers the content. `AttemptOutcome`, `ExitStatus`, and `AdmissionState` of `execution.openapi.json` and `ContentDigest` and `WorkflowRunBinding` of `sdlc.openapi.json` are copied byte for byte, as `mergeSchemas` requires.
2. **Agent session.** The session timeline's session is named an agent session on the wire (`AgentSessionId`, `AgentSessionGeneration`, `/agent-sessions/`, `listAgentSessions`), because 9a's `readSession`, `SessionState`, and `/session` already name the login session; one term per concept. Names that do not clash keep the domain's vocabulary (`TurnId`, `NativeRequestKey`, `SessionActivity` of product ports section 3.6).
3. **Schemas 9d reuses.** 9d's worker messages deliver turns and responses and carry session observations, so they need the same values. These schemas are named for that reuse and use only keywords that draft-07, the message schemas' dialect, reads as 2020-12 does (a test): `AgentSessionId`, `AgentSessionGeneration`, `TurnId`, `TurnText`, `TurnOutcome`, `HarnessFailure`, `NativeRequestId`, `NativeRequestKey`, `NativeRequestKind`, `HarnessText`, `NativeAnswer` (permission, input, and the host's delegation result), `PermissionDecision`, `DelegationResultOutcome` (the name `DelegationOutcome` already means the admission outcome of `requestDelegation`), and `IdempotencyKey`. The values mirror `harness-values.ts` and `session-records.ts`, and the tests compare each enumeration with the domain constant.
4. **Unpaged views.** The board, task detail, inbox, and counts are one snapshot each, as their ports return them, because product ports section 2, rule 2 gives a view one `asOf` and one `position`, and pages read at different times would show no single state. Every `list*` operation pages (test). The risk is a large board; a later minor version can page it without breaking clients.
5. **Stamp on every read.** Product ports stamps the board, detail, and inbox views. The session reads, pages, and output carry the same stamp, so that any read can be the snapshot the stream resumes from (decision 12); no source requires it for sessions.
6. **Roles.** The trust model section 3 gives `project-operator` the sessions, turns, and native responses, and product ports section 2, rule 1 the inbox answers by kind. An `installation-owner` reads every project's views, as 9a lets it read every project (9a design decision 8), but acts in a project only with a project role, because answering and turns are project capabilities. The installation-scoped inbox and its stream are `installation-owner`'s (product ports section 4.1).
7. **Answer order.** An item's `answerableBy` role needs the item, so the control plane checks `project-operator` or above, then reads the item, still before the body, and refuses a lower role with 403. Section 2 of the contract page requires the role before the body; the item read reveals only that the item exists, which a `project-viewer` reads anyway.
8. **Typed failures.** No 9b command compares a revision, so 409 answers only a duplicate, as product ports section 2, rule 6 uses `conflict`: `CommandConflict` with `already-answered` or `idempotency-key-reused`. 422 answers a changed state with a typed reason: `AnswerRefusal` (`item-closed`, `attempt-not-current`, `subject-changed`, from product ports sections 2, rule 2 and 4.2), `TurnRefusal` (`session-stopped`, session timeline section 4.1), and `ResponseRefusal` (`attempt-not-current`, section 5.2). Every path parameter answers 400 (test). Unknown, expired, and unresolved requests answer 404, as the domain does.
9. **Two ways to answer a native request.** The brief asks for inbox answers and for session responses. `answerInboxItem` maps `NeedsYouSource.answer`; `respondToNativeRequest` carries what architecture section 7 requires of a response: the request with its generation, the authenticated responder, and the attempt with its ownership generation. Both reach the native request source, which consumes one answer, so whichever commits first wins and the other answers 409 `already-answered`. A person's answer is `PersonAnswer`, permission or input only, because only the host answers a delegation request (session timeline section 5.2, rule 7).
10. **Idempotency keys.** Inbox answers carry a key (product ports section 2, rule 7). The domain's `consumeResponse` has none, so a repeated response would answer `conflict`; the wire gives responses a key too, so that a client can retry a response whose answer it lost, and item 13 stores it with the response. A key is scoped to the item or request it answers; the turn key is the domain's. The key repeated with the same input returns the first outcome, and with other input answers 409 `idempotency-key-reused`.
11. **Turn identity.** The domain takes the caller's `TurnId` (session timeline section 2, rule 6); on the wire the caller is the control plane, which mints it as 9a mints identifiers, with the letter `t`. A turn read omits the idempotency key, which only the author's retry needs.
12. **Request positions.** The domain lists requests in recording order and only appends them (`appended` and `replaced` in `session-records.ts`), so a request's place in that order is a stable position from 1, which `listAgentSessionRequests` pages by and item 13 derives without a new field.
13. **Output.** `readOutputAfter` returns `cursor-expired` as a success value, so the wire returns it as a 200 variant, not an error status; a page holds at most 100 entries, since the domain's window can hold 10 MiB. A cursor after the last position is the domain's `invalid`, 400.
14. **Stream positions.** Product ports section 2, rule 2 leaves `position` a string. The wire makes it a decimal integer of at most 16 digits from one installation-wide sequence, `0` before any event, so that a client can compare a view's position with an event's, and assigns it after the commit in commit order. Commit-before-display (session timeline section 5.1, architecture section 7) then holds on the wire: no position names an uncommitted change, and no lower position follows a higher one. A position of a project stream has gaps, because the sequence is shared.
15. **Events carry records.** Each event carries the whole record that its read returns, not a notice to read again, so a live screen needs no extra request and an event shows nothing a read does not. A card event covers changes of its task detail too, and a client showing the detail reads it again; an inbox item event moves the counts, which a client derives (product ports section 4.2). Replaying an event already reflected in a view is skipped by position (decision 14).
16. **Cursor and resynchronization.** `Last-Event-ID` is the durable cursor. A browser sends it only on reconnection, so the first connection carries a view's position in `after`, and the header wins when both are present. A cursor the stream cannot serve gets a `resync` event in a 200 response, with no `id`, after which the stream ends; an error status would make a browser give up instead of reconnecting. The reasons are `cursor-expired` (older than the retention, which item 14 sets) and `cursor-unknown` (beyond the head, or from before a restore).
17. **Installation stream.** The installation-scoped inbox has no project, so a project stream cannot carry it; `streamInstallationEvents` carries its item events for an `installation-owner`.
18. **Agent text.** Architecture section 11 keeps secret values out of event payloads, and events carry agent text. The control plane therefore redacts agent text with `@taskelith/secrets` before the timeline records it (item 13), so a read and an event carry the same text. Request logs keep 9a's allowlist, which never holds a request body (`execution-observability` "Logs without secrets" forbids logging payloads).
19. **Acknowledgement kind.** The kind is `delivery-acknowledgement`, named for the uncertain delivery it acknowledges. It is answerable by `project-operator` or above, the role that answers the native requests whose responses it concerns, and its only answer is `acknowledge`, because an uncertain delivery is final and nothing may be resent (session timeline sections 5.4 and 6). `NeedsYouAnswer` gains its variant, and its card subject uses the existing fields. One item opens per request that `uncertainDeliveries` lists, whatever its kind and responder, as session timeline section 5.5 states.
20. **Input answer bound.** Product ports section 4.1 bounds an input answer at 64 KiB (`MAX_INPUT_ANSWER_BYTES`) without an encoding; the wire reads it as UTF-8 bytes, the encoding of JSON text. A schema counts code points, so a text within the schema can still answer 400.
21. **Test helpers.** The 9a and 9b contract tests read the document through one helper module, `packages/contracts/test/control-plane-document.ts`, rather than a second copy of 9a's helpers.

## Risks / Trade-offs

- A large board or inbox is one response (decision 4).
- 9c edits `execution.openapi.json` in parallel. If it changes `AttemptOutcome`, `ExitStatus`, or `AdmissionState`, the generator fails after both merge until the copy here is updated.
- SSE framing is prose and tests of the frame schemas; item 14's tests must check the real frames, the `Last-Event-ID` precedence, and the resynchronization.
- Redacting agent text before recording changes what the timeline holds; a secret of no known shape still reaches members, as it would on a terminal.
