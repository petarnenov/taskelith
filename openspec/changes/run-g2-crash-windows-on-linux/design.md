## Context

Item 24b (`run-g2-crash-windows`, archived on 2026-10-26) added `apps/control-plane/test/crash-windows.integration.test.ts`: a crash at each launch window W1 to W6 and each supervisor step CP1 to CP12, then a restart, and a duplicate delivery of the offer, against a composition of the real control plane in the test process and a real worker child process on the `make` services. It skipped every scenario off Darwin, because on Linux the worker launches only with a containment parent and an execution account (`apps/worker/src/settings.ts:137-158`), needs its home cgroup outside that parent (`packages/adapters/worker-supervisor/src/linux.ts:264-276`) and an execution account that owns none of the cgroups (`linux-self-check.ts:24-69`), and needs the privileges to set the child's uid and gid and to kill containments. The only container that has these, the one of `make verify-linux-cgroup`, runs with `--network none`.

The coordinator assigned this change on 2026-10-27 with binding decisions: option B, the privileged test image with network to the services; a new Makefile target, kept out of `make verify` unless it is as cheap and portable as `verify-linux-cgroup`; the macOS path unchanged; Linux expectations per section 6 of the supervisor identity contract; and no product fix for a failing Linux scenario, which is recorded as a candidate defect with its expected outcome kept.

## Decisions

1. **Spec delta: yes.** The living `g2-failure-scenarios` spec, which 24b extended, says in "Crash scenario records", scenario "Linux host", that every scenario is skipped on Linux, and "Supervisor window crash recovery" names only the macOS outcome of CP7. Running the scenarios on Linux contradicts the first and adds Linux outcomes to the second, so both requirements are modified: "Crash scenario records" now runs the scenarios on Linux through `make verify-linux-crash-windows` and skips them only where the composed worker cannot supervise, and "Supervisor window crash recovery" gains the Linux scenarios of CP7 and CP9. `skip_specs` would be wrong, because this is not documentation-only work. The capability exists, so the delta has no `## Purpose`. The pinned OpenSpec replaces a modified requirement whole and refuses to drop a scenario, so the delta keeps the scenario name "Linux host" with its new text.
2. **Option B with the host network.** The container joins the host network (`--network host`), so the URLs that `scripts/services.sh run` exports, `127.0.0.1` with ephemeral ports, work unchanged, and the in-process control plane's API on `127.0.0.1:0` is reachable by the composed worker as on macOS. A user-defined network with the services would need the Compose network name and the services' internal ports, which `services.sh` does not export; publishing on another address would widen the services beyond localhost. The services secrets directory is mounted read-only at `/secrets`, with `TASKELITH_SERVICES_SECRETS=/secrets`; root in the privileged container reads it although it is the host user's `0700` directory.
3. **Not in `make verify`.** The target needs `--privileged` and the host network, which a Docker Desktop host gives only inside its virtual machine, and it builds the test image and starts a services project of its own; one run takes about 90 s with the image cached. `verify-linux-cgroup`, the bar the coordinator set, is itself opt-in, and this target is neither cheaper nor more portable, so it stays opt-in. `make verify` on Linux still runs the test file, which skips every scenario because the Linux launch settings are absent (decision 6).
4. **Cgroup layout.** The image's existing layout moves into `tools/linux-cgroup/cgroup-layout.sh`, which both entry points source: every process of the private cgroup namespace moves into the leaf `init/`, and `executions/` beside it is the containment parent. The test runner, and with it the composed worker and its supervisors, start in `init/`, so the worker's home cgroup is outside the parent. `run.sh` of `verify-linux-cgroup` keeps its behavior; `make verify-linux-cgroup` passed after the move.
5. **Execution account.** The new entry point `taskelith-linux-crash-windows` sets `TASKELITH_CONTAINMENT_PARENT=/sys/fs/cgroup/executions` and `TASKELITH_EXECUTION_UID` and `TASKELITH_EXECUTION_GID` to the image's `taskelith-exec` account, uid and gid 2000 (`tools/linux-cgroup/Dockerfile`). The test runs as root in the container, which owns `init/` and `executions/` and holds `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL`; the account owns no cgroup file and differs from the subtree's owner, as the self-check requires.
6. **The guard.** The scenarios run on Darwin as before, and on Linux only when all three launch settings are set (`LINUX_LAUNCH` of the harness). Without them, as in `make verify` on any Linux host, each scenario is skipped with the reason that the composed worker supervises natively on macOS and on Linux in `make verify-linux-crash-windows`. Inferring the container from the cgroup layout instead would let a host that happens to have such a layout run as root without being asked to.
7. **The harness on Linux.** The worker inherited the test's environment already; the harness now passes the three settings explicitly, so the composed worker's configuration states them. The armed supervisor, which the worker fixture starts in place of the product's at CP4, gets the product's arguments past its main module from `supervisorCommand`, so on Linux it receives `--containment-parent` as CP4 passes it; without it the supervisor program refuses to run on Linux. The scripted child runs as the execution account, so the scenario's base directory becomes `0711`, and the `spawns` and order-trace files are created up front and owned by that account; the child finds the release file and appends its process ID and a release by the bound as on macOS.
8. **A fresh volume for the journal.** The worker journal refuses overlayfs as its volume (`unsupported-volume`), and the container's root file system is overlayfs, so `/tmp`, where the harness creates each scenario's data roots, is an anonymous volume on the host's file system, removed with the container, as `make linux-test-suites` does.
9. **An init process.** The container runs with `--init`, so its PID 1 reaps orphans as a service manager does. A supervisor whose worker died is reparented to PID 1; without a reaper, the orphans of crashed supervisors would stay zombies for the rest of the run. The namespace incarnation that recovery compares is read from that PID 1 for the whole run, so it stays current across the worker's restarts.
10. **Linux expectations, section 6.** The rows of the recovery table that differ from macOS are those with a claim, no live supervisor, and no `exit`:
    - CP7 (claim written, nothing spawned): the containment that CP6 created is empty in the recorded namespace incarnation, so the worker writes `exit` with an unknown status and, without `handle`, an unproven start; nothing spawned.
    - CP8 (child spawned, no `handle`): the containment is populated, so an adopting supervisor watches it and, once it empties, writes `exit` with an unknown status, the start unproven because `handle` is missing. The child is released only after the adopter's `supervisor.2` exists (`after-adoption`), so the populated row is the one exercised; on macOS CP8 keeps `after-restart`.
    - CP9 (`handle` written): the populated row as for CP8, with the start proven.
    - Every other window has the same outcome on both hosts: W1 to W6 follow journal section 5; CP1 to CP6 find no launch record and seal (a containment created at CP6 is empty); CP4, CP10, and CP12 find a live supervisor or a recorded `exit`; CP11 reports the recorded exit.
    An exit with an unknown status ends the execution, and section 6 states that automatic retry of it needs operation-specific repeatability within the retry budget of `0` for uncertain execution ([operational targets](../../../docs/operational-targets.md) section 1), so every window keeps the check of one attempt.
11. **The commit of a record.** The scenario recorder reads the commit with `git rev-parse HEAD`, but the image has no git and the worktree's `.git` file points outside the mounted checkout. `scripts/linux-crash-windows.sh` reads the commit on the host and passes `TASKELITH_SCENARIO_COMMIT`, which the recorder accepts only as a full 40-digit hash; without the variable it reads git as before. The results file is created on the host before the run and mounted as a single file, so it stays the caller's although root appends to it.
12. **Defects are recorded, not fixed.** The coordinator's decision 3: a failing Linux scenario keeps its section 6 expectation, is recorded in `verification.md` with its seed and exact output as a candidate defect, and gets no product fix here. For CP9's candidate defect L1 the coordinator then decided, on 2026-10-27, as 24b did for D1: CP9 on Linux keeps its expectation and is marked `expectFailure`, matched on L1's signature (the one-attempt assertion fails on a second attempt with `retryOf`), so any other failure stays red. The mark is the constant `L1` and its one use in `LINUX_UNSUPERVISED`; the fix, the separate change `stop-automatic-retry-of-unknown-exit`, removes both as its fail-before test. macOS CP9 is unchanged.

## Risks and limitations

- The evidence comes from one x86_64 host, Ubuntu 26.04.1 with kernel 7.0.0-38-generic, running the Ubuntu 24.04 test image; it does not establish the arm64 Linux entry or the Ubuntu 24.04 kernel.
- The test runs as root in a privileged container; the composed worker is not the worker image of the installation, which runs with its own seccomp profile and capability set (item 25a).
- `native-acceptance.sh` runs the crash windows only in its macOS entry; adding this target to its Linux entry is outside this change.
