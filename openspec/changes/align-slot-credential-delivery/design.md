- `@taskelith/secrets` matches only Taskelith's shapes and URL user information (`packages/adapters/secrets/src/scrub.ts`, `SECRET_SHAPE_RULES` of `@taskelith/observability`); a subscription token has none.

- The `control-plane/` namespace is a file subtree of `0600` files (`/docs/contracts/installation-and-enrollment.md` section 3); the G3 plan places encrypted credential storage there (`/docs/g3-plan.md`, item 12).

## Decisions

1. **M5, option (a): subscription tokens only.** The contract delivers only `subscription-token` credentials. The add-slot command rejects a `device-login` slot with `invalid`, and the delivery reveals nothing for a slot of another mechanism, until a later item defines a state directory format and a compare-and-set write-back by the reserving run (sections 3.1, 7.1, and 10). Reason: D6 chose a subscription token per slot for Claude Code, the only harness G3 admits (item 19), and did not choose the device login, so no G3 item needs device-login delivery; defining a format and a write-back no harness uses would be unverifiable. The restriction is revisited only if item 35 overturns D6. Coordinator confirmation (Niki, 2026-10-27): option (a). Review pass 1 found that the restriction contradicted "Subscription account slots" of `harness-account-pools`, which accepts any declared subscription mechanism, and that the requirement let it lapse once a later item defines a format; a `harness-account-pools` delta now modifies that requirement, and both requirements tie the restriction to item 35 and D6 only. `SlotSecret` stays one text; only its comment and the contract say it is a subscription token. The pool still treats `mechanismId` as opaque: the add-slot command and the delivery, both outside the pool's ports, compare it with `subscription-token`. This change makes no claim about provider terms for subscription tokens; D15 and ADR 0005 decision 2 are pending with the owner.
2. **M6, memory only, a new delivery per execution.** Section 7.3 keeps the credential in the worker host's memory for one execution and out of the journal, a grant, `worker/executions/<executionId>/`, `worker/logs/`, and the outbox. Every execution after W3, recovered or adopted, requests it again through a new delivery with the checks of section 7; an adopted execution needs it for redaction even when its harness already has it. Review pass 1 found that an adopted execution cannot meet section 7's launch authorization condition: its grant expires after 30 s, and the launch authorization contract allows no new authorization of a started execution. Section 7.3 therefore replaces that condition for a re-delivery with an ownership check that reuses the launch authorization checks a started execution still passes (quarantine, epoch, worker, assignment, ownership generation, attempt, owning execution without a revoked grant) and their section 9 reasons, plus the reservation and slot checks. A refused worker sends none of the run's output off its host, because it cannot redact it by value. No delivery or worker code exists yet, so the tests are obligations of item 18 in section 9, and the spec states them as scenarios.
3. **M7, redaction by value in `@taskelith/secrets`.** The SCM follow-up (`/openspec/changes/archive/2026-10-27-align-scm-port-with-g2-credentials/design.md`, decision 1) kept one redaction boundary: shapes join the shared `SECRET_SHAPE_RULES`, which both log redaction and `@taskelith/secrets` use. A slot token has no shape, so a shape rule cannot match it; the same boundary instead takes the run's revealed values. `redactSecrets(text, revealed)` and `redactFailure(failure, revealed)` redact each exact revealed text; `revealed` defaults to none, so every existing caller of `redactSecrets` keeps its behavior. Review pass 1 showed that replacing values one after another with `split` and `join` breaks other occurrences, re-processes markers, multiplies the output, and can hide a shape secret's suffix from its rule. The replacement now finds every occurrence of every value in the original text, overlapping ones included, with a Knuth-Morris-Pratt scan (linear per value), merges overlapping or touching ones, and emits one `REDACTED` per merged span (`packages/adapters/secrets/src/revealed-spans.ts`). The shape rules are opaque text rewrites, so their spans cannot be read; instead, because no shape secret holds whitespace, the whitespace-free word around a span is checked with the shape rules, and a word in which they match anything is redacted whole. That over-redacts only text glued to a credential, and proves that neither the credential nor the shape secret leaves a visible part; the shape rules then run on the result as before. An empty value is ignored. The package takes plain strings, not `SlotSecret`, so it does not depend on Scheduling. Item 18 applies them to the run's harness output, logs, and failures (section 7.4). `scrubEnvironment` is unchanged: the plugin injects the credential on purpose.
4. **L6, transport.** Section 7.2: delivery only over item 26's TLS or to a worker co-located with the control plane on its host; a remote worker gets no slot credential before item 26.
5. **L7, storage.** Section 1: `AccountSlots` is in the installation's PostgreSQL database; the `SlotCredentials` key, or its whole store, is in the `control-plane/` namespace, never in the database. Section 6.2 now cites section 1 for that, instead of section 7.
6. **L8, the check belongs to the delivery.** `reveal` checks no reservation, attempt, or slot state; the delivery checks them in a capacity transaction and calls `reveal` after the commit (sections 6.2 and 7). The modified "Redacted slot credentials" says so; the port comment says so.
7. **Failure keys (pass 1).** `redactFailure` kept detail keys unredacted, so a credential used as a key leaked. It now redacts keys with the same function. Keys that become equal, for example two credentials that both become `[redacted]`, keep one entry whose value joins theirs, in their order, with `, `, so that no detail is lost; a `Map` keeps keys such as `__proto__` and `toString` as plain keys. Callers without revealed values now also get their keys redacted by the shape rules, which only removes secrets.
8. **Rotation and emergency revocation (pass 1).** Re-delivery after an adoption must reveal the token the run started with, or redaction by the new value misses output that holds the old one. Review pass 1 proposed refusing a rotation with `conflict` while a live reservation names the slot. That check alone races: the rotation's transaction commits, a reservation and its delivery reveal the old token, and the store, outside the database, then replaces it. Section 8.1 therefore also requires the slot to be `revoked`, which admits no new reservation and no delivery, so the check holds until the store finishes; an operator rotates by revoke, rotate, and reinstate. Coordinator confirmation (Niki, 2026-10-27): the rotation rule, on the condition that emergency revocation is never blocked. A revoke of a reserved slot therefore succeeds and, in its transaction, cancels every attempt whose held reservation names the slot: a cancellation, which as an invalidating writer of the launch authorization contract section 5 revokes the attempt's grants and writes its cancellation command, and which releases the reservation only with the execution's terminal fact (capacity reservation contract section 6). The worker keeps redacting the run by the delivered value until the run ends. No revoke, rotate, or worker code exists yet, so the tests are obligations of items 12 and 18 in contract section 9. A removal drains or rejects instead (decision 10).
9. **L9, one constant in the kernel.** `REDACTED` moves to `@taskelith/kernel`, which every module already depends on. `@taskelith/observability` re-exports it, so its readers, `@taskelith/secrets` among them, are unchanged; `@taskelith/scheduling` imports it and no longer exports it.
10. **Removal keeps draining (pass 1 follow-up).** The pass 1 fix `2eef8d7c` made a removal cancel the slot's attempts as a revocation does. ADR 0005 decision 6 says that removal drains or rejects its in-flight sessions, and "Session affinity" of `harness-account-pools` lets an unavailable slot's session be drained or ended, so that fix narrowed the ADR. A removal therefore keeps the ADR: a held reservation does not block it, and it drains or rejects the slot's in-flight attempts by policy or an operator; only a revocation cancels them at once, so a removal after a revocation finds them cancelled. A drained attempt keeps its delivered credential, but its re-delivery is refused, because the slot is not `active` (contract sections 7.3 and 8). Coordinator confirmation (Niki, 2026-10-27): the stricter rotation rule of decision 8 and the cancellation by revocation are kept, and removal does not drop draining.
