## Context

The `pre-push` hook ran `scripts/check-pre-push.ts`, which reads git's ref lines on standard input, and then `make verify`. `scripts/pre-push-checks.ts` already treats an all-zero local object name as a deletion. Archiving was a separate coordinator step with its own branch and pull request, after the task's pull request merged.

## Decisions

1. **Delete-only decision in TypeScript.** `isDeleteOnlyPush` in `scripts/pre-push-checks.ts` is true when the hook input holds at least one ref and every ref's local object name is all zeros, of any length, so that SHA-256 repositories match too. Empty input is not delete-only, so the hook keeps its old behavior for it.
2. **Exit status as the hook protocol.** The hook's standard input can be read only once, and `check-pre-push.ts` reads it. That script exits with `DELETE_ONLY_PUSH_STATUS` (100) for a delete-only push, before its other checks, which only protect `make verify`; the hook exits 0 for that status, 1 for any other failure, and otherwise runs `make verify`. Node.js, `sh`, and the repository's wrapper scripts use no status 100.
3. **Tests.** A unit test covers `isDeleteOnlyPush`. A hook test runs the real `.githooks/pre-push` in a temporary repository holding copies of the hook's scripts, with a fake `make` on `PATH` and no nvm, and checks that a delete-only push (SHA-1 and SHA-256 lengths) skips `make verify`, and that a mixed, a normal, and an empty push run it. Both run in `npm test`, so in `make verify`.
4. **Archive on the task branch.** After the last review pass and its fixes, the worker runs `npm run openspec -- archive <change> --yes`, `npm run openspec -- validate --all --strict`, and `make verify`, and commits the archive as the last commit of the branch. The archive only applies the reviewed change with the pinned CLI, so it needs no further review pass; `make verify` and the `pre-push` hook check it.
5. **Spec conflicts go back to the worker.** A branch changes the living specs only through its archive. When the coordinator's merge of `origin/dev` conflicts under `openspec/specs/` or `openspec/changes/archive/`, it aborts the merge and returns the task. The worker reverts the archive commit without committing and commits that as `docs: restore the active <title> change to merge dev`, which restores the active change and the specs from before the archive; it then merges `origin/dev`, which leaves the living specs to `dev`, resolves any other conflict, runs `make verify`, has the assigned reviewer review the resolved diff, records it, and archives again onto `dev`'s specs. Other merges are unchanged: the coordinator completes a clean merge, regenerates a stale dependency inventory, and returns other conflicts or invalidated evidence under the existing conflict step.
6. **Integration gate in the archived record.** `verification.md` is complete before the archive and names `Integration into dev by the coordinator (single pull request)` as a remaining gate. Nobody edits the archived record at integration; the merge pull request and its merge commit record the integrated revision. Only the worker's conflict step adds to the record afterwards, before the next handoff.
7. **No active change at integration.** `npm run verify:archive` passes with no active change, as its requirement already states, so a branch that carries an archived change passes `make verify`. No script, hook, or CI job reads an active change at integration time. The coordinator checks that the branch carries the archived change.

## Risks / Trade-offs

- A delete-only push is not verified; it changes no commit on the remote, and the branch protection of `main` and `dev` blocks their deletion.
- The archive directory carries the date of the archive commit; a re-archive on a later day gets a new date.
- The archive commit is not independently reviewed; it is the pinned CLI's mechanical application of the reviewed deltas, checked by strict validation and `make verify`.
