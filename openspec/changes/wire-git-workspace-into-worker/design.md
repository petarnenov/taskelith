## Goals / Non-Goals

**Goals:** every worker-side rule of contract sections 2, 3, 7, and 14 that item 16 owns is composed and enforced in `apps/worker`, on Linux with a separate execution account and on macOS with one account, and each is tested with fail-before evidence.

**Non-Goals:** preparing a workspace for an assignment, handing it off before a harness, or reclaiming it after the exit inside the launch path; these need the run credential and the repository binding of the harness host (item 18, contract section 14), which calls the slot service of decision 6 (question Q1).

## Decisions

1. **Separate execution account.** A worker's executions "run under a separate account" exactly when its launch settings carry an execution account, that is on Linux with `TASKELITH_WORKER_COMMAND` set, from which `TASKELITH_EXECUTION_UID` and `TASKELITH_EXECUTION_GID` are read today (`apps/worker/src/settings.ts`, `readLaunch`). Every rule below that the contract gives such a worker keys on that value, never on the platform alone (question Q3).
2. **Workspace composition.** A new module `apps/worker/src/workspace-composition.ts` builds the provider for the composition root (`main.ts`, `productionDependencies`, as `WorkerDependencies.workspace`), and only for a worker with a launch command (question Q3): where decision 1 holds it first checks `fs.protected_hardlinks` (decision 5); it then verifies the platform's pin of `GIT_CLIENT_PINS` with `verifyGitClient`, and composes `GitWorkspaces` with the data root, the remote policy `https-only`, and the reclaim host of the platform (`reclaimHostFor`): `LinuxReclaimHost` with the containment parent and the execution account where decision 1 holds, `ProcessGroupReclaimHost` otherwise. `startWorker` calls it after the admission checks' composition and before it opens or enrolls the root, so a mismatched client fails the start with `precondition-failed` and reason `git-client-mismatch` before the worker enrolls or opens its journal (contract section 7). The runtime then runs `sweep` before anything can prepare a workspace (contract section 3, step 5); a sweep that rejects fails the start. The host's side (the setting's reader, the umask, and the gate) is injected as `WorkspaceHost`.
3. **Execution group and umask.** `startWorker` passes the execution account's gid as `executionGroup` to `openWorkerRoot` and `claimWorkerRoot` (`worker-start.ts`, `rootOptions`; contract section 14). Where decision 1 holds, the composition sets the process umask to `0007` once the Git client passed its gate (`CLONE_UMASK`), so the clone writes with the group bits of contract section 2; elsewhere the umask is unchanged, because every directory keeps `0700` there. The worker container's entrypoint (`infra/installation/worker-entrypoint.sh`) gives a worker with a launch command the execution group as its only supplementary group (`setpriv --groups "$TASKELITH_EXECUTION_GID"`), so `prepare` can `chown(path, -1, gid)` without `CAP_CHOWN`; without a launch command it adds no group, as decision 1 and question Q3 say.
4. **Single slot and its start refusal.** In `readWorkerSettings`, where decision 1 holds, `TASKELITH_WORKER_SLOTS` unset gives one slot, `1` gives one slot, and a value above `1` fails the settings with `invalid`, an error that names `TASKELITH_WORKER_SLOTS` and the execution account (question Q8), and the detail `variable`. Elsewhere the slot count keeps its rule (default `2`). The failure is the worker's start failure: `workerMain` writes it and exits with `1` before it enrolls.
5. **`fs.protected_hardlinks`.** Where decision 1 holds, the composition reads `/proc/sys/fs/protected_hardlinks` through the injected `WorkspaceHost`, as `linux-containment-check.ts` reads `/proc/self/cgroup` through its probe, and fails the start with `precondition-failed` and reason `hardlinks-unprotected` (a new value of `WORKSPACE_FAILURE_REASONS`) unless the content is exactly `1` followed by an optional newline; a read error also refuses, never reads as `1` (question Q2). It is a start precondition, not an admission check of the self-check. macOS and a Linux worker without a launch command never read it.
6. **Held slot.** The worker keeps the set of handed-off attempts in memory, loaded at the start from the adapter's new `handOffRecords()`, which reads the record of each attempt that `handedOff()` returns, and changed only by the worker's own `handOff` and `reclaim` through the worker-side slot service `WorkspaceSlots` (`apps/worker/src/workspace-slots.ts`), because the worker process is the only writer of hand-off records (contract section 1). The service is composed at the root and exposed as `RunningWorker.workspaceSlots`, for item 18 to call (question Q1). A failed `handOff` re-reads the records and holds the slot when the record exists or cannot be read. `refusalOf` counts, once per attempt, the journal's counted attempts together with these attempts, so a handed-off workspace whose assignment ended still fills the slot and an offer beyond it is refused with `worker-slots-exhausted` (contract section 3, step 6). A read of the records that rejects at the start fails the start, so a held slot is never read as free. A held slot counts as a slot only; its attempt's CPU and memory are counted while its journal counts it (question Q7). The count applies to every worker that composes the workspace: on macOS it only fills one of the slots it is given (follow-up question N2).
7. **Capacity again after the reclaim.** After a reclaim that removes a hand-off record of a held attempt, the slot service journals `worker.capacity.declared` again, also when its values are unchanged, so that the scheduler finds it eligible again (contract section 3, step 6; capacity reservation contract section 8, "Refusal"). This amends worker-runtime "Capacity declaration" (question Q4). The obligation is durable (review pass 1, finding 1): before the reclaim of a held attempt the service calls the journal port method `oweCapacityDeclaration`, which clears the journal's last declared capacity, and after every successful reclaim it calls `recordCapacity`, which journals a declaration whenever the stored one differs, so an owed one too. A journal failure after the reclaim leaves the debt for the next successful reclaim; a crash between the record's removal and the declaration leaves it for the next start, whose `recordCapacity` journals it. The service runs its reclaims one at a time (review pass 3, finding 2), so the declaration of one reclaim never clears the debt that a concurrent one owes before it removes its record. This is the simplest correct design: the journal, which already holds the last declaration, holds the debt in the same column, with no new file, schema, or flag. Its cost: a reclaim that fails after the debt was recorded leaves a declaration due, which journals an unchanged capacity at the next reclaim or start; the scheduler then refuses no work it would otherwise place, because a held slot still answers an offer with `worker-slots-exhausted`.
8. **`reclaim-failed`.** A reclaim that fails with `reclaim-failed` keeps the attempt in the held set, so its slot stays held, logs one warning `worker.workspace.reclaim-failed` with the attempt, and never retries the program. A workspace that a start finds with `reclaimFailed` in its record is held and logged the same way, with its containment's name or process group. The line never holds a path, a credential, or checkout content: it carries only those fields, never the failure's message (question Q5).
9. **Program past its run bound, and the failed program's cgroup.** In the adapter (`git-workspaces.ts`, `#failedProgram`), a program past `RECLAIM_RUN_BOUND_MS` or one that failed after `go` has its failure recorded durably first; then `LaunchedReclaim.kill` kills its containment, through `cgroup.kill` on Linux and with `kill(-pgid, SIGKILL)` on one account only while Node has not reaped the program's leader, so the group identifier cannot be another group's yet; the adapter proves the containment empty and frees it. The record keeps `reclaimFailed`, the slot stays held, and nothing retries (question Q6). A containment still populated at the proof's bound stays, and the `reclaim-failed` failure says so. Once the failure is durable, every outcome of the cleanup is `reclaim-failed` (review pass 1, finding 2, `#cleanedUp`): a fault of the kill, the proof, or the release ends the cleanup with the fixed remainder "the cleanup of its containment is unfinished", never the fault's message, so the slot service logs `worker.workspace.reclaim-failed`. A later `reclaim` of a record with `reclaimFailed`, also after a restart, finishes the cleanup without starting the program: it calls the new `ReclaimHost.killRecorded`, which on Linux writes the recorded cgroup's `cgroup.kill` (the name is the attempt's own, so it cannot be another cgroup), and on one account signals nothing, because a recorded process group identifier may be another group's by then (question Q9); then it proves the containment empty and frees it, and fails with `reclaim-failed` as before. A fault of the durable write of the failure still kills, proves, and frees the containment, and the reclaim fails with `unavailable` (review pass 2, finding 4); `failingFileSystemAsUnavailable` turns a fault that the write throws, such as one of its `rename`, into that result first, while a simulated crash still rejects (review pass 3, finding 1). A later reclaim follows the record that it reads (review pass 3, finding 3): a fault before the rename into place leaves the containment without the failure, so a later reclaim proves it empty and runs the program once more, as after a crash at `WS8.after`; a fault after the rename, a failed flush of the directory, leaves `reclaimFailed`, so a later reclaim finishes the cleanup without the program. The slot stays held until a reclaim succeeds (Q6). `ProcessGroupReclaimHost` takes its signal call as an injected `SendSignal`, so tests show that it signals the group of an unreaped program and never that of an exited program or a recorded group (review pass 2, finding 3; answer A2).
10. **Scan exclusion.** At the start the worker reads the hand-off records once (decision 6), and `worker-start.ts` wraps the launch host's containment scan so that it leaves out the cgroups those records name (`skippingRecorded`); the scan for unrecorded processes, which runs once at the start (`launch-orchestrator.ts`, `#findUnrecordedProcesses`), thus skips them (contract section 3, step 7), and `launch-orchestrator.ts` is unchanged. A populated `reclaim-<name>` that no record names is still reported.
11. **macOS composition.** One account: `ProcessGroupReclaimHost`, no execution group, no umask change, no `fs.protected_hardlinks` read, and the slot count it is given; `handOff` there refuses no second workspace. The Git client gate uses Apple's pin.
12. **Spec placement.** Every worker rule goes into the `worker-runtime` delta, which also amends "Worker settings" with the default of one slot. `resource-admission` is the scheduler's side of the capacity reservation contract, whose declared slot count and `worker-slots-exhausted` handling already cover the held slot, so it gets no delta. In `git-workspace-port` (question Q10), "Single slot with a shared execution account" is removed, and "One handed-off workspace per Linux worker" is narrowed to the adapter's `other-workspace-handed-off` refusal: because the pinned OpenSpec refuses a `MODIFIED` block that drops scenarios, the delta removes it and adds "Handed-off workspace refusal in the adapter" with its two adapter scenarios unchanged, and the delegated-child scenario moves to worker-runtime. The kill after the run bound adds "Killed reclaim containment" and modifies the scenario "Program past its run bound" of "Reclaim program containment".
13. **Ports.** The worker's runtime depends on the narrow `WorkerWorkspace` interface (`sweep`, `handOffRecords`, `handOff`, `reclaim`), and the slot service on the last three; only `workspace-composition.ts` names `GitWorkspaces` (ADR 0004, principles 2 and 3). The slot service reaches the journal only through two functions, `oweCapacityDeclaration` and `declareCapacity`, which `worker-start.ts` binds to the journal port.
14. **Start failures without paths** (review pass 1, finding 3). A start that fails because `fs.protected_hardlinks`, the sweep, or the hand-off records cannot be read reports a fixed message with only a system error code that matches `E[A-Z0-9]+`, such as `EACCES` (`apps/worker/src/fault-code.ts`, `faultMessage`), never the error's own message, which may name a checkout path that the credential redaction does not remove. A test checks the line that `workerMain` writes for each of the three.

## Test plan

- **Host unit tests (`apps/worker/test/*.test.ts`), both platforms through injected host facts.** Settings: Linux with an execution account and `TASKELITH_WORKER_SLOTS=2` fails naming the variable and the account, unset gives `1`; macOS and Linux without a command keep `2`. The hard-link check: `0`, `2`, empty, and a read error refuse the start, `1` and `1\n` pass; macOS never calls the reader. Admission: a fake `WorkspaceLifecycle` whose `handedOff` returns an attempt whose intent ended makes `refusalOf` answer `worker-slots-exhausted`, and after the reclaim the offer is admitted and a new capacity declaration is journaled. `reclaim-failed` keeps the slot and logs once; a restart with a failed record holds it. The scan skips a recorded containment and reports an unrecorded one. The composition picks `ProcessGroupReclaimHost` and Apple's pin for `darwin`, `LinuxReclaimHost` and the Linux pin for Linux with an account, and a mismatched pin fails the start with `git-client-mismatch`.
- **Fail-before.** Each new behavioral test is first run against the production files of `dev` `f68d4f76` with the new test files, and `verification.md` records how it failed.
- **Linux in the worker image.** `make verify-linux-git-workspace` runs the adapter's privileged suite in the worker image, with two additions: a program past a short run bound is killed and its `reclaim-<name>` cgroup removed, and the failed program's empty cgroup is removed. The worker's own wiring (the entrypoint's group, the umask, the slot refusal, the hard-link reader, and the held slot) is tested on the host through injected facts and the entrypoint's fakes; a whole worker started through the image's entrypoint is not run (`verification.md`, limitations).
- **macOS.** The host unit tests above run on every host; the composition's tests with the real `ProcessGroupReclaimHost` run natively on the iMac with the carried macOS gate.

## Risks / Trade-offs

- The held set in memory is right only while the worker is the only writer of hand-off records; the root lock makes it so (worker journal contract section 2).
- A held slot after `reclaim-failed` stops a Linux worker from taking work until an operator acts, as the contract intends; question Q5 decides how that becomes visible.
- A process group identifier on macOS can be reused after its group ends (16a and 16d risks); question Q9.

## Obligations and residual risks

- **Item 21, the `reclaim-failed` observation (Q5).** Until item 21, a failed reclaim is visible only as the log line `worker.workspace.reclaim-failed` and as the held slot. Item 21 owns the observation that the control plane reads for reconciliation, from the hand-off record's `reclaimFailed`, and its change of the execution OpenAPI document and the journal contract.
- **Reused process group on macOS (Q9).** A recorded process group identifier can be reused by an unrelated group after the program's group ended, so the proof reads it as populated. This is accepted as a residual risk: it only delays the reclaim to the proof's bound and reports the workspace, and never releases one early (contract section 3). The kill after the run bound (decision 9) never signals a group whose leader Node has reaped, so it cannot kill a reused group.
