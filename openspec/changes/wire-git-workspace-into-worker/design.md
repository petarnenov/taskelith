## Context

G3 item 16 implements the Git workspace contract (`docs/contracts/git-workspace.md`) in sub-changes 16a to 16e (`docs/g3-plan.md`, row 16). 16b to 16d built `@taskelith/git-workspace`: `GitWorkspaces` implements the whole `WorkspaceProvider`, with the hand-off record, the reclaim program, `LinuxReclaimHost` and `ProcessGroupReclaimHost`, the pinned Git client gate (`verifyGitClient`), and the Linux tests in the worker image (`make verify-linux-git-workspace`). No worker composes it yet: `apps/worker/package.json` depends on neither `@taskelith/git-workspace` nor `@taskelith/workspace`, and the worker's admission counts only its journal (`apps/worker/src/assignment-admission.ts`, `countedAttempts`).

This change, sub-change 16e, is "the worker wiring and admission: the execution group, the single slot and its start refusal, `fs.protected_hardlinks`, `reclaim-failed` handling, and the macOS composition". It also takes the items that the archived sub-changes left to 16e:

- 16a (`2026-10-28-align-git-workspace-adapter-contract`, design decision 9): the single slot in the worker settings; the worker half of "One handed-off workspace"; the macOS proof's details for a reused process group.
- 16b (`2026-10-28-implement-git-runner-and-snapshot`, design): the start refusal on `git-client-mismatch`; the clone umask `0007` and the execution group.
- 16c (`2026-10-28-implement-git-remote-operations`, verification): the clone umask and the worker log of "No secret in a log".
- 16d (`2026-10-28-implement-workspace-handoff-and-reclaim`, design decisions 8 and 10 and "16e handoff notes"): the worker's reclaim host, the umask, the scan's exclusion of a recorded containment, a program left running past `RECLAIM_RUN_BOUND_MS` (killing it, freeing the slot, any retry), and the empty `reclaim-<name>` cgroup of a failed program.

Out of scope: the delegated-child half of "One handed-off workspace" (item 38), the harness host (item 18), reconciliation itself (item 21), and any new third-party dependency. Carried gates, arranged by the coordinator: the suite natively on macOS with Apple's Git on the iMac, and `verify-worker-image-reproducible`.

## Goals / Non-Goals

**Goals:** every worker-side rule of contract sections 2, 3, 7, and 14 that item 16 owns is composed and enforced in `apps/worker`, on Linux with a separate execution account and on macOS with one account, and each is tested with fail-before evidence.

**Non-Goals:** preparing a workspace for an assignment, handing it off before a harness, or reclaiming it after the exit inside the launch path; these need the run credential and the repository binding of the harness host (item 18, contract section 14), unless the coordinator decides otherwise (question Q1).

## Decisions

1. **Separate execution account.** A worker's executions "run under a separate account" exactly when its launch settings carry an execution account, that is on Linux with `TASKELITH_WORKER_COMMAND` set, from which `TASKELITH_EXECUTION_UID` and `TASKELITH_EXECUTION_GID` are read today (`apps/worker/src/settings.ts`, `readLaunch`). Every rule below that the contract gives such a worker keys on that value, never on the platform alone (question Q3).
2. **Workspace composition.** A new module `apps/worker/src/workspace-composition.ts` builds the provider at the composition root (`main.ts`, `productionDependencies`): it verifies the platform's pin of `GIT_CLIENT_PINS` with `verifyGitClient`, and composes `GitWorkspaces` with the canonical data root, the remote policy `https-only`, and the reclaim host of the platform: `LinuxReclaimHost` with the containment parent and the execution account where decision 1 holds, `ProcessGroupReclaimHost` otherwise. A mismatched client fails the start with `precondition-failed` and reason `git-client-mismatch` before the worker enrolls or opens its journal (contract section 7). The start then runs `sweep` before anything can prepare a workspace (contract section 3, step 5).
3. **Execution group and umask.** `startWorker` passes the execution account's gid as `executionGroup` to `openWorkerRoot` (`worker-start.ts`, `rootOptions`; contract section 14). Where decision 1 holds, the worker sets its process umask to `0007` before the composition, so the clone writes with the group bits of contract section 2; elsewhere the umask is unchanged, because every directory keeps `0700` there. The worker container's entrypoint (`infra/installation/worker-entrypoint.sh`) gives the worker identity the execution group as its supplementary group (`setpriv --groups`), so `prepare` can `chown(path, -1, gid)` without `CAP_CHOWN`.
4. **Single slot and its start refusal.** In `readWorkerSettings`, where decision 1 holds, `TASKELITH_WORKER_SLOTS` unset gives one slot, `1` gives one slot, and a value above `1` fails the settings with `invalid`, an error that names `TASKELITH_WORKER_SLOTS` and the execution account (question Q8), and the detail `variable`. Elsewhere the slot count keeps its rule (default `2`). The failure is the worker's start failure: `workerMain` writes it and exits with `1` before it enrolls.
5. **`fs.protected_hardlinks`.** Where decision 1 holds, the start reads `/proc/sys/fs/protected_hardlinks` through an injected reader, as `linux-containment-check.ts` reads `/proc/self/cgroup` through its probe, and refuses to start unless the content is exactly `1` followed by an optional newline; a read error also refuses, never reads as `1` (question Q2). macOS and a Linux worker without an execution account never read it.
6. **Held slot.** The worker keeps the set of handed-off attempts in memory, loaded from `handedOff()` at the start and changed only by the worker's own `handOff` and `reclaim` through a small worker-side service, `apps/worker/src/workspace-slots.ts`, because the worker process is the only writer of hand-off records (contract section 1). `refusalOf` counts, once per attempt, the journal's counted attempts together with these attempts, so a handed-off workspace whose execution exited still fills the slot and an offer beyond it is refused with `worker-slots-exhausted` (contract section 3, step 6). A `handedOff` read that rejects at the start fails the start, so a held slot is never read as free. A held slot counts as a slot only; its attempt's CPU and memory are counted while its journal counts it (question Q7).
7. **Capacity again after the reclaim.** After a reclaim that removes a hand-off record, the worker journals `worker.capacity.declared` again, also when its values are unchanged, so that the scheduler finds it eligible again (contract section 3, step 6; capacity reservation contract section 8, "Refusal"). This amends worker-runtime "Capacity declaration" (question Q4).
8. **`reclaim-failed`.** A reclaim that fails with `reclaim-failed` keeps the attempt in the held set, so its slot stays held, logs `worker.workspace.reclaim-failed` with the attempt and the containment, and never retries the program; the reconciliation record that item 21 reads is question Q5. A workspace that a restart finds with `reclaimFailed` in its record is held and logged the same way.
9. **Program past its run bound, and the failed program's cgroup.** Question Q6 decides whether the worker kills a program past `RECLAIM_RUN_BOUND_MS`, frees its empty cgroup, and retries; the slot stays held in every option, because the hand-off record stays.
10. **Scan exclusion.** At the start the worker reads the hand-off records once and passes their recorded cgroup containments to the scan for unrecorded processes (`launch-orchestrator.ts`, `#findUnrecordedProcesses`), which skips them (contract section 3, step 7). A populated `reclaim-<name>` that no record names is still reported.
11. **macOS composition.** One account: `ProcessGroupReclaimHost`, no execution group, no umask change, no `fs.protected_hardlinks` read, and the slot count it is given; `handOff` there refuses no second workspace. The Git client gate uses Apple's pin.
12. **Spec placement.** Every worker rule goes into the `worker-runtime` delta. `resource-admission` is the scheduler's side of the capacity reservation contract, whose declared slot count and `worker-slots-exhausted` handling already cover the held slot, so it gets no delta; the worker rules that `git-workspace-port` still holds are question Q10.
13. **Ports.** The worker's runtime depends on the narrowest ports: the start on `WorkspaceLifecycle` (`sweep`, `handedOff`) and the slot service on `handOff` and `reclaim`; only the composition root names `GitWorkspaces` (ADR 0004, principles 2 and 3).

## Test plan

- **Host unit tests (`apps/worker/test/*.test.ts`), both platforms through injected host facts.** Settings: Linux with an execution account and `TASKELITH_WORKER_SLOTS=2` fails naming the variable and the account, unset gives `1`; macOS and Linux without a command keep `2`. The hard-link check: `0`, `2`, empty, and a read error refuse the start, `1` and `1\n` pass; macOS never calls the reader. Admission: a fake `WorkspaceLifecycle` whose `handedOff` returns an attempt whose intent ended makes `refusalOf` answer `worker-slots-exhausted`, and after the reclaim the offer is admitted and a new capacity declaration is journaled. `reclaim-failed` keeps the slot and logs once; a restart with a failed record holds it. The scan skips a recorded containment and reports an unrecorded one. The composition picks `ProcessGroupReclaimHost` and Apple's pin for `darwin`, `LinuxReclaimHost` and the Linux pin for Linux with an account, and a mismatched pin fails the start with `git-client-mismatch`.
- **Fail-before.** Each new test is first run against the worker of `dev` `f68d4f76` (the test files only), and `verification.md` records its failing output: the slot refusal (the settings accept `2`), the hard-link check (the start passes with `0`), the held slot (the offer is admitted), the redeclaration, the scan exclusion, and the `reclaim-failed` hold.
- **Linux in the worker image.** A privileged suite, beside `linux-git-workspace.privileged.ts`, starts the worker through the image's entrypoint and checks: the worker's `/proc/self/status` shows the execution group among its groups and umask `0007`; `TASKELITH_WORKER_SLOTS=2` exits `1` with the variable and the account in the error; the real `/proc/sys/fs/protected_hardlinks` is read (the host's value, expected `1`), and a reader pointed at a file holding `0` refuses the start, because a container cannot change the kernel setting; and a handed-off workspace of a real hand-off holds the slot across the exit and is released by the reclaim.
- **macOS.** The host unit tests above run on every host; the composition's tests with the real `ProcessGroupReclaimHost` run natively on the iMac with the carried macOS gate.

## Risks / Trade-offs

- The held set in memory is right only while the worker is the only writer of hand-off records; the root lock makes it so (worker journal contract section 2).
- A held slot after `reclaim-failed` stops a Linux worker from taking work until an operator acts, as the contract intends; question Q5 decides how that becomes visible.
- A process group identifier on macOS can be reused after its group ends (16a and 16d risks); question Q9.

## Coordinator questions

Each question needs the coordinator's answer before code. "Amends the contract" says whether the answer changes `docs/contracts/git-workspace.md`.

1. **Q1, who calls `handOff` and `reclaim` in 16e.** The contract (section 14) gives the calls around each execution to the harness host (item 18), but 16e must count, release, and redeclare a held slot, which only happens around those calls. Options: (a) 16e adds the worker-side slot service (decision 6) that wraps `handOff` and `reclaim`, composed at the root and tested directly, and item 18 calls it; nothing in the launch path prepares or hands off yet. (b) 16e also calls `handOff` before each launch and `reclaim` after a proven exit in `launch-orchestrator.ts`, for attempts that have a workspace; nothing prepares one before item 18, so the path is dead code until then. Recommendation: (a). Amends the contract: no.
2. **Q2, how the worker refuses to start on `fs.protected_hardlinks`.** Contract section 2 says the worker "refuses to start", but worker-runtime "Self-check at every start" says a failed admission check never fails the start (it refuses offers with `worker-self-check-failed`). Options: (a) a start precondition, like the slot refusal and `git-client-mismatch`: the start fails before enrollment with `precondition-failed`, reason `hardlinks-unprotected`, naming `fs.protected_hardlinks`, and an unreadable setting also refuses; (b) an admission check `linux-protected-hardlinks` in the self-check report, so the worker starts and takes no work; (c) both. Recommendation: (a), with the reason added to contract section 9's table beside `git-client-mismatch`. Amends the contract: yes, section 9 (the reason) and section 2 (an unreadable setting refuses).
3. **Q3, which worker has a separate execution account.** The settings read the execution account only on Linux with a launch command; the image sets `TASKELITH_EXECUTION_UID` and `TASKELITH_EXECUTION_GID` always. Options: (a) the account exists only with a launch command (decision 1): a Linux worker without a command keeps its slots, and runs no hard-link check; (b) every Linux worker has the account, read always, so the one-slot rule, the hard-link check, and the Git client gate apply to every Linux worker. Sub-question: does a worker without a launch command compose the workspace and run the Git client gate at all? Recommendation: (a), and a worker without a launch command composes no workspace and runs no Git gate, since it runs no execution and holds no workspace; this keeps the smoke installation, which has no command, unchanged. Amends the contract: yes, one sentence in section 3, "One slot", that a worker with executions under a separate account is a Linux worker with a launch command.
4. **Q4, declaring the capacity again after the reclaim.** Worker-runtime "Capacity declaration" journals a declaration only when a value changes, and the slot count is still `1` after a reclaim. Options: (a) after every reclaim that removes a hand-off record, journal `worker.capacity.declared` with unchanged values; (b) only after a reclaim that follows a `worker-slots-exhausted` refusal since the last declaration. Recommendation: (a), simpler and always correct; the cost is one observation per attempt. Amends the contract: no (section 3 already says so); amends worker-runtime "Capacity declaration".
5. **Q5, how `reclaim-failed` is reported for reconciliation before item 21.** Options: (a) a structured log line `worker.workspace.reclaim-failed` (attempt, containment, never a path that could hold a secret) at the failure and at each start that finds the record, with the slot held, and item 21 adds the observation the control plane reads; (b) a new journaled observation kind now, which changes the execution OpenAPI document and the journal contract. Recommendation: (a); (b) is a wire change outside item 16. Amends the contract: no.
6. **Q6, a program past `RECLAIM_RUN_BOUND_MS`, the failed program's cgroup, and retries.** 16d records such a program as failed and leaves it running (contract section 3, step 7: "killing it, freeing the slot, and any retry are the reconciliation policy of sub-change 16e"). Options: (a) leave it running; the workspace and its slot stay held until an operator; (b) after the bound kill the program's containment (`cgroup.kill` on Linux, `kill(-pgid, SIGKILL)` on macOS), prove it empty, remove the empty `reclaim-<name>` cgroup, and keep the record with `reclaimFailed`, so the workspace stays handed off and the slot held, without a retry; (c) as (b), then retry the program once. Freeing the slot without a successful reclaim is not offered, because the checkout would stay reachable by the next execution through the shared account. Recommendation: (b), and the empty cgroup of a program that failed after `go` is removed the same way. Amends the contract: yes, section 3, step 7 ("without killing the program" becomes a kill after the bound, with the record kept).
7. **Q7, what a held slot counts.** Contract section 3 says the handed-off workspace holds "its slot". Options: (a) the slot only: after the exit the attempt's CPU and memory are free, because its processes are proven gone; (b) the slot and the attempt's requested CPU and memory until the reclaim. Recommendation: (a). Amends the contract: no; stated in the worker-runtime delta.
8. **Q8, how the start refusal names the execution account.** Contract section 3, "One slot", and the git-workspace-port scenario "Two slots requested" expect `taskelith-exec`, but the settings hold only the uid and gid. Options: (a) name it by uid and gid, `uid 10003, gid 10003`, and reword the scenario; (b) resolve the name from `/etc/passwd` through an injected reader, falling back to the uid; (c) a new variable `TASKELITH_EXECUTION_USER`, set by the image. Recommendation: (a), no new setting and no file read on a failure path. Amends the contract: no; the git-workspace-port scenario's wording changes (question Q10).
9. **Q9, the macOS proof of a reused process group.** A recorded process group can be reused by an unrelated group after it ends, so `kill(-pgid, 0)` may read a foreign group as populated (16a and 16d risks). Options: (a) accept it: a reused group only delays the reclaim to the proof's bound and reports it, never releases early; (b) record the leader's start time with the group and treat a group whose leader differs as empty. Recommendation: (a) for G3, since the failure mode is safe (held, never released early), stated as a residual risk in contract section 3. Amends the contract: yes, one sentence.
10. **Q10, worker rules in `git-workspace-port`.** The living `git-workspace-port` spec holds worker rules: "Single slot with a shared execution account" and the slot half of "One handed-off workspace per Linux worker" (declared slot, `worker-slots-exhausted`, redeclaration). A past review flagged such a rule there as scope. Options: (a) move them: this change adds them to `worker-runtime` and `resource-admission`, removes "Single slot with a shared execution account" from `git-workspace-port`, and narrows "One handed-off workspace per Linux worker" to the adapter's `other-workspace-handed-off` refusal; (b) leave the port spec as is and only add the worker deltas, which duplicates the rule. Recommendation: (a). Amends the contract: no.
