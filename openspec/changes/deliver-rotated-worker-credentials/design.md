## Context

Row 26 of the [G3 plan](/docs/g3-plan.md#work-items) includes the delivery of a rotated credential generation to an enrolled worker. Sub-changes 26a ([design](/openspec/changes/archive/2026-10-28-issue-installation-certificates/design.md)) and 26b ([design](/openspec/changes/archive/2026-10-28-enroll-remote-worker-over-tls/design.md)) gave the installation its CA and pinned it on the worker. Before this change `EnrollmentService.rotate` minted generation N+1 on the control plane, NKey seed included, `rotate-worker` printed those secrets, and the predecessor stayed valid only for the 10-minute grace window; the worker never learned of a rotation, so it lost access when the window ended ([installation contract](/docs/contracts/installation-and-enrollment.md) section 6). The worker's runtime read its credentials once at start, its HTTP clients held a fixed bearer, and its broker session reconnected with fixed `.creds` text forever.

## Decisions

1. **Keep N until the confirm, with a hard cap** (run `20261027T221048Z-claude-63826` decision 6). The previous generation stays valid until the worker confirms N+1 or the cap passes; after the cap a worker that never renewed must re-enroll. The time-only wording of the installation contract is replaced (decision 8 of run `20261028T065320Z-claude-17941`).
2. **`rotate-worker` only requests** (run `20261027T221048Z-claude-63826` decision 7; run `20261028T065320Z-claude-17941` decision 2). It records `{generation N+1, requestedAt, deadline}` in the worker's record, prints `{workerId, credentialGeneration, deadline}`, and prints no secret. Re-enrollment stays the documented recovery path for a worker that is offline past the cap. It takes `--actor` and `--reason`, as `reset-operator-credential` does, because its audit event needs them (author's choice, from decision 5's audit rows). A repeat while a rotation is open returns that rotation unchanged, writes no second audit event, and sends the notice again, so an operator can resend a lost notice (author's choice).
3. **The worker generates the NKey** (run `20261027T221048Z-claude-63826` decision 9). The control plane never sees the seed; it signs the user JWT for the public key the worker sends, after it checks that the key is an NKey user key.
4. **Notice over JetStream** (run `20261028T065320Z-claude-17941` decision 1, option a only). The notice `worker.credentials.rotation-requested {credentialGeneration, deadline}` joins `COMMAND_SUBJECT_NOTICES` (`packages/adapters/nats/src/wire-message.ts`). The control plane appends it to the worker's command subject through the outbox in the transaction that records the request, so the JetStream publisher sends it, never core NATS. `apps/worker/src/command-intake.ts` dispatches it. There is no HTTP status endpoint; the worker's durable command consumer keeps an unacknowledged notice, which is the catch-up path for a worker that was offline. The notice carries no identity, so the outbox sends it without `Nats-Msg-Id`, like the inventory request. The decision's `generation` is named `credentialGeneration`, as in `Enrollment`.
5. **The worker's own bearer** (run `20261028T065320Z-claude-17941` decision 2, option a). The worker generates the `tkwk_` secret with `NodeSecrets.issue('worker')` of `@taskelith/secrets`, the generator the control plane uses, which the worker already depends on. The renewal body carries `{credentialGeneration, brokerUserPublicKey, controlPlaneSecretSha256}`; the answer is `{credentialGeneration, brokerUserJwt, deadline}`.
6. **The cap** (run `20261028T065320Z-claude-17941` decision 3). `deadline = requestedAt + max(rotationGraceMilliseconds, 7 days)`, measured from `rotate-worker`, stored in the record and in the new query column `workers.rotation_deadline`, and echoed in the renewal answer and the notice. At the cap, a renewed but unconfirmed N+1 drops N, keeps N+1, and writes the audit event `worker-credential.rotation-expired` with reason `unconfirmed`; a rotation that was never renewed revokes the worker, with the audit reason `rotation-expired`. The confirm drops N at once, with no drain. The cap extends `EnrollmentService.expireGraceWindows()`, so no second sweep exists. `rotationGraceMilliseconds` stays the provisional 10 minutes of O4 and acts as a floor; `rotationHardCapMilliseconds` is 7 days, also provisional (operational targets).
7. **Bounded authentication failures** (run `20261028T065320Z-claude-17941` decision 4). `brokerFailure` in `broker-failure.ts` gives NATS authorization violations and expired user authentication the reason `credentials-rejected`, keeping the code `unavailable`, so no other caller's retry changes. On such a failure the worker tries every generation it holds locally: the current one, then a kept predecessor whose successor is not yet confirmed. After 3 consecutive rounds in which all were rejected it stops with code `forbidden`, reason `credentials-expired`, and a message that names re-enrollment; other broker failures keep the endless retry.
8. **Audit** (run `20261028T065320Z-claude-17941` decision 5). `audit_events` gets `subject text NOT NULL` in its creating migration `1792930800000_installation-and-enrollment.sql`, as Taskelith is pre-release, with no new migration; `workers.rotation_deadline` goes into the same migration on the same ground. Operator credential events write `operator`, worker events the worker identifier. The four kinds are `worker-credential.rotation-requested` (actor and reason of the operator), `.renewed` and `.confirmed` (actor `worker`), and `.rotation-expired` (actor `control-plane`, reason `unconfirmed` or `rotation-expired`); every event names generation N+1. Failed renewals go to logs only. One helper, `appendAuditEvent` in `packages/adapters/postgres/src/audit-events.ts`, writes every row, the operator credential's former inline `INSERT` included. The `AuditEvent` of `@taskelith/access` carries `subject` and the four kinds, and the registry port reads a worker's trail with `credentialAuditTrail`.
9. **Enrollment keeps its server-made NKey** (run `20261028T065320Z-claude-17941` decision 6). `BrokerAuthority.user()` still mints the enrollment generation's seed. A follow-up line under row 26 of the G3 plan records "enrollment-side NKey generated by the worker".
10. **Implementation choices accepted with two conditions** (run `20261028T065320Z-claude-17941` decision 7). (i) The OpenAPI `info.version` is the next minor above the version it builds on: 0.6.0 over 26b's 0.5.0, and 0.7.0 since the merge of `dev`, whose sub-change 9c took 0.6.0. (ii) The worker confirms only after a successful NATS connection with N+1, and the contract states that this worker-side rule is why the control plane checks no broker connection (no `CONNZ` lookup).
11. **Contract wording** (run `20261028T065320Z-claude-17941` decision 8). The installation contract's generation bullets and the "not yet" bullet of section 10 take the confirm-or-cap wording, and section 9's 26c sentence is extended.

## Implementation (author's choices)

- **Record.** `WorkerCredentials` keeps `current` and `previous`, and gains `rotation {generation, requestedAt, deadline, brokerUserJwt?}`. At the renewal N+1 becomes current, N becomes previous with `validUntil = deadline`, and the rotation keeps the signed JWT, which a replay returns; the JWT is not a secret without the seed. The confirm, or the cap, clears `previous` and `rotation`. So `validGenerations` and the existing hash columns are unchanged, and a predecessor is never older than N.
- **Renewal rules.** The caller must authenticate as N and name the open rotation's N+1, else 409 `rotation-not-requested`. Once N+1 is renewed, the same key and hash answer the stored JWT and deadline; another key or hash is 409 `renewal-mismatch`. A refused renewal is logged as `fleet.credentials.renewal-refused` with the worker, the generation, the code, and the reason, never a key or hash (review pass 2, L3). The registry checks again under its row lock, so a racing renewal with the same material gets the winner's JWT. It also reads the service's clock after that lock, so a first renewal at or after the deadline, also one that waited for the lock, is `forbidden` (401 `worker-not-authorized`) and leaves the rotation to the cap (review pass 1, F1).
- **Confirmation rules.** The caller must authenticate as the generation it names, else 409 `confirmation-mismatch`. Confirming the renewed current generation drops N, records N's broker user for revocation at the confirmation time, and publishes revocations after the commit; the answer's `revocationsPublished` reports that publication, and the sweep retries a failed one. At or after the deadline, read after the row lock, the confirmation first applies the cap's transition: N is dropped as unconfirmed with `worker-credential.rotation-expired`, and the confirmation is then a replay (review pass 1, F3). Confirming the current generation with no renewed rotation open is a replay: 200, nothing dropped, no audit event; every confirmation, a replay included, publishes the recorded revocations, so `revocationsPublished` reports that publication (review pass 1, F4).
- **Sweep revocation.** A worker revoked at the cap goes through the same transaction as `revoke-worker` (`LaunchRevokingFleetRegistry`, which frees what it cannot run), then its command consumer is removed and the revocations published. A failed removal makes the sweep report `unavailable` after it published, naming the worker, while the revocation stays committed; a later start removes the consumer while the worker is among the latest revoked.
- **Worker files.** Before it renews, the worker creates `worker/credentials/pending.<N+1>` once, mode `0600`, holding the new bearer secret and NKey seed, so a crash never loses key material the control plane may have signed for. After the renewal it creates `control-plane.<N+1>` and `broker.<N+1>.creds` once (an existing file with the same content counts as written, another content is `corrupt`), then replaces `worker/identity`, format 2, with N+1 current and N under `previous`. After the confirmation it replaces the identity without `previous` and removes N's files and the pending file. The identity is the durable record of that step: every start whose identity keeps no predecessor removes the files of the generation before the current one and the current one's pending file, which completes a removal that a crash interrupted (review pass 1, F5). Format 1 identities are still read; a format above 2 is refused as before.
- **Worker runtime.** `CredentialRotation` (`apps/worker/src/credential-rotation.ts`) owns the generations: the launch authority reads its bearer per request, and the broker session's connection reads its candidates per attempt. A notice for the generation after the current one creates the pending file before the consumer acknowledges it, also while an adopted generation is unconfirmed, for example after a confirmation whose answer was lost; the driver confirms that one first and then renews the stored one (review pass 1, F2). Other notices are acknowledged and ignored. The driver runs at every start and after each notice: it renews a pending generation with the current bearer, adopts it, has the broker session re-dial unless its link already uses N+1, and confirms only when the new link is N+1's. A refused renewal or confirmation (400, 401 or 403, 409) ends the round with a log line; any other failure, a 500 or an unavailable control plane or broker, decided nothing and is retried after 5 s doubling to 60 s with jitter (review pass 2, M1).
- **Stop.** The terminal failure stops the runtime through the broker session; `serveUntilStopped` prints the redacted failure and sets exit status 1. A supervisor that restarts the worker gets the same stop after 3 more rejected rounds, until the operator re-enrolls.

## Review checklist

The coordinator's brief listed the checklist in [checklist.json](checklist.json) (dev commit `f3a53f17`): the most frequent review categories are contract-drift, error-handling, redaction, docs, spec-wording, evidence-mismatch, and missing-fail-before-test; for records also stale-citation, process, and scope.

How the change guards against them: both documents, the route table, the specs, and the contracts change in one commit before the code, and the route test checks every route's statuses against the document (contract-drift, docs); every new failure is a `Result` with a reason, and the sweep, the confirmation, and the worker driver report what failed instead of dropping it (error-handling); no secret, seed, or bearer crosses the wire on a renewal, logs name generations and reasons only, and the pending file is `0600` (redaction); each scenario states an observable outcome (spec-wording); each required behaviour has a test shown failing first, recorded with real counts (missing-fail-before-test, evidence-mismatch).

## Risks and limitations

- A worker that crashed after the renewal answer and before its adoption, and stays offline past the cap, has the seed of N+1 but no JWT and no valid bearer to renew with; it stops with `credentials-expired` and must re-enroll.
- A worker offline past the cap without a renewal is revoked; re-enrollment is the documented recovery.
- The 7-day cap and the 10-minute floor are provisional, verified in G6.
- The Linux suites and the native scenarios depend on hosts this change could not fully exercise (see `verification.md`).
