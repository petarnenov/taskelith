## Coordinator decisions

- **D1 Docs-only path set.** `docs/**` except `docs/review-findings/**` and `docs/qualification/**`, `openspec/**`, and root-level `*.md` files except `CHANGELOG.md`. Tests read `docs/review-findings/**` and `docs/qualification/**`, so a change to them gets the full profile (coordinator decision of 2026-10-27). `.claude/**`, `scripts/**`, and everything else are not documentation and get the full profile. The docs-only profile skips only the Docker test suites; every other check of `make verify` still runs. It applies only to branches; integration always runs the full profile.
- **D2 Verified-tree stamp.** Stored in `$(git rev-parse --git-common-dir)/taskelith-verify-stamps/<key>`, shared by the worktrees of a clone and never tracked. The key covers the HEAD tree, the Node.js and npm versions, the lockfile hash, the test image digests, and the profile, so a docs-only stamp never satisfies a full requirement. A dirty tree or any key change means a full run, and no stamp is written for a dirty tree. Promotion CI from `dev` to `main` never skips.
- **D3 Docker slot lock.** The lock directory is `${XDG_STATE_HOME:-$HOME/.local/state}/taskelith/docker-slot.lock`: a `mkdir`-based first-in, first-out queue with stale-lock recovery by process ID, portable to macOS, which has no `flock`, and Linux, with a wait and hold log next to it; a waiter prints the holder. It is host-wide per user.
- **D4 Context warning hook.** A hook in the tracked `.claude/settings.json` estimates the context from the transcript, warns near 150,000 tokens, only warns and never blocks, stays fast, never prints transcript content, and is documented as an estimate. Refinement accepted by the coordinator on 2026-10-27: the estimate comes from the usage of the last main-thread assistant message in the transcript's last 1 MiB, and the transcript size divided by four only when there is none.
- **D5 Integration script.** `scripts/integrate.sh` keeps the pause file of the coordinator's former `resume.sh`, now in the lock's state directory, and its 2400 s alarm, both as options. `make integrate` always requires a full stamp of the merged tree.

Coordinator decisions of 2026-10-27, taken during the work:

- **Unpushed coordinator merge.** `make integrate` commits the merge of `origin/dev` on the local `itg-<branch>` and pushes it only after the full `make verify` passed. On a return the coordinator deletes the local `itg-<branch>` and its worktree, so a returned branch never carries a coordinator merge.
- **Tested documentation paths.** `docs/review-findings/**` and `docs/qualification/**` leave the docs-only path set of D1, because tests read them.
- **Stamp and the handoff push.** Documented only: the stamp rarely spares a worker's handoff push, because recording the `make verify` result in `verification.md` changes the tree after the stamped run.
- **Context estimate.** The D4 refinement above.

## Decisions per recommendation

1. **Verified-tree stamp** (`scripts/verify-stamp.ts`). `make verify` now runs `verify-stamped`, which asks the script for the profile and for the start tree (the HEAD tree when the working tree is clean, `dirty` otherwise), runs `verify-checks` with that profile, and asks the script to write the stamp. The script writes it only when the tree was clean at the start and is still clean and unchanged at the end, so an edit during the run never gets stamped. The key is the SHA-256 of the HEAD tree, its merge base with `origin/dev` (`none` without one), which the contract compatibility check and the findings validation read, profile, `node` and `npm` versions, the SHA-256 of `package-lock.json`, and the digest-pinned image references of `infra/services/compose.yaml`; the images are already part of the tree, and the key names them so that the stamp follows D2 literally without calling Docker. A full stamp satisfies a docs-only requirement, never the reverse. `make -n` still runs recipe lines that call `$(MAKE)`, so the script reads `MAKEFLAGS` and writes no stamp in a dry run. The `pre-push` hook runs `verify-stamp.ts check` after its existing checks; it skips `make verify` only for a clean tree with a satisfying stamp, prints the stamp's time, and otherwise runs `make verify` as before. CI never reuses a stamp and never skips: a CI run may write a stamp, which nothing reads, because `check` refuses whenever `CI` is set, and the GitHub job calls `make verify`, not the hook.
2. **Docker slot lock** (`scripts/docker-slot.ts`). `make test` runs the services and `npm test` under `docker-slot.ts run --`. `run` starts a holder process as the leader of a new process group and forwards signals to that group; the holder takes the ticket and runs the command in its group. A ticket is taken as in Lamport's bakery algorithm: the holder writes a `choosing/<id>.json` marker, picks one past the highest ticket number it sees, creates `queue/<number>-<id>` with `mkdir` and its record, and only then removes the marker; `<id>` is the process ID and random bytes, so a ticket path is never reused and a late cleanup never removes a newer ticket. The ticket holds the slot when no live run is choosing and its name is the lowest, so two runs that read the queue at once never both hold it, and the order is first-in, first-out. Each ticket records the process ID, the process start time from `ps`, the worktree, and the time. A ticket is stale only when its process ID is free or belongs to a process with another start time and its process group has no process left, because a process ID is never reused while its group exists; so a command that outlives its killed holder keeps the slot. A ticket or marker without its record for longer than a minute is stale too. The waiter prints the holder's process ID, worktree, and start whenever the holder changes, and the log `docker-slot.log` gets one line per acquire and release with the wait and hold seconds. Signals during the wait remove the ticket; signals while the command runs reach its whole group, and the ticket is removed after the command exits. The holder starts in a new session (Node.js `detached: true`, which calls `setsid`), so the command it wraps has no controlling terminal; `services.sh` needs none. A new process group without a new session (Perl `setpgrp`) was rejected because a background group that touches the terminal risks `SIGTTOU` and `SIGTTIN` stops; the worker (Pepi) decided this. Only `make test` takes the slot: `make contract-compatibility` runs one short `oasdiff` container, and the opt-in targets keep their own projects.
3. **Docs-only verify profile.** `verify-stamp.ts profile` lists the paths changed since the merge base with `origin/dev`, committed, staged, unstaged, and untracked, renames as both paths, and returns docs-only only when every path matches D1. `dev`, `main`, a detached HEAD, `CI`, `TASKELITH_VERIFY_PROFILE=full`, a missing merge base, and an empty change get the full profile; `TASKELITH_VERIFY_PROFILE` accepts no other value, so nothing can force the docs-only profile. `verify-checks` skips `make test` under `VERIFY_PROFILE=docs-only` and prints so. `AGENTS.md` now says that `make verify` runs its branch's profile and that the hook reuses a passing stamp.
4. **Integration script** (`scripts/integrate.sh`, `make integrate`). It follows the coordinator's former scripts, after a check that the main clone is on a clean `dev` that `origin/dev` fast-forwards (exit 8 otherwise): an integration worktree `../taskelith-worktrees/itg-<branch>` from `origin/<branch>`, a check that the branch carries its archived change (exit 5 otherwise), the merge of `origin/dev` (on a conflict it aborts, prints `CONFLICT <branch>`, and exits 3), `make setup`, a clean integration worktree (`NOT CLEAN`, exit 7, otherwise), the full stamp or a full `make verify` under the alarm (on failure, or when the passing run left no full stamp of the merged tree, `VERIFY FAIL <branch>`, the log's tail, exit 4), the push, `gh pr create --base dev` unless the branch has an open pull request or one merged at the pushed commit, `gh pr merge --merge` unless it is merged, removal of the worktree and local branch, the update of the main clone, the deletion of the remote branch and a check of it (exit 6 when it remains, exit 9 when `git ls-remote` fails), and `LANDED <branch> <url> <head>`. `make verify` runs as its own process group; on the alarm, and when it ends, a small Perl supervisor stops what is left of the group, `TERM` first and `KILL` after ten seconds, and waits until the group is gone; the Docker slot's command group, which the holder started in its own session, gets the `TERM` forwarded. The merge is committed on the local `itg-<branch>`, because D2 stamps only a clean tree and D5 requires a full stamp of the merged tree; it is pushed only after that stamp exists, so the guarantee of "Uncommitted coordinator merge" moves to "Unpushed coordinator merge". The verify log goes to the state directory, not the worktree, where it would make the tree dirty. `--resume` (`RESUME=1`) continues in an existing integration worktree. Arguments reach the script through the environment, never as shell text, like the installation targets; `make` would expand `TITLE` and `BODY` when exporting them, so the target unexports them and passes their raw `$(value ...)` under other names, and the script's own `make` calls get no `MAKEFLAGS`. Paths come from `git worktree list`, never from a home directory.
5. **Generated records** (`scripts/verification-record.ts`, `make record`, `make record-check`). The generated part sits between `<!-- make record: begin -->` and `<!-- make record: end -->`; `make record` replaces it, or inserts it before `## Independent review` (or appends it) the first time, and touches nothing else. From the given `make verify` log it takes the last run, from its profile line to the result line that `verify-stamp.ts write` prints (passed, profile, tree), which must end the log; it refuses a run with repeated, failing, or contradictory test totals, and a full run without totals or coverage; it runs the change's strict OpenSpec validation and the findings validation, takes `git diff --stat` of `openspec/specs` against the merge base with `origin/dev`, and lists the passes of `passes.jsonl`. Every part is deterministic, so `make record-check` recomputes them and compares the text; for the `make verify` part it checks that a stamp of the recorded tree and profile exists, that the working tree differs from that tree only in the change's `verification.md`, and that the recorded line equals the one `make record` stored next to that stamp, the simplest check that catches a hand edit of a count or coverage figure; the log itself stays the worker's evidence. The check needs the local stamps, so it is a protocol step before pass 1, not part of `make verify`. `CHANGE` and `LOG` reach the script as typed, like the arguments of `make integrate`: the targets unexport them and pass their raw `$(value ...)` under other names, without `MAKEFLAGS`.
6. **Conditional pass 3.** `docs/governance.md` (policy version 6) and the review-process spec: pass 3 runs only when the pass 2 fixes change a file outside the records and documentation (`openspec/changes/**` except spec deltas, `docs/**` except `docs/contracts/**`, root-level Markdown), or pass 2 reported a Critical or High finding. Otherwise the pass 2 fixes are recorded as `fixed-unreviewed`, an outcome the findings schema already has. The three-pass cap and the Low-only rule are unchanged.
7. **Thin context and fresh subagents.** The protocol's "Context size" and "Subagent execution" sections and the skills state the practice. The hook is `scripts/context-warning.ts`, run on `UserPromptSubmit` with a 5 s timeout: it reads at most the last 1 MiB of the transcript and takes the context of the newest assistant message's usage (input, cache creation, and cache read tokens), which also stays right after `/compact`; without such a line it estimates four bytes per token from the transcript size, as D4 states. At 140,000 tokens or more it prints one line with the estimate and the protocol section. It prints no transcript text and always exits 0.
8. **Reviewer assignment by measured yield.** No edit: `normalize-reviewer-keys` records it.
9. **No owner `/clear`.** Worker step 9, coordinator step 4, "Context size", the skills, and `docs/fleet.md` now keep the worker's session across tasks; the coordinator briefs the worker right after the landing report.
10. **Flaky tests at the source.** A "Test authoring" section in the protocol, and the plan checklist of every brief already carries the category `test-flakiness`, so `categories.txt` needs no new line. `stabilize-workspace-handoff-race-conformance` fixes the current flaky test; this change does not touch it.

## Alternatives considered

- `flock` for the slot: not available on macOS by default (D3).
- Stamping a staged but uncommitted merge: D2 writes no stamp for a dirty tree, so the merge is committed locally instead.
- A stamp check inside `make verify` itself: rejected; `make verify` always runs its checks, and only the hook and `make integrate` reuse a stamp.

## Review checklist

Review checklist (files scripts/**, Makefile, .githooks/**, docs/agent-task-protocol.md, docs/governance.md), most frequent finding categories first:
1. contract-drift (11): Code, a contract document, and its specification disagree. Example: "The missedBy order diagnostic omitted the finding's artifact, although the protocol says messages name it"
2. error-handling (7): A failure is swallowed, misreported, or leaves inconsistent state. Example: "The Linux crash windows script mounted the services secrets without checking that their variable is set"
3. redaction (4): A secret or private value can leak into output, logs, or records. Example: "The NATS seed pattern misses server, cluster, and curve seeds"
4. docs (3): Documentation is missing, wrong, or out of date with the change. Example: "The protocol and the statistics requirement did not mention misses that name a pass without a record"
5. process (3): A protocol, governance, or review rule was not followed. Example: "The findings operations have no Makefile entry"
6. naming (2): A name hides intent or uses two terms for one concept. Example: "Pass summaries were parsed from a type named for findings, and the valid-output helper called its changes files"
7. evidence-mismatch (1): A recorded result, count, or claim differs from what the checks show. Example: "The harness variant build was not run with Docker after the change"

Record quality (archived findings under openspec/changes/), most frequent finding categories first:
1. evidence-mismatch (53): A recorded result, count, or claim differs from what the checks show. Example: "The record gave the spec delta body as 477 characters, one more than its length"
2. docs (42): Documentation is missing, wrong, or out of date with the change. Example: "The record groups the #settle comment with comments that said a pass stops only when the store fails, though it was about waits"
3. spec-wording (23): A requirement or scenario is ambiguous, untestable, or inaccurate. Example: "Scenario Capacity freed during a pass expects the next pass to place the declined task, which fails when earlier offers were own declines and one placement, leaving the cursor before a later project"
4. stale-citation (21): A cited file line, commit, or record no longer matches its target. Example: "The plan checklist named a capability that does not exist and a docs glob that matches no file"
5. process (9): A protocol, governance, or review rule was not followed. Example: "Task 4.2 is unticked although review pass 1 is recorded"
6. contract-drift (8): Code, a contract document, and its specification disagree. Example: "The proposal and verification record said the index and checklist commands were unchanged, although they now refuse invalid pass summaries"
7. scope (5): The change does more or less than its assigned scope. Example: "Design D6 defines size M as a contract, its spec, and its port types, while the SCM follow-up also changes the port's readers and conformance case"

How this change meets it: contract-drift: the Makefile, hook, scripts, protocol, governance, skills, and spec deltas are checked against each other for every rule they share; error-handling: every script fails closed (no stamp, no skip, a nonzero exit) and its failure paths are tested; redaction: the hook prints no transcript text and the slot prints no command arguments, only a process ID and a worktree path; evidence-mismatch and stale-citation: `make record` generates the mechanical evidence, and every hand-written count and `file:line` in `verification.md` is checked against the tree.

## Risks

- A change under `docs/review-findings/**` or `docs/qualification/**`, which tests read, gets the full profile; a test that reads another file under `docs/` runs on a docs-only branch only in the full `make verify` at integration.
- The stamp rarely spares a worker's handoff push: recording the `make verify` result in `verification.md` changes the tree after the stamped run.
- A stamp is local to a clone, so another machine runs `make verify` again.
- The stamp key covers the tree, the profile, the toolchain, the image digests, and the merge base with `origin/dev`, but not the branch's own history: two histories with the same tree and merge base count as equivalent, a theoretical residual of review finding 4 for the findings validation, which reads branch commits. Keying on the HEAD commit would defeat stamp reuse across the record commit, so it is not adopted.
- The context estimate depends on the transcript format of Claude Code; when it changes, the hook falls back to the size estimate or prints nothing.
