## Decisions

Each decision names its source.

1. **Names.** The capability is `session-turn-model`, after the change name and the `*-model` capabilities of the other pure domains (`execution-model`, `scheduling-model`, `sdlc-workflow-model`). The contract is `docs/contracts/session-timeline.md`, because the architecture and the harness port contract call the concept the "session timeline"; the domain files use the same term. Source: `openspec/specs/`; architecture section 7; agent harness port contract section 2 rule 6.
2. **A contract document first.** Items 3 and 5, the sibling contracts of the G3 plan's items 3 to 8, each added a contract under `docs/contracts/` with a spec and port types; G2 item 7, a pure domain without a contract, had only its spec. The G3 plan counts item 4 among the G3 contracts, and item 9 derives wire schemas from it, so this item writes a contract. Source: [G3 plan](/docs/g3-plan.md) "Work items" ("Items 3 to 8 are the G3 contracts"); archived `define-agent-harness-port` and `define-account-pool-contract`.
3. **Module placement.** The domain lives in `packages/modules/execution/src/domain/` and is exported from `@taskelith/execution`. Source: architecture section 6; agent harness port contract section 1.
4. **Reuse, not redefinition.** The model uses the existing `AttemptId`, `PrincipalId`, `IdempotencyKey`, `NativeRequestId`, and `HarnessPluginId` (`domain/identifiers.ts`), `TaskId`, `OwnershipGeneration`, and `EvidenceReference` (`@taskelith/sdlc`), `StandingRuleId` (`ports/standing-approval-rules.ts`), and the port's `TurnOutcome`, `HarnessFailure`, `PermissionDecision`, `DelegationOutcome`, `HarnessRequestKind`, and `MAX_HARNESS_TEXT_LENGTH`. It adds only what the port carries as plain strings or numbers: `SessionId`, `TurnId`, and `NativeSessionId` as kernel identifiers, and `SessionGeneration` as a positive integer brand parsed like `RecoveryEpoch`. Source: brief; agent harness port contract sections 2 and 5.
5. **No slot in the session.** A session records its `HarnessPluginId` only; the slot stays in Scheduling's reservation (`providerCredentials`), which the account pool's affinity reads, and nothing imports Scheduling's reservation module. Recording a Scheduling slot type would make Execution import Scheduling, the reverse of the dependency `align-harness-identifiers` set. The coordinator accepted this on 2026-10-28. Source: account pool contract section 4.3; capacity reservation contract section 10; archived `align-harness-identifiers`.
6. **At most one active attempt per session.** A session binds attempts of its own task one at a time: binding an attempt while the bound attempt has not ended fails with `precondition-failed` and changes nothing, as the task's second active attempt does in `execution-model`. An attempt of another task, an attempt the session already bound, and an attempt another session of the task holds each fail with `conflict`. Source: capacity reservation contract section 10; account pool contract section 3.2; `execution-model` "Task ownership"; decision 20.
7. **Generations.** A session's first generation is 1, and the next one is exactly one more and starts only after the previous one ended. Every turn delivery, request, and response names the generation it belongs to. Source: agent harness port contract section 2 rule 5 and section 5.
8. **Turn identity and idempotency.** A submission carries an `IdempotencyKey`, the author, the text, and a new `TurnId` that the caller generates, since the domain reads no random source. A key is unique per session: a repeat with the same text returns the existing turn unchanged, whatever its state, and with another text fails with `conflict`. A `TurnId` already in the timeline fails with `conflict`. Each new turn takes the next position in the session's turn order, which never changes. Source: architecture section 7; [product ports contract](/docs/contracts/product-ports.md) section 2 rule 7; agent harness port contract section 6.
9. **Serialized delivery.** All turns are treated as mutable, because no harness declares concurrent turns in G3. At most one turn of a session is delivered and without an outcome, and turns are delivered in their order. A submission while a turn runs is recorded and queued (decision 21). Source: architecture section 7; agent harness port contract section 6, "One turn at a time".
10. **One outcome per turn.** A turn records exactly one outcome from the port's `turn-ended` (`TurnOutcome`, with its `HarnessFailure` when `failed`); a second outcome fails with `conflict` and changes nothing. Source: agent harness port contract section 9.1.
11. **Requests recorded before display.** A request enters the timeline only by being recorded, keyed by session, generation, and `NativeRequestId`, with its kind, turn, and text. The only read that lists requests awaiting an answer returns recorded ones, so an inbox item derives from a recorded request. Recording the same key again with the same content changes nothing; with other content it fails with `conflict`. Permission and input requests are displayable; a delegation request is recorded under the same rules and answered by the host (item 38). Source: architecture section 7 and invariant 6; agent harness port contract section 7.1; product ports contract section 4.2.
12. **A response is consumed once.** A response names the request key, the answer, the responder (a `PrincipalId`, or a `StandingRuleId` of the product ports contract section 5), and the attempt with its ownership generation. The first valid one is consumed; a second fails with `conflict`; an unknown, expired, or unresolved request fails with `not-found`, which covers a request of an ended generation; an attempt or ownership generation that is not the session's active bound one fails with `precondition-failed`; an answer of the wrong kind fails with `invalid`. A response names its generation through the request key, so a request's generation is always the current one while it can still be answered. Source: architecture section 7; agent harness port contract section 7.3; product ports contract sections 4.2 and 5.
13. **A reused native request ID is another request.** A request of a later generation with a native ID that an earlier generation used is a different request and is accepted. A response that names the earlier generation never applies to it, and no stored answer is copied to it. Source: agent harness port contract sections 7.1 and 7.3; architecture section 7; source note 1.
14. **Delivery of a consumed response.** After consumption the response is `delivered` once the host reports the port's success, `refused` when the port reports `conflict` or `not-found`, or `delivery-uncertain` when a timeout or a crash leaves the outcome unknown. Nothing is resent automatically, whatever the state: a second delivery report fails with `precondition-failed`. Source: architecture section 7 ("a native provider may not offer exactly-once response delivery").
15. **Reconciliation at a generation's end.** When a generation ends, each of its requests without a response becomes `unresolved`, each consumed response not yet reported becomes `delivery-uncertain`, and each delivered turn without an outcome becomes `outcome-unknown` (decision 22). These states are final, are shown, and lead to no resend, no answer, and no new turn. A request of the next generation is a new request for a fresh decision. Source: agent harness port contract sections 5 ("Host restart"), 6, and 7.3; architecture invariant 14.
16. **Output stream and cursor.** Each `output` event becomes an entry at the next session-wide position, from 1 without gaps, tied to its turn and generation. The model keeps a retained window bounded by `OUTPUT_RETENTION_BYTES` (decision 25). Reading after a cursor returns the retained entries after it, or `cursor-expired` with the earliest retained position when the cursor is older, so that the caller falls back to a durable snapshot, which item 14 provides. Source: architecture section 7 and R14; [operational targets](/docs/operational-targets.md) section 2, "Live session/terminal stream ring buffer".
17. **Limit handoff.** A turn that ends as `account-limit-reached`, or a `limit` signal of the session's slot, stops the session: it accepts no further turn, delivery, or generation, while outcomes, requests, responses, and output of a running turn are still recorded. Once its generation has ended, the host writes the session's one handoff (decision 24). The handoff stays with the session's task until a next session of that task takes it, once; a second take fails with `conflict`. Source: ADR 0005 decision 4 as amended; account pool contract section 4.4; agent harness port contract section 4.1; `harness-account-pools` "Session affinity"; decision 20.
18. **Pure and neutral.** The domain reads no clock, random source, file, or network, returns kernel `Result`s for expected outcomes, produces frozen values, and names no harness, vendor, model, or native field. Source: `execution-model` "Pure execution domain"; agent harness port contract section 2 rule 1; architecture section 7, microkernel.
19. **Fail-before tests.** Each requirement's tests are written against exported stubs and run failing before the domain is implemented; `verification.md` records the failing run. Source: ADR 0004; the brief's review checklist ("missing-fail-before-test").

### Decisions on the open questions

Away delegate decision, 2026-10-28, relayed by the coordinator: this applies to each of decisions 20 to 25 (away run `20261028T051911Z-claude-82696`, Claude Fable 5.1, deciding for the coordinator). Phase 1's options and recommendations remain in this file at the phase 1 commit.

20. **What a session spans: one task (open question 1, option (a), conditioned).** A session spans one task's successive stage admissions within one run: it binds attempts of that task only, one at a time, across the task's re-admissions, and a task belongs to one run (`TaskAdmission`, "one task of a run"). A delegated child task gets its own session, since it is another task. This replaces phase 1's recommendation (b), a session across several tasks of a run. Source: ADR 0005 decisions 4 and 5 ("The binding is per session, not per task: a new session of the same task"); account pool contract sections 4.4 and 10 (the handoff "that a limited session writes and the next session reads"); product ports contract section 3.6 (a card is a task, and its session in `waiting-for-admission` waits for the task's next stage admission); capacity reservation contract section 10 (attempts counted per task).
21. **A submission during a running turn is queued (open question 2, option (a)).** It is recorded in order and delivered when the running turn ends, one at a time; the port's rejection of a second turn never fires for a queued turn. This conforms to the UI POC, whose sent turn shows "accepted, delivered at the next turn boundary". Source: [UI POC](/docs/ui-poc/README.md) "Requests" ("turns carry a client turn key") and `docs/ui-poc/src/screens/Session.tsx` line 291; decision 9.
22. **A delivered turn without an outcome becomes `outcome-unknown` (open question 3, option (a)).** When its generation ends, the turn is `outcome-unknown`, final. A retry with the same idempotency key returns that turn; a new attempt at the same text needs a new key, and so a new turn. The turn is never delivered again, automatically or on a retry. Source: agent harness port contract section 6 ("No second submission"); architecture invariant 14.
23. **Inbox after a restart (open question 4, option (c)).** An unresolved request closes its inbox item (`closed`, product ports contract section 4.1) and stays in the timeline as `unresolved`. Only a `delivery-uncertain` response opens an acknowledgement item, because its answer may have run an action. The model exposes both as reads (`requestsAwaitingAnswer` and `uncertainDeliveries`); the items themselves are the inbox source's (item 13). Source: product ports contract sections 4.1 and 4.2; architecture section 7 ("expose an unresolved request"); source note 4.
24. **The handoff is a host-written record (open question 5, option (a)).** It holds the session, its task, its harness, the reset time when the `limit` signal carried one, the last turn with an outcome, the session's unresolved requests, and a reference to an evidence snapshot of the timeline. The host writes it once the stopped session's generation has ended, so that the unresolved requests are final. No agent-written text is in it; the prompt that the next session receives is item 18's. Source: ADR 0005 decision 4 as amended; account pool contract section 4.4.
25. **The retention bound (open question 6, option (a)).** `OUTPUT_RETENTION_BYTES`, a named parameter of the model, is `10 MiB` (10,485,760 bytes) of UTF-8 output text per session. With at most one active attempt per session it equals the operational target of `10 MiB` per active attempt. Source: [operational targets](/docs/operational-targets.md) section 2, "Live session/terminal stream ring buffer".

### Details of the model

26. **Generations run under the bound attempt.** A generation starts only while the session has an active bound attempt, and records that attempt. The first generation records the native session ID, and a later one must name the same ID, because a resume keeps it; another ID fails with `conflict`. Ending the bound attempt also ends a running generation, with the reconciliation of decision 15. Ending a generation that has ended changes nothing. Source: agent harness port contract section 5 ("Resume"); architecture section 7 (correlation with the attempt).
27. **Everything of a turn belongs to its generation.** Delivering a turn needs the session's current generation running, no stop, no other delivered turn without an outcome, and the turn to be the earliest queued one; otherwise it fails with `precondition-failed`. A request or an output entry names a turn delivered in the current, running generation and still without an outcome, and an outcome names the generation the turn was delivered in; otherwise they fail with `precondition-failed`. Source: agent harness port contract sections 6 and 7.1.
28. **A request expires with its turn.** When a turn records its outcome, each of its requests still without a response becomes `expired`, final; a response to it fails with `not-found`. Source: agent harness port contract section 7.3 ("A request expires when its turn ends").
29. **One attempt, one session.** Because a session holds one task's attempts (decision 20), the check that no other session holds an attempt reads the task's other sessions, which the caller passes; their storage is item 13's. Source: decision 6.
30. **Text bounds.** A turn's text is 1 to `MAX_HARNESS_TEXT_LENGTH` characters; a request's text, an output entry's text, and the free text of an answer are at most that many characters. Text outside its bound fails with `invalid` before any state is checked. Source: agent harness port contract section 2 rule 2 and its bounds table.
31. **Failure codes.** `invalid` for text, a cursor, or an answer of the wrong kind or shape; `not-found` for an unknown turn, request, generation, or handoff, or an expired or unresolved request; `conflict` for a repeated key with other content, a repeated turn ID, a second outcome or response, a held attempt, another native session ID, and a second handoff write or take; `precondition-failed` for every other state the operation does not allow. Source: kernel `FAILURE_CODES`; agent harness port contract section 9.3.

## Source notes

1. **Request identity.** A request is keyed by session, provider generation, and native request ID, as the [agent harness port contract](/docs/contracts/agent-harness-port.md) section 7.1 sets. A native ID reused in a later generation is a new request and is accepted; only a response or stored answer from an earlier generation is rejected (section 7.3). This is the reading of the [G3 plan](/docs/g3-plan.md) row 4 phrase "a duplicate response or a reused native request ID under another provider generation rejected"; the plan row is not edited.
2. **Handoff owners.** The agent harness port contract section 4.1 assigns the handoff to items 5, 12, and 18, while the account pool contract sections 4.4 and 10 and the G3 plan row 4 assign it to items 4 and 18. This change follows the plan and does not edit section 4.1; the follow-up "add item 4 to the handoff owners of the agent harness port contract section 4.1" is the coordinator's (`tasks.md` 4.4).
3. **Attempt generation.** Architecture section 7 correlates output with the "attempt generation". The model reads it as the session generation, with the attempt and its ownership generation recorded beside it (decisions 12 and 26).
4. **Acknowledgement items.** Decision 23 opens an acknowledgement item for a `delivery-uncertain` response, but the product ports contract section 4.1 lists no such item kind in G3. The model exposes the read; adding the kind belongs to the item that builds the inbox source (item 13), and this change does not edit the product ports contract.

## Risks / Trade-offs

- **Unfrozen harness port.** The port stays at `0.1.0` until a second harness passes its suite in G4; a port change may change this model.
- **Session scope.** Decision 20 binds a session to one task; a later decision to span a run would change the attempt binding and the handoff's owner, which the contract states in one place.
- **Bound measured in the model.** A byte bound needs a UTF-8 length, which the model computes without I/O.
- **Queued turns of a stopped session.** A stopped session keeps its queued turns undelivered; the handoff does not carry them (decision 24), so item 18 decides whether the next session's prompt mentions them.
