## Decisions

Where a source is silent, the change takes the minimal shape and records it here with the source it relies on.

1. **One document.** Every operation goes into `execution.openapi.json`: `retireEvidence` shares its path with `readEvidence`, and the generator refuses one path in two documents (`scripts/generate-contracts.ts`, `mergeOpenapi`); the delegation and credential operations serve the worker; the reconciliation reads and the re-admission extend the G2 execution operations beside `listQuarantine`. No other document defines their paths, under `/evidence/`, `/delegations/`, `/reconciliation/`, `/executions/`, and `/runs/{runId}/`, and 9b's paths belong to the control-plane document, whose paths the generator compares with these.
2. **Version 0.6.0 and the breaking change.** The brief said 0.4.0 to 0.5.0, but G3 sub-change 26b already moved the document to 0.5.0 on `dev` (`bf25c6d5`), so the next minor version is 0.6.0. Serving evidence only to a role on its project narrows who may read it, which a caller of the same request observes as a 404. `make contract-compatibility` compares schemas only: with the document left at 0.5.0, it reported "0 breaking change(s)" for `execution.openapi.json` against `ff7ab7a0` (run 2026-10-28 in this worktree). The change still takes the next minor version, the rule of [ADR 0004](/docs/decisions/0004-first-class-engineering-principles.md) principle 6 while the major version is 0, and states the narrowing in the contract page section 8.2. At `ff7ab7a0` the repository had no breaking-change declaration file. `declare-contract-breaking-changes` landed in `dev` (`a3a0ac4c`) before the handoff, and the branch merged it: `make contract-breaking-changes` prints no entry for `execution.openapi.json` 0.6.0 against `a3a0ac4c`, because oasdiff reports 0 breaking changes, and `packages/contracts/breaking-changes.json` holds only changes the check computes, at least one per entry, and refuses an entry it does not find. The narrowing therefore has no entry there; the minor version and the contract page section 8.2 declare it.
3. **Shared schemes and schemas.** `browserSession`, `csrfToken`, `AuthenticationFailure`, `AccessDenial`, `CsrfRejection`, `ExternalId`, and `RemoteUrl` are copied unchanged from the control-plane document, because the generator requires one definition per name; a test compares them. The operator bearer stays the definition of every document.
4. **Evidence reads.** A `project-viewer` or above on the record's project, or an `installation-owner`, as 9a decision 8 reads a project. The project is known only from the record, so the record is read before the role is checked, an exception to control-plane section 2's order that covers the operations of the record's path, `readEvidence`, `downloadEvidence`, and `retireEvidence` (decision 5), and no other; a principal without a role that reads the record gets the 404 of an unknown record, so that it learns nothing, and the reads declare no 403. The convention of 9a and 9b differs: their project operations name the project in the path or query, check the role first, and answer a principal without it 403 `role-required` (control-plane section 2; 9a decision 8; 9b decision 7, which reads an item only after the role on the project of its path). 9c follows that convention wherever the caller can name the project, as `listUnknownExecutions` and `readmitTask` do (decisions 7 and 8), and departs from it only on the evidence path, which names no project and which the trust model section 3 isolates by project. Source: trust model section 3 ("Cross-project isolation ... artifact/evidence downloads"); G3 plan row 10.
5. **Retirement.** A `project-maintainer` on the record's project. No source names the role: the trust model gives evidence reads to project roles and project configuration to the maintainer, and retirement destroys a project's evidence, so it takes the project's administrative role, not the installation's. It applies the existing rule: 365 days after publication, `publishedAt` and not `capturedAt` (`retentionEndsAt`, `checkRetentionElapsed`; evidence-store spec), with the end in the required `details.retainedUntil`, then the content under the digest lock (`EvidenceService.retire`). A record is immutable, so there is no revision to compare; a repeat or the loser of a race answers 404. The roles follow decision 4: a principal that may not read the record gets 404, a reader below `project-maintainer` 403. The record and its content are removed in two transactions (`EvidenceService.retire`), so once the record's removal commits, the retirement answers 204 even when the content's removal fails, because a repeat would answer 404 and never remove it; item 10 adds a sweep of digests that no record refers to, and a 500 or 503 means that the record stays. A download reads the record and its content in two steps too (`EvidenceService.download`), so one whose record is retired in between answers 404, not the 500 of corrupt content.
6. **Delegation results.** `DelegationOutcome` already names the request's admission outcome, so the result uses new names: `DelegationResult`, `DelegationResultOutcome` (the four outcomes of agent harness port section 7.4, equal to `DELEGATION_OUTCOMES`), and `DelegationSummary` (at most `MAX_HARNESS_TEXT_LENGTH`). The reader is the worker that holds the active attempt of the parent task, the delegating one or a later one that resumed the session, because section 7.4 delivers to a resumed session; any other worker gets 404, as an evidence record does.
7. **Reconciliation reads.** Per project for unknown executions, because product ports section 4.1 answers them per project, and installation-wide for unrecorded processes, which name no project and belong to the `installation-owner`. The project is a required query parameter; a principal without a role on it gets 403 `AccessDenial`, as 9a's project operations answer, because the caller named the project. Pages of 100 with `next`, as 9a decision 17, but by a composite key, because an `executionId` is unique only within its task (`locateExecution`) and an `observationId` only per worker (the key `(worker_id, observation_id)` of `unrecorded_processes`): task then execution identifier, and worker then observation identifier, each pair a cursor object in `next` and two query parameters. An execution's evidence list has no bound, because `withEvidence` keeps every entry and no source bounds them, and item 44 bounds the answer in the domain, for example by condensing repeated entries (contract page section 9); it holds at least one entry of a kind other than `cancellation-not-applied` (`isUnknownExecution`). A process count is bounded at 256, the `processes` bound of `execution.unrecorded-process`. The answers stay inbox answers (product ports section 4.2; 9b).
8. **Re-admission.** An explicit command of a `project-operator` or above, whom the trust model lets trigger retries, because product ports section 3.9 has an ended task resumed only by a re-admission and no source names who starts the explicit command. It names the project as the query parameter `projectId`, so the role is checked before the task is read, as 9a's operations do (decision 4), and a principal without the role gets 403 whether the task exists or not. It names the ownership generation it read and answers 409 when it moved, so two concurrent re-admissions cannot both bind, and a `readmissionId`, the idempotency key of [product ports](/docs/contracts/product-ports.md) section 2, rule 7: a repeat with the same key and input returns the first 201, and the same key with another input answers 409. Its refusals are `rebindAdmission`'s active-attempt rule, an admission not yet dispatched, which placement still owns, and an SDLC refusal of the new admission. Item 44's automatic re-admission, of a launch rejected under a stale admission and of a task whose launch grant a product writer revoked (G3 plan row 44), is a control-plane writer through the same checks and has no wire operation. The answer is the existing `TaskSubmission`.
9. **Slot credential delivery.** `GET /executions/{executionId}/slot-credentials/{slotId}` with the attempt, ownership generation, and recovery epoch as query parameters, so that the checks of account pool section 7.3 can compare what the worker holds; a GET because it changes nothing. The 422 reasons are those of section 7.3 in its order. Section 7.3 names the refusal for a mechanism without an admitted delivery `invalid`; on this API 400 means a malformed request, so it is the typed reason `delivery-not-admitted`. A slot that the reservation does not name is `capacity-not-reserved`, and an unknown attempt or execution is `assignment-not-active` after the installation and worker checks, as `rejectUnknownAssignment` answers a launch, so the operation has no 404. The architect decided on 2026-10-28 that the same operation is also the first delivery, with no new operation: after its launch authorization the worker fetches the slot's current credential version, and a later fetch re-delivers that version. The fetch is scoped to the run's reservation and the slot: the control plane finds the execution by the attempt and the execution identifier together, because an execution identifier is unique only within its task (decision 7), and refuses a slot that the attempt's reservation does not name. Account pool section 7 sends a credential only with a valid launch authorization for the attempt, so an `authorized` execution with no earlier delivery also needs its grant unexpired and not `revoked`, found from the execution with no new parameter, or gets `execution-conflict`; for an execution that already had a delivery, `started` or adopted, the ownership checks of section 7.3 stand in, because its grant may have expired (section 7.3, "Re-delivery to an adopted execution"). Section 7 now says so, section 7.3 names the wire reason `delivery-not-admitted`, and sections 8 and 8.1 name the refusals that section 7.3's order gives after a removal and a revocation. `LaunchGrant` still carries no credential, and item 12 implements this form and defines no other.
10. **Per-run SCM credential.** Two operations: `issueRunScmCredential` (POST, because it may issue) returns the run's current version, and `fetchRunScmCredential` (GET) the version that 9d's notice names. A repeated issue returns the same version only while no refresh came between; an issue whose current version a revocation ended answers `credential-ended`, as a fetch of an ended version does, because the issue re-delivers and does not issue anew. `RunCredential` has no version (`packages/modules/integrations/src/ports/source-control.ts`), so the control plane numbers the secrets of a credential, 1 at issue and one more per refresh, which makes each version written once. A run's credential belongs to the run (source control section 3), so the worker of any attempt of a task of the run may fetch it. The ownership refusals reuse the reasons of launch authorization section 9 for the same checks, so a worker branches on one vocabulary. The remote re-check runs on every call, after the ownership checks and before any lookup of the credential, with `repository-unbound` and the `bindRepository` URL reasons in their order; `merge-method-undeclared` does not apply. A new schema, `ScmCredentialRefusal`, holds them, because `BindingRefusal` would add a reason that never occurs here, and a refusal names only the reason and identifiers, never the remote URL or a secret. The first issue is serialized per run, so of concurrent first issues one issues and the others return its version and issue nothing. An unknown run is `assignment-not-active` after the installation and worker checks, as in decision 9, so 404 answers only an unknown credential or version after all checks. A version that expired answers `credential-ended`, as a revoked one, because an issue never issues anew; the refresh of source control section 3 gives the next version. The delivery carries the bound remote URL that passed the check and the `authorization` header value of git workspace section 7, so the worker never pairs a credential with another URL. The architect confirmed on 2026-10-28 that both operations stay in 9c with this re-check and these refusal reasons in this order, and that 9d's notice carries `runId`, `credentialId`, and `version`.
11. **Never kept.** The three deliveries are the only responses with a secret; each sends `Cache-Control: no-store`, the worker holds the value only in memory, and a request log holds only the allowlist of control-plane section 7, never a body. Their secret schemas are not `writeOnly`, because they are responses by design, and a test lists exactly these three operations as revealing.

## Risks / Trade-offs

- The authorization of the evidence reads is prose and roles; item 10's tests must check the 404 for a principal of another project.
- A worker that fetches an SCM credential for a run must name an attempt it holds; a run whose tasks run on several workers delivers the same secret to each, as `RunCredential` per run implies.
- The first slot credential delivery is a fetch after the launch authorization, a round trip more than a grant that carried it (decision 9); the grant stays free of secrets, because the worker journals it (account pool section 7.3).
