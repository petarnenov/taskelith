## Decisions

1. **Crash points.** `CrashPoints` accepts `^[A-Z][A-Za-z0-9]*(?:\.(?:before|after))?$` (`packages/testing/src/crash-points.ts:5`), so the lifecycle points are `WS1` to `WS10`, each with `.before` and `.after`, and the bare `WS8` while the reclaim program runs (the contract's "during"). Contract section 3 holds the table and what a crash test checks around them; the spec's "Crash-safe lifecycle" names them. No constant is added to the package: 16b adds the points with the code that reaches them, and the workspace package does not depend on `@taskelith/testing`.
2. **Snapshot format (Q1).** The snapshot is Taskelith's own tar, content type `application/x-tar`, never `git archive`, so `export-subst` and `export-ignore` do not apply and the bytes do not depend on the Git version. The rules (contract section 10, spec "Snapshot archive format"): files and links only, in byte order of the UTF-8 paths, ustar fields with modes `0644`, `0755`, or `0777`, owner, group, and time `0`, empty names, a pax header (`path`, `linkpath`, `size`) only where a ustar field cannot hold the value, and two zero blocks at the end. A gitlink is refused with `precondition-failed` and reason `gitlink-in-tree`. The rules are a pure domain function, `encodeHeadSnapshot`, so the double and the 16b adapter produce the same bytes, and unit tests check the archive with the system `tar`. A path or link target that is not valid UTF-8 is refused with `precondition-failed` and reason `non-utf8-path` (`decodeGitPath` for Git's bytes, and `encodeHeadSnapshot` refuses a string with a lone surrogate), because the port's string paths cannot carry other bytes; keeping raw bytes would need byte paths through the port, the fixture, and the double (review pass 1, finding 7).
3. **Credential transport (Q2), with the coordinator's ruling.** The SCM plugin's credential binding supplies the complete, already encoded `Authorization` value as `WorkspaceCredential.authorization`; the GitHub plugin, the first instance, forms `Basic ` and the base64 of `x-access-token:<secret>`. The adapter neither parses nor builds it: it places `Authorization: <authorization>` into `http.extraHeader` in command-scope environment configuration (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`, built by `gitConfigEnvironment`), and treats the whole value as a secret everywhere: never an argument, a file, a credential helper, or a log. This is the coordinator's ruling (b) on review pass 1 ("done the cheap way"); no Forgejo work. The built environment is exact (`GIT_BUILT_ENVIRONMENT`: `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`; `GIT_COMMAND_SCOPE_SETTINGS` in a fixed order with `credential.helper` empty and `core.hooksPath=/dev/null`), and no other `GIT_*` variable or `SUDO_UID` is inherited. Remotes are HTTPS without user information (`checkRemoteTransport`, reason `insecure-remote`, checked in `prepare` after the target's repository and before the credential); plain `http://127.0.0.1` only under the test policy `https-or-loopback-http`. The policy is a two-value type, not a boolean flag. Review pass 2 tightened this: the environment is an allowlist (`PATH`, a `HOME` that does not exist, `LC_ALL=C`, and the Git values), because `XDG_*`, `*ASKPASS`, and proxy or certificate variables act despite the Git variables (Medium 1); and a process that needs no checkout, `ls-remote` and the clone, starts in `/` (`GIT_NEUTRAL_DIRECTORY`), because Git reads the configuration of the repository it starts in, so an `ls-remote` in a handed-off checkout would follow a planted `insteadOf` or proxy with the header (High 1). `/` was chosen over `GIT_CEILING_DIRECTORIES` or an empty `GIT_DIR`: it needs no further variable, no agent can write it, and nothing lies above it. The scenario on the GitHub form moved to an obligation on item 20 (contract section 14), as `git-workspace-port` cannot test a plugin (Medium 3). On macOS an agent of the same account can read a Git process's environment; contract section 7 records that as an accepted residual risk (Low 10).
4. **Push "never forced" (Q3).** Contract section 8 defines it as "the remote task branch never moves to a commit that does not descend from the leased head" and requires both parts: a lease alone does not ensure it, because Git lets a push whose lease matches replace the branch with any commit. So the adapter checks ancestry before the push (`not-fast-forward`), and the lease catches a move after that check (`remote-moved`). The push is exactly `push --atomic --force-with-lease=refs/heads/<branch>:<expected-sha> <remote> HEAD:refs/heads/<branch>` (`taskBranchPushArguments`), empty expected value on the first push, after at most `-C <checkout>`; the suite compares the whole argument list, so a later `--no-atomic` or `--no-force-with-lease` cannot cancel a guarantee (review pass 1, finding 1). Two cases, remote-moved and not-fast-forward, check the outcomes and that a successful push started one such process; five defective variants (no lease check, no ancestry check, a bare lease, a cancelled `--atomic`, a cancelled lease) show the cases catch a wrong adapter.
5. **Hand-off state.** `WorkspaceLifecycle.handedOff()` returns the listed attempts whose hand-off record exists, in the order of `list`, read from the records. A new case checks it before, during, after a restart, and after the reclaim; the defective variant that keeps the state in memory misses the hand-off after a restart.
6. **Reclaim containment.** `reclaim-<name>` (`reclaimContainmentName`, `RECLAIM_CONTAINMENT_PREFIX`) under the worker's containment parent, written durably into the hand-off record before the program starts. The scan for unrecorded processes skips a containment that a hand-off record names. After a restart the worker polls until the containment is empty, never kills it, and at a bound that 16d fixes reports the workspace for reconciliation. A failed or killed program leaves the workspace handed off with `reclaim-failed`, and the record keeps that outcome, so the program is never run again for that hand-off (new requirement "Failed reclaim program").
7. **Same-identity platforms (Q5).** On macOS the reclaim program runs as the worker identity without a containment, in its own process group, which the hand-off record names in place of a containment (new requirement "Reclaim program on one account").
8. **Pinned Git client.** New requirement "Pinned Git client": the explicit path from the worker's tool manifest and an exact `git --version` string gate (`checkGitClient`, reason `git-client-mismatch`), with the pin injected so a test can give another. `GIT_CLIENT_PINS`: Linux `/usr/bin/git` printing `git version 2.43.0`, from the package `git=1:2.43.0-1ubuntu7.4`, whose package revision the version string does not show, so the image build checks it (16d); macOS `/usr/bin/git` printing `git version 2.50.1 (Apple Git-155)` (`docs/g3-dependencies.md` section 4). The tool manifest and the images come in 16d and 16e.
9. **Slots (Q4).** A Linux worker with a separate execution account has one slot and refuses to start with `TASKELITH_WORKER_SLOTS` above `1`, naming the variable and the account (contract section 3, new requirement "Single slot with a shared execution account" in `git-workspace-port`). `capacity-reservation` and `worker-runtime` are not changed; 16e implements it in the worker settings.
10. **Sections 13 and 14 (Q7).** Only the delegated-child half of the "One handed-off workspace" test moves to item 38 (contract sections 13 and 14, item 38 row). The worker half stays with item 16: its Linux tests in 16d and its admission in 16e. The item 16 row names 16a to 16e; nothing is reordered.
11. **Fixture hooks for 16d.** `gitProcesses()` returns each Git process the adapter started, at its start: its arguments, its process identifier, its environment with every value that holds a credential's secret or `authorization` value replaced by `<redacted>` (`REDACTED_VALUE`), and the checkout's `.git/config` as the process found it. The brief named environment keys only; review pass 1 (finding 4) showed that names cannot prove a built environment, since an inherited `GIT_CONFIG_GLOBAL=/attacker/config` or an extra `GIT_CONFIG_KEY_<n>` keeps the names, so the hook now reports values, redacted where they could carry a credential. The configuration at the start shows a planted setting that an adapter used and removed afterwards (finding 6). `plantGitSetting` writes with `git config --file`, so the planted file is valid Git configuration (finding 5), and `gitConfig` reads it. The checks live in `src/ports/git-process-checks.ts`: a finding names a process by its identifier and subcommand and shows a sensitive argument as `<redacted>`, so it never repeats a credential (finding 3), and a credential's forms are its secret, its `authorization` value, the parts after the scheme, and the base64 of each (finding 2). Review pass 2 added the process's working directory, and the configuration is now that of the repository Git finds from it; the fixture shows a value that is exactly `Authorization: <authorization>` as that credential's marker (`redactedHeader`), so the suite can require the operation's own header, and a header of the bare secret or another scheme no longer passes as `<redacted>` (Medium 2). The suite also scans every value the fixture left unredacted for a credential form, requires `argv[0]` to be a pinned path, and requires exactly the allowlisted variables.
12. **Native macOS conformance (Q10).** The existing gate tables (`docs/worker-platforms.md` "Native acceptance gates", the G3 plan's deferral table) are per area or per G2 deferral, not per contract, so the pending gate is a row of a new small table at the end of contract section 13. It has not run.

## Test double behavior

- Every simulated Git call is recorded as a process with `argv[0]` the Linux pin's path, a process identifier from 1000 on, its working directory, `/` unless it works on a checkout, `gitConfigEnvironment` of the call's credential, which holds the whole allowlist, and the configuration of the checkout it works in, read at that moment; the fixture shows the header as its credential's marker and redacts every other credential form.
- The double's archive reader takes pax records by their byte length and reads into objects without a prototype, as does its working tree, so a path with a newline or named `__proto__` survives (findings 10 and 11).
- A remote operation (the `ls-remote` of a prepare, a remote head read, and a push) counts as a remote call, so the existing credential case keeps its counts.
- A push reads the remote first and refuses before starting a push process, so only a successful push starts one; a real adapter may also start a push that the lease refuses, which the cases allow.

## Risks

- The suite now assumes the Git CLI's push arguments and environment in three cases; an adapter on another Git implementation would need the suite changed, which D3 (a) excludes for G3.
- `encodeHeadSnapshot` takes a map, so a path named `__proto__` cannot be lost to an object's prototype (review pass 2, Medium 6); it buffers the whole archive in memory; a large tree's snapshot needs a streaming variant later.
- The macOS process group of the reclaim program can be reused by an unrelated group after it ends; 16e decides the proof's details on macOS.
