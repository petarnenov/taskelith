## Context

`PlacementService` (`apps/control-plane/src/application/placement-service.ts`) runs a pass every 5 s over at most `PLACEMENT_BATCH` (100) waiting tasks, in the rotation order of `fairWaitingOrder`, each in its own transaction. `#settle` recorded the outcome of each offer in the per-task `RetrySchedule`: a task placed or no longer waiting was forgotten, a retry that still backs off was delayed to its due time, and every other outcome counted a failure, a delay of `placementBackoff` (5 s to 60 s with jitter); a task whose delay has not passed is excluded from the next read. A pass without any candidate worker settled every read task with `no-candidate` the same way. So a decline for lack of fleet capacity, which says nothing about the task, kept the task out of the reads until its jitter ended, and a freed slot went to the first task that was due, whatever the rotation cursor said.

## Decisions

- **No backoff after a decline for lack of fleet capacity (option (a), away decision `20261027T085757Z-opencode-1447`).** `#settle` leaves the task's wait as it was when the outcome is such a decline: it counts no failure and forgets nothing. The task stays readable, so the next pass that reads it, within its batch, offers it in its place in the rotation. The other options of the follow-up, a backoff per project or always reading the project after the cursor, were not chosen.
- **One classification.** A decline for lack of fleet capacity is a failed placement whose `details.reason` is in `FLEET_REASONS` (`quarantined`, `worker-not-eligible`, `worker-capacity-exhausted`, `no-candidate`), as `lacksFleetCapacity` in `packages/modules/scheduling/src/domain/capacity-reasons.ts` answers; it is the same set that stops the rotation cursor (`advance-placement-rotation-cursor`). The service names it once, `isFleetCapacityDecline(outcome)`, and both `#offer` (the cursor) and `#settle` (the backoff) call it, so the cursor and the backoff cannot disagree on what a capacity decline is. Every other decline (`project-quota-exhausted`, `run-quota-exhausted`, `provider-concurrency-exhausted`, `control-not-enforceable`, `delegation-awaiting-capacity`, and a failure without a reason) is the task's own and backs off as before.
- **The wait is kept, not forgotten.** A task that backed off for its own reason and is later declined for lack of fleet capacity keeps its failure count, so its next own-reason wait still grows; the requirement "Backoff forgetting" (forget only when placed or no longer waiting) is unchanged. The unit test `a fleet capacity decline keeps the failure count of an own-reason backoff` checks it (review pass 1, L2).
- **A pass without a candidate settles nothing.** Its `no-candidate` outcome is a fleet capacity decline, so the loop that settled every read task with it would do nothing; it and the constant `NO_CANDIDATE` are removed.
- **Both stores.** The backoff is recorded only in the control plane's memory (`RetrySchedule` in `PlacementService`) and applied through the `excluding` argument of `PlacementQueue.waiting`, which `InMemoryPlacementQueue` (`packages/modules/scheduling/src/adapters/in-memory-placement.ts:26`) and `PostgresPlacementQueue` (`packages/adapters/postgres/src/capacity-repositories.ts:159`) both honour; the decline reasons come from `decidePlacement` in the scheduling domain over the snapshot that either store reads. No adapter holds a backoff or a reason list of its own, so neither needed a change: the service passes fewer exclusions to both. The unit tests script the transaction outcomes over `InMemoryPlacementQueue`; the integration test runs the same fifty-to-one case through `PostgresDatabase` and its real placement transactions.
- **Bounded cost.** Without the backoff, a full fleet costs up to `PLACEMENT_BATCH` placement transactions per pass, every 5 s, where tasks backing off cost fewer. The contract section 5 states the bound.
- **Contract-first.** The capacity reservation contract sections 5 and 13, the operational targets, and the `execution-placement` requirement "Placement backoff" changed in their own commit before the code.

## Out of scope

- Ending a pass at its first decline for lack of fleet capacity, the candidate fix for the timing risk that `advance-placement-rotation-cursor` recorded (review pass 3, L2): a slot that frees during a pass can still go to a later project of the same read. It changes the pass, not the backoff, and was not decided.
- The rotation cursor and the retry backoff of an automatic retry (`observation-consumption` requirement "Retry backoff") are unchanged.

## Risks

- A full fleet now costs up to 100 placement transactions every 5 s, about 20 per second, against the store; a quarantined installation the same. The batch bounds it, and each such transaction rolls back its writes.
- The classification sees only the last candidate's reason, as the cursor rule does (`advance-placement-rotation-cursor`, review pass 2, L4); with hard controls a task could end on `control-not-enforceable` and back off although a full worker supports it. G2 requests no hard control.
- `worker-capacity-exhausted` depends on the task's own request (the held load plus the request exceeds the worker's capacity), so the classification is exact only while all requests are equal, as in G2 (`DEFAULT_ATTEMPT_REQUEST`): a smaller task could then fit where a larger one was declined. Per-task requests must revisit whether that reason is a fleet capacity decline (review pass 1, L3).
- A task declined for lack of fleet capacity stays readable, so with per-task requests a full batch of such tasks, read again every pass, could hide a later task that would fit. In G2 this is safe: when one task is declined for lack of fleet capacity, none fits, because all requests are equal, eligibility does not depend on the task, and the worker is checked before the quotas. The requirement therefore dropped the clause "so that a pass reaches the tasks after it", which held only while every declined task backed off, also to stay within the 500 characters a requirement may have (review pass 2, L1).
