## Context

Item 4 defined the workflow model and its text input shapes (`WorkflowDefinitionInput`, `WorkItemInput`, `ArtifactRevisionInput`); item 5 (`sdlc-gates`) made structural validation, semantic approval, and platform records distinct evidence kinds. The [SDLC framework mapping](/docs/sdlc-framework-mapping.md) for OpenSpec 1.14.3 and SpecKit 1.2.3 shows a deterministic CLI on one side and agent-executed prompt commands on the other, a structural validator in one framework only, native finalization (archive) in one framework only, review gates without a native operation in one and human workflow gates in the other, and per-working-copy current-feature state in SpecKit. Facts being settled by item 9: SpecKit's bundled gates cannot be decided headlessly, its current-feature pointer is per working copy, and its agent steps need a harness.

## Goals / Non-Goals

Goals: a draft port that both frameworks can implement, a capability declaration, and a conformance-suite skeleton for items 10 to 12. Non-goals: adapters, fixtures, the freeze, registration, application services that call the port, and the other ports of architecture section 6.

## Decisions

- **Location.** The port and the suite are in `@taskelith/sdlc` under `src/ports/`, not in the plugin SDK. Architecture section 6 makes outbound ports module-owned, the SDLC row says the module depends on framework-neutral ports, item 6 does not depend on item 8, and `@taskelith/plugin-sdk` does not exist on `dev` yet. The suite checks results with the module's own domain parsers, which it can only do inside the module.
- **Plain shapes.** Requests and results are plain text shapes and reuse the item-4 input types, so a plugin can implement the port without depending on the module's branded domain types, and the module parses every result: plugin output is untrusted input (architecture section 6), and TypeScript types are not a trust boundary. Untrusted data is first copied (`copyPlainData` in `plain-data.ts`), reading every property once through its descriptor and never through a getter, and rejecting accessors, symbol and non-enumerable properties (including array elements), array holes and extra array properties, objects that are not plain, cycles, and values that cannot be inspected; a small runtime shape checker then checks strings, booleans, dense arrays, plain objects, and records with exactly their defined fields before any domain parser sees the copy; a field the port does not define is rejected, so a result cannot carry, for example, an approval flag. Wire contracts and generated validators (item 13, decision D3 (a)) are for HTTP and messages; this in-process port adds no schema dependency.
- **Operations.** `discoverWorkItems`, `resolveWorkflow` (the stage graph, the digest of the exact native definition, and the upstream tool version that a run binding records; with a work item, the workflow that item uses, since OpenSpec selects the schema per change before the project default; without one, the workflow a new item would get), `describeArtifacts` (required artifacts, their producing stage, prerequisites, and presence), `inspectArtifactRevisions`, `prepareStageInstructions`, `validateStructure`, and `finalize`. All are asynchronous, because adapters spawn pinned tools, and return a kernel `Result`; expected failures use the kernel codes, such as `not-found` for an unknown work item and `unavailable` for a missing tool or an undeclared operation. A thrown error is a defect, which the suite reports.
- **Explicit work items.** Every work-item operation names the working copy and the work item's native reference. No operation may rely on an implicit current item kept in the working copy, as SpecKit's `.specify/feature.json` is, so that parallel runs in one working copy cannot pick up each other's item.
- **No approvals from plugins.** No operation returns a semantic approval or decides a gate. `validateStructure` returns a structural report whose verdict is `valid` or `invalid`, which the module records as structural-validation evidence (item 5); semantic approvals and platform records are recorded by the platform. A framework's native human gate that cannot be decided headlessly is therefore a platform gate requiring semantic approval, not a port operation.
- **Agent steps.** `prepareStageInstructions` returns the instructions, input revisions, and expected output artifacts for the agent task that performs a stage. The port never runs an agent step; that needs a harness, scheduled by the Execution module (G2 and later).
- **Capability declaration.** A plugin declares the optional operations it supports (`validateStructure`, `finalize`) and the lifecycle obligations its native stages cover. An undeclared optional operation fails with `unavailable`, and the platform supplies a platform-managed gate or record for that obligation. Plugin identity, versions, and the supported plugin API range belong to the manifest of item 8.
- **Evidence references.** Validation and finalization reports carry a reference to where the plugin retained the native output, parsed as an item-5 `EvidenceReference`; the domain never interprets it.
- **Conformance suite.** `runSdlcFrameworkConformance(framework, cases)` takes the plugin and a list of cases, each an operation, a request, and the expected outcome (a value compared structurally, or a failure code), and returns a frozen report of findings; an empty list means the plugin conforms on those cases. The suite is plain code without a test runner, so a plugin package's tests drive it with any runner and their own fixtures, and the suite stays framework-neutral. Before the plugin runs, every case's request and expected outcome are copied by the same rules, and the plugin receives a fresh copy of its request, so that a plugin changing a request or a shared expected value cannot make a case pass; a case that is not plain data is a `fixture` finding and is not run. A thrown error or an unreadable result becomes a finding for that case, and the suite continues with the next case. It checks: the capability declaration has the declared structure and values, read without running any case if it does not; each operation resolves to a well-formed kernel `Result` whose failure has a kernel code, message, and string details; no operation throws; an undeclared optional operation fails with `unavailable`; each outcome matches the expected one, compared as plain data with key order ignored; each successful result has the runtime structure of its operation and parses with the domain parsers (work items, workflow definition, digest, tool version, artifact and stage identifiers, artifact revisions, validator identity, evidence references); work items are unique; prepared instructions name a valid stage identifier, are for the requested stage, and are not empty; a structural report has a structural verdict and problems exactly when invalid; and the native stages of the resolved workflow cover exactly the declared native obligations.
- **Draft status.** The port may change until item 12 freezes it as semantic version 1 with an ADR (decision D7 (a)).

## Open Questions

- **Plugin access to the port type.** The boundary check lets the source of a package under `packages/plugins/` import only `@taskelith/kernel`, `@taskelith/plugin-sdk`, and `@taskelith/contracts`, so the item-11 plugin cannot import the port type from `@taskelith/sdlc` in its source; its tests can. The plain shapes let the plugin implement the port structurally meanwhile, with the suite checking it at run time. Options before item 11 or at the freeze: (1) allow a plugin to import the root export of the module whose port it implements; (2) move or re-export the port through `@taskelith/plugin-sdk` (item 8). This change does not alter the boundary rules.

## Risks / Trade-offs

- Side-effecting operations (`finalize`, and later scaffolding) need an operation journal and postcondition reconciliation before retry (architecture section 6); the port does not yet carry an operation identifier or cancellation, which arrive with the execution protocol.
- The suite compares exact values; a plugin whose output contains volatile data, such as timestamps, needs fixtures that pin it.
