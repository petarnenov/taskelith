## Context

Item 4 defined the workflow definition (a stage graph whose dependencies are acyclic prerequisites), artifact revisions (identity by artifact and digest), and left rework loops, gates, and evidence to this item. Architecture section 6 lists the gate states, separates structural validation from semantic approval, adds platform-managed gates and records for obligations a framework has no operation for, requires durable compare-and-set transitions, and invalidates approvals when the specification changes. [ADR 0008](/docs/decisions/0008-product-ui-and-integration-authority.md) decision 4 shows the gate states on the task detail and makes accept and integrate a gate between Review and Archived; decision 1 lets auto-merge integrate only when all gates have passed. Decision D4 (a) of the G1 plan keeps this item to SDLC stages and gates.

## Goals / Non-Goals

Goals: pure, deterministic domain rules for gate transitions, evidence kinds, invalidation, and stage transitions, which item 7 composes into admission. Non-goals: ports, application services, admission, repositories, events, reviewer independence, and code-head identities.

## Decisions

- **Capability.** A new capability `sdlc-gates`, not a delta to `sdlc-workflow-model`. The workflow model is a set of immutable values parsed from a framework; this item adds behavior with state, transitions, and concurrency rules that admission, events, and the UI will reference on their own. A separate capability keeps each specification about one concern, while the package requirement in `sdlc-workflow-model` still covers the module as a whole.
- **Gate transitions.** The frozen table `GATE_TRANSITIONS` is the only authority: pending to passed, failed, blocked, or stale; passed to stale; failed to pending or stale; stale to pending; blocked to pending or stale. Every operation checks the table, and every other pair is rejected with `precondition-failed` and the details `from` and `to`. A decided gate is never overturned in place: a passed gate does not fail or reopen, it only becomes stale when its subject is superseded, so that an approval stays tied to the revisions it judged. Failed, stale, and blocked gates return to pending through one operation, `reopenGate`, which takes the subject for the new decision.
- **Subject.** A gate judges an exact subject: one or more artifact revisions, at most one per artifact, so that a newer revision identifies exactly the one it replaces. Evidence decides a gate only when its subject is the same set of revisions (by artifact and digest, in any order); evidence about other revisions is rejected, which is how approvals are not carried across changed artifacts (invariant 12).
- **Evidence kinds.** `structural-validation` (a validator's form and reference check), `semantic-approval` (a reviewer's judgement of the content), and `platform-record` (a record the platform keeps for an obligation without a native operation, such as integration or closure). Each is a separate type with its own source identity (`ValidatorId`, `ApproverId`, `RecorderId`) and its own verdicts (`valid`/`invalid`, `approved`/`rejected`, `satisfied`/`unsatisfied`), built only by its own parser. A gate names the one kind it requires and rejects evidence of another kind with `precondition-failed`, so a validator run, an exit code, or a checked box recorded as structural or platform evidence can never pass a semantic gate (invariant 11). A stage that needs both, such as a specification that must validate and be approved, has two gates. Each evidence value records when it was recorded and a reference to where the output or record is kept; neither is interpreted.
- **Decision and block reason.** A passed or failed gate keeps the evidence that decided it; a stale gate keeps that evidence to show what was superseded; reopening clears it. A blocked gate records a free-text reason for display, because the platform must show exact reasons; an unavailable mandatory reviewer leaves a gate pending, not blocked (architecture section 6).
- **Invalidation.** `isGateOutdatedBy` answers whether a revision is a different revision of an artifact in the gate's subject; the same content read elsewhere is not. `markGateStale` is a separate command that rejects a revision that does not outdate the gate. Any undecided or decided gate except a stale one can become stale. Selecting which gates of a run to invalidate, and the effect on admissions and started attempts, belong to item 7 and G2.
- **Stage transitions.** Stage progress holds the workflow definition, one state per stage (`not-started`, `in-progress`, `completed`), and a generation. The frozen table `STAGE_TRANSITIONS` allows not started to in progress, in progress to completed, and completed to in progress; the last is how a rework loop returns to a stage, since dependencies are acyclic prerequisites. A stage becomes in progress only when every stage it depends on has passed, and completes only when it has itself passed; a stage has passed when it has at least one gate and all its gates have passed, so a stage without gates never counts as validated. The transitions read the current gates, which the caller passes in, rather than a stored copy of each stage's outcome: a completed stage whose gate later became stale does not let a dependent stage start (architecture invariant 6). An unknown stage is `not-found`.
- **Generations.** Gates and stage progress each carry a generation that starts at 1 and increases by one with every accepted transition. Every transition takes the generation the writer read and fails with `conflict`, naming both generations, when it differs, before any other rule is checked. This is the domain half of compare-and-set; the persistence adapter applies the same comparison atomically.
- **Purity.** No operation reads a clock, random source, or I/O; each takes the time of the change as an `Instant` and returns a new frozen value or a kernel failure. Instants are recorded, not compared.
- **Display text.** The rule for free text the domain stores but never interprets (1 to 1024 UTF-16 code units without a character of category `Cc`) is shared by native references, evidence references, and block reasons.

## Risks / Trade-offs

- Gates are matched to stages by stage identifier, and the caller supplies the gates of the run; a caller that omits a gate can make a dependency look unmet, never met, because a stage needs at least one gate and all of them passed. Binding gates to a run is item 7's aggregate.
- Head-bound verification and review (architecture section 6) need a code-head identity, which is not yet modeled; a code head could later be an artifact revision of the code, so the same invalidation rule would apply.
- Reviewer independence from the implementation attempt is project policy over attempts, which arrive in G2.
