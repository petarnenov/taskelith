## Context

Architecture section 7 lists the plugin contract: stable ID, package version, supported plugin API range, declared protocol capabilities, configuration schema, credential requirements, lifecycle hooks, capability discovery, and error mapping. It requires startup registration of pinned trusted packages and compatibility validation by the composition root before work is accepted; section 6 requires runtime schema validation of all plugin inputs. The G1 plan's item 8 limits this change to the subset the OpenSpec adapter needs. The owner decided D2 (contracts in `packages/contracts`) and D3 (document-first schemas with generated types and validators). The [contract tooling evaluation](/docs/contract-tooling.md) proposes ajv 8.20.0 with `Ajv2020` and, for schemas shared between OpenAPI and AsyncAPI, the keyword subset common to draft-07 and 2020-12.

## Goals / Non-Goals

Goals: a manifest schema for the subset, a registration function that tests exercise, and rejection of an invalid manifest, an unknown port, or an incompatible plugin API range before admission.

Non-goals: configuration schemas, credential requirements, lifecycle hooks, factories, capability discovery against a port's declaration (item 6 defines the port's capabilities), a registry that holds registered plugins or rejects duplicate identifiers, versioned manifests and UI selection (G4), a composition root or runnable application, and generated types.

## Decisions

1. **The manifest schema lives in the plugin SDK, not in `packages/contracts`.** D2 places the HTTP and message contracts, the OpenAPI and AsyncAPI documents and what is generated from them, in `packages/contracts`. The plugin manifest is not exchanged over HTTP or NATS: it is read in process by the registration function, which the SDK owns, and plugin authors build against the SDK. Keeping the schema next to its only consumer avoids a dependency from the SDK on the contracts package for one document. The schema is still a standalone JSON Schema document, written first and compiled by the validator, as D3 requires; if a later wire contract carries manifests (for example plugin listing in G4), the document moves to `packages/contracts` and the SDK imports it.
2. **JSON Schema 2020-12 within the shared subset.** The document is compiled with `Ajv2020` in strict mode, whose default dialect is 2020-12, but declares no `$schema`, as the [contract tooling evaluation](/docs/contract-tooling.md) proposes for shared schemas, because AsyncAPI tools read schemas as draft-07. Besides the identifier `$id` and the annotations `title` and `description`, it uses only `type`, `properties`, `required`, `additionalProperties`, `items`, `uniqueItems`, `maxItems`, `maxLength`, and `pattern`, which mean the same in draft-07. It therefore stays reusable from an AsyncAPI document and within the subset `json-schema-to-typescript` supports. It uses no `format`, so `ajv-formats` is not installed.
3. **The type is written by hand for now.** D3 generates types from schemas, but no generator is wired into the build yet; item 13 wires generation for the wire contracts. Adding `json-schema-to-typescript` (eight dependencies, including prettier and lodash) for one five-field interface is not justified in this change. `PluginManifest` is written by hand next to the schema, with a comment naming the schema, and generating it is a follow-up once item 13 wires type generation.
4. **Closed manifest.** `additionalProperties` is false: a manifest written for a later manifest version is rejected rather than half-read. G4's versioned manifests decide how versions are negotiated.
5. **Field formats.** `id` and each capability are 1–64 lowercase letters, digits, and inner hyphens, starting with a letter (for example `sdlc-openspec`, `structural-validation`); `version` is a semantic version, prerelease and build metadata allowed; `port` is a PascalCase port name (for example `SdlcFramework`); capabilities are unique, at most 64. Every string has a length limit.
6. **Plugin API compatibility through a caret range only.** `pluginApiRange` is restricted by the schema to `^MAJOR.MINOR.PATCH`, with npm's caret semantics: same major from 1.0.0, same minor below 1.0.0, exact version below 0.1.0. One range form covers "compatible with this API" without a range parser; adding the `semver` package for one comparison would be a second runtime dependency. The SDK implements plugin API `0.1.0`, so plugins declare `^0.1.0` until the API changes. Wider range syntax, if needed, comes with G4's versioned manifests.
7. **The host offers ports; the SDK owns the API version.** Ports are owned by modules (for example the SDLC module's `SdlcFramework`), so the composition root passes the ports it offers to `registerPlugin`. The plugin API version is the SDK's own contract, so it is a constant of the SDK rather than an argument.
8. **ajv stays behind a local adapter.** `manifest-schema-validator.ts` compiles the schema on first use and returns either the manifest or readable schema violations; no ajv type leaves that file, so replacing the validator or moving to generated standalone validators changes only the adapter.
9. **Rejections are kernel failures with stable codes.** A manifest that fails the schema is `invalid`, and the message lists every schema error with its location, because a plugin author fixes them together. A port the host does not offer is `not-found`, with the plugin identifier and port in the details. An excluded plugin API version is `precondition-failed`, with the identifier, the range, and the SDK version in the details. The port is checked before the API range. An admitted manifest is returned as a frozen copy.
10. **Workspace packages may ship JSON from `src/`.** A composite TypeScript project must list every file it compiles, and the package contract forbids a package from overriding `include`. The shared `tsconfig.package.json` therefore enables `resolveJsonModule` and includes `src/**/*.json`, so an imported schema is type-checked and emitted to `dist/` beside the code; the package imports it with `with { type: 'json' }`. `tsconfig.check.json` enables `resolveJsonModule` so the boundary type check accepts the import.

## Risks / Trade-offs

- ajv compiles validators with `new Function`. The SDK runs in trusted Node processes, so this is acceptable now; a CSP-restricted context would need standalone validators, which remain unverified.
- The validator is compiled on the first validation, a one-time cost.
- A hand-written type can drift from the schema. The tests assert that a schema-valid manifest round-trips through the typed result, and generation replaces the hand-written type later.
- The caret-only range is narrower than npm ranges; a plugin supporting two majors cannot express it until G4.
