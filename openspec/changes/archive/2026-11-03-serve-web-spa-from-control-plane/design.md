# Design: serve-web-spa-from-control-plane

## Context

G3 item 28 (`docs/g3-plan.md`, row 28), sub-change 28c: "static serving of the built SPA under `/app/` on the browser endpoint with the SPA fallback and the content security policy". 28a (`scaffold-web-spa-workspace`, archived 2026-10-29) builds the SPA with Vite under the base `/app/` into `apps/web/dist`, and 28b (`build-web-spa-shell`, archived 2026-11-03) added the session shell; its design names the risk that an inline color scheme script "would conflict with the CSP of 28c". Architecture section 11 serves the SPA and the API behind one same-origin HTTPS endpoint. The coordinator Niki briefed this change on 2026-11-03 for the worker Desi.

## Coordinator brief (verbatim scope)

> - control plane serves the built SPA under /app/ (static assets with correct content types and cache headers: hashed assets long-lived and immutable, index.html no-cache);
> - SPA fallback: unknown path under /app/ returns index.html, but a missing asset with a file extension returns 404 and an API path is never shadowed;
> - strict Content-Security-Policy and related security headers on SPA responses (no inline script; Mantine style needs justified in design.md if style-src needs more than 'self');
> - path traversal refused, with a fail-before test;
> - behaviour when the build is absent: a clear failure or a 404, decided in design.md, not a crash;
> - make wiring: control-plane image or start path includes the web build, so make targets stay the entry points;
> - spec deltas for product-ui and control-plane-api, as needed.

## Decisions

1. **No library for file serving.** The control plane has no HTTP framework: its API is `node:http` and `node:https` with its own route table (`src/api/api-server.ts`), so no framework static plugin fits. `serve-static` and `send` are Express-style handlers that map every request path to the file system and resolve it per request, which is the traversal surface this change must close, and they would add a runtime dependency and its inventory for what is a fixed, small build (one `index.html` and hashed `assets/`). The control plane instead reads the build once at start into a map of its regular files (decision 5) and answers from the map, so no request path ever reaches the file system. The content types are a fixed table of the extensions that the build or a later public file may have (`.html`, `.js`, `.css`, `.svg`, `.png`, `.ico`, `.json`, `.txt`, `.webmanifest`, `.woff2`); any other is `application/octet-stream`, which `nosniff` keeps from being sniffed.
2. **Routes first, then the SPA.** The listener matches every route of its table first; only a request that matches none, is a GET or HEAD, and has the path `/app` or one under `/app/` reaches the SPA (`webAppAnswer`). No operation of `control-plane.openapi.json` lies under `/app`, which a test checks against the document, and a test route under `/app/` proves that an operation would still win. Other methods under `/app/` and every path outside it get the API's JSON 404 `not-found`, as before. The SPA is passed only to the browser listener (`src/composition/control-plane.ts`); the worker endpoint never serves it. The request log names the operation `web-app`, a name no camelCase operation can take, and holds no path or query, as for any operation without declared query parameters.
3. **Fallback rules.** After decoding (decision 6): `index.html` and every path whose last segment has no file extension (`posix.extname` is empty), `/app` and `/app/` included, answer `index.html`, so React Router's routes and its not-found page work on a reload; a path with an extension answers the build's file or, when the build has none, a JSON 404 `not-found`, so a missing script or style sheet never answers HTML.
4. **Cache policy.** Files under `assets/`, Vite's default `build.assetsDir`, carry a content hash in their name, so they are answered with `Cache-Control: public, max-age=31536000, immutable`. `index.html` and every other file, such as a later favicon, are `no-cache`: the browser revalidates each use. The page has no validator because its nonce differs per answer, so each revalidation fetches it again; it is about 1 KB. The API's `no-store` is unchanged.
5. **Absent build.** `TASKELITH_WEB_APP_DIR` names the build directory (`src/composition/settings.ts`). With it set, the composition reads the build at start (`readWebAppDirectory`, the file-system adapter behind the `WebAppFiles` port of `src/api/web-app.ts`), before any listener starts; a directory that cannot be read or lacks a regular `index.html` fails the start with `precondition-failed` and names the variable and the directory, like the other files the start reads, with the system error's code, such as `ENOENT`, `EACCES`, or `ENOTDIR`, for a directory that cannot be read; no file content is named. Without the variable the browser endpoint serves no SPA and `/app/` answers the API's 404 `not-found`, so the integration tests and any API-only use keep working, and nothing crashes. A failed start is chosen over a 404 for a configured but broken build, because an operator who set the variable expects the SPA, and the image always sets it (decision 9).
6. **Path confinement.** Guards on both sides. The adapter opens the build root, each directory, and each file with `O_NOFOLLOW` and decides by the descriptor's own type (`fstat`), so no entry is read through a link in its last component, and it refuses a build root that is a symbolic link. An entry that `readdir` listed as a file or directory but that is a link when it is opened fails the start, and after the read each directory's path must still lead to the directory, by device and inode, that was opened, so a directory swapped for a link while its files were read fails the start as well (`precondition-failed`, "a build that stays unchanged while it is read"). A link or other entry that `readdir` lists is left out and remembered (`WebAppFiles.isLeftOut`), and a path that names it or lies below it is a 404 `not-found` before the fallback, so `/app/outside` and `/app/outside/sessions` answer neither a file outside the build nor the page. The answer side takes the path as sent, before the WHATWG URL parser removes literal and `%2e` dot segments and turns backslashes into slashes, splits it below `/app/` into segments, and decodes each; a segment that is not valid percent-encoding is a 400 `invalid`, and a decoded segment that is `.`, `..`, empty before the last, or holds a slash, a backslash, or NUL is refused with 404 `not-found` without a lookup or the fallback. Each guard has a fail-before test (`verification.md`).
7. **Content security policy.** Every SPA answer, a failure included, carries `default-src 'none'; script-src 'self'; style-src 'self'[ 'nonce-…']; img-src 'self'; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. Scripts come only from the origin: the built `index.html` loads one module script from `/app/assets/` and holds no inline script, style, or event handler attribute, which a root test checks on the real build. `connect-src 'self'` covers the API and its event streams on the same origin; `img-src` and `font-src` stay `'self'` because the shell uses inline SVG and system fonts. The related headers are `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` for browsers without `frame-ancestors`, `Cross-Origin-Opener-Policy: same-origin`, and `Cross-Origin-Resource-Policy: same-origin`. A failure keeps the API's JSON body and `Cache-Control: no-store`. No `Strict-Transport-Security`: the local composition serves `127.0.0.1` and `localhost`, where a remembered HSTS policy would also bind every other local service; an operator's proxy may add it.
8. **Why style-src needs a nonce.** Mantine 9 injects its theme's CSS variables and responsive style props as `<style>` elements at run time (`MantineCssVariables`, `MantineClasses`, `InlineStyles`, and the transition guard of a color scheme switch, each marked `data-mantine-styles`, each with the nonce of `getStyleNonce` when there is one), which `style-src 'self'` alone refuses, so the shell would render without its theme. The options were `'unsafe-inline'`, which would admit any injected style sheet and with it CSS-based exfiltration, hashes, which change with every theme and responsive prop, or a nonce, which Mantine supports through `MantineProvider`'s `getStyleNonce` and Vite through `html.cspNonce`. This change takes the nonce: Vite writes the placeholder `TASKELITH_CSP_NONCE` into the build's `index.html`, in a `<meta property="csp-nonce">` tag and on its script and style sheet tags; the control plane replaces every occurrence with 128 random bits in base64, fresh per answer, and names the same nonce in the page's `style-src`; `pageStyleNonce` reads the tag's `nonce` (the attribute, which a browser hides once the policy applies, is the jsdom fallback), and `App` passes it to Mantine. Style attributes need nothing more, because React sets them through the CSSOM, which the policy does not restrict. Under `make web-dev` the placeholder stays and no policy applies. A test checks that every Mantine style element carries the nonce, and a mutation without `getStyleNonce` fails it.
9. **Image and make wiring.** The image's build stage already runs `npm run build`, which builds `apps/web/dist` and fails without its `index.html` (`scripts/build-workspaces.ts`), and `npm prune --omit=dev` keeps it; the runtime stage copies `/opt`. The control-plane stage now sets `TASKELITH_WEB_APP_DIR=/opt/taskelith/apps/web/dist`, so `make installation-build` and `make installation-start` serve the SPA with no new target; a test of `test/installation-composition.test.ts` checks the chain. `make web-dev` stays the development server.
10. **No OpenAPI change.** The SPA is not an operation: it is served outside the API's paths, takes no credential, and answers only static files, so `control-plane.openapi.json` does not change; the behaviour is specified in the `control-plane-api` delta, and the installation contract's listeners name the variable. The wire contracts' section 1 reserves `/app` and every path below `/app/` for the SPA, not for API paths, and the test that no operation of the document lies under `/app` checks that sentence too.
11. **The worker image keeps the build.** 28a left this decision to 28c. The control-plane and worker images both come from the `runtime` stage, which copies the build stage's whole `/opt`, so the worker image holds `apps/web/dist` too, about 0.8 MB. It stays: the worker image sets no `TASKELITH_WEB_APP_DIR` and runs no listener that reads it, so the files are inert there; leaving them out would need a second build or prune stage for the worker, or a later `rm` layer that would not shrink the image, and either would change the stages that `make verify-worker-image-reproducible` checks, for no gain in what the worker can do.

## Risks and trade-offs

- The build is held in memory, about 1 MB today; a later build that grows by orders of magnitude would need a bound, which this change does not add. Changing the build needs a restart, which the image's immutable build already implies.
- Node.js has no `openat`, so the walk opens entries by their paths. A directory swapped for a link and back again between its open and the identity check after the read, within one start, would pass both checks; the directory is the image's own, written by root at build time, and the control plane runs as `taskelith` (uid 10001), which cannot write it, so this residue is accepted. The requirement states what the guards ensure: no entry opened through a link in its last component, and a failed start for a replacement that the checks see.
- `no-cache` lets a cache store the page but makes it revalidate before each reuse; because the page has no validator, each revalidation fetches it again with a fresh nonce. A browser may still restore it for back and forward navigation with its old nonce, which matches the policy that answer carried.
