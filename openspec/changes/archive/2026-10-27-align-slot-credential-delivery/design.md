## Context

Review B pass 2 of the G3 item 0 revalidation of item 5 (HEAD `b71f19ff`) found M5, M6, M7, L6, L7, L8, and L9 against the account pool contract. L3, L4, L5, L10, L11, and M1 to M4 of the same review belong to other tasks. G2 facts that the decisions rest on:

- The agent harness port names two subscription mechanisms: `subscription-token`, a long-lived token per slot, and `device-login`, a per-slot state that the session receives as its state directory (`/docs/contracts/agent-harness-port.md` section 4.1; `StartSessionRequest.stateDirectory`).
- G3 decision D6 (`/docs/g3-plan.md`, "Owner decisions"), decided by the owner on 2026-10-25: (a), a long-lived subscription token per slot, stored encrypted and injected per run, if item 35 confirms it; (b), a device login per slot, was not chosen. Items 19 and 35 depend on it.
- The worker journal holds launch authorization requests and grants (`/docs/contracts/worker-journal.md` section 1), commits a grant at W3 (section 5), and recovery after a W3 grant without W4 starts a new execution (section 5, recovery table).
- `@taskelith/secrets` matches only Taskelith's shapes and URL user information (`packages/adapters/secrets/src/scrub.ts`, `SECRET_SHAPE_RULES` of `@taskelith/observability`); a subscription token has none.
- G2 runs plain HTTP and NATS (`/docs/contracts/installation-and-enrollment.md` section 7); TLS is G3 item 26.
- The `control-plane/` namespace is a file subtree of `0600` files (`/docs/contracts/installation-and-enrollment.md` section 3); the G3 plan places encrypted credential storage there (`/docs/g3-plan.md`, item 12).
- `REDACTED` was defined twice, in `packages/modules/observability/src/domain/redaction-rules.ts` and `packages/modules/scheduling/src/domain/slot-secret.ts`, and both packages exported it.

## Decisions

1. **M5, option (a): subscription tokens only, scoped per harness after pass 2.** The contract defines only the `subscription-token` delivery. As first written, the add-slot command rejected every `device-login` slot with `invalid`, and the delivery revealed nothing for a slot of another mechanism, until a later item defined a state directory format and a compare-and-set write-back by the reserving run (sections 3.1, 7.1, and 10). Reason: D6 chose a subscription token per slot for Claude Code, the only harness G3 admits (item 19), and did not choose the device login, so no G3 item needs device-login delivery; defining a format and a write-back no harness uses would be unverifiable. The restriction is revisited if item 35 overturns D6. Coordinator confirmation (Niki, 2026-10-27): option (a). Review pass 1 found that the restriction contradicted "Subscription account slots" of `harness-account-pools`, which accepts any declared subscription mechanism, and that the requirement let it lapse once a later item defines a format; a `harness-account-pools` delta now modifies that requirement, and both requirements then tied the restriction to item 35 and D6 only. `SlotSecret` stays one text; only its comment and the contract say it is a subscription token. The pool still treats `mechanismId` as opaque: the add-slot command and the delivery, both outside the pool's ports, compare the pair of its harness and mechanism with the admitted deliveries. This change makes no claim about provider terms for subscription tokens; D15 and ADR 0005 decision 2 are pending with the owner. Review pass 2 (M6) found that a refusal of `device-login` for every harness widened D6, which is scoped to Claude Code, and narrowed ADR 0005 decision 2, which names a device login per slot; a later harness such as Codex, whose subscription state is a per-home `auth.json` (`/docs/qualification/codex.md`), would stay refused while D6 stands. Coordinator decision (Niki, 2026-10-27), replacing the reviewer's proposal of a second revisit trigger: the refusal is scoped per harness. The add-slot command and the delivery refuse a mechanism for which the slot's harness has no admitted delivery (contract sections 3.1 and 7.1). G3 admits only Claude Code, whose only admitted delivery by D6 is `subscription-token`, so a `device-login` slot of Claude Code is refused; another harness gets its mechanism's delivery when the item that admits it defines one. The admitted pairs live in the control plane, outside the pool, which stays harness-neutral. The D6 and item 35 revisit stays a remaining gate in `verification.md`, not a requirement, because a process obligation cannot be tested (pass 2, L6). No ADR is edited.
2. **M6, memory only, a new delivery per execution.** Section 7.3 keeps the credential in the worker host's memory for one execution and out of the journal, a grant, `worker/executions/<executionId>/`, `worker/logs/`, and the outbox. Every execution after W3, recovered or adopted, requests it again through a new delivery with the checks of section 7; an adopted execution needs it for redaction even when its harness already has it. Review pass 1 found that an adopted execution cannot meet section 7's launch authorization condition: its grant expires after 30 s, and the launch authorization contract allows no new authorization of a started execution. Section 7.3 therefore replaces that condition for a re-delivery with an ownership check that reuses the launch authorization checks a started execution still passes (quarantine, epoch, worker, assignment, ownership generation, attempt, owning execution without a revoked grant) and their section 9 reasons, plus the reservation and slot checks. A refused worker sends none of the run's output off its host, because it cannot redact it by value. No delivery or worker code exists yet, so the tests are obligations of item 18 in section 9, and the spec states them as scenarios.
3. **M7, redaction by value in `@taskelith/secrets`.** The SCM follow-up (`/openspec/changes/archive/2026-10-27-align-scm-port-with-g2-credentials/design.md`, decision 1) kept one redaction boundary: shapes join the shared `SECRET_SHAPE_RULES`, which both log redaction and `@taskelith/secrets` use. A slot token has no shape, so a shape rule cannot match it; the same boundary instead takes the run's revealed values. `redactSecrets(text, revealed)` and `redactFailure(failure, revealed)` redact each exact revealed text; `revealed` defaults to none, so every existing caller of `redactSecrets` keeps its behavior. Review pass 1 showed that replacing values one after another with `split` and `join` breaks other occurrences, re-processes markers, multiplies the output, and can hide a shape secret's suffix from its rule. The replacement now finds every occurrence of every value in the original text, overlapping ones included, with a Knuth-Morris-Pratt scan (linear per value), merges overlapping or touching ones, and emits one `REDACTED` per merged span (`packages/adapters/secrets/src/revealed-spans.ts`). The shape rules are opaque text rewrites, so their spans cannot be read; instead, the whitespace-free word around a span is checked with the shape rules, and a word in which they match anything is redacted whole, even when the shape secret lies far from the occurrence inside that word. That over-redacts at most that word, and leaves no visible part of the credential or of a shape secret without whitespace. The one shape rule that spans whitespace is the `.creds` block; review pass 2 (L1) showed that a value inside one can break its end marker, but the JWT and seed inside the block match their own rules, so nothing leaks, and the comment no longer claims that no shape secret holds whitespace; the shape rules then run on the result as before. An empty value is ignored. The package takes plain strings, not `SlotSecret`, so it does not depend on Scheduling. Item 18 applies them to every text of the run, whatever its channel, the terminal stream included, before it writes the text to a worker record or sends it off the host (section 7.4). Review pass 2 (M2, M3) found that redacting only text that leaves the host let buffered logs and outbox entries hold the credential, and that a pure function over one text misses a credential split across stream chunks or cut by truncation; section 7.4 now requires redaction before every write, a sliding window that holds back the trailing word and at least `max(len(value)) - 1` characters, and truncation only after redaction. Both are item 18 obligations, because the stream code is item 18's; the functions here stay pure. `scrubEnvironment` is unchanged: the plugin injects the credential on purpose.
4. **L6, transport.** Section 7.2: delivery only over item 26's TLS or to a worker co-located with the control plane on its host; a remote worker gets no slot credential before item 26.
5. **L7, storage.** Section 1: `AccountSlots` is in the installation's PostgreSQL database; the `SlotCredentials` key, or its whole store, is in the `control-plane/` namespace, never in the database. Section 6.2 now cites section 1 for that, instead of section 7.
6. **L8, the check belongs to the delivery.** `reveal` checks no reservation, attempt, or slot state; the delivery checks them in a capacity transaction and calls `reveal` after the commit (sections 6.2 and 7). The modified "Redacted slot credentials" says so; the port comment says so.
7. **Failure keys (pass 1).** `redactFailure` kept detail keys unredacted, so a credential used as a key leaked. It now redacts keys with the same function. Keys that become equal, for example two credentials that both become `[redacted]`, keep one entry whose value joins theirs, in their order, with `, `, so that no detail is lost; a `Map` keeps keys such as `__proto__` and `toString` as plain keys. Callers without revealed values now also get their keys redacted by the shape rules, which only removes secrets.
8. **Rotation and emergency revocation (pass 1, corrected after pass 2).** Re-delivery after an adoption must reveal the token the run started with, or redaction by the new value misses output that holds the old one. Review pass 1 proposed refusing a rotation with `conflict` while a live reservation names the slot, and the pass 1 fix added that the slot must be `revoked`, checked in a transaction before an unguarded `store`. Review pass 2 (M1) found that this still races: between the transaction and the store, a reinstatement lets a reservation and its delivery reveal the old token before the store replaces it, and a removal's `destroy` can run before the store writes a live credential into the tombstone. Two designs fix it: a pending-rotation marker in the slot record, which reinstatement and removal refuse while it is set, or a versioned credential switched by compare-and-set. The marker needs a recovery rule after a failed or crashed rotation, and a takeover by a second rotation cannot know whether the first one's store is still running, so its late store could replace the credential after a reinstatement. The versioned credential needs no recovery rule and blocks nothing, so it is chosen. `SlotCredentials.store` writes under a new `SlotCredentialVersion` that it assigns and returns, and never replaces a version; the slot record's `credentialVersion` names the current one; the rotate command stores first and then, in one capacity transaction, switches the record by compare-and-set only while the slot is `revoked`, no held reservation names it, and the version is still the one it read, and refuses with `conflict` otherwise, leaving its version as an orphan that no record names; it discards the lower versions after the switch. A delivery reads the version in its transaction and reveals that version; it holds a reservation, so the version is never switched or discarded before it reveals it. `destroy` removes every version and keeps no later store, so a removal racing a rotation leaves nothing; the adapter can keep a destroyed mark per slot, because a removed slot's identifier is never reused. A rotation that stops between store and switch leaves an unreferenced version that no delivery reveals and that the removal destroys; the operator runs the rotation again. The store assigns the version from its own per-slot counter instead of the command deriving it from the record, because two rotations would derive the same next number. Port and type changes: `AccountSlot.credentialVersion`, `SlotCredentialVersion`, and `store`, `reveal`, `discard`, and `destroy` with versions; the `SlotCredentials` conformance suite checks versions, discarding, and destruction with a later store, and two adapters that break them fail it. Coordinator confirmation (Niki, 2026-10-27): the rotation rule, on the condition that emergency revocation is never blocked; it is not, because a rotation needs the slot to be revoked already. A revoke of a reserved slot succeeds and, in its transaction, cancels every attempt whose held reservation names the slot: a cancellation, which as an invalidating writer of the launch authorization contract section 5 revokes the attempt's grants and writes its cancellation command. Review pass 2 (M5) found that the reservation is not always released with the execution's terminal fact: by capacity reservation contract section 6, "Cancellation", the revoke transaction itself releases it when no execution under the assignment is `authorized` or `started`, for example for a reserved attempt not yet launched, so section 8.1 and the requirement now cite that rule, and the cancellation is the justifying fact. The worker keeps redacting the run by the delivered value until the run ends. No revoke, rotate, or worker code exists yet, so the tests are obligations of items 12 and 18 in contract section 9. A removal drains or rejects instead (decision 10). Coordinator requirement (Niki, 2026-10-27), accepting this design: superseded secrets are not retained, neither the replaced version after a switch nor a version that a crashed or refused rotation left until the slot's removal. The smallest port addition is one command, `SlotCredentials.discardOlderThan(slotId, version)`, rather than a query that lists a slot's versions, which would expose stored state to the control plane only so that it can discard it. After its switch commits, the rotate command calls it with its own version, so one call discards both the replaced version and the lower orphans (contract sections 6.2 and 8.1), and then advances the slot's revision once. A discard before the switch, or a sweep that discards every version but the current one, would race a concurrent rotation that stored a version and then switched to it, leaving the record naming a discarded version. The rotate command is item 12's, so its tests are section 9 obligations; this change adds `discardOlderThan` to the port and conformance cases that an adapter which retains lower versions, discards higher ones, or reuses a version fails. Coordinator decision (Niki, 2026-10-27): two residual cases are accepted as a remaining gate that item 12 must meet. A rotate command that crashes after its switch leaves the replaced version until the next rotation or the slot's removal, and the add-slot command stores a version before it adds the slot record, so a crash between them leaves a version under a slot identifier without a record. Item 12 must add a sweep that calls `discardOlderThan` with the `credentialVersion` it reads from each slot record and discards every stored version under a slot identifier without a record, with a test for each crash point (contract sections 8.1 and 9); until then a crashed rotate or add-slot command can leave one encrypted secret version at rest. Review pass 3 (Medium) found that the earlier cleanup, which discarded every version but the rotation's own, could delete another rotation's current version: rotation A switches to its version, rotation B reads that revision, stores, and switches, and A's cleanup then deletes B's version, so the record names a deleted version; A's later revision advance cannot fence it, and B can also switch between A's cleanup and A's advance. Decision (away delegate (claude fallback; OpenCode out of quota) on behalf of the owner, 2026-10-27), applied without another review and recorded `fixed-unreviewed`: `store` assigns and returns a per-slot, strictly increasing version from a counter it stores, never reused, even after a discard or `destroy`, so never one more than the highest surviving version; `discardOlderThan` replaces the earlier command and destroys only lower versions; the rotate command, after a successful compare-and-set, calls `discardOlderThan` with its own version and then advances the revision, and after a failed compare-and-set leaves its own version as an orphan. The cleanup is safe because a rotation reads the record before it stores: a rotation that switches later read the record after this switch, so its version is higher and kept, and one that read it before fails its compare-and-set. A failed rotation's orphan that is higher than the version current after a switch stays encrypted at rest until a later successful rotation, whose own version is higher, discards it. `SlotCredentialVersion` becomes a branded positive integer with `parseSlotCredentialVersion`, and `parseAccountSlot` rejects a record whose `credentialVersion` is not one. Item 12 gate tests (contract section 9): A switches, B then stores and switches, and A's cleanup keeps B's version and the slot stays deliverable; of two rotations that read the same revision the first switch wins, the other's compare-and-set fails, and the record never names a deleted version; and an orphan newer than the current version is discarded by the next successful rotation.
9. **L9, one constant in the kernel.** `REDACTED` moves to `@taskelith/kernel`, which every module already depends on. `@taskelith/observability` re-exports it, so its readers, `@taskelith/secrets` among them, are unchanged; `@taskelith/scheduling` imports it and no longer exports it.
10. **Removal keeps draining (pass 1 follow-up).** The pass 1 fix `2eef8d7c` made a removal cancel the slot's attempts as a revocation does. ADR 0005 decision 6 says that removal drains or rejects its in-flight sessions, and "Session affinity" of `harness-account-pools` lets an unavailable slot's session be drained or ended, so that fix narrowed the ADR. A removal therefore keeps the ADR: a held reservation does not block it, and it drains or rejects the slot's in-flight attempts by policy or an operator; only a revocation cancels them at once, so a removal after a revocation finds them cancelled. A drained attempt keeps its delivered credential, but its re-delivery is refused, because the slot is not `active` (contract sections 7.3 and 8). Coordinator confirmation (Niki, 2026-10-27): the stricter rotation rule of decision 8 and the cancellation by revocation are kept, and removal does not drop draining.
11. **Re-delivery, channel, and scenario precision (pass 2).** The requirement "Re-delivery to an adopted execution" now names every check of section 7.3, quarantine, recovery epoch, and worker included, with a scenario for quarantine (M4). The re-delivery checks run in section 7.3's order, so a cancelled attempt is refused with `attempt-not-launchable` and a live attempt with a revoked grant with `execution-conflict`, each in its own scenario (L7). A refused worker discards the run's output text and never writes or sends it, keeping only facts without run text, such as exit and cancellation (M2). The credential travels only in the control plane's API response, never in a broker message, which would keep it at rest (L4). The living scenario "Slot revoked during a session" of `harness-account-pools` now says the session is cancelled, matching the revocation rule (L8).
