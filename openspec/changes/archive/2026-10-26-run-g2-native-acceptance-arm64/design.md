## Context

The [native acceptance gates](/docs/worker-platforms.md#native-acceptance-gates) list seven rows; G2 owns process ownership, journal and storage, cancellation, the G2 part of connectivity, and the G2 part of service lifecycle (install, start, stop, and restart of the worker with its persistent volume and dedicated account, [G2 plan](/docs/g2-plan.md) item 25). Resource budgets and real integrations belong to later gates. D11 (a) selects all four matrix entries. Items 24a, 24b, and 25a already proved parts of these rows on single hosts and recorded them through the harness's scenario recorder, but no record names the matrix entry or the row, the macOS-only crash windows have never been tied to the macOS entry, and `make verify-linux-cgroup` refused arm64.

## Decisions

1. **One runner, two entry kinds, detected from the host.** `scripts/native-acceptance.sh` runs the macOS entry when `uname -s` is `Darwin` and the Linux entry whenever Docker runs, so a macOS host runs both and a Linux host only the Linux entry; `ENTRIES` narrows it. `scripts/native-acceptance.ts platform` derives the entry and fails on a host that is not one: macOS needs `sw_vers` major 26, Linux needs the pinned base image's `PRETTY_NAME` to start with `Ubuntu 24.04`, and the architecture comes from `uname -m` or `docker info` (`arm64` or `aarch64` give `arm64`, `x86_64` gives `x86_64`). Nothing else depends on the architecture: the clone syscall number of the 25a scenario, the Node.js tarball of the Linux test image, and the images of the installation already follow it. 25c therefore runs `make native-acceptance` unchanged on the x86_64 iMac.
2. **A proof is a command with a row and a target.** `prove ROW SCENARIO TARGET COMMAND...` exports `TASKELITH_ACCEPTANCE`, runs the command with its output also in a log, and records one line `acceptance-<proof>` with the exit status and the node:test counts or the last log line. Every proof runs, also after a failure, and the run fails at the end if any failed. A proof that records itself (a Compose scenario or the crash windows) adds its own lines, which carry the same context through the environment.
3. **The recorder field.** `RunEnvironment` gains an optional `acceptance`, which `runEnvironment` parses from `TASKELITH_ACCEPTANCE` and validates (entry, row, nonempty proof, and six nonempty platform strings), and `scenarioResult` copies it into the record only when present. Two targets join: `host-test-suite` and `linux-test-container`, so that a test suite is not labelled a composition or an installation, as worker-platforms "Evidence and release limits" asks. A record without the field, and every existing caller, is unchanged; no code reads `results.jsonl` files.
4. **Where the Linux entry runs.** The Compose scenarios run the worker image itself. Test suites run in the test image of `make verify-linux-cgroup`, which is the worker image's base: the digest-pinned Ubuntu 24.04 and the checksummed Node.js tarball, now of the Docker host's architecture. The worker image has no development dependencies, because its build prunes them, so the suites cannot run in it. `make linux-test-suites` runs them as an unprivileged user (uid 2000), without network, with `/tmp` on a fresh anonymous volume, so that the journal sees a persistent file system rather than the overlay; the privileged cgroup tests keep `make verify-linux-cgroup`, which now passes test runner options (`PATTERN`).
5. **Proofs per row.**

   | Row | macOS entry (native) | Linux entry (worker image under Docker) |
   | --- | --- | --- |
   | Service lifecycle | `make scenario-native-worker-lifecycle` | `make scenario-worker-lifecycle` |
   | Process ownership | supervisor suites on the host; 24b crash windows without the duplicate delivery (harness composition) | `make scenario-worker-kill`; `make verify-linux-cgroup` (supervisor crashes at CP5 to CP11, adoption after a worker restart) |
   | Journal and storage | journal and data-root suites on the host, with the new path tests | the same suites in the test image; `make scenario-worker-disk-loss` |
   | Cancellation | supervisor and command intake suites, tests named `cancel` or `descendant` | `make verify-linux-cgroup PATTERN=...`; the same suites in the test image |
   | Connectivity (G2) | 24b duplicate delivery (harness composition); offline launch and worker contact suites | offline launch and worker contact suites in the test image |

6. **Lifecycle scenarios.** `scenario-worker-lifecycle` reuses the 24a steps: a fresh installation, an enrolled worker, a task whose execution must run as uid 10003 in `executions/<executionId>` (read as in 25a), then the `installation-stop` and `installation-start` steps; the restarted worker must keep its identity file's digest and its enrollment, log its first reconciliation and its broker contact from a new process, keep its containment, and run a second task the same way. `installation-start` recreates the worker container, because the enrollment token is no longer set, so the identity also survives a new container on the same volume. The API's host port is read again after the restart, because the throwaway project's ports are ephemeral. `scenario-native-worker-lifecycle` starts the installation without a Linux worker and runs `node apps/worker/dist/main.js` of the checkout on the host, with a token for its platform and architecture, a data root whose path holds spaces, and a one-second scripted process; `SIGTERM` is the service stop and must give status 0. Both record the platform in their detail.
7. **The disk floor on the native data root.** The worker refuses new launches while free space is below `max(5 GiB, 10 %)` of the data root's volume (operational targets; `apps/worker/src/admission-pressure.ts`). The Apple Silicon host had 12 GiB free of 228 GiB, below its 22.8 GiB floor, and the first native run timed out with `worker.admission-pressure.changed` `disk-floor`: correct behavior, not a defect. `NATIVE_DATA_PARENT` therefore places the data root on another volume; the evidence run used a 16 GiB sparse APFS disk image, local and attached with owners on, which the record names. The disk image is a qualified macOS file system (local APFS) but not the boot volume; the record says so.
8. **Path rules on macOS.** Two journal tests run in every `make verify` and in the acceptance suites: a data root whose path holds spaces enrolls, reopens, and keeps its lock; on a case-insensitive volume, as default APFS, a case-variant path of a held root is refused as `root-locked`. The second skips on a case-sensitive volume, such as the Linux test container's.
9. **Expected failures stay failures.** The 24b crash windows keep their D1 expected failures (`expectFailure` with D1's signature), so the test run passes while eleven records say `failed`; the acceptance table reports those windows as failed on D1. No proof is skipped or retried to obtain a pass.

## Rows that stay open

- **Linux composed crash windows.** The 24b scenarios supervise natively on macOS only (24b design 8): on Linux the composed worker needs a delegated cgroup and an execution account, which only the privileged test container provides, and that container has no network to the services. The Linux process ownership row therefore rests on the supervisor-level crash points of `make verify-linux-cgroup` and the untimed `SIGKILL` of the worker container, and the composed crash windows on Linux remain open until a privileged composition with services exists.
- **Cancellation races, partition and reconnect, stale generations, stale writes** belong to 24c (`run-g2-partition-and-races`), not yet merged; duplicate delivery on Linux needs the same composition as the crash windows.
- **Service lifecycle beyond G2**: reboot, drain before upgrade, a supervisor (systemd or launchd), logout and login, and a dedicated macOS service account are G6 (D5: launchd stays with G6); the macOS native worker runs under the invoking user.
- **Connectivity beyond G2**: credential rotation delivery is G3 item 26 (recorded limitation), epoch quarantine and restore are G6, sleep and wake and network changes on macOS need a host procedure that G2 does not have.

## Risks and limitations

- The Linux entry under Docker Desktop runs in a Linux VM of the host's architecture with the `linuxkit` kernel, not on an Ubuntu host kernel; the record names the kernel. A Linux host with AppArmor or SELinux is not observed.
- The suites in the test image use the host's built `dist/` and `node_modules/`, mounted read-only; they hold no native add-on used on Linux.
- The records name the commit that ran, not a clean tree; `verification.md` states the revision.
