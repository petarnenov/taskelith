# Design: build-web-spa-shell

## Context

G3 item 28 (`docs/g3-plan.md`, row 28) builds the SPA on the stack of D1 and Mantine (D17) from the proof of concept in `docs/ui-poc/` (ADR 0011). Sub-change 28a (`scaffold-web-spa-workspace`, archived `2026-10-29`) left `apps/web` with one scaffold page, the generated control-plane types, a typed fetch that sends `X-CSRF-Token` on every request other than GET, the bundle boundary, and the Vitest coverage in `make verify`. This change, 28b, replaces the scaffold page with the shell. The owner returned the UI track (items 28 to 34 and 40) to the worker Desi on 2026-11-02; the coordinator Niki briefed this change the same day.

## Coordinator decisions (verbatim)

The brief of 2026-11-02 lists the item 28 decisions in force:

> - the SPA lives under /app/;
> - no openapi-fetch (own typed wrapper with CSRF, from 28a);
> - system fonts;
> - empty pages that name the item which builds them, no mock data;
> - theme contrast through Mantine createTheme, with a >= 4.5:1 contrast test;
> - the 7 POC SVG icons are kept;
> - Mantine only, no custom components or style overrides (D17).

It also carries the follow-up of #417: "The web build must ignore NODE_ENV: test/check-web-bundle.test.ts fails when the shell exports NODE_ENV=development. Fix it with a fail-before test." 28a's design records the decisions D1 to D5 of 2026-10-29 verbatim; D4 (no interactive badge, tested with Testing Library) and D5 (theme settings in `createTheme` are not overrides; a WCAG contrast test in both schemes) apply here.

## Decisions

1. **Existing session operations only.** The OpenAPI document already has `readSession` (`GET /session`), which starts an anonymous session and returns its CSRF token, `logIn` (`POST /session`), and `logOut` (`DELETE /session`), so no operation and no control-plane code change. `createSessionGateway` (`src/session/control-plane-session.ts`) is the adapter: it calls them through the 28a typed fetch, keeps the CSRF token of the latest session answer for the next non-GET request, forgets it after a logout, and translates the answers into the shell's types (`src/session/session.ts`): `logIn`'s 401 `login-failed` is wrong credentials, 400 an invalid request, 401 `unauthenticated` and 403 `csrf-token-invalid` an expired form, and any other answer or a network failure an unreachable control plane; `logOut`'s 204 and 401 both end the browser session, any other answer fails it. The typed fetch does not check bodies, so the gateway checks the fields it uses (`state`, `csrfToken`, the principal's `loginName`, `installationRoles`, a readable `expiresAt`, and a 401's `details.reason`); a body without them, an empty one, an HTML page, or JSON that does not parse reads as an unreachable control plane (pass 1 finding 3). Answers can arrive in any order, so the gateway keeps a count of the logins and logouts that ended: an answer to a request sent before one of them ended keeps no token, and a late logout does not forget the token of a later login (pass 1 finding 1).
2. **Session state in a provider.** `SessionProvider` holds one view, checking, unavailable, signed out with its notice (none, expired, or signed out), or signed in with the operator, and nothing else of the product renders before the first `readSession` answer (`Shell`). After an expired form it reads a fresh anonymous session, so the next login has a valid token, and takes over an authenticated session that another tab logged in meanwhile. A successful logout shows the sign-in page at once, which also cancels the expiry check, and only then reads the next anonymous session for its token, taking over only an authenticated answer (pass 1 finding 2). Every answer changes the view only if no other view showed since its request was sent, so a late logout, expiry read, or post-logout read never undoes a newer login or logout. The provider wraps the gateway so that a rejected call reads as an unreachable control plane or a failed logout, and the sign-in form always leaves its submitting state.
3. **Expiry by reading again.** The control plane renews an authenticated session on use (`packages/modules/access/src/domain/session.ts`), so other requests may move its end. The provider therefore schedules, through an injected `Clock`, a `readSession` for when the announced `expiresAt` has passed, plus a margin of 10 s, so that a client clock slightly ahead of the server's does not read a still-live session; an anonymous answer shows the sign-in page saying that the session expired, an authenticated one keeps the page and schedules its new end. The margin is also the least delay, so a session that already looks ended is read at most every 10 s. The timer is cancelled as soon as a logout succeeds and on unmount. The browser clock caps the delay at the 2^31 - 1 ms that `setTimeout` takes.
4. **Routes from one screen table.** `src/screens.ts` lists the D10 screens with their path, label, title, and the G3 item and change that build them: the board at `/app/` (item 29 `build-board-and-task-detail`), agent sessions at `/app/sessions` (31 `build-agent-session-screen`), reviews at `/app/reviews`, SCM integrations at `/app/integrations`, and plugins at `/app/plugins` (34 `build-reviews-and-settings-screens`), workers and account pools at `/app/workers` (33 `build-workers-and-pools-screens`), the "Needs you" inbox at `/app/inbox` (32 `build-needs-you-inbox`), and new task at `/app/new-task` (30 `build-new-task-screen`). `appRoutes` turns it into React Router routes under the `Shell` layout route, with a not-found page for any other address, and `main.tsx` creates a browser router with the base `/app`; tests use a memory router over the same routes. Each page is the same `PlannedPage`, which names the screen, its item, and its change and says that it shows no data. Task detail has no route yet: it opens from a board card, and item 29 adds it.
5. **Layout from the proof of concept.** `AppLayout` follows `docs/ui-poc/src/main.tsx` (`Shell`): a Mantine `AppShell` with a 68 px header, the logo and name, the header navigation from Mantine's `xl` breakpoint, a `Burger` below it that opens the navbar of `NavLink`s and closes it after a choice, and on the right the "New task" and "Needs you" links, the color scheme toggle, and the account menu behind the avatar. Below Mantine's `sm` breakpoint the header keeps only the burger, the logo, "Needs you", and the account menu, and the navbar adds "New task" and the color scheme switch, through Mantine's `visibleFrom` and `hiddenFrom` props (pass 1 finding 5): at 320 px the header needs 16 + 44 + 12 + 22 + 12 + 66 ("Needs you" with its icon and button padding) + 12 + 44 + 16 = 244 px, where "New task" and the toggle added 66 + 44 and two gaps of 12, 378 px in all. The sign-in fields take at most the 64 characters of `LoginName` and the 1024 of `Password`, and the invalid-request hint states the `LoginName` pattern, including the leading letter or digit (pass 1 finding 9); `maxLength` counts UTF-16 code units, so a password of characters outside the Basic Multilingual Plane is capped below 1024 code points. `SignInPage` follows the proof of concept's `SignInScreen`, and the session check its "Checking your session…" loader. Links are Mantine `Button` and `NavLink` rendered as React Router `Link`s, with `aria-current="page"` on the current screen.
6. **Theme settings only.** `src/theme.ts` keeps the proof of concept's `primaryColor` `indigo`, `defaultRadius` `md`, `respectReducedMotion`, and its component default props for 44 px targets (`docs/ui-poc/src/theme.ts`), drops its IBM Plex fonts for Mantine's system font stacks, and adds four theme settings for contrast (D5): `primaryShade` light 7 instead of 6 (white on filled indigo 4.32:1 to 4.98:1), `gray.6` `#6c757d` instead of `#868e96` (light dimmed text 3.32:1 to 4.69:1), `dark.2` `#999999` instead of `#828282` (dark dimmed text 4.04:1 to 5.45:1 on the page and 3.53:1 to 4.77:1 on a dropdown), and `indigo.2` `#c8d3ff` instead of `#bac8ff`, the light scheme's hovered light variant behind `indigo.9` (4.13:1 to 4.59:1, pass 1 finding 4). No CSS and no Styles API override is added.
7. **Contrast test from Mantine's resolvers.** `test/contrast.ts` merges the theme into Mantine's default theme and takes the colors from `defaultCssVariablesResolver` and `defaultVariantColorsResolver`, Mantine's own functions, so the test measures what Mantine renders; it resolves `var()` chains, blends translucent backgrounds over the page, and computes the WCAG 2.2 ratio. `test/theme-contrast.test.ts` checks, in both schemes, every pair the shell draws: text and dimmed text on the page, a dropdown, an input, a hovered menu item, and a hovered navigation link, filled and light primary, subtle gray, and default, each at rest and hovered (the resolver's `hover` background with its `hoverColor`, or its `color` when it names none), and the title and message of the indigo and red alerts. Surfaces that Mantine's stylesheets set rather than its resolvers (dropdown, input, menu and navigation link hover, alert message) are named per scheme in the test. A guard test shows that Mantine's default dimmed text fails, so the test can fail.
8. **Color scheme kept per browser.** `MantineProvider` uses `localStorageColorSchemeManager` with the key `taskelith-color-scheme` and starts dark, the specification's default.
9. **Accessibility of controls (D4).** Every button, link, and menu item of the shell is focusable and named; buttons that show only an icon below a breakpoint carry an `aria-label`, the `Burger` carries `aria-expanded`, and the sign-in form is named. The shell has no badge; a test checks every rendered control and that no badge sits inside one. The seven icons are inline SVG with `aria-hidden`.
10. **Production build whatever NODE_ENV says.** Vite takes `NODE_ENV` from the environment when it is set, and with `development` it built React's development bundle, whose diagnostics name `react.dev` links, so the bundle check failed. Vite reads `NODE_ENV` for production mode after it loads the configuration, so `vite.config.ts` sets it to `production` for the `build` command; `npm run build`, `make web-build`, and a direct `vite build` all make the production bundle. The fail-before test builds the SPA with `NODE_ENV=development` into a temporary directory and runs the bundle check over it.
11. **React Router's texts in the bundle.** The router brings four texts that the URL pattern of `scripts/check-web-bundle.ts` reads as URLs: the base `http://localhost` and `server://singlefetch/` against which it parses paths, the documentation link of its missing data router error, and `//g,`, which its regular expression `/\//g,` becomes once the script decoder unescapes `\/`. None is ever requested. Each enters `ALLOWED_URLS` as an exact string with its reason and a comment naming its source in React Router 8.5.1 (`lib/router/history.js` `createBrowserURLImpl` and `lib/router/navigation.js`, `lib/dom/ssr/single-fetch.js` `singleFetchUrl`, `lib/hooks.js` `getDataRouterConsoleError`, `lib/router/utils.js` `decodePath`), and passes only in scripts; the check compares whole URLs with `Map.has`, never a prefix or a pattern. The format test of the list accepts a scheme other than HTTP and a scheme-relative entry; any variant of an entry still fails, and a test shows that near misses such as `http://localhost:1234` and the entries outside a script still fail.

## Proof of concept

The change follows `docs/ui-poc/src/main.tsx` (shell, navigation, session check, account menu, sign-in screen), `docs/ui-poc/src/theme.ts`, and `docs/ui-poc/src/icons.tsx`. Departures, each required by a requirement or decision ("Reference proof of concept"):

- **No Knowledge or Board states entry.** POC: the `NAV` list of `docs/ui-poc/src/main.tsx` holds "Knowledge" (marked G5) and "Board states". D10 puts knowledge in G5, and the board states are states of the board (item 29), not a screen; the product UI requirement "Web SPA screen routes" forbids entries of later gates.
- **No project picker and no "Needs you" count.** POC: `Shell` and `NeedsYouButton` of `docs/ui-poc/src/main.tsx`. Both need project or inbox data, which the pages of this change do not show (empty pages, no mock data; D10 places the inbox in item 32); items 29 and 32 add them. Without a count, "Needs you" uses the primary light variant instead of the POC's teal or orange.
- **"New task" in the header.** POC: the board opens new task (`docs/ui-poc/src/screens/Board.tsx`). D10 lists new task as a G3 screen, and the board is empty until item 29, so the header carries the link, and below `sm` the navbar (decision 5); item 29 may move it. Its route is only the empty `PlannedPage` stub that names item 30 `build-new-task-screen`, like every other screen.
- **Account menu.** POC: `AccountMenu` of `docs/ui-poc/src/main.tsx`. It names the logged-in operator and the installation-wide roles of the session and offers "Sign out"; the proof of concept's persona switch is a demonstration, and "Account settings" and "Change password" have no operation yet (item 10). "Sign out" is not red, and the signed-out notice is an indigo alert instead of teal, because Mantine's red menu item text (4.13:1 in the dark scheme) and teal alert title (4.33:1 in the light scheme) are below 4.5:1.
- **Sign-in form.** POC: `SignInScreen` of `docs/ui-poc/src/main.tsx`. "Login name" instead of "Username", after the OpenAPI document's `loginName`; no placeholders, whose Mantine colors are below 4.5:1, and no required-field asterisk, whose error color is below 4.5:1 in both schemes; failures in a red alert instead of the password field's error text, whose dark scheme color is below 4.5:1; field limits of the OpenAPI schemas (decision 5).
- **No tooltip on the color scheme toggle.** POC: `ColorSchemeToggle` of `docs/ui-poc/src/main.tsx` wraps it in a `Tooltip`. Its `aria-label` names the action. Below `sm` it moves into the navbar (decision 5).
- **System fonts.** POC: `docs/ui-poc/src/theme.ts` sets IBM Plex. The coordinator's decision for item 28 replaces it with Mantine's system stacks.

## Risks and trade-offs

- A client clock more than 10 s ahead of the server's reads the session before it ends, which renews it on the server; the absolute lifetime of 24 hours still ends it. The SPA does not see the server's time.
- Requests of later items that the server answers with 401 `unauthenticated` do not yet move the shell to the sign-in page; the expiry check catches the end at the announced time. The item that first sends such requests routes their answer into the session state.
- The contrast test covers the pairs the shell draws; each later item adds the pairs its screens draw.
- No `ColorSchemeScript` runs before React, so a reload in the light scheme may show the dark scheme for a moment; an inline script would conflict with the CSP of 28c.
- The gateway keeps the CSRF token in memory only, so a reload reads it again through `readSession`.
