## Context

ADR 0006 selects GitHub.com as the first SCM plugin, with a GitHub App per installation and a per-run installation token limited to the project's repositories. The GitHub qualification states the port's needs in SCM-neutral terms ("Consequences for the SCM port"): per-run credentials limited by repository and permission, merge blocking that the plugin's own identity cannot bypass, a reviewer identity separate from the identity that opens a change, webhooks verified on the raw body with opaque identifiers, and a refresh path for tokens that last about an hour. The owner decided D8 (a) on 2026-10-25: review is Taskelith evidence, posted as a required commit status that branch protection enforces. The architecture places SCM ports in the "SCM / Tracker integrations" module and names the port `SourceControlProvider`.

## Goals / Non-Goals

Goals:

- A small, SCM-neutral port that the GitHub plugin can implement and that Forgejo can map onto.
- A conformance suite that every SCM plugin passes with its own credential against its service.

Non-goals: the GitHub plugin, item 8's product ports, SCM I/O, the module's use cases (credential delivery to a run, webhook deduplication, merge orchestration), the plugin SDK re-export, and wire contracts.

## Decisions

- **Module.** The ports belong to `@taskelith/integrations`, the architecture's integrations module, which item 8 (`define-product-ports`) added while this change was in progress. This change merges the two skeletons: it adds a `./port` entry that exports only the plugin-facing port types and constants, like `@taskelith/sdlc/port`, and keeps item 8's root exports and dependencies.
- **Names next to item 8.** Item 8's `MergeQueue` already exports `MergeRequest` for a queued merge, so the port's merge input is `ChangeRequestMerge`. Like item 8's `IntakeSource` and `WriteBack`, the plugin-facing port uses plain strings; item 8's branded `BranchName` and `CodeHead` stay internal to the module.
- **Contract document.** `docs/contracts/source-control.md` holds the contract, the SCM mapping, and the conformance suite's checks, as `docs/contracts/product-ports.md` does for item 8.
- **Three ports.** Credential issuance, change requests, and webhook verification have different clients: the launch path, the integration flow, and the HTTP receiver. Each client depends on its own port (ADR 0004 principle 2). `SourceControlProvider` combines them with the capabilities for the plugin to implement.
- **Draft version.** The port is `0.1.0`. ADR 0009 froze the SDLC port only after both frameworks ran through it; here only GitHub will run before Forgejo is added. The plugin SDK re-export and the plugin API version change belong to item 20, which first needs the port from a plugin.
- **Plain data.** Requests and results are plain strings and arrays, as in the SDLC port. The suite checks every result at run time, because plugin output is untrusted. Enumerated values (`SCM_PERMISSIONS`, `MERGE_METHODS`, `COMMIT_STATUS_STATES`, `CHANGE_REQUEST_STATES`, `WEBHOOK_EVENT_KINDS`, `REVIEW_EVIDENCE_KINDS`) are typed as `string` in results, so that an unknown value is a finding rather than a type lie.
- **Opaque identifiers.** Repositories, change requests, commits, credentials, runs, and deliveries are opaque strings that the module compares exactly and never parses. GitHub's numeric pull request numbers and Forgejo's indexes both become strings.
- **Credentials.** `issueRunCredential` takes the run, its repositories, and the SCM-neutral permissions it needs, and returns the effective repositories and permissions with an expiry. `refreshRunCredential` keeps the scope and returns a new secret with a later expiry for long runs; expiries are kernel instants (UTC, `YYYY-MM-DDTHH:mm:ss.sssZ`), so a plugin normalises its service's format; `revokeRunCredential` ends it. The secret goes only to its run and is never logged or stored. Effective permissions may exceed the request when the service has no narrower permission, and the plugin reports them, except that a credential requested without `write-code` never has it; the suite checks that the effective set covers the request and is what the credential can actually do in the project, that it can do nothing outside the project, reads included, and that two runs' credentials stay independent. A refresh returns a new secret and ends the previous one; the suite refreshes a read-only credential and one with every permission, so that a refresh that widens the grant is found, and it can check on the service that the refresh is real while the original is still within its expiry; after a refresh or a revocation the previous credential can do nothing, reads included.
- **Merge blocking.** `ensureMergeProtection` sets the required statuses on the base branch and reports `bindsProvider`, which is true only when the service enforces the protection against the plugin's own identity. The suite then tries the most privileged native merge with that identity through the fixture, so the block is tested on the service, not only in the plugin. `mergeChangeRequest` returns the base branch head after the merge as its merge commit, which the suite compares with the service, and observes the method used natively. It names the expected head, so that only the verified and reviewed head can merge, and the project's merge method; a pending or failed required status or a moved head fails with `precondition-failed`, and an undeclared method with `unavailable`.
- **Review identity.** By D8 (a), the review result is a commit status with the project's review context, required by merge protection. `required-status` is the mandatory review evidence; `native-approval` is reserved for a separate reviewer identity (D8 (b)), which no plugin declares yet. The port has no approval operation, because the identity that opens a change cannot approve it.
- **Webhooks.** `verifyWebhookDelivery` receives the headers and the raw body bytes and fails with `forbidden` unless the signature over those bytes is valid. The suite also sends a body that was parsed and re-serialized, which a verifier of the parsed payload would accept, a signature made with another secret, and a delivery without its signature header. A redelivery yields the same `deliveryId`, by which the module will deduplicate.
- **Conformance fixture.** The suite cannot reach a service by itself, so the plugin's test supplies a fixture: the provider, a project repository and a foreign one that the plugin's own identity can access, the base branch, the merge method, and native helpers to create and advance a head branch, to read a branch head, to observe the method of a merge, to attempt with a run credential the action that each permission allows (`attemptAction`), to attempt a bypassing merge, and to sign a delivery with the plugin's secret or another one. The suite checks every refusal on the service as well: a refused merge leaves the change request open and the base branch unchanged, a bypassing merge succeeds on a change request whose statuses all succeed, so that a broken helper cannot pass as protection, and each required status, including any the service already required, blocks the merge on its own while it is missing, pending, failed, or in error, with the whole matrix of contexts and blocking states, and a moved head, checked for every declared merge method. The plugin runs the suite through `make` with its own credential (item 20). This change runs it against a test-only in-memory fake and against defective variants that each violation must be reported for.

## SCM mapping

The GitHub and Forgejo mapping is in section 7 of the [contract](/docs/contracts/source-control.md#7-scm-mapping). The Forgejo column is an unsourced assumption that the Forgejo plugin must confirm at a pinned version before admission.

## Risks / Trade-offs

- With one SCM before Forgejo, an SCM-specific shape could pass review unnoticed. The mapping table and the suite reduce the risk; Forgejo's admission may revise the draft port.
- The conformance suite mutates a live service and needs disposable repositories; item 20 owns that setup and its cleanup, as the SCM qualification requires.
- The suite requires a refreshed expiry later than the original. A service that reports expiries in whole seconds can return the same expiry for a refresh within one second of issue, so its plugin's fixture must wait or its refresh must guarantee a later expiry.
- Effective permissions wider than requested, other than `write-code`, are reported but not refused by the port; the policy that accepts or refuses them belongs to the module's use cases.
- The suite does not wait for a credential's original expiry, which lasts about an hour on GitHub; it checks a refresh through the new secret and the ended previous one. A run that outlives the original expiry is item 20's evidence.
