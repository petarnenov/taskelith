## Context

The `pre-push` hook ran `scripts/check-pre-push.ts`, which reads git's ref lines on standard input, and then `make verify`. `scripts/pre-push-checks.ts` already treats an all-zero local object name as a deletion. Archiving was a separate coordinator step with its own branch and pull request, after the task's pull request merged.

## Decisions

1. **Delete-only decision in TypeScript.** `isDeleteOnlyPush` in `scripts/pre-push-checks.ts` is true when the hook input holds at least one ref line and every line has exactly four whitespace-separated fields whose two object names are SHA-1 or SHA-256 hex (40 or 64 characters), the local one all zeros. Invalid input never gets the delete-only bypass; the standard checks may refuse it before verify. Empty input is not delete-only either, so the hook runs `make verify` for it as before.
2. **Exit status as the hook protocol.** The hook's standard input can be read only once, and `check-pre-push.ts` reads it. That script exits with `DELETE_ONLY_PUSH_STATUS` (100) for a delete-only push, before its other checks, which only protect `make verify`; the hook exits 0 for that status, 1 for any other failure, and otherwise runs `make verify`. Node.js, `sh`, and the repository's wrapper scripts use no status 100.
3. **Tests.** A unit test covers `isDeleteOnlyPush`. A hook test runs the real `.githooks/pre-push` in a temporary repository holding copies of the hook's scripts, with a fake `make` on `PATH` and no nvm, and checks that a delete-only push (SHA-1 and SHA-256 lengths) skips `make verify`, and that a mixed, a normal, and an empty push run it and are blocked when it fails; the fake `make` exits with a status the test sets. The unit test also covers missing and extra fields, invalid object names, and extra whitespace. Both run in `npm test`, so in `make verify`.
4. **Archive on the task branch.** After the last review pass and its fixes, the worker ticks every task and runs `npm run openspec -- archive <change> --yes`. On the resulting working tree it runs `npm run openspec -- validate --all --strict` (active changes and living specs) and `make verify`, checks its own change's line in `npm run openspec -- validate --archived --no-interactive` (task completeness of archived changes; the command fails as a whole on older archived changes), and checks that `git diff "$(git merge-base HEAD origin/dev)" -- openspec/specs` holds only the change's intended edits. The archive only applies the reviewed deltas with the pinned CLI, so it needs no further review pass.
5. **One rule for every return.** The coordinator merges `dev` with `git merge --no-commit --no-ff origin/dev`, commits the merge only when it will integrate, and on any return runs `git merge --abort`, so a returned branch never carries a coordinator merge. On any return of a branch that carries its archive commit, the worker restores the active change by reverting that commit, merges `dev`, reconciles each restored delta with `dev`'s current requirement text, keeping others' edits, has the assigned reviewer review the resolved diff and the reconciliation, records it, and archives again as the last commit; a branch without an archive commit only needs step 7. The coordinator returns a task when merging `origin/dev` conflicts in any file other than the dependency inventory, when that merge invalidates the evidence, or when the branch lacks its archive commit. Because the merge stays uncommitted until the coordinator integrates, a clean merge that invalidates the evidence is aborted like a conflicting one, and the returned branch keeps its old merge base. The worker reverts the archive commit without committing and commits that as `docs: restore the active <title> change to merge dev`, which restores the active change and the living specs from before the archive; merging `origin/dev` then leaves the living specs to `dev`, because the branch changes them only through the archive. One rule keeps the archive commit last on every handoff, also after a conflict outside the specs. A clean merge that keeps the evidence valid stays with the coordinator, including a regenerated dependency inventory staged with the merge.
6. **Reconciling restored deltas.** The pinned OpenSpec replaces a whole `MODIFIED` requirement block and checks only that no scenario name disappears, so a restored delta written against the old requirement silently undoes `dev`'s later edits to it. Before the checks and the review, the worker rewrites each delta whose requirement `dev` changed since `git merge-base <archive commit> origin/dev` from `dev`'s current text, keeping those edits; after re-archiving, the spec diff against the merge base shows only the task's own edits. `rearchive-demo.sh` in this change demonstrates both outcomes on a scratch repository, for a conflicting merge and for a clean merge in which `dev` edits the scenario of the same requirement; it also shows that after a committed merge `git merge-base HEAD dev` hides `dev`'s edit, while the merge base of the archive commit and `dev` shows it; `verification.md` records its run.
7. **Integration gate in the archived record.** Before the archive, `verification.md` is complete except for the archive's own checks; it names `Integration into dev by the coordinator (single pull request)` as a remaining gate. The worker writes the results of the checks of the archived working tree into the moved record and commits them in the archive commit, so the checked state is that commit's tree. The coordinator does not edit the archived record; the merge pull request records the integration checks, and its merge commit is the integrated revision.
8. **No active change at integration.** `npm run verify:archive` passes with no active change, as its requirement already states, so a branch that carries an archived change passes `make verify`; `validate --all --strict` covers active changes and living specs, not the archive. No script, hook, or CI job reads an active change at integration time. The coordinator checks that the branch carries the archived change.

## Risks / Trade-offs

- A delete-only push is not verified; it changes no commit on the remote, and the branch protection of `main` and `dev` blocks their deletion.
- The archive directory carries the date of the archive commit; a re-archive on a later day gets a new date.
- The archive commit is not independently reviewed; it is the pinned CLI's mechanical application of the reviewed deltas, checked by strict validation, `make verify`, and the spec diff. After a return, the reconciled deltas and the spec diff are reviewed.
- Reconciling deltas is manual; the spec diff check and the review are what catch a lost edit.
