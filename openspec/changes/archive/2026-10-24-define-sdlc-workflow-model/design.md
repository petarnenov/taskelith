## Context

The SDLC module owns workflow runs, stage transitions, artifact references, gate decisions, and framework bindings (architecture section 6). Framework plugins resolve native workflows and artifacts; the module must model them without naming OpenSpec, SpecKit, or any other framework (ADR 0003 decision 8). The [SDLC framework mapping](/docs/sdlc-framework-mapping.md) shows that OpenSpec's artifact dependencies form a graph without review gates, that SpecKit's bundled workflow is linear with two human gates, and that verification, review, and in SpecKit closure have no native operation in at least one framework. The shared kernel (`@taskelith/kernel`, item 2) supplies `Identifier<Kind>`, `parseIdentifier`, `Failure`, and `Result`.

## Goals / Non-Goals

Goals: an immutable, validated value model for workflow definitions, run bindings, work items, and artifact revisions that items 5 to 7 build on. Non-goals: transitions, gates, evidence, admission, the port, run aggregates, selection precedence, migration between frameworks, persistence, and generated identifiers.

## Decisions

- **Package.** `@taskelith/sdlc` follows the workspace package contract and depends only on `@taskelith/kernel`. Its `tsconfig.json` sets `types: []`, as the kernel does, because the domain uses no Node.js API. All code is in `src/domain/`; `application/` and `ports/` are added by the items that need them.
- **Parse, then trust.** Each constructor (`parseWorkflowDefinition`, `parseWorkflowRunBinding`, `parseWorkItem`, `parseArtifactRevision`, and the value parsers) takes plain text, as the kernel's `parseEventMetadata` does, and returns `Result`. Values are branded and deeply frozen, and arrays are copied, so a value cannot change after validation. Wire-level schema validation (ADR 0004 principle 6) is still required at HTTP, message, and plugin boundaries; these parsers enforce domain invariants and do not replace it.
- **Failures.** Every rejection is a kernel failure with code `invalid`. The composite constructors add a `field` detail naming the input path, for example `stages[1].dependsOn`, and start the message with that path; the single-value parsers (`parseContentDigest`, `parseNativeReference`, `parseLifecycleObligation`, `parseStageOrigin`), like the kernel's `parseIdentifier`, know no field and leave that to their caller. Graph problems use the field `stages` and name the stage, the dependency, or the uncovered obligations in further details. Parsing stops at the first problem, as the kernel's parsers do.
- **Obligations.** The six obligations follow architecture section 6: `intake`, `specification` (specification and planning), `implementation`, `review`, `verification`, and `closure`. They correspond to the board columns of [ADR 0008](/docs/decisions/0008-product-ui-and-integration-authority.md) decision 4 (Propose, Specify, Implement, Verify, Review, Archived). Acceptance and integration, a separate row in governance "Lifecycle and records", is the merge gate between Review and Archived in that decision, and release is a separately authorized stage; both are gates rather than workflow obligations here, for item 5 to model if needed. A stage covers one or more obligations, because native steps can combine them; each obligation must be covered by at least one stage, and several stages may cover the same obligation.
- **Origin.** Each stage is `native` or `platform-managed`, so that the UI can tell a framework feature from a gate or record the platform supplies for a gap.
- **Dependencies are acyclic.** `dependsOn` lists prerequisites, so a cycle could never start. Rework and clarification loops return to an earlier stage through transitions, which item 5 defines; they are not dependency edges. The cycle check is an iterative depth-first search, so that a long chain cannot exhaust the call stack, and reports the stages on the first cycle it finds. The obligation and origin lists are frozen, because the parsers read them at run time.
- **Versioning.** A workflow definition is identified by its `WorkflowId` and `WorkflowVersion`, both opaque identifiers whose format belongs to the framework; the domain never compares versions. A changed native workflow is a new version, never an edit.
- **Run binding.** The binding holds exactly the fields that architecture section 6 says to persist in a run; ADR 0008 decision 1 keeps that rule for every project, including Taskelith itself: a new default applies to new work only, and running work keeps its binding. It is a flat immutable value; selecting it (explicit choice, project default, installation default) and checking that the plugin supports the governance policy are application concerns for later items. The workflow digest identifies the exact native workflow or schema content the run was bound to.
- **Digests.** `ContentDigest` is `sha256:` followed by 64 lowercase hexadecimal characters, the only algorithm accepted until another is needed; a fixed, lowercase form makes equal content compare equal as text.
- **Native references.** A `NativeReference` is the plugin's own name or location of a work item or artifact, such as a change directory or a path at a commit. It is stored for display and traceability and never interpreted, so it allows spaces and non-ASCII text that an identifier rejects, up to 1024 UTF-16 code units without a character of the Unicode category `Cc`.
- **Work items and artifact revisions.** A work item pairs a stable `WorkItemId`, which the plugin maps from the native identity, with its native reference. An artifact revision holds the `ArtifactId`, the content digest, and the native reference; two revisions are the same when artifact and digest match, whatever location they were read from. The binding of revisions to work items, stages, and admissions belongs to items 5 and 7.

## Risks / Trade-offs

- The package was written against the kernel while item 2 was in review. The final kernel on `dev` changed only identifier message text, which the tests now take from the kernel.
- Stopping at the first problem means a plugin author fixes a workflow one problem at a time; collecting every problem can be added without changing the result shape.
- The obligation names are a platform vocabulary. Renaming or removing one later is a breaking change for stored definitions.
