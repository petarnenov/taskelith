## Context

The capacity reservation contract (item 6) states the reservation transaction, the release rules, delegation budgets, and the reasons; item 7 modeled assignments, reservations, and justified releases as pure transitions; item 11 added `PostgresDatabase.transaction`, which runs work at SERIALIZABLE and reruns it on a lost serialization race, and the assignment and task repositories. The transaction reads facts that no module persists yet: workers and their capacity (item 13 and the worker runtime, item 20), installation quarantine (item 13), quotas, parent links, and consumption charges.

Goals: the scheduler side of the contract, decided inside one SERIALIZABLE transaction per operation and tested against real PostgreSQL, including replica races and quota exhaustion. Non-goals: worker-side limits (item 20), recording observations and terminal facts (item 21), enrollment and capacity declarations (item 13), the scheduling loop that picks candidate workers and drives waiting tasks, provider credential selection (G3), and wire schemas (item 8; the command payloads are provisional).

## Decisions

1. **Pure decisions, transactional reads.** `decidePlacement` takes a `PlacementSnapshot`, which `readPlacementSnapshot` fills, (quarantine, the attempt's standing, the worker's standing and held occupancy, the request, the quota standings, the charge standing) and returns `fits` or the first failed reason in the contract's order: quarantine, attempt, request (a hard spend limit, then the per-attempt ceiling), worker (eligibility, hard controls, slots, CPU, memory), quotas (project, then each charged run), and consumption (tree attempts, then the retry allowance). The service fills the snapshot inside the transaction, so a count is never read outside it (contract section 4). `decideDelegation` does the same for delegation. Both are pure and tested without a database.
2. **Narrow read ports owned by Scheduling (coordinator, Q1 a).** `PlacementWorkers` (a worker's eligibility flags, capacity, controls, and the fleet's eligible slots), `InstallationGuard` (quarantine), `QuotaSettings` (project and run quotas with the operational targets' defaults), `TaskLineage` (parent links), and `CapacityLedger` (occupancy from held reservations, charges, delegations). Lineage, charges, delegations, and quotas are Scheduling's tables. The `workers` and `installation` tables hold only the columns placement reads; item 13 owns and extends them, Scheduling never writes them, and tests seed them directly. Every writer of a table the transaction reads runs at SERIALIZABLE; the contract's new section 13 records that obligation for items 13, 20, and 21.
3. **Operations inside the caller's transaction.** `placeInTransaction`, `cancelInTransaction`, `releaseInTransaction`, and `supersedeInTransaction` take a `CapacityTransaction`, so that the transaction recording a terminal fact (item 21) releases in it, as contract section 6 requires, and the creating transaction admits a delegation (`admitDelegation`). `ResourceAdmissionService` runs each as its own transaction for callers without one, and adds bounded retries.
4. **One unit of work port.** `CapacityStore.transaction` gives the work a `CapacityTransaction` with the assignment and task repositories, the outbox, the read ports, the ledger, and `now()`, the database clock at the start of the transaction (contract section 3). `PostgresDatabase` satisfies it structurally. The services are tested against PostgreSQL; there is no in-memory unit of work, because rolling back an in-memory store would be a second implementation of transactions that no production path uses.
5. **Reservation.** The request names the ownership generation the scheduler claimed for the placement, and a stale one fails with `conflict` (`stale-ownership-generation`), so an assignment never carries an older owner's generation; an automatic retry must name the earlier attempt that the active attempt retries. `reserve` reads the task and the attempt (active, uncancelled), whether the attempt holds a reservation, the lineage, the worker, the installation, the quotas the reservation charges (its project, its run, and its root's run, once when they are one), the charges, and the concurrency of each provider credential it holds (none in G2). An automatic retry needs an earlier attempt of the task that ended `not-started` or `exited` with a proven start and released its reservation (contract section 5); any other is uncertain. When the placement fits, it inserts the assignment with its held reservation, the attempt's charge if it has none, and the provisional `scheduling.assignment.offered` command, all in the transaction. An attempt's later reservation, after a refusal or a supersession, charges nothing (contract section 2). A waiting or rejecting reason writes nothing. `attempt-already-reserved` and `attempt-not-reservable` are standing reasons: the contract gives them no outcome, so they neither queue nor end the task's admission. Two replicas placing one attempt race on the held-reservation index or on serialization; the loser's rerun sees the held reservation, and a loser stopped by the held-reservation check has its `conflict` (which names the attempt) mapped, so either way it returns `attempt-already-reserved`; a `conflict` over an existing assignment identity is returned as it is. A task without lineage, or whose root has none, is `attempt-not-reservable`; another failure to read the task is returned as it is.
6. **Retries.** Lost serialization races are retried by the transaction itself (item 11, up to five attempts). `reserveWithRetry` retries a placement whose result is `unavailable`, except a commit of unknown outcome, which may already have placed the attempt, up to `PLACEMENT_RETRY_ATTEMPTS` (5) in all, waiting `placementBackoff`: a base that doubles from 5 s to 60 s, plus jitter of up to one more base below the 60 s cap, so that every delay stays within the contract's `[5s, 60s]`. The pause and the jitter draw are a `RetryTiming` given to the service's constructor, so tests replay a recorded seed.
7. **Release (D-B and section 6).** `cancelAssignment` reads the executions under the assignment: with none that can run, the assignment ends, releases, and writes `scheduling.assignment.ended`; with one `authorized` or `started`, it ends without releasing and, as an invalidating writer of launch authorization section 5, revokes that execution's grants with `attempt-not-launchable`, which also requests the attempt's cancellation, and writes `execution.attempt.cancel`. `releaseInTransaction`, which item 21 calls in the transaction that records a terminal fact, ends an active assignment whose attempt has ended (`attempt-ended`, contract section 6 condition 1), releasing and writing `scheduling.assignment.ended` when nothing under it can run, and releases an ended assignment once nothing under it can run (`execution-terminal`); tests record `not-started`, and an attempt's end, and release in the same transaction. Every release runs the invalidating read of launch authorization section 5 by assignment: the releasing transaction reads every execution under the assignment, and the domain transition releases only when none can run, so the read finds no grant to revoke. The one case that revokes, an operator reconciliation that resolves an execution as gone without a terminal fact, belongs to item 21.
8. **Bounded supersession.** The pure `isSupersessionDue` decides when; `supersede` ends an assignment that never received a grant when its worker is unknown, revoked, draining, or unreachable, when it stayed unacknowledged for `UNACKNOWLEDGED_SUPERSESSION_BOUND_MILLISECONDS` (2 min) since its reservation was created, or when its worker has reported admission pressure for `ADMISSION_PRESSURE_SUPERSESSION_BOUND_MILLISECONDS` (10 min); it releases and writes `scheduling.assignment.ended`. Otherwise it fails with `precondition-failed`, and a granted assignment is never superseded.
9. **Delegation admission (Q2 a, D-A, D-C).** `admitDelegation` runs in the transaction that creates the child. It first checks the parent's ownership generation that the delegating worker names, and that the delegating attempt is the parent task's active, uncancelled attempt and holds a reservation, as a running attempt does, since the parent comes from the delegating attempt and never from a request field alone (contract section 7). It reads the parent's chain to the root, then rejects a child deeper than 3 (`delegation-depth-exceeded`) and a chain larger than a quota it charges (`delegation-chain-exceeds-quota`, fail-closed, D-C): the chain holds one project unit per member, and in each run the child charges one unit per member that charges that run. It then counts the units waiting parents would hold afterwards, adding the parent's held reservation if it is not yet waiting, and admits only if a unit stays free in the project, the child's run, the root's run, and the fleet's eligible slots (D-A). Otherwise the result is `waiting` with `delegation-awaiting-capacity` until `DELEGATION_CAPACITY_WAIT_BOUND_MILLISECONDS` (10 min) after the caller's `waitingSince`, measured on the database clock, and then `rejected` with that reason. An admitted child gets its lineage link and an open delegation; item 21 closes it at the child's terminal outcome.
10. **Fair order.** `fairPlacementOrder` orders waiting placements round-robin across projects, oldest first within each, as the default of contract section 5; the scheduling loop that uses it belongs to a later item.
11. **Provisional values.** The new bounds and the backoff are recorded as provisional rows in `docs/operational-targets.md`, next to the retry budget, and in the capacity contract's section 13, besides the named constants.
12. **Fail-closed inputs.** An installation without its record is treated as quarantined; a worker without a record is not eligible; a hard spend limit is `spend-limit-not-enforceable`; each provider credential is checked against its default concurrency of 4, and no reservation holds one in G2.

## Risks / Trade-offs

- [Read ports without writers] Until items 13 and 20 write workers and the installation, only tests do. → The tables and the obligations are documented, and the fail-closed defaults admit nothing on missing records.
- [Count queries] Occupancy is counted from held reservations in every transaction. → Partial indexes on held reservations by worker, project, run, and root; counter rows remain an option the contract allows if counts become slow.
- [Delegation wait clock] The wait starts at the caller's `waitingSince`. → The caller records it with the delegation request; the bound is measured against the database clock.
