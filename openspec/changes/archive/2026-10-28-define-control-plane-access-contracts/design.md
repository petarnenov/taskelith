## Context

G3 item 9 ([G3 work plan](/docs/g3-plan.md), row 9) defines the G3 wire contracts. The coordinator and architect split it on 2026-10-28 into 9a (this change: login and sessions, project setup, workers and enrollment tokens, account slots, SCM integration setup, and the webhook receiver, in a new document), 9b (board, task, inbox, sessions, turns, and SSE in the same document), 9c (extensions of `execution.openapi.json`), and 9d (AsyncAPI worker messages and the terminal). The architect decided the security schemes on 2026-10-28: a browser session cookie (`apiKey` in a cookie, `HttpOnly`, `Secure`, `SameSite=Strict`) with a CSRF header on every mutation, the existing `operatorToken` bearer kept for the CLI and the owner, and only the schemes and their error responses defined here; item 10 implements them.

Inputs read at `dev` `9196804b`: [ADR 0004](/docs/decisions/0004-first-class-engineering-principles.md) principle 6; [architecture section 11](/docs/architecture.md#11-spa-authentication-and-live-traffic); the [trust model](/docs/trust-model.md) sections 1, 3, and 4; G3 plan rows 9 to 12, 20, 26, 33, 34, and 44 and decisions D2, D10, and D11; [ADR 0015](/docs/decisions/0015-g2-closure.md) decision 5; the contracts [installation and enrollment](/docs/contracts/installation-and-enrollment.md), [worker admission](/docs/contracts/worker-admission.md), [account pool](/docs/contracts/account-pool.md), [source control](/docs/contracts/source-control.md), [product ports](/docs/contracts/product-ports.md), and [execution wire contracts](/docs/contracts/execution-wire-contracts.md); the documents and tests of `@taskelith/contracts`; `scripts/generate-contracts.ts` and `scripts/check-contract-compatibility.ts`; and the archived `define-execution-wire-contracts` and `define-sdlc-wire-contracts` changes as models.

## Goals / Non-Goals

**Goals:** the document, its schemes and failures, the operations of 9a with their roles, the generator's security scheme check, contract tests, the contract page, and the spec.

**Non-Goals:** adapters, handlers, routes, and persistence (items 10 to 15, 20); the 9b to 9d operations and messages; principal administration (item 10); any change to the existing documents, whose versions therefore stay.

## Decisions

Where a source is silent, the change takes the minimal shape and records it here with the source it relies on.

1. **One new document.** `control-plane.openapi.json` holds 9a and later 9b, because both serve the SPA on the browser endpoint ([installation contract](/docs/contracts/installation-and-enrollment.md) section 7) with the same schemes; it shares no path with the other documents, which the generator would refuse. It reuses `Failure`, `Identifier`, `Instant`, `DisplayText`, `Generation`, `Platform`, and `Architecture` of `execution.openapi.json` and `SelfCheckResult`, `SelfCheckId`, and `NotApplicableReason` of `execution.asyncapi.json` byte for byte, as the generator requires (`scripts/generate-contracts.ts`, `mergeSchemas`).
2. **Security scheme check.** `mergeSecuritySchemes` gives security schemes the rule that `mergeSchemas` gives schemas, through one `mergeComponents`, and `mergeOpenapi` uses it in place of `Object.assign`. The requirement goes into `sdlc-wire-contracts` "Generated types", which already holds the generator's path rule, not into `contract-tooling`, whose requirements cover the tool evaluation only (`openspec/specs/contract-tooling/spec.md`).
3. **Pre-login session.** Architecture section 11 requires CSRF protection for mutations and the architect's decision requires the header on every mutation, so login needs a token before any login. `readSession` therefore starts an anonymous server-side session with a CSRF token when none is presented, and `logIn` gives the session a new identifier and token, so a fixed session identifier is worthless. Source: architecture section 11; the alternative, a login without CSRF, would break the "every mutation" rule.
4. **Cookie name.** `__Host-taskelith-session`: the `__Host-` prefix makes a browser refuse the cookie without `Secure` and `Path=/` or with `Domain`, which enforces the decided attributes on the client too. `HttpOnly` and `SameSite=Strict` are stated in the scheme description, because OpenAPI has no field for them. The CSRF header is `X-CSRF-Token`.
5. **Operator bearer.** `operatorToken` is accepted on every operation except the session operations and the webhook receiver. It authenticates the principal that item 10 creates from the G2 bootstrap credential, the first `installation-owner` (G3 plan row 10); authorization then checks that principal's roles like any other's. A bearer request needs no CSRF token, because a browser never adds a bearer by itself. The scheme is the other documents' definition, unchanged (decision 2).
6. **Failure bodies.** Every failure is the kernel `Failure` shape. As `enrollWorker` answers 401 with code `forbidden` and a reason (`execution.openapi.json`; installation contract section 5), 401 is `AuthenticationFailure` (`unauthenticated` or `login-failed`) and 403 is `AccessDenial` (`role-required`) or `CsrfRejection` (`csrf-token-invalid`). Each is a full object schema that fixes the code and the reason, so a body matches exactly one; a mutation's 403 is `oneOf` the two 403 schemas, because one status can have only one response.
7. **Members.** The trust model gives `installation-owner` the management of operator principals and `project-maintainer` the project defaults and integrations, not membership (section 3). Assigning and removing project roles is therefore an `installation-owner` command, a project has no member until one is assigned, and creating a project gives its creator no role. A principal has one role per project. An assignment names no revision and replaces the principal's role, so of two concurrent assignments the one serialized last stays. This is an explicit exception to [product ports](/docs/contracts/product-ports.md) section 2, rule 7, under which the same natural key with other input fails with `conflict`: only an `installation-owner`, who holds every installation authority, assigns, and the role it sends is the whole state of the membership, so a reassignment is a deliberate replacement rather than a repeat. No source requires a compare-and-set here; a later change can add a membership revision without breaking clients that send none.
8. **Project reads.** A `project-viewer` or above reads its project ([product ports](/docs/contracts/product-ports.md) section 2, rule 1); an `installation-owner`, who creates projects (trust model section 3), also reads every project, since otherwise the creator could not see a project before assigning members. `listProjects` returns the caller's projects. Renaming is a `project-maintainer` command, as the other project settings are.
9. **Defaults.** G3 plan row 11 names framework, auto-merge, implementer, reviewer, and spec approval policy; the [account pool contract](/docs/contracts/account-pool.md) section 4.1 takes the harnesses a task may use, in the project's order of preference, and the policy for no eligible slot from the project's defaults. The defaults are therefore the framework plugin (`pluginId`; the version is fixed at run binding, product ports section 3.3 `framework`), `implementers` (ordered, the first the default implementer, the rest the after-limit order of section 4.4), `reviewer`, `specApprover` (`SPEC_APPROVERS`), and `noEligibleSlot` (`wait` or `reject`, section 4.5). A project is created with them, because a project without harnesses could run nothing. The project's policy revision is left out: making a new one current is a writer with auto-merge rule obligations (product ports section 5) that a later change defines.
10. **Auto-merge.** Its own resource with its own revision, as the `AutoMergeSettings` port keeps it (product ports section 6.2), rather than a field of the defaults, although plan row 11 lists it among them.
11. **Repository binding.** One repository per project, of one SCM integration, with the integration branch (product ports section 6.3) and the merge method ([source control contract](/docs/contracts/source-control.md) section 4); the repository is an opaque external identifier of at most 1024 characters (section 2, rule 3). The binding also holds the repository's HTTPS remote URL without user information, query, or fragment, because a workspace prepare takes the repository identifier, its remote URL, and the base branch from the project's binding ([git workspace contract](/docs/contracts/git-workspace.md) section 3), the remote must be HTTPS without user information (section 7, `checkRemoteTransport`), and the SCM port has no operation that resolves a URL from the opaque identifier; the integration branch is that base branch. Its schema bounds it at 2048 characters, a request bound. A branch is any name that `git check-ref-format --branch` accepts, non-ASCII included; Git sets no length limit, so 1024 characters only bound the request, as for the repository. A first binding has no expected revision, a change needs one. A remote URL outside the integration's allowed origin is refused with 422 (decision 21). A merge method that the integration's plugin does not declare in its `SourceControlCapabilities` is refused with 422 `precondition-failed`, because every merge with it would fail with `unavailable` (source control contract section 2, rule 5, and section 4); no port operation checks that the plugin can reach the repository, so the binding does not. Plan row 11 says "the repository binding" in the singular; several repositories per project can come later as a new operation.
12. **Enrollment tokens.** The brief asks to issue, rotate, and revoke enrollment tokens; today only `issue-enrollment-token` exists, and tokens are stored by hash without an identifier (`packages/modules/fleet/src/domain/enrollment.ts`). The minimal shape adds a minted `tokenId`, lists pending tokens, defines rotation as revoking a pending token and issuing a new one with its constraints in one transaction, and revocation of a pending token; both serialize with a redemption on the token's row lock, as redemptions already do (installation contract section 5, "Atomicity"). Revocation adds a stored state that check 1 of that section does not list, so a redemption treats a revoked token as `token-invalid`, like an unknown, used, or expired one; item 26, sub-change 26c (26b landed before 9a defined revocation), which owns the enrollment endpoint where redemption happens, owes that refusal (architect, 2026-10-28). Revoking a revoked or expired token answers 204, because neither can be redeemed; a used token answers 422 `token-used`; a token that a rotation replaced answers 422 `token-rotated` naming the replacement, because the replacement stays redeemable and a 204 would tell the owner that the token it meant to stop is stopped. The secret is revealed only in the 201 of issue and rotation. Worker credential rotation and worker revocation (`rotate-worker`, `revoke-worker`, installation contract section 4) stay administrative commands: a rotated generation's secrets belong to the worker, and G3 item 26 delivers them to it, so a browser response must not carry them.
13. **Account slots.** The operations map the account pool commands one to one (sections 2, 3.1, 7.1, 8, and 8.1): add with the write-only credential, change allowed projects or concurrency limit, revoke, reinstate, rotate the credential, and remove; each names the expected revision (section 2, rule 3). Removal is `POST .../removal` with a body rather than `DELETE`, because it needs the expected revision. `listProjectAccountSlots` meets section 2, rule 1's requirement on item 9: a project member sees the active slots of its pools with `sharedWithOtherProjects`, never other projects' names. The usage window length per harness and the default cooldown are installation settings that no 9a operation changes.
14. **SCM integrations.** Installation-wide, because the GitHub plugin uses "the installation's GitHub App" (G3 plan row 20), and an `installation-owner` command, who manages installation settings (trust model section 3). Settings and secrets are plugin-defined maps, so the core document names no SCM (source control contract section 2, rule 1); secrets are write-only and only their names are returned. An integration also holds the allowed origin of its remote URLs, a core field rather than a plugin setting, because the control plane compares it (decision 21). Any authenticated principal may read the integrations, which hold no secret, because a `project-maintainer` chooses one to bind a repository.
15. **Webhook receiver.** One receiver path per integration, so the control plane knows which plugin verifies the delivery; no security requirement, a raw body of any media type, verification by the plugin over the exact bytes with lower-cased headers (source control contract section 6). The plugin names its headers, so the document declares none. An unknown integration, an identifier that is not an `Identifier` included, and a failed verification answer the same 401 with its own fixed schema, `WebhookRejection` (`signature-invalid`), the one exception to decision 6's `AuthenticationFailure`, because the receiver has no session or bearer to name; a verified payload that the plugin cannot parse answers 400 `invalid` (source control contract section 2, rule 5) and is not recorded; a verified delivery and a repeat answer 202, the repeat deduplicated by `deliveryId`; 413 marks a body over the receiver's limit, which item 20 sets.
16. **Minted identifiers.** New identifiers are minted as `workerId` is (installation contract section 2): one lowercase letter (`p` project, `u` principal, `e` enrollment token, `s` slot, `i` SCM integration) and 32 hexadecimal digits from 128 random bits, a safe name. The wire type stays the kernel `Identifier`, so identifiers minted elsewhere still fit.
17. **Pages.** Lists return at most 100 items in identifier order, the code-unit order of [account pool contract](/docs/contracts/account-pool.md) section 2, rule 2, with a `next` identifier for `after`, as `listQuarantine` pages with `next` in `execution.openapi.json`. The workers view is one snapshot, as `WorkerAdmissionView.workers()` returns it (worker admission section 8).
18. **No caching.** A response with the token's secret or a CSRF token sends `Cache-Control: no-store`; no source requires it, but without it an intermediary or the browser cache could keep a secret.
19. **Login name and password.** A login name is 1-64 lowercase letters, digits, `.`, `_`, or `-`, starting with a letter or digit; a password is 1-1024 characters and write-only. G3 decision D2 (a) fixes password login; item 10 sets the password policy and hashing.
20. **Request logs.** `@taskelith/secrets` redacts known shapes and a run's revealed credentials only (installation contract section 8), and the session identifier, the CSRF token, a password, a slot credential, and SCM secrets have no such shape. A request log therefore holds only an allowlist of request parts and never a request body that reaches a `writeOnly` schema or the `Cookie`, `X-CSRF-Token`, or `Authorization` header; what it holds is still redacted with the library. The alternative, prefixes on the session identifier and the CSRF token, would still leave the request bodies.

21. **Remote origin.** Review pass 2 finding H1: a `project-maintainer` could bind any remote URL, and the [git workspace contract](/docs/contracts/git-workspace.md) section 7 sends the run's SCM credential to exactly that URL. Option (c) was decided (architect, 2026-10-28): apply (a) now and record (b) as a follow-up.
    - (a), applied: each SCM integration holds an allowed origin, the scheme https, a host, and an optional port, which only an `installation-owner` sets. Origins are compared after normalization: https only, the host in lower case, and the port explicit, 443 by default. `bindRepository` refuses with 422 `BindingRefusal` a remote URL that is not HTTPS (`remote-not-https`), holds user information (`remote-userinfo`), a query (`remote-query`), or a fragment (`remote-fragment`), or whose origin differs (`remote-origin-mismatch`). The bound URL schema `RemoteUrl` refuses the same forms, and the request takes the wider `RemoteUrlCandidate`, so that these refusals reach the typed 422. The allowed origin itself is a strict schema, so a malformed one is a 400. Its host is a host name, not an IPv6 literal, which has no single lower-case form to compare, and its port is 1 to 65535.
    - Defense in depth: every time the control plane issues or re-delivers a per-run SCM credential, a 9c re-delivery included, it re-checks the binding's remote URL against the integration's current origin; on a mismatch it issues no credential and records the reason `remote-origin-mismatch`, so narrowing an origin later covers existing bindings.
    - Worker obligation, not in 9a's schemas: the worker sends the credential only to the remote URL that the control plane sent with the run (git workspace contract section 7); items 16c and 16e owe it.
    - (b), follow-up: item 7's SCM port gains an operation that derives the remote URL from the repository, which item 20 implements; `remoteUrl` then becomes output-only.

## Fail-before

On `9196804b`, `mergeOpenapi` of two documents that define `operatorToken` as `bearer` and as `basic` returned `{"operatorToken":{"type":"http","scheme":"basic"}}` without an error; with this change it fails with "The security scheme operatorToken of b.json differs from the one of a.json".

## Risks / Trade-offs

- The CSRF and cookie attributes are prose in the scheme descriptions; item 10's tests must check the real headers.
- The operator bearer reaches project operations only through roles item 10 assigns to its principal; until then the CLI can do only installation-scoped operations.
- `oneOf` in a mutation's 403 response is exact only while the two reasons differ; a later reason added to one schema must not be added to the other.
