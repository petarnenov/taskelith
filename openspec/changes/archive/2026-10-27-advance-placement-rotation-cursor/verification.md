## Author self-check

- **Cursor rule (after the pass 2 fixes).** After a pass, `#after` moves only by the offers made before the pass's first decline for lack of fleet capacity, even when a later offer is placed: to the project of the last of them that placed its task, else of the last of them, else it is unchanged (empty read, no candidate worker, an outage at the first offer, or a full fleet at the first offer). An offer is a placement transaction that ended without an outage (`placed`, `ended`, `backing-off`, declined, or not waiting); a decline for lack of fleet capacity has the reason `quarantined`, `worker-not-eligible`, `worker-capacity-exhausted`, or `no-candidate` (`FLEET_REASONS`, with `NO_CANDIDATE_REASON`, and `lacksFleetCapacity` in `domain/capacity-reasons.ts`, which the service uses too). An outage stops the pass and the cursor still moves by the offers before it; the failed task is not counted. `control-not-enforceable` is a worker reason but the task's own requirement, so it counts as a decline and such a task cannot pin the cursor.
- **Outcome shapes checked (H1).** `PlacementWorkers.candidates()` returns every eligible worker, full ones included (`ports/placement-workers.ts:31`, `adapters/in-memory-capacity.ts:50`), so a full fleet keeps `anyCandidate` true; `placeTask` returns `precondition-failed` with `details.reason` set to the last candidate's reason, which for a full fleet is `worker-capacity-exhausted` after `triesNextCandidate` tried every candidate, and `quarantined` breaks at the first candidate.
- **Why not keep the cursor when nothing was placed.** Projects with no capacity-eligible task would hold the rotation: with 1200 blocked older projects, every read would return the same first 100, and the "Many blocked projects" test would fail. Moving to the last offer skips only projects that were offered and declined, so such a pass jumps past its whole read, as the code did before.
- **Why keep it without a candidate.** No transaction is opened and no project is offered capacity, so none loses its turn.
- **Section 12.** A pass that places moves the cursor past the last project served; one that places nothing moves it past every project it offered before the fleet ran out of capacity; while the fleet is full, the cursor stays, and a slot freed later in the pass does not move it past the projects that waited. A project declined because the capacity ran out is offered first in the next pass that reads its task, subject to its task's placement backoff (limitations); a blocked project is offered again and declined, costing a transaction, not capacity. The 1200-project test passes unchanged.
- **Boundaries.** The rule is a small domain class with no I/O; `RotationCursor` takes one exclusive event per offer (`placed`, `declined`, or `ranOutOfCapacity`), in offer order; the events after the first `ranOutOfCapacity()` do not move it; the service's `#offer(order, after)` builds it and returns `outcome`, the count or the outage, with `next`, which `#placeDue` stores. The service offers in `fairWaitingOrder(waiting, after)` (entries carry the project id); `fairPlacementOrder` keeps its conformance callers. The no-candidate path settles every task with `NO_CANDIDATE` as before, without the loop. `npm run check:boundaries` passed.
- **Queues unchanged.** Both queues already start after the cursor they are given; the PostgreSQL query is untouched.

"Waiting placements" now names the rotation cursor instead of the previous read's project (text and two scenarios, same names); "Project rotation" states the cursor rule, including that it moves only by the offers before its first decline for lack of fleet capacity and that an offer the store failed does not count (481 characters; "Waiting placements" 459), and adds the scenarios "One free slot", "Full fleet between placements", "Capacity freed during a pass", "Several placements in a pass", "No candidate worker", and "Outage during a pass".

## Limitations

- The service tests use an in-memory queue and a scripted transaction that declines with `worker-capacity-exhausted` when no slot is free; the PostgreSQL queue is unchanged and covered by its existing conformance cases, which take the cursor as an argument. The fleet reasons are classified from `placeTask`'s failure details, not by an end-to-end test against the PostgreSQL reservation transaction.
- The M1 and L1 red runs used temporary mutants, because those tests pass on the code they guard.
- The per-task placement backoff after a decline for lack of fleet capacity (contract section 5) can keep the project that waited out of the read when a slot frees, while another project's task is due; under jitter the rotation then degrades towards a share proportional to the waiting tasks. The tests move the clock a minute per pass, past every backoff, and do not show this. Not a regression; deferred to `placement-backoff-preserves-rotation` (review pass 2, M1).
- The fleet capacity check sees only the last candidate's reason; with hard controls, `control-not-enforceable` on the last candidate can hide a full worker (review pass 2, L4). G2 requests no hard control.
- The cut-off keeps the cursor while slots freed during a pass go to later projects of the same read; if every pass started with a full fleet and slots freed only during passes (for example with a second scheduler replica), a project behind 100 deep backlogs would never be read, weakening section 12 (review pass 3, L2). Timing-dependent and not reachable in the single-replica tests. Input to `placement-backoff-preserves-rotation`, with the candidate fix of ending the pass at the first decline for lack of fleet capacity (design, Risks).
- The L3 red run is the committed test on the code of `a5f56a02`; the L6 tests pass on that code and their red runs used temporary mutants.
- The bounded-pass argument for mixed backlogs is reasoned in the design; the tests cover blocked projects (1200), one and two slots per pass, no candidate, and an outage.

## Follow-ups (out of scope)

- `#after` lives only in the placement service's memory and resets when the control plane restarts; a follow-up for `close-g2`.
