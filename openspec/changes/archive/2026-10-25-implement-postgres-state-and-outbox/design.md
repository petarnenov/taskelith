## Context

G2 item 11 provides durable state for the control plane. Item 7 defined the execution and scheduling domains without ports; G1 defined `AdmissionRepository` and its in-memory adapter. The contracts of items 3 and 6 need SERIALIZABLE transactions that read compared values and write state and outbox records together, retried as a whole on a serialization failure. The coordinator decided the open questions on 2026-10-25: a minimal workflow run record with gates stored per run (Q1 a), and an `Outbox` port declared by each writing module with the `Inbox` on the consuming side (Q2).

Goals: module ports with shared conformance suites that the in-memory and the PostgreSQL adapters both pass; versioned migrations with a checksum check; a transaction primitive that items 16 to 18 can write their use cases in; an atomic outbox and an inbox with named crash points; integration tests against the real PostgreSQL. Non-goals: the publisher and broker (item 12), the launch authority and resource admission (items 17 and 18), application services, observability (item 22), and read models for listing or scheduling queries beyond those the ports need.

## Decisions

1. **Ports stay in their modules.** `WorkflowRunRepository`, `GateRepository`, and an `Outbox` in SDLC; `TaskRepository`, an `Outbox`, and `Inbox` in Execution; `AssignmentRepository` and an `Outbox` in Scheduling. The three `Outbox` ports are structurally identical, so one adapter implements all of them, and no module depends on another for it; SDLC must not depend on Execution. The `Inbox` belongs to the consuming side, which is Execution for observations; another consumer adds its own. Item 12 adds the publisher port on top of the relay.
2. **A minimal workflow run.** `WorkflowRun` is the existing `RunContext` (binding and progress) with an identifier, `WorkflowRunId = Identifier<'RunId'>`, the same kind as Scheduling's `RunId`, so a reservation scope names it. It lives in SDLC because the kernel declares no module identifier kinds. `beginWorkflowRun` rejects a binding to another workflow or version than the definition. A run is compared on `progress.generation`, which every stage transition raises. Gates keep no run field; the gate repository stores the run beside each gate, set once by `add`.
3. **Conformance suites at the ports.** Each module exports cases (`ConformanceCase<Port>`: a name and a `check` that returns problems), built from fixed inputs through the domain's own constructors. They need no test runner, as the SDLC framework conformance suite before them, because module packages compile without Node types. Every suite checks round trips, `not-found` and `conflict` codes, compare-and-set with the record kept after a rejected write, and two concurrent writes at one generation of which exactly one wins, the other being a `conflict`, with the winner's record stored. A replacement must carry the generation after the expected one (`checkNextGeneration`): checked after existence and the stored generation, so that G1's codes stay as they were, it fails with `invalid` for an unchanged or older generation, which would otherwise let a stale snapshot be written back. Every domain transition raises the generation by exactly one. Comparison treats a field set to `undefined` as absent, as an optional field, compares numbers exactly, and compares arrays index by index, holes included. Races use two distinct candidates at one generation, and the stored record must be the winner's; of two competing adds the loser's record must not exist. The in-memory adapters check and write without awaiting between the two, which the concurrency case requires; `InMemoryAdmissionRepository.replace` awaited, so two concurrent writes could both pass, and it is fixed.
4. **One row per aggregate, JSON records.** Each table holds the identifier, the generation that compare-and-set compares (`UPDATE ... WHERE id = $1 AND generation = $2`) as a `bigint`, which holds the domain's safe-integer range, the query columns the ports need (admission state and artifact identifiers, a gate's run, a task's admission, an assignment's attempt, worker, and reservation state), and the record as JSON text. `jsonb` would reject strings that the domain and JSON payloads accept, such as NUL or an unpaired surrogate, which `JSON.stringify` writes as escapes; records are never queried inside, so text loses nothing. A task row holds the task with its attempts, executions, and grants, guarded by one generation, as item 7 allowed. Records are read back as frozen plain data; launch parameters, the one class in the records, are rebuilt through `parseLaunchParameters`, and a stored grant that fails to parse is a defect. The adapter does not otherwise re-validate its own rows: only it writes them, and a later format change is a migration.
5. **Uniqueness without aborting.** Inserts use `ON CONFLICT DO NOTHING` and then tell an existing identifier (`conflict`) from another unique constraint, so a duplicate does not abort the surrounding transaction. One held reservation per attempt is a partial unique index (capacity contract section 4). The assignment repository checks it before writing, after existence and the stored and next generations, in the in-memory adapter's order, so that a call inside a transaction gets the same result as the in-memory adapter; a concurrent writer that still breaks the index raises SQLSTATE 23505, which the transaction reports as `conflict`.
6. **The transaction primitive.** `PostgresDatabase.transaction(work)` runs the work in `BEGIN ISOLATION LEVEL SERIALIZABLE` on one pooled connection. The work receives a `PostgresTransaction` with every repository and the outbox and inbox; an `Err` rolls back and is returned. A serialization failure or deadlock (40001, 40P01) reruns the whole work, at most `SERIALIZATION_ATTEMPTS` (5) times in all, waiting `SERIALIZATION_BACKOFF_MILLISECONDS` (10) doubled per retry, and then returns `unavailable`; the work is rerun with the same inputs, so a command keeps its identity. A lost connection returns `unavailable`; one lost during COMMIT returns `unavailable` with `outcome: unknown` and is not retried, because the commit may have happened. A COMMIT that the server answers with `ROLLBACK`, because the work caught a failed statement and returned `Ok`, returns `internal` with `outcome: rolled-back` and reaches no `.after` crash point. A rollback that is not confirmed destroys the connection instead of returning it to the pool. Only a server error carries an SQLSTATE; a socket error code such as `EPIPE` is a lost connection. Any other exception, including a failed statement that is none of these, is a defect: the transaction rolls back and the exception propagates. Neither contract needs row locks; ordering relies on SSI, as they state. Committing facades (`CommittingAdmissionRepository` and the others) run each port call as its own transaction, for callers without a unit of work.
7. **Outbox and inbox.** One `outbox` table serves every module: an identity column gives append order, the event identity is unique, and `published_at` marks a sent message. Append order is not commit order: of two concurrent transactions the later appender can commit first. The relay selects by `published_at IS NULL`, not by a cursor, so a message that commits late is still read; no global order across transactions is promised, and item 12 decides any per-subject order. Payloads are JSON objects (`JsonObject`), and both adapters reject a payload that JSON cannot carry unchanged, such as `NaN`, `-0`, `undefined`, a `Date`, an array with holes, or a cycle, with `invalid`; strings with NUL or unpaired surrogates are carried. The relay reads unpublished messages in append order and marks them; marking twice is harmless, since a publisher may resend before it marks. The `inbox` table's key is consumer and message identity; `accept` returns `duplicate` for a repeat, and the consumer applies the message in the same transaction.
8. **Crash points.** The adapter names `OutboxCommit` and `InboxCommit`, each `.before` and `.after` the COMMIT of a transaction that appended to the outbox or accepted an inbox entry, and `OutboxPublish` around marking a message published. The hook is structural (`reach(point)`), so tests pass the harness's `CrashPoints`; production passes `NO_CRASH_POINTS`, which the adapter defines, since product code cannot import the harness.
9. **Migrations and checksums.** Migrations are SQL files under `migrations/`, run by node-pg-migrate's `runner` with one transaction per file and order checking, under the adapter's own advisory lock held across the whole run. Because node-pg-migrate records only names, the adapter keeps `schema_migration_checksums` (name and SHA-256). Before applying anything it fails with `precondition-failed` when an applied migration's file is missing, its checksum differs, or it has no checksum; then it records the checksums of all pending files, replacing those of files that never applied, and only then runs them. A file applied by a run that fails later therefore has its checksum, and a pending file fixed after a failure is checked by its new content.
10. **Tests against the real database.** Test files that partition the shared Toxiproxy hold `acquireProcessLock`, a lock across test processes that the harness adds, named after the Toxiproxy port, so that one file's partition or reset never reaches another's. The lock is an exclusive listen on a loopback port derived from its name: taking it is atomic, and the operating system frees it when a holder dies, so no stale lock needs to be taken over. Integration tests create a database per test file (files run in parallel), migrate it, and drop it at the end. They run every conformance suite against the committing facades, the transaction cases (atomic placement, rollback on `Err`, each crash point with a thrown crash, a forced serialization conflict between two real transactions held at a barrier, retry exhaustion, the unique-index conflict, a defect), a `SIGKILL` of a child process before and after the outbox commit (R05), and connection loss through the Toxiproxy route: a disconnected route, a connection lost during the work, a black-holed rollback, and a black-holed COMMIT. The serialization tests are a write skew: each writer reads both rows and inserts one, which SERIALIZABLE must break. Barriers, child processes, and the lock have deadlines, and a child killed at its deadline fails the test instead of passing as a crash.

## Risks / Trade-offs

- [JSON records] Querying inside records needs a migration that adds a column. → The ports name their query columns; items 17, 18, and 21 add columns and indexes for the predicates of the invalidating writers.
- [Unknown commit outcome] A caller cannot tell whether a lost COMMIT applied. → The result says so, and the command identity and the inbox make a rerun idempotent.
- [Retry bound] Heavy contention can exhaust five attempts. → The result is `unavailable`, which callers retry later; the bound is a named constant.
