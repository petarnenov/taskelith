## Decisions

Where a source is silent, the change takes the minimal shape and records it here with the source it relies on.

1. **Protocol version 2 and the build.** The messages require `SessionProtocolVersion`, at least 2, because execution wire contracts section 3 requires the next version for anything a version 1 worker cannot execute, and a version 1 worker then fails closed on them through `VersionedCommand`. `SESSION_PROTOCOL_VERSION` is exported for items 13 and 18. `EXECUTION_PROTOCOL_VERSION` and `SUPPORTED_PROTOCOL_VERSIONS` stay 1: raising them now would make the worker declare a version it cannot execute, which `AGENTS.md` ("keep bootstrap status honest") forbids; items 18 and 13 raise them. For the same reason the NATS adapter's schema tables gain no session message; its test `the schema tables cover every protocol version 1 message of the execution channels` leaves out the schemas that require `SessionProtocolVersion`, and item 13 adds them.
2. **Three session commands.** Turn delivery, response delivery, and delegation result delivery are separate commands, because 9c's contract page section 9 obliges 9d to reuse `DelegationResult`, `DelegationResultOutcome`, and `DelegationSummary` unchanged, and the timeline's `NativeAnswer` carries a delegation result in another shape. The response command therefore admits no `delegation-result` answer and no `host` responder, and a standing rule only with a permission answer ([product ports](/docs/contracts/product-ports.md) section 5); the delegation command admits only an `ended` result.
3. **Approvers.** The response command names `Responder`, the timeline's union of principal, standing rule, and host, unchanged from 9b. A council decision ([ADR 0014](/docs/decisions/0014-decision-council-and-delegated-approval.md)) is a later variant in a later protocol version, which keeps runtime approval behind an approver as [ADR 0013](/docs/decisions/0013-intents-campaigns-and-proposal-graphs.md) "Forward-compatibility obligations" requires.
4. **Serialized turns.** The control plane sends a turn only when `nextDeliverableTurn` returns it, so serialization stays in one place, the timeline (session timeline section 4.2). The command names the generation it is sent for, because `deliverTurn` fails for a turn delivered in a generation that no longer runs; the worker reports `session.turn.not-delivered` then, or on a port refusal that proves non-acceptance, and `session.turn.acceptance-unknown` when it cannot tell ("Architect answer on pass 1 finding 3"), so every command has an outcome observation, as every G2 command does (worker journal W1).
5. **Command identity.** One `commandId` per turn and generation, and per consumed response, minted by the control plane, stored with the record, and reused on a resend, so that the worker's inbox makes the resend idempotent. A derived identifier could exceed the 128 characters of `Identifier`, since a `TurnId` alone may have 128.
6. **Notice and adoption.** The notice carries exactly the run, the credential, and the version, the parameters of `fetchRunScmCredential` (9c's contract page section 9, "G3 sub-change 9d"). One notice per attempt of the run that a version 2 worker holds, because the fetch names the attempt. Adoption follows source control section 3 and G3 plan rows 18 and 21; `not-adopted` gives the control plane a reason when the worker keeps its version: a refused fetch, a later version adopted first, or an attempt no longer held. No source names these cases; they are the outcomes a fetch can have.
7. **Observations.** One observation per host report that session timeline section 1 lists: generation start and end, turn delivery and outcome, requests, output, limit signals, and delivery reports. Each identity derives from its source, as execution wire contracts section 5 requires; output and limit signals, which have no identity in the port, are numbered per generation. Text is redacted by value on the worker (account pool section 7.4) and again by the control plane before it is recorded (control-plane section 7).
8. **The terminal upgrade path.** `GET /projects/{projectId}/agent-sessions/{sessionId}/terminal` in the control-plane document, under the session it belongs to, as 9b's session operations are. The query names the attempt, its ownership generation, and the session generation the caller read, a compare-and-set that answers 422 `attempt-not-current`, so a terminal never attaches to an attempt the caller did not see; there is no revision, so no 409.
9. **CSRF on a WebSocket.** Architecture section 11 requires CSRF protection for mutations, and terminal input is one, but a browser cannot set the `X-CSRF-Token` header on a WebSocket handshake. The upgrade therefore checks the `Origin` of a cookie upgrade and answers a foreign one with 9a's `CsrfRejection`, and the first frame carries the session's `CsrfToken`. A token in the URL was rejected, because control-plane section 7 logs query parameters.
10. **Role.** `project-operator` or above, because the trust model section 3 gives that role "interact with sessions/turns", and an `installation-owner` needs a project role, as for `submitTurn`. The role is checked before the session is read, so a principal without it gets 403 `role-required` whether the session exists or not (control-plane section 2).
11. **One terminal per attempt, one client.** No source fixes the count; one terminal and one attached client bound the resources that G3 plan row 39 requires bounded, and a new attach supersedes the old one so that a lost browser never locks the terminal. Closing the client ends neither the execution (architecture section 11) nor the terminal, so item 40 can reattach; an idle timeout, which item 39 sets, ends a terminal nobody attaches to.
12. **The relay.** One outbound WebSocket per worker, multiplexed by `terminalId`, because architecture section 8 draws one "Outbound relay connection" per worker and G3 plan row 39 relays "over the worker's outbound connection". Its upgrade, `openWorkerRelay`, is in `execution.openapi.json`, because worker-facing operations stay there (architect decision 1). It never uses the broker, so terminal traffic never blocks a command or a cancellation and terminal text is never at rest in a stream.
13. **No address on the terminal channels.** The AsyncAPI channels have `address: null` and name their upgrading operation, so no path appears in two documents.
14. **Bounds and close codes.** Input frames hold at most 4,096 characters and output frames 65,536, the bound of session text (`MAX_HARNESS_TEXT_LENGTH`); columns and rows 1 to 1,000. The relay buffer is the operational targets' `10 MiB` per active attempt. Close codes 4400 to 4503 lie in the private range 4000 to 4999 of RFC 6455; their reason text is `TerminalCloseReason`. Item 39 sets the rate limit, the attach timeout, and the idle timeout.
15. **Versions and breaking changes.** `execution.asyncapi.json` 0.8.0: the asyncapi diff lists its 110 additions (messages, schemas, `ClassifiedOperation` since review pass 1, the turn acceptance unknown message and schemas since the architect's answer on finding 3, operation entries, and the offer's `session`, `if`, `then`, and `else`) as unclassified, and `make contract-breaking-changes` prints them, so `packages/contracts/breaking-changes.json` declares them in its one 0.8.0 entry, since 0.8.0 is not yet on `dev`; no other existing message changed, and a version 1 offer is valid exactly as before. `control-plane.openapi.json` 0.3.0 and `execution.openapi.json` 0.7.0 each add one operation, which oasdiff reports as no breaking change; the minor versions let a client tell the documents apart, as 9b did. No semantic narrowing hides from the check: no existing operation or message changed its meaning.
16. **Wording fixes.** The G3 plan row 9 and source control section 3 said that item 9's message carries the refreshed credential, which account pool section 7 forbids; both now say notice and fetch, and the `scm-port` requirement "Refreshed credential delivery" with them. Account pool section 7 and execution wire contracts section 8.7 already said so.
17. **Base.** The worktree was created from `dev` `72989e7c` as briefed; before the first commit 9c landed in `dev` (`10fc3bbe`, #395), and the branch, still without commits, fast-forwarded to it, so that 9c's `execution.openapi.json` 0.6.0 and its schemas are the base. The checklist was saved `--at 72989e7c`, as the brief names.

## Session binding of the offer

The first draft left an open question: the assignment offer carried no agent session, because G2 left "the harness invocation joins the offer with the agent harness port in G3" (execution wire contracts section 4), and no G3 source defined how the worker learns the session, harness, and resume state of the attempt it starts. The architect answered on 2026-10-28 that 9d owns the binding, additively, in the protocol version 2 offer:

- **Shape.** `AssignmentOfferPayload` gains `session`, an `AssignmentSessionBinding`, required when `protocolVersion` is a `SessionProtocolVersion` and absent otherwise (`if`, `then`, `else`), so an offer of version 1 is valid exactly as before and the gate is the one every session message uses. A version 1 worker never reads a version 2 offer: it fails closed on the version (decision 1).
- **Fields.** `sessionId` reuses `AgentSessionId`, the name the documents share, for the stable identity that [ADR 0013](/docs/decisions/0013-intents-campaigns-and-proposal-graphs.md) "Forward-compatibility obligations" keeps the read models on; `harness` is the harness plugin, as in 9b's `AgentSession`; `model` and `effort` are per session, as [ADR 0014](/docs/decisions/0014-decision-council-and-delegated-approval.md) "Forward-compatibility obligations" requires and G3 plan rows 18 and 19 implement (this tree has no G3 plan section on ADR 0013 and 0014 obligations); `resume`, absent for a new session, names the native session ID and the next generation, at least 2, which `resumeSession` takes ([agent harness port](/docs/contracts/agent-harness-port.md) section 5). The port's start and resume requests do not take a model or effort yet; items 18 and 19 carry them.
- **No credential.** The binding names no credential: the slot credential keeps its own channel, the HTTPS fetch of 9c, and the contract page's redaction rule and a test say so.
- **Owner.** Item 18 implements the binding on the worker: it starts or resumes the bound session with its harness, model, and effort.

## Review pass 1 fixes

Reviewer A's pass 1 found three High and four Medium findings ([verification](verification.md) "Pass 1"). The fixes and the sources that ground them:

- **Run-wide end of a refreshed version.** Execution wire contracts section 8.7 says the attempts of a run's tasks share its credential, and source control section 3 keeps the previous secret until the run confirms adoption, so one attempt's confirmation cannot end it. Contract page section 6, "Run-wide end": a version ends only once every attempt of the run that held it adopted it or a later one or no longer holds its ownership, decided serialized per run by the lock or unique key of the first issue (section 8.7 there). An attempt that starts after the refresh gets the current version from `issueRunScmCredential`.
- **Recovery epoch on every new observation.** Execution wire contracts section 5 and launch authorization section 7 make every execution observation carry `recoveryEpoch` and keep one of another epoch, or one received in quarantine, as evidence only. The 11 new observations now require it, a session observation with the epoch of its execution's launch intent and an adoption with the epoch its fetch named, and contract page section 9 applies the same rule before any timeline, inbox, output, or credential effect. The payloads are new in 0.8.0, which is not yet on `dev`, so the required field needs no other protocol version (execution wire contracts section 3).
- **Classified operation.** Agent harness port section 7.2 gives a permission request an optional `operation`, a `push` with its full ref, and product ports section 5 needs it for `push-to-task-branch`. `RequestRecordedPayload` carries it as `ClassifiedOperation`, only for a permission request (`if`, `then`), and the ref pattern is a subset of the port's `refs/heads/` check (`agent-harness-data.ts`), which stays the full check. The control plane matches a rule only for a push to the task's branch, in the use transaction.
- **Answered requests.** Session timeline section 4.1 admits a host turn only for an `expired` or `unresolved` delegation request, and section 5.2 fails a second response with `conflict`; contract page section 5 now names those two states and treats a result for an `answered` request, `delivery-uncertain` included, as a repeat that sends nothing (section 5.4 there).
- **Rejected delegation.** Execution wire contracts section 8.3 ends a delegation that `requestDelegation` rejected with `rejected`; the command is now due when the result becomes `ended`, not when a child ends.
- **Terminal start failure.** Agent harness port section 9.3 lets `terminalProgram` fail with `internal` or `unavailable`, and a pseudo-terminal can fail to start; `TerminalRefusalReason` gains `terminal-start-failed`, with no error text, so every refusal stays typed (the 9a lesson of design "Context"). `precondition-failed` maps to `generation-not-running`.
- **A turn the port refuses as already seen.** Deferred to the architect at first, because no source defined the timeline transition; resolved by the architect's answer below.

## Architect answer on pass 1 finding 3

Agent harness port section 6 answers `conflict` for a turn ID the native session has seen, which proves acceptance rather than refusal, and asks a host that cannot tell whether a turn reached the harness to reconcile it through the timeline and never resubmit it. The architect (Niki) decided on 2026-10-28, option (b) of verification "Pass 1" amended:

- **Narrowed refusal.** `session.turn.not-delivered` with `port-refused` stays only for a refusal that proves non-acceptance: `invalid`, `not-found`, `precondition-failed`, or `unavailable` of `submitTurn` (agent harness port section 9.3). Its description and contract page section 3 say so.
- **New observation.** `session.turn.acceptance-unknown`, protocol version 2 only, with the reasons `conflict`, `timeout`, and `crash` and the fields of `session.turn.not-delivered` other than the reason, byte-identical: `sessionId`, `turnId`, `generation`, and `recoveryEpoch`. Its `observationId` derives from the command's `commandId`, as the refusal's does. A plugin's `internal` failure and a restart that finds the command journaled without its outcome are `crash`, because the architect named no fourth reason and neither proves non-acceptance.
- **Timeline operation.** `recordTurnAcceptanceUnknown` ([session timeline](/docs/contracts/session-timeline.md) section 4.4, the `session-turn-model` requirement "Turn acceptance unknown") makes the earliest `queued` turn `outcome-unknown`: final, never resent, and `nextDeliverableTurn` moves past it, the state section 6 gives a delivered turn whose outcome is lost. It does not need a running generation, because the report can follow a crash.
- **Item 13 obligation (architect's answer, 2026-10-28).** Item 13 adds `recordTurnAcceptanceUnknown` to the session timeline domain and service, with its tests and crash points, and applies `session.turn.acceptance-unknown` through it after the recovery epoch check (contract page section 12; session timeline section 9). Item 18 reports it instead of a second submission. The G3 plan row 13 carries no obligation notes, so the plan is unchanged.
- **Breaking changes.** The four additions that `make contract-breaking-changes` computes, the message, its two schemas, and its operation entry, join the 0.8.0 entry of `packages/contracts/breaking-changes.json`, 110 in all; all are additive.
