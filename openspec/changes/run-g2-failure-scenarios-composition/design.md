## Context

Item 24 needs recorded results for every scenario it runs, on several hosts and targets, and three changes (24a, 24b, 24c) produce them. The harness of item 10 already records a seed and prints a rerun hint (`seedFromEnvironment`, `rerunHint`); it has no record of a scenario's outcome. The item 23 installation runs the control plane, PostgreSQL, NATS, and a Linux worker in Docker Compose, and its smoke submits, assigns, and executes one task.

## Decisions

1. **The recorder lives in `@taskelith/testing`.** It is test infrastructure, so it belongs in the harness package, which depends only on the kernel and Node built-ins, and which product code cannot import (deterministic test harness, "Test-only harness package"). The pure part, `scenarioResult`, builds and validates a result from a run, a `RunEnvironment`, and a time; the adapters are `FileScenarioRecorder`, which appends, and `runEnvironment`, which reads the operating system and `git rev-parse HEAD`.
2. **The API.** A scenario reports a `ScenarioRun`: `scenario` (lowercase words joined by hyphens), `seed`, `target`, `outcome`, and an optional `detail`. A `ScenarioRecorder` has one method, `record(run): Promise<void>`. A recorded `ScenarioResult` adds `rerunHint`, `host` (`os.type()` and `os.release()`), `arch` (`os.arch()`, so `arm64` or `x64`), `commit`, and `recordedAt`. `target` is `harness-composition` or `compose-installation`; `outcome` is `passed` or `failed`. An expected product outcome, such as an `uncertain` attempt, is an assertion of the scenario and may appear in `detail`, not an outcome of the record.
3. **JSON Lines, opted in by the environment.** `scenarioRecorderFromEnvironment()` returns a file recorder when `TASKELITH_SCENARIO_RESULTS` names a file, resolved against the working directory, and otherwise `discardingScenarioRecorder`, which validates the run and writes nothing. A scenario therefore records the same way under `make verify` and in an evidence run, and only an evidence run, which sets the variable to `openspec/changes/<change>/results.jsonl`, changes the tree. Each result is one `appendFile` of one line, so several test processes can record into one file. JSON Lines is chosen over a Markdown table because appending needs no parsing and each line stays machine-readable; `verification.md` summarizes the results in prose or a table.
4. **The commit is `HEAD`, without a dirty marker.** An evidence run appends to the change directory, so the tree is dirty after the first record; a marker would carry no information. The results are committed in the same change, after the commit they name.
5. **Adoption by 24b and 24c.** Each scenario test calls `scenarioRecorderFromEnvironment()` once and `record` after its assertions, with the seed it used and its target, and records `failed` before it rethrows a failure. Each change records into its own directory, so the archive keeps the results with the change that produced them.
6. **Crash windows run through the harness on test-side compositions.** Decided by the owner's delegate on behalf of the owner (away run `20261026T145841Z-opencode-11793`): the process-launch crash windows of 24b run on test-side compositions of the real worker modules against the `make` services, with armed crash points and `SIGKILL`, and count as runs "through the harness" with target `harness-composition`. The composed worker has no crash seam: `apps/worker/src/execution-supervision.ts:75` hard-wires `crashPoint: () => undefined`, and product changes are out of scope.
7. **Compose scenarios use the item 23 installation.** The happy path, the worker disk loss, and the untimed `SIGKILL` run against a throwaway Compose project, like the item 23 smoke, and record target `compose-installation`. The untimed `SIGKILL` is not a crash window: it hits whatever the worker is doing and checks only that reconciliation ends consistently.
8. **The scenario steps are `installation.sh` commands.** `scenario-fresh-composition` runs the `smoke` command in a child process, so that a failed smoke is still recorded; the other two build their own throwaway project with the smoke's override and `infra/installation/scenarios/compose.yaml`, whose process runs ten seconds, long enough to interrupt. A trap records `failed` with the step that failed, prints the logs, and removes the project. `scripts/installation-scenario.ts` is the operator side (submit, await, read the result) and the recorder's entry; it reuses the smoke's functions, which take the task as a parameter, and runs each task in its own run. The scenarios read the control plane's state from PostgreSQL with `psql` in the `postgres` container, read-only, because the API exposes no execution state.
9. **Disk loss deletes files, never a volume.** The worker is killed with `SIGKILL`, because a stop could let it report the execution; the files go through `find -delete` in a one-off container of the worker image on the project's worker volume, first the journal only (the worker journal's "Journal missing with an identity"), then the whole data root ("Whole data root lost"). No operator action starts a new journal incarnation in G2, so the operator path is `revoke-worker` and a new enrolment; revocation is what makes the started execution uncertain (launch reconciliation, "Attempts of a revoked worker").
10. **The kill pause comes from the seed; the interval is measured.** The planned pause is `seed mod 25000` milliseconds, slept after the submission was answered, which spans the placement, the run of the ten-second process, and its end on Docker Desktop, so a rerun with `TASKELITH_TEST_SEED` repeats the pause, though not the timing of the services. Nothing blocking runs between the pause and the kill: the container is looked up before the submission, and the control plane's executions are read just after the kill. The record names both the planned pause and the measured interval, from the submission's answer to the kill's return on the monotonic clock (`process.hrtime`), which includes the start of one Node.js process for each timestamp. Agreement with the journal is checked on a copy, read with `node:sqlite` in the worker image after the worker stopped, since the journal holds an exclusive lock and a shared-memory file would make the next start refuse it.
11. **Proof from the worker, not only from the state.** After the kill, the scenario first waits for a new worker process: the container runs with a start time other than the killed one's, and that process logged `worker.reconciliation.planned`, its first reconciliation pass, and `worker.contact.online`; only then does it wait for the executions, and before the comparison it checks that the same process still runs. An execution that had already ended therefore cannot hide a restart that failed. For the missing journal, the restart policy of the container is off for one start, so that the worker's exit with a failure, after the `journal-loss` refusal logged since that start, is observed rather than masked by a restart; the policy is restored afterwards.
12. **Deadlines are monotonic and bound each probe.** `await_condition` keeps its deadline on the monotonic clock, runs each probe in the background for at most the remaining time, and then kills the probe with its child processes, so a slow or blocked probe, such as a hung `docker compose exec`, cannot extend the wait. After the kill, the wait for the new worker process and the wait for the executions share one deadline, two minutes from the restart, and the first is also bounded to one minute. 13. **A pass is recorded only after the cleanup.** `finish_passed` removes the project, records `passed`, and only then disarms the failure trap, so a failed `down --volumes` or image removal is recorded as `failed` with the step `cleaning up`; `remove_throwaway`, which disarms the trap first, stays as it was for the smoke and the other callers. Any run of the trap counts as a failure, even with status 0, since bash can report 0 after an expansion error under `set -u`.

The scenario steps live in `scripts/installation-scenarios.sh`, which `installation.sh` sources, so that tests run them against stubbed `compose`, `docker`, and `psql`.

## Risks and limitations

- `host` and `arch` describe the host that runs the scenario. For `compose-installation` on Docker Desktop, the Linux worker runs in a virtual machine of the same architecture; the record does not name the engine version, which `verification.md` states.
- The record does not prove that the tree at `commit` is the one that ran; `verification.md` states the revision of each evidence run.

- The kill's moment is reproducible, but what the worker is doing at that moment depends on the services' timing; `detail` records what it was.

## Follow-ups

- Multi-arch tooling for the Linux cgroup checks (`make verify-linux-cgroup`): the Linux supervisor crash windows of 24b run on the x86_64 iMac.
- No operator cancel API, and no Toxiproxy or second worker in the Compose installation: these belong to 24c.
