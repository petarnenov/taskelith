## Context

The [worker journal contract](../../../docs/contracts/worker-journal.md) names the commits W1 to W6 (W5s and W5e apart) as crash points, before and after each, and section 13 asks for a crash at each, followed by recovery, with the result of its recovery table. The [supervisor identity contract](../../../docs/contracts/supervisor-identity.md) names the launch steps CP1 to CP12 (section 4) and asks, in section 13, that a crash of the worker or a supervisor at each gives the result section 6 assigns and never a second spawn. Items 14 and 15 already crash the journal adapter and the supervisor program alone; 24b crashes the composed system. The owner's delegate decided that these scenarios run "through the harness" as test-side compositions of the real modules against the `make` services, with armed crash points, and that the product worker gains no crash seam (24a design decision 6).

## Decisions

1. **The composition.** `apps/control-plane/test/harness-composition.ts` starts, per scenario, a database, a data root, and a broker account of its own on the `make` services, initializes the installation with the administration CLI, and starts the real control plane in the test process with short test timings. The worker is a child process, `fixtures/composed-worker.ts`, that runs the real `workerMain` with `productionDependencies`; it overrides only the free-space and daemon-overhead sensors, which are not under test, the transport timings, and the jitter draw. The scenario submits a planning task through the operator API, as the item 23 smoke does, and the control plane places, offers, and authorizes it. The test-only scripted child appends its process ID to a `spawns` file and runs for three seconds.
2. **Crash points without a product seam.** The worker journal adapter already calls an `onCommitPoint` hook at `W<n>.before` and `W<n>.after`, but `startWorker` does not expose it. The worker process registers a `node:module` resolution hook before it loads the worker, so every import of `@taskelith/worker-journal` resolves to `fixtures/armed-journal.ts`, which re-exports the adapter and passes the hook into `openWorkerRoot` and `claimWorkerRoot`. The supervision port of the launch host is wrapped: `prepare` reaches CP1 on entry and CP2 after it wrote `intent`, `start` reaches CP3 on entry and CP4 after the supervisor started, and `read` reaches CP10 when it first returns a handle and CP12 when it first returns an exit. `start` launches `fixtures/armed-supervisor.ts`, the real supervisor program with its existing `crashPoint` option, which reaches CP5 to CP9 and CP11; adopting supervisors stay the product's. `TASKELITH_CRASH_POINT` arms one point in both processes, the harness's `CrashPoints` kills the process that reaches it with `SIGKILL`, and the point is appended to a trace file first, so the test knows which process died where.
3. **Restart.** A crashed worker is started again on the same data root. After a supervisor's crash, the test waits until the supervisor is gone and stops the worker with `SIGTERM`, as a service restart; the next start runs the recovery of journal contract section 5. The restarted worker must log its first reconciliation pass and its broker contact before it is stopped. W6 commits only in a recovery that seals, so its scenarios crash first at W3.after and then at W6 in the recovering worker.
4. **The checks.** After the restart, the test waits for the outcome in the control plane's task: an attempt that ended `exited`, or an execution with `uncertain` evidence. It then stops the worker and checks one attempt; exactly one execution beyond `not-started` in the control plane and in the worker journal, the same one, with exit code 0 and a proven start or with `uncertain`; one launch intent; the number of spawns; and, once the child had time to exit, no live process whose command line names the scenario's directory, which covers the worker, every supervisor, and the child.
5. **Duplicate delivery.** The test reads the offer from the commands stream, which keeps acknowledged messages, and publishes the same bytes again under new broker message identities, as a redelivery after the deduplication window: one to three copies while the child runs and one to three after the result, the counts drawn from the seed. It checks that every copy is acknowledged, one launch intent, one execution in the control plane and the journal, one spawn, and one result.
6. **Seeds.** The suite takes one seed from `TASKELITH_TEST_SEED` or draws one; each worker run of a scenario seeds its jitter with the seed plus the run's index, and the duplicate counts come from the seed. Identifiers stay random, because an execution identity must never repeat across restarts. Every record carries the seed.
7. **Expected outcomes on macOS.** The tables of journal section 5 and supervisor section 6 give: W1 to W5e, W6, CP1 to CP6, and CP10 to CP12 end `exited` with code 0 and one spawn, after a seal and a new execution where no supervisor claimed; CP7 (a claim, no spawn) and CP8 (a spawn, no handle) end `uncertain`, because macOS has no containment that proves no process; CP9 ends `uncertain` too: the restarted worker adopts the child, an adopting supervisor on macOS only observes, and once the child is gone nothing proves that no descendant lives.
8. **Platform scope.** The scenarios run natively on macOS, where the worker supervises without a containment, and are skipped elsewhere. On Linux the worker needs a delegated cgroup and an execution account, which only the privileged container of `make verify-linux-cgroup` provides, and that container has no network for the `make` services; the supervisor-level crashes at CP5 to CP11 with a containment already run there (item 15). Item 25 runs item 24's scenarios on each Linux matrix entry.
9. **Expected failures for D1.** The evidence run found defect D1 (`verification.md`): a relaunch after `not-started` is rejected with `execution-conflict`, so eleven windows that seal an authorized execution and launch again (W3, W4, and W6 on both sides, CP1, CP2, CP3, CP5, CP6) never reach their outcome. The coordinator decided to keep them as expected failures, not skips: each carries `expectFailure` of `node:test` with D1's signature, which the scenario raises only after the control plane logged `execution-conflict` for the relaunch and the worker journal holds that operation `rejected-final` with nothing spawned. They still record `failed`. Once D1 is fixed they fail, until the fix's change turns them back into ordinary scenarios.
10. **D1 and O1 are fixed elsewhere.** The owner's delegate decided both in away run `20261026T161148Z-opencode-90873`: D1 by option (b), an optional `reportsNotStartedFor` in the launch request that the authority applies before the ownership rule, in one transaction, which changes the launch authorization contract; O1, a live worker that does not notice a supervisor dead before its claim, by (A), a liveness check of an authorized but unclaimed record after a bound. Both come in the follow-up change `fix-launch-recovery-reauthorization`, which reruns this evidence with seed `2776760789`; this change touches no product code or contract.

## Not applicable on this host

- The Linux containment of CP6 (create, admit, remove) and the Linux rows of the recovery table: the scenarios run on macOS, where CP6 is reached as a named point without a containment. Covered at the supervisor level by `make verify-linux-cgroup`; the composition on Linux belongs to item 25.

## Risks and limitations

- The resolution hook replaces the journal module by its specifier; a worker that imported the adapter under another name would escape it. The trace file and the `SIGKILL` status prove that each armed point was reached.
- The launch supervisor of the scenarios is the real program run from a test fixture with test timings, not the worker's built entry; adopting supervisors are the product's.
- The control plane runs in the test process, so a crash of the control plane is out of scope here.
