## Context

A Linux launch runs the configured command under a separate execution account, inside a per-execution cgroup v2 directory under a delegated containment parent ([supervisor identity contract](../../../docs/contracts/supervisor-identity.md) section 8). The supervisor creates that directory, moves the child into it, writes `cgroup.kill`, and signals the child's process group. The worker reads `TASKELITH_CONTAINMENT_PARENT` on every Linux start, so that start reconciliation and the unrecorded-process scan run; without it they are deferred ([worker runtime](../../specs/worker-runtime/spec.md)). The contract leaves the container runtime settings that provide this to items 15 and 25; this item provides them for the minimal local installation.

What the 23a worker container lacks:

- Docker mounts the container's cgroup namespace read-only, and the container's processes sit in the namespace root, which therefore cannot delegate children.
- The worker runs as `taskelith` without capabilities, so its supervisor cannot spawn a child under another user ID or signal it.

## Decisions

1. **Cgroup layout.** The worker container uses a private cgroup namespace (`cgroup: private`), so `/sys/fs/cgroup` is the container's own cgroup. The entrypoint, as root:
   - remounts `/sys/fs/cgroup` read-write when Docker mounted it read-only;
   - creates `/sys/fs/cgroup/init` and moves every process of the namespace root into it, and fails if any remains;
   - creates `/sys/fs/cgroup/executions`, the containment parent, as a sibling of `init/`.

   The worker, its supervisors, and Docker's init sit in `init/`; each execution gets `executions/<executionId>/`. The worker's own cgroup is thus never at or under the containment parent, which a later worker self-check refuses. The common ancestor of `init/` and an execution is the namespace root, whose `cgroup.procs` only root can write. All directories and files belong to root with modes 0755 and 0644, so the execution account can write no `cgroup.procs` of the worker. No controller is enabled in `cgroup.subtree_control`: the worker declares no hard control until the supervisor enforces one, and `cgroup.kill` and `cgroup.events` are core files.
2. **The containment parent is set in the image.** The worker image sets `TASKELITH_CONTAINMENT_PARENT=/sys/fs/cgroup/executions` and the execution account `TASKELITH_EXECUTION_UID=10003` and `TASKELITH_EXECUTION_GID=10003` (`taskelith-exec`, created in the image) as image environment, so every container of the image names them, with or without a launch command. The entrypoint refuses a parent that is not a direct child of the cgroup root other than `init`.
3. **The worker runs as root with three capabilities.** The supervisor spawns the child under the execution account and signals its process group, which needs `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL`. Kept by a non-root worker, they would survive the child's change of user ID, because the kernel clears capabilities only when a process leaves user ID 0, and as ambient capabilities they would survive its `execve`: the child could switch back to the worker's user and write its cgroups. A root worker whose child changes to the execution account loses every capability, enforced by the kernel and independent of the command. The entrypoint therefore ends with `setpriv --bounding-set=-all,+setuid,+setgid,+kill --inh-caps=-all --no-new-privs`, so the worker and its supervisors are root with these three capabilities only. This replaces the 23a requirement that the worker run as `taskelith`; the image keeps `USER taskelith`, so a container started without the Compose service settings stays unprivileged and its entrypoint refuses to start. It deliberately reverses the contract that 23a review finding 6 protected, the non-root worker service and the test's rejection of a Compose `user` on the Taskelith images ([23a verification](../archive/2026-10-25-compose-minimal-local-installation-images/verification.md)).
4. **Compose service settings.** `user: "0:0"`, `cap_drop: [ALL]`, and `cap_add` with exactly the seven capabilities the entrypoint needs: `SYS_ADMIN` for the remount, `CHOWN` and `DAC_OVERRIDE` to hand the data root to root, `SETPCAP` to reduce the bounding set, and the three the worker keeps. `security_opt` sets `no-new-privileges=true`, so set-user-ID programs of the image give an execution nothing, and `apparmor=unconfined`, because Docker's default AppArmor profile forbids the remount on hosts that use AppArmor. `init: true` runs Docker's init as process 1, which reaps an execution whose supervisor ended first; process 1 still marks the namespace incarnation.
5. **Data root ownership.** The worker checks that its own user owns every component of its control paths. The entrypoint changes the owner of the data root to root on every start, so a worker volume of a 23a installation, owned by `taskelith`, keeps its enrollment.
6. **The smoke as an override.** The default installation installs no workflow and no launch command, as before: G2 has no workflow resolution (coordinator decision Q8) and only a test-only scripted process. `make installation-smoke` adds `infra/installation/smoke/compose.yaml`, which sets `TASKELITH_WORKFLOWS` to the tracked `infra/installation/smoke/workflows.json` in the image and `TASKELITH_WORKER_COMMAND` to a Node.js process that exits 0 after one second. The workflow's digest is the SHA-256 of its definition's JSON; a test keeps them consistent.
7. **The operator side runs on the host.** `scripts/installation-smoke.ts`, run with the pinned Node.js, calls the published API like an operator: `createRun`, `submitTask` for a planning task of the `specs` stage, and `readTaskResult` every second for at most two minutes. It succeeds only for an `ended` result whose outcome is `exited` with code 0 and `startProven`. The script uses Node.js built-ins only; its HTTP adapter sits behind a small port, so the tests drive the flow without Docker.
8. **A dedicated throwaway project.** The smoke uses the Compose project `<installation>-smoke`, separate from the operator's installation and from `verify-installation`. Like `verify-installation`, it removes that project's leftovers before it starts and removes the project with its own volumes and images at the end, also on failure, after it prints the control-plane and worker logs. No other project or volume is touched.

## Risks and limitations

- The worker container needs `SYS_ADMIN` and no AppArmor confinement until its entrypoint has dropped them; anyone who runs `docker exec` in it gets the container's capability set. The worker process itself runs as root with three capabilities. Item 25 qualifies the container settings on Linux hosts; this item ran the smoke on Docker Desktop only.
- The worker runs as root in its container, which can change files of its image; a read-only root filesystem is not part of this item.
- Running the smoke on a Linux host with AppArmor or SELinux is not yet observed.
- The image contains the test-only workflow file; only the smoke override names it.
