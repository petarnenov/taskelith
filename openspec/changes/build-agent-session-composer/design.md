# Design: build-agent-session-composer

## Context

G3 item 31 (`docs/g3-plan.md`, row 31), sub-change 31b under the coordinator's split. Its base is `dev` `743f4661` (#440) with the session screen of 31a ([archive](/openspec/changes/archive/2026-11-04-build-agent-session-timeline/design.md): the `BoardGateway` session reads, the shared live feed with `amend`, the session view with its `freshness` per turn, `SessionPage`), the shell and session gateway of 28 and 29a (the CSRF token keeper of `control-plane-session.ts`, `expiryOfRequest`, `BoardServices`). The server side is item 13's `submitTurn` (`control-plane.openapi.json` 0.5.0): a `TurnSubmission` of `idempotencyKey` (1 to 128 printable ASCII characters) and `text` (1 to 65,536 characters), answered 201 `recorded` or 200 `duplicate` with the `Turn`, 400 invalid, 401, 403 `role-required` or `csrf-token-invalid`, 404, 409 `idempotency-key-reused`, 422 `session-stopped`, 500, 503. The server resolves a repeat by the key's author and text digest (session-turn-model "Turn identity and idempotency"; wire contracts "Turn submission on the wire", "Retry after a lost response", "Stopped session").

Architecture: `docs/architecture.md` section 7 "Durable chat turns and provider approvals" (lines 363 to 371: immutable turn identity, idempotent submission) and R29 "Chat and approval recovery" (line 611: retry a user turn with the same key).

**Goals.** The composer that stays visible, `submitTurn` with the session's CSRF token, the idempotency key per composed message kept for a retry across a reload, and honest states for every documented answer.

**Non-goals.** The output tail (31a follow-up), native requests and the inbox (item 32), an unsent draft that survives a reload (decision Q5), a shared pending list across tabs (decision Q7), any OpenAPI or control-plane change.

## Decisions

1. **The token reaches the board gateway through a getter (Q1).** `createSessionGateway` returns a `ControlPlaneSessionGateway`, the `SessionGateway` port plus `csrfToken: () => string | undefined`, the keeper's `current`; `main.tsx` passes it to `createBoardGateway({ csrfToken })`, whose typed fetch sets `X-CSRF-Token` on every request other than GET while the getter answers a string (product UI "Web SPA control-plane client"). The port, `App`, and the contexts carry the gateway as `SessionGateway`, and `SessionProvider` wraps it in `settledGateway`, which copies only `read`, `logIn`, and `logOut`, so no component can reach the getter, and no string of the token is held outside the keeper's closure. `createBoardGateway` without the option sends no token, as before. A test with both real gateways and a scripted control plane checks that the submit carries the token and that no HTML of the page, no value of `sessionStorage` or `localStorage`, and no console argument contains it.
2. **`submitTurn` on the port.** `BoardGateway.submitTurn(projectId, sessionId, submission)` answers a `SubmitResult`: `recorded` or `duplicate` with the `Turn` (the body checked by `turnSubmittedOf`, `isTurn` of 31a; a 201 whose `effect` says `duplicate`, or a 200 that says `recorded`, is a wrong answer and reads as `unavailable`), `invalid` (400), `csrf-rejected` (403 with the reason `csrf-token-invalid`), `denied` with the role (403 with the reason `role-required`), `key-reused` (409 with the reason `idempotency-key-reused`), `session-stopped` (422 with the reason `session-stopped`), and the 29a read failures for 401 (`unauthenticated` by reason, else `unavailable`), 404, 5xx, undocumented statuses, and no answer. A 403, 409, or 422 whose body lacks its documented reason, or names another (`already-answered` of `CommandConflict` is not a turn refusal), reads as `unavailable`, so the composer keeps the key instead of asserting a refusal the answer did not establish (pass 1 finding 1). `BoardServices` routes `submitTurn` through the same expiry check as the reads, now generic over any `{ kind }` result, so a 401 `unauthenticated` shows the sign-in page, and a gateway that throws reads as `unavailable`.
3. **Which answers end the key (Q3).** `composer-model.ts` is the composer's rule, free of React: `outcomeOf(result, tokenRefreshed)` answers `recorded` (the turn shows and the submission leaves), `duplicate` (the turn shows; the notice names it), `retry-with-new-token` (the first `csrf-rejected`), `retryable` (`unavailable`, which covers no answer, 500, 503, undocumented statuses, and a refusal without its reason; `unauthenticated`; and, from the hook, `token-not-renewed` when the session read after a CSRF refusal gave no answer, and `session-changed` when another sign-in, a sign-out, or the composer's unmount came before the key could be sent again, findings 2 and 9), or `terminal` with the state to show (`key-reused`, `session-stopped`, `not-found`, `invalid`, the second `csrf-rejected`, and `denied` with the role). The once-per-key session read is the record's `tokenRefreshed`, set only after a read that renewed the token, so the rule holds across failures, manual retries, and a reload: a key whose read was spent before the reload meets its next CSRF refusal as final (finding 8). A retry sends the submission's plain record (`recordOf`, without the shown state), and spending the read merges only `tokenRefreshed` into the shown submission, so the store holds the documented shape and the submission stays pending, with the composer blocked, until the resend is answered (pass 2 finding 1). A retryable outcome keeps the record for a retry with the same key; every other outcome drops it, because the control plane can never record that key with this text, or already has.
4. **The retry records (Q4).** `turn-records.ts` keeps `{ key, text, sentAt, tokenRefreshed? }` per session under `taskelith-turn:` and the session's address of `session-address.ts`, each identifier `encodeURIComponent`-encoded and joined by `/`, so `a/b` + `c` and `a` + `b/c` never share a name; the same text keys the live session and the composer in `SessionPage` and `useLiveSession`, so no two addresses share a React or feed identity either (finding 5). At most `MAX_TURN_RECORDS` (20) per session, the oldest leaving first; `add` replaces the record of a key it knows in place. Every read and write runs through one `attempt` with a try/catch: from the first throw on, whether the storage itself (`window.sessionStorage` can throw) or a method (`setItem` over quota), the store serves this page's records from memory, which mirrors every read and write made before; a stored value that is not a list of records reads as none. `clearAll` drops every key with the prefix and leaves other keys, and tries the storage whatever threw before, because a write over quota leaves earlier text in the storage that must not outlive the shell's session (finding 4); a throw there keeps the records out of this page's reads. It answers whether any record was dropped. The store is one object made in `main.tsx` and given to `App`, so that tests give a throwing one.
5. **Records end with the shell's session (coordinator decision, Niki, 2026-11-04, on Q3 against Q4 for a 401: option (a), Q4 wins and supersedes Q3 for a 401).** `TurnRecordsProvider` (`agent-session/`, so `board/` stays free of it) holds the store in a context and clears it whenever the session view is `signed-out`: after a logout, after a 401 `unauthenticated` of any read or command, after the expiry check, and on a first visit without a session; a `checking` or `unavailable` view keeps them, so a reload while signed in keeps the records for the retry. A session-ending 401 clears every record. Q3's retry after sign-in applies only to a late 401 that did not end the session (a late answer of an earlier session, which `expiryOfRequest` ignores): the composer shows it as not sent with a retry. Refinement: when the outcome of a send is unknown, because it was in flight, or got no answer before the 401 or the sign-out, the notice must not claim that the turn was not sent. `clearAll` answers whether it dropped a record, the provider keeps that, and `Shell` gives it to `SignInPage`, whose expired and signed-out alerts and whose first-visit text (a reload after the server session ended, or a visit without a session) then add "Your last turn may not have been sent; check the timeline after signing in."; a sign-out that dropped no record says nothing of a turn. The drop holds while the shell stays signed out, also when StrictMode runs the clearing effect twice, and the next sign-in forgets it, so a later clean sign-out says nothing of a turn (pass 2 finding 3). The server's author and text deduplication covers a re-typed identical turn (pass 1 finding 11).
6. **A composed message and its key (Q2).** `useComposer` restores the session's records as `unconfirmed` submissions on mount, mints `crypto.randomUUID()` for each send, adds the record before the request, and settles the record by the answer whether or not the composer still shows, so no settled key is sent again after a reload. Its `Submission` list holds each key's state: `pending`, `unconfirmed`, `failed` with the retryable failure, `duplicate` with the turn, `refused` with the reason, or `denied` with the role. One send runs at a time: the hook holds a synchronous in-flight flag, so a send or retry while a record is being sent does nothing, and `sending` blocks the composer (finding 7); a retry re-delivers the same record, and a dismiss hides a settled notice. On `retry-with-new-token` the hook awaits `Session.refresh`, a read of the session whose answer renews the keeper's token and which now answers the `SessionRead` (and shows the sign-in page if the session is gone, or the operator another tab logged in). The key is sent again only after an `authenticated` read, from a composer still mounted, under the `signedInGeneration` it was sent under (`Session.signedInGeneration`, a number that grows on each signed-in view after none or with another operator's login name, read at call time): an `unavailable` read keeps the record as `token-not-renewed`, and an `anonymous` one, another sign-in, a sign-out, or an unmount meanwhile keeps it as `session-changed`, so no message is sent under a replacement session or from a page that left (findings 2 and 9), and no submission stays pending in a composer the sign-out left mounted (pass 2 finding 2). The read's success spends the record's `tokenRefreshed`, so a second refusal is terminal.
7. **The turn shows at once (Q10).** `startSessionFeed` gains `showTurn(turn)`, an `amend` with `withSubmittedTurn` of the session model: a turn the view already knows by `turnId` keeps its read or event state (the stream may have delivered it before the answer), and an unknown one joins the turns in position order with no `freshness` entry, so the next `turn-changed` for it applies at any position above the view's, a later page read replaces it, and a new snapshot drops it for its own read, unless the amendment came while that read ran: the live feed keeps the changes and amendments of a running read and applies them over its snapshot, so a resync whose read captured a snapshot older than the submission answer still shows the acknowledged turn, whose record is already settled (finding 10). The timeline shows each `turnId` once. `useLiveSession.showTurn` is bound to the feed of its session address and load: a submission answered after a move to another session, or after a retry of this one, amends no other feed, while its record still settles (finding 6). Before the session is shown, `amend` does nothing; the composer is blocked then anyway (Q6), and a late answer's turn arrives through the next snapshot.
8. **Blocked composer (Q6).** `blockOf` chooses, in order: the feed failed, the session not yet shown, `session.limit` set (stopped), a send in flight, or a `denied` notice shown (a 403 that named the role disables sending until the notice is dismissed, since the role does not change by retrying). The `Textarea`, the send button, and every Retry button are disabled, with the reason as the field's description, so a retry obeys the same rules as a send (finding 7). An unreachable worker or an uncertain process state does not block: the control plane queues the turn. A 422 from a race still reaches the composer as `session-stopped`, and the `agent-session-changed` that follows shows the limit and blocks it.
9. **Message length (Q8).** `checkTurnText` trims the draft, refuses an empty one, and counts code points (`[...text].length`), as the control plane's Ajv validator counts `maxLength`, so an emoji counts once on both sides; the limit is `MAX_TURN_TEXT_LENGTH` 65,536, mirrored from `TurnText`. The counter shows from `COUNTER_FROM_LENGTH` 60,000 on; a longer draft shows by how much it is over and disables the send. A 400 is still mapped as `invalid`, the fallback of decision Q8.
10. **Rendering (Q9).** The composer is a Mantine `Paper` rendered as a `form` named "Composer", `pos="sticky"` and `bottom={0}` as style props (D17: no `style`, `classNames`, or CSS file), `withBorder`, at the end of the session page's `Stack`, so it stays visible however long the timeline is and the page scrolls nowhere sideways; it is rendered under every state of `SessionContent`, keyed by the session's address. The field is a `Textarea` labelled "Message the agent" of three rows (not autosized: Mantine's autosize measures through `getComputedStyle`, which jsdom cannot answer, and a fixed field is enough); the send is the theme's 44 px `Button`. Each submission is an `Alert` (red with `role="alert"` for a failure, refusal, or denial; indigo or gray with `role="status"` otherwise) with the message's text through 31a's `TurnText`, the state's text, and its Retry or Dismiss button; a pending one shows a `Loader` unless the system asks for reduced motion, with `aria-busy`. The `Paper` has the page's background, the field is the tested input surface, and the alerts are the tested indigo, red, and gray ones. The over-limit error draws one pair the contrast matrix had not tested: Mantine's error color on the page under the field and as the erroneous field's own text, red.6 in the light scheme (3.28:1) and red.8 in the dark one (3.44:1 on the page, 3.01:1 in an input). The theme's `cssVariablesResolver`, given to `MantineProvider` in `App`, sets `--mantine-color-error` to red.9 in the light scheme and red.5 in the dark one (5.46:1 and 5.59:1 on the page, 4.89:1 in a dark input), the way the theme already lifts dimmed text, and `theme-contrast.test.ts` measures both pairs through the same resolver (finding 3). A send disables the button that held the keyboard focus, and a retry hides its Retry button once the turn is recorded; the composer gives the focus back to the field once the answer arrives and no block holds, so a keyboard operator continues where the turn was typed (pass 2 finding 7).

## Recorded risk

**Turn text in `sessionStorage` (Q4).** Each unconfirmed submission's text sits in the browser profile's session storage, unredacted, until the control plane settles it or the shell is signed out, so a message that holds a secret before the control plane's redaction is readable by anything that reads this origin's storage in this tab (another script under the same origin, which the CSP of 28c limits; the profile on disk while the tab lives). Bounds: at most 20 records per session, cleared on every confirmed or refused key and on any signed-out shell; `sessionStorage` is per tab and gone when the tab closes; the text is rendered only in the composer's notice and the timeline (where the server's turn shows it anyway), and never logged. Accepted by the coordinator (decision Q4) against the alternative of losing the retry after a reload.

## Departures

- **Retry after a 401 (Q3 against Q4)** is no departure: the coordinator decided it (decision 5).
- **A denied notice blocks sending** until dismissed (decision 8), beyond the three blocks decision Q6 lists; the role does not change by retrying, and the research's Q6 (a) named it.

## Proof of concept

The composer follows `docs/ui-poc/src/screens/Session.tsx`: the field "Message the agent" with a send action, a draft that is trimmed, refused when empty, and cleared on send, a key minted per send, and the entry's "accepted, delivered at the next turn boundary" against "sending". Departures, each required by a requirement or decision ("Reference proof of concept"):

- **Sticky at the end of the page, not inside the conversation card.** POC: the field at the bottom of the Conversation `Paper`, scrolled away with it. "Product screens": the composer stays visible (Q9).
- **A `Textarea` with a send button, not a `TextInput` that sends on Enter.** A turn's text holds newlines, which the timeline shows line by line (31a); Enter adds a line.
- **Every documented answer has a state.** POC: sending and accepted only. The states of decision 3, with the retry by the same key (R29).
- **Role refusals come from the control plane.** POC: `RoleButton capability="send-turn"` hides the send for a viewer. The SPA has no role model before item 32's inbox; the 403 names the role, and the composer shows it (decision 8).
- **No stop button.** As 31a: the contract has no stop operation.

## Risks and trade-offs

- A `refresh` after a CSRF refusal shows the session's answer in the shell (a signed-in view with the operator the control plane names, or the sign-in page), so a tab whose session another tab replaced shows the truth, and the key is not sent again under it; an unreachable control plane changes nothing, and the key stays for a manual retry.
- The error color override reaches every Mantine input with an `error`; only the composer sets one today, and the sign-in page shows its failures in an alert.
- The submission list is React state of the composer, keyed by the session's address; a navigation away drops the notices, while the records keep what still matters, the unconfirmed keys, and the next mount restores them as `unconfirmed`.
- `sessionStorage` is per tab (Q7): a retry from another tab is impossible, and two tabs that send the same message mint two keys and record two turns, as two operators would; the server's digest dedups only a repeat of the same key.
- A duplicate (200) of a turn before the loaded window shows that turn above the window, out of its window, in position order; "load earlier" reads it again and replaces it by `turnId`.
