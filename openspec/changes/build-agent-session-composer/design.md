# Design: build-agent-session-composer

## Context

G3 item 31 (`docs/g3-plan.md`, row 31), sub-change 31b under the coordinator's split. Its base is `dev` `743f4661` (#440) with the session screen of 31a ([archive](/openspec/changes/archive/2026-11-04-build-agent-session-timeline/design.md): the `BoardGateway` session reads, the shared live feed with `amend`, the session view with its `freshness` per turn, `SessionPage`), the shell and session gateway of 28 and 29a (the CSRF token keeper of `control-plane-session.ts`, `expiryOfRequest`, `BoardServices`). The server side is item 13's `submitTurn` (`control-plane.openapi.json` 0.5.0): a `TurnSubmission` of `idempotencyKey` (1 to 128 printable ASCII characters) and `text` (1 to 65,536 characters), answered 201 `recorded` or 200 `duplicate` with the `Turn`, 400 invalid, 401, 403 `role-required` or `csrf-token-invalid`, 404, 409 `idempotency-key-reused`, 422 `session-stopped`, 500, 503. The server resolves a repeat by the key's author and text digest (session-turn-model "Turn identity and idempotency"; wire contracts "Turn submission on the wire", "Retry after a lost response", "Stopped session").

Architecture: `docs/architecture.md` section 7 "Durable chat turns and provider approvals" (lines 363 to 371: immutable turn identity, idempotent submission) and R29 "Chat and approval recovery" (line 611: retry a user turn with the same key).

**Goals.** The composer that stays visible, `submitTurn` with the session's CSRF token, the idempotency key per composed message kept for a retry across a reload, and honest states for every documented answer.

**Non-goals.** The output tail (31a follow-up), native requests and the inbox (item 32), an unsent draft that survives a reload (decision Q5), a shared pending list across tabs (decision Q7), any OpenAPI or control-plane change.

## Decisions

1. **The token reaches the board gateway through a getter (Q1).** `createSessionGateway` returns a `ControlPlaneSessionGateway`, the `SessionGateway` port plus `csrfToken: () => string | undefined`, the keeper's `current`; `main.tsx` passes it to `createBoardGateway({ csrfToken })`, whose typed fetch sets `X-CSRF-Token` on every request other than GET while the getter answers a string (product UI "Web SPA control-plane client"). The port, `App`, and the contexts carry the gateway as `SessionGateway`, and `SessionProvider` wraps it in `settledGateway`, which copies only `read`, `logIn`, and `logOut`, so no component can reach the getter, and no string of the token is held outside the keeper's closure. `createBoardGateway` without the option sends no token, as before. A test with both real gateways and a scripted control plane checks that the submit carries the token and that no HTML of the page, no value of `sessionStorage` or `localStorage`, and no console argument contains it.
2. **`submitTurn` on the port.** `BoardGateway.submitTurn(projectId, sessionId, submission)` answers a `SubmitResult`: `recorded` or `duplicate` with the `Turn` (the body checked by `turnSubmittedOf`, `isTurn` of 31a; a 201 whose `effect` says `duplicate`, or a 200 that says `recorded`, is a wrong answer and reads as `unavailable`), `invalid` (400), `csrf-rejected` (403 with the reason `csrf-token-invalid`), `key-reused` (409), `session-stopped` (422), and the 29a read failures for 401 (`unauthenticated` by reason, else `unavailable`), 403 (`denied` with the role), 404, 5xx, undocumented statuses, and no answer. A 409 and a 422 map by status: the document names one reason for each (`idempotency-key-reused`, `session-stopped`), and either way the key or the session is spent. `BoardServices` routes `submitTurn` through the same expiry check as the reads, now generic over any `{ kind }` result, so a 401 `unauthenticated` shows the sign-in page, and a gateway that throws reads as `unavailable`.
3. **Which answers end the key (Q3).** `composer-model.ts` is the composer's rule, free of React: `outcomeOf(result, tokenRefreshed)` answers `recorded` (the turn shows and the submission leaves), `duplicate` (the turn shows; the notice names it), `retry-with-new-token` (the first `csrf-rejected`), `retryable` (`unavailable`, which covers no answer, 500, 503, and undocumented statuses, and `unauthenticated`), or `terminal` with the state to show (`key-reused`, `session-stopped`, `not-found`, `invalid`, the second `csrf-rejected`, and `denied` with the role). A retryable outcome keeps the record for a retry with the same key; every other outcome drops it, because the control plane can never record that key with this text, or already has.
4. **The retry records (Q4).** `turn-records.ts` keeps `{ key, text, sentAt }` per session under `taskelith-turn:<projectId>/<sessionId>` in `sessionStorage`, at most `MAX_TURN_RECORDS` (20) per session, the oldest leaving first. Every storage access runs through one `attempt` with a try/catch: from the first throw on, whether the storage itself (`window.sessionStorage` can throw) or a method (`setItem` over quota, `removeItem`), the store serves this page's records from memory, which mirrors every read and write made before; a stored value that is not a list of records reads as none. `clearAll` drops every key with the prefix and leaves other keys. The store is one object made in `main.tsx` and given to `App`, so that tests give a throwing one.
5. **Records end with the shell's session.** `TurnRecordsProvider` (`agent-session/`, so `board/` stays free of it) holds the store in a context and clears it whenever the session view is `signed-out`: after a logout, after a 401 `unauthenticated` of any read or command, after the expiry check, and on a first visit without a session; a `checking` or `unavailable` view keeps them, so a reload while signed in keeps the records for the retry. Decision Q3's retry of a 401 "after sign-in" therefore applies only to a 401 that did not end the shell's session (a late answer of an earlier session, which `expiryOfRequest` ignores): the composer shows it as not sent with a retry; once the sign-in page shows, the records are gone and the operator composes again, because the next operator may be another person.
6. **A composed message and its key (Q2).** `useComposer` restores the session's records as `unconfirmed` submissions on mount, mints `crypto.randomUUID()` for each send, adds the record before the request, and settles the record by the answer whether or not the composer still shows, so no settled key is sent again after a reload. Its `Submission` list holds each key's state: `pending`, `unconfirmed`, `failed` with the retryable failure, `duplicate` with the turn, `refused` with the reason, or `denied` with the role. One send runs at a time (`sending` blocks the composer), a retry re-delivers the same record, and a dismiss hides a settled notice. On `retry-with-new-token` the hook awaits `Session.refresh`, a read of the session whose answer renews the keeper's token (and shows the sign-in page if the session is gone, or the operator another tab logged in), and delivers the same key once more with `tokenRefreshed`, so a second refusal is terminal.
7. **The turn shows at once (Q10).** `startSessionFeed` gains `showTurn(turn)`, an `amend` with `withSubmittedTurn` of the session model: a turn the view already knows by `turnId` keeps its read or event state (the stream may have delivered it before the answer), and an unknown one joins the turns in position order with no `freshness` entry, so the next `turn-changed` for it applies at any position above the view's, a later page read replaces it, and a new snapshot drops it for its own read. The timeline shows each `turnId` once. Before the session is shown, `amend` does nothing; the composer is blocked then anyway (Q6), and a late answer's turn arrives through the next snapshot.
8. **Blocked composer (Q6).** `blockOf` chooses, in order: the feed failed, the session not yet shown, `session.limit` set (stopped), a send in flight, or a `denied` notice shown (a 403 that named the role disables sending until the notice is dismissed, since the role does not change by retrying). The `Textarea` and the send button are disabled with the reason as the field's description. An unreachable worker or an uncertain process state does not block: the control plane queues the turn. A 422 from a race still reaches the composer as `session-stopped`, and the `agent-session-changed` that follows shows the limit and blocks it.
9. **Message length (Q8).** `checkTurnText` trims the draft, refuses an empty one, and counts code points (`[...text].length`), as the control plane's Ajv validator counts `maxLength`, so an emoji counts once on both sides; the limit is `MAX_TURN_TEXT_LENGTH` 65,536, mirrored from `TurnText`. The counter shows from `COUNTER_FROM_LENGTH` 60,000 on; a longer draft shows by how much it is over and disables the send. A 400 is still mapped as `invalid`, the fallback of decision Q8.
10. **Rendering (Q9).** The composer is a Mantine `Paper` rendered as a `form` named "Composer", `pos="sticky"` and `bottom={0}` as style props (D17: no `style`, `classNames`, or CSS file), `withBorder`, at the end of the session page's `Stack`, so it stays visible however long the timeline is and the page scrolls nowhere sideways; it is rendered under every state of `SessionContent`, keyed by the session's address. The field is a `Textarea` labelled "Message the agent" of three rows (not autosized: Mantine's autosize measures through `getComputedStyle`, which jsdom cannot answer, and a fixed field is enough); the send is the theme's 44 px `Button`. Each submission is an `Alert` (red with `role="alert"` for a failure, refusal, or denial; indigo or gray with `role="status"` otherwise) with the message's text through 31a's `TurnText`, the state's text, and its Retry or Dismiss button; a pending one shows a `Loader` unless the system asks for reduced motion, with `aria-busy`. No new color pair is drawn: the `Paper` has the page's background, the field is the tested input surface, and the alerts are the tested indigo, red, and gray ones.

## Recorded risk

**Turn text in `sessionStorage` (Q4).** Each unconfirmed submission's text sits in the browser profile's session storage, unredacted, until the control plane settles it or the shell is signed out, so a message that holds a secret before the control plane's redaction is readable by anything that reads this origin's storage in this tab (another script under the same origin, which the CSP of 28c limits; the profile on disk while the tab lives). Bounds: at most 20 records per session, cleared on every confirmed or refused key and on any signed-out shell; `sessionStorage` is per tab and gone when the tab closes; the text is rendered only in the composer's notice and the timeline (where the server's turn shows it anyway), and never logged. Accepted by the coordinator (decision Q4) against the alternative of losing the retry after a reload.

## Departures

- **Retry after a 401 (Q3 against Q4).** A 401 that ends the shell's session clears the records (Q4), so the operator cannot retry that key after signing in again; the key survives only a 401 that did not end the session (decision 5). The coordinator's Q4 is the later and the safer rule.
- **A denied notice blocks sending** until dismissed (decision 8), beyond the three blocks decision Q6 lists; the role does not change by retrying, and the research's Q6 (a) named it.

## Follow-ups

- **Output tail (31a Q4).** Unchanged: `readAgentSessionOutput` and `output-appended` with an honest cursor-expired notice.
- **Native requests** of a session go with item 32.
- **An unsent draft across a reload (Q5 (b))**, if wanted: the same adapter with a draft key, with the same recorded risk.

## Proof of concept

The composer follows `docs/ui-poc/src/screens/Session.tsx`: the field "Message the agent" with a send action, a draft that is trimmed, refused when empty, and cleared on send, a key minted per send, and the entry's "accepted, delivered at the next turn boundary" against "sending". Departures, each required by a requirement or decision ("Reference proof of concept"):

- **Sticky at the end of the page, not inside the conversation card.** POC: the field at the bottom of the Conversation `Paper`, scrolled away with it. "Product screens": the composer stays visible (Q9).
- **A `Textarea` with a send button, not a `TextInput` that sends on Enter.** A turn's text holds newlines, which the timeline shows line by line (31a); Enter adds a line.
- **Every documented answer has a state.** POC: sending and accepted only. The states of decision 3, with the retry by the same key (R29).
- **Role refusals come from the control plane.** POC: `RoleButton capability="send-turn"` hides the send for a viewer. The SPA has no role model before item 32's inbox; the 403 names the role, and the composer shows it (decision 8).
- **No stop button.** As 31a: the contract has no stop operation.

## Risks and trade-offs

- A `refresh` after a CSRF refusal shows the session's answer in the shell (a signed-in view with the operator the control plane names, or the sign-in page), so a tab whose session another tab replaced shows the truth; an unreachable control plane changes nothing, and the resend then shows the second refusal.
- The submission list is React state of the composer, keyed by the session's address; a navigation away drops the notices, while the records keep what still matters, the unconfirmed keys, and the next mount restores them as `unconfirmed`.
- `sessionStorage` is per tab (Q7): a retry from another tab is impossible, and two tabs that send the same message mint two keys and record two turns, as two operators would; the server's digest dedups only a repeat of the same key.
- A duplicate (200) of a turn before the loaded window shows that turn above the window, out of its window, in position order; "load earlier" reads it again and replaces it by `turnId`.
