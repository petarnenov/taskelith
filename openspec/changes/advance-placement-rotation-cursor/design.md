## Context

A placement pass reads at most `PLACEMENT_BATCH` waiting tasks with `PlacementQueue.waiting(limit, excluding, after)`, rank first and then the projects after the cursor `after`, wrapping, and offers them in the same order (`fairWaitingOrder`, `align-fair-order-rotation`). Each offer runs its own transaction; only the tasks that a candidate accepts receive capacity. The service then set `#after` to the last row's project. The last row belongs to the last round, which is the project with the deepest backlog in the read, so a read that holds every waiting task always ends with the same project and the rotation never moves past it.

## Decisions

- **The cursor is the project that last received capacity.** After a pass, `#after` is the project of the last task the pass placed, in offer order. With several placements in one pass this is the project of the last one, so the next read starts with the projects that the pass reached after it, or that it did not reach, and the project just served goes to the back. With one slot per pass, `a1` to `a3` and `b1` to `b3` place `a1`, `b1`, `a2`, `b2`, `a3`, `b3`.
- **A pass that placed nothing moves the cursor to the last project it offered before the fleet ran out of capacity.** An offer is a placement transaction that ended without an outage, whatever its outcome: declined, a retry still backing off, an attempt ended by a rejecting reason, or no longer waiting. Keeping the cursor instead would let projects with no capacity-eligible task hold the rotation: with 1200 blocked older projects, every read would return the same first 100 and never reach the placeable task, which the "Many blocked projects" scenario forbids. Moving to the last offered project skips only projects that were offered and declined for their own reasons.
- **A decline for lack of fleet capacity stops the cursor (review pass 1, H1; pass 2, L3).** `candidates()` returns every eligible worker, full ones included, so with a full fleet every offer is declined: `placeTask` returns `precondition-failed` with `details.reason` set to the last candidate's reason, `worker-capacity-exhausted`. Counting those as offers moved the cursor to the read's last project again, and with one slot freed every other pass `p-a` drained first. A decline whose reason is `quarantined`, `worker-not-eligible`, `worker-capacity-exhausted`, or `no-candidate` (the transaction found no candidate) is a decline for lack of fleet capacity. The cursor moves only by the offers before the pass's first such decline: to the last of them placed, else the last of them. A slot freed later in the same pass may still place a later project's task, but the cursor does not move past the projects that waited, so they are offered first in the next pass. `control-not-enforceable`, although a worker reason that tries the next candidate, is the task's own requirement (contract section 9): no freed slot satisfies it, so it counts as an offer and such a task cannot pin the cursor. `FLEET_REASONS` and `lacksFleetCapacity` in `domain/capacity-reasons.ts` name the set, `NO_CANDIDATE_REASON` included; the service uses the same function.
- **A pass that offered nothing keeps the cursor.** That is an empty read, a pass without any candidate worker (no transaction is opened), or an outage at the first offer. No project was offered capacity, so none loses its turn; when candidates return, the rotation resumes where it stopped.
- **An outage stops the pass and still moves the cursor.** The placements that committed before the outage received capacity, so the same rule applies to the offers made before it; the task whose transaction failed is not counted as offered.
- **Section 12 and bounded passes.** Every pass either places, and moves the cursor past the last project served, or places nothing and moves it past every project it offered before the fleet ran out of capacity; while the fleet is full, no project receives capacity, so none overtakes another. The cursor stays put only when a pass offered nothing, and a project with a waiting task is reached once each project ahead of it in the rotation has been served or declined; with blocked projects only, that is the ceil(P / batch) reads of the "Many blocked projects" scenario. A project declined only because the fleet capacity ran out is offered first in the next pass that reads its task, which is the fairness section 12 asks for; its task's placement backoff can keep it out of the reads that come first (see Risks). A project after the cursor that is blocked is offered again and declined, which costs a transaction, not capacity.
- **The domain owns the rule.** `RotationCursor` in `domain/fair-order.ts` starts at the read's cursor and takes one event per offer, in any combination: `placed(projectId)`, `declined(projectId)`, or `ranOutOfCapacity()`, after which no event moves it; `next` answers the cursor. The service's `#offer(order, after)` builds it, offers the tasks, and returns `outcome`, the number placed or the outage, together with `next`; `#placeDue` stores `next` in `#after`, on success and on an outage. It offers in `fairWaitingOrder(waiting, after)`, whose entries carry the project id; `fairPlacementOrder` stays for its other callers.
- **Contract-first.** The capacity reservation contract states the cursor rule in sections 5 and 13 before the code changes.

## Out of scope

- `#after` lives only in memory and resets when the control plane restarts; a follow-up for `close-g2`.
- The per-task placement backoff after a capacity decline (review pass 2, M1; not a regression): contract section 5 backs off a task waiting for capacity by 5 s to 60 s with jitter, the pass runs every 5 s, and a task still backing off is not read. A freed slot therefore goes to the read's first task that is due, and a project with many waiting tasks almost always has one due, so under jitter the rotation degrades towards a share proportional to the waiting tasks. Changing the backoff needs an owner decision, recorded as the follow-up change `placement-backoff-preserves-rotation` with the options: no task backoff after a decline for lack of fleet capacity; a backoff per project instead of per task; or always reading the project right after the cursor. The owner's delegate chose option (a) (away run `20261027T085757Z-opencode-1447`, relayed by the coordinator): no per-task backoff after a decline for lack of fleet capacity, only for the task's own reasons, so such a task waits for the next pass; contract first, as its own change after G2.
- The queues and their query are unchanged: they already start after the cursor they are given.

## Risks

- The cursor rule sees only the last candidate's reason (review pass 2, L4): `reserveOnCandidate` returns the outcome on the last candidate tried. With hard controls, a task whose controls one full worker supports and the last candidate does not ends with `control-not-enforceable`, counts as an offer, and moves the cursor as before H1. G2 requests no hard control (`DEFAULT_ATTEMPT_REQUEST`), so the case cannot arise yet; it matters once hard controls exist.
- A pass whose last placement is early in its read reads the projects after it again in the next pass. They were offered and declined, so this costs reads and transactions, not fairness; a pass that places nothing still jumps past the whole read.
