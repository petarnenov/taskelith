## Context

G3 item 16 implements the Git workspace contract (`docs/contracts/git-workspace.md`) with the pinned `git` CLI in sub-changes 16a to 16e (`docs/g3-plan.md`, row 16). 16b ([design](/openspec/changes/archive/2026-10-28-implement-git-runner-and-snapshot/design.md), decisions 11 and 13) and 16c ([design](/openspec/changes/archive/2026-10-28-implement-git-remote-operations/design.md), decision 10) left the hand-off, the reclaim, the crash points `WS5` to `WS10`, the 6 conformance cases that need them, and the Linux tests in the worker image to this change. The coordinator's brief settles the scope; 16e keeps the worker wiring and admission, item 38 the delegated-child half of "One handed-off workspace".

## Decisions

1. **Hand-off record.** `worker/workspaces/<name>/handed-off` holds JSON `{ containment, reclaimFailed }`: `containment` is null, `{ kind: 'cgroup', name }`, or `{ kind: 'process-group', id }`. It is written with `replaceFileAsync` of `@taskelith/data-root` (a new `0600` file, synced, renamed into place, the directory synced), read with `O_NOFOLLOW`, and removed with a directory sync. Its presence alone is the hand-off state (contract section 3, step 6), so `inspect`, `snapshot`, `push`, and `remove` keep 16b's refusal; a malformed record fails `handOff` and `reclaim` with `internal`, and an unreadable one rejects `handedOff`, never reads as absent (section 9).
2. **One hand-off at a time.** With an execution account, `handOff` refuses while another workspace's record exists (`other-workspace-handed-off`). The check and the write of the record run as one step of a promise chain per workspace root, shared by every adapter of the process, so of two concurrent hand-offs exactly one succeeds (the checklist's concurrency-race finding of 16a's double). One worker process owns a data root (its root lock), so a chain in the process is atomic per worker. A repeated hand-off keeps its record, a recorded failure included, after it proves a recorded containment empty, and opens the checkout again.
3. **Reclaim order.** `reclaim` reads the record (absent: done; `reclaimFailed`: `reclaim-failed` without a start), proves a recorded containment empty, launches the program and waits for its readiness signal, writes the containment into the record (`WS7`), lets the program run (`WS8.before`, `WS8`, `WS8.after`), proves its containment empty and frees it, sets the checkout `2700` (`WS9`), and removes the record last (`WS10`). A failure of the record write, or a crash before `go`, abandons the program.
4. **Program start.** The program starts waiting on its input for `go` and changes nothing before it; the worker writes `go` only after the record names the containment, so the record is durable before the program does anything (section 3, step 7). On Linux the program, started as root by the worker, writes its own process identifier into `<parent>/reclaim-<name>/cgroup.procs`, drops every supplementary group, and switches to the execution account (`setgroups([])`, `setgid`, `setuid`), and then writes `ready` on its output, which `launch` waits for (review pass 1, finding 1), before it reads `go`; on one account it is the leader of its own process group, whose identifier the record names. A worker that dies before `go` closes the input, and the program exits with code 3 without a change; so does a program that gets no `go` within its window, `RECLAIM_GO_BOUND_MS` (60 s), which `--go-within-ms` overrides for tests. The host maps exit code 3 to the outcome `abandoned`, and `reclaim` then fails with `unavailable`, keeps the record without a failure, and a retry proves the containment empty and runs a new program. So on Linux a waiting program sits in its cgroup only between the launch and the record write, and never outlives its worker (coordinator decision Q3).
5. **Proof.** `ReclaimHost.populated` reads the cgroup's `cgroup.events` (`populated 1`; a missing cgroup is empty) or `kill(-pgid, 0)` (`ESRCH` is empty, `EPERM` populated). The adapter polls every 200 ms (`RECLAIM_PROOF_INTERVAL_MS`) up to 30 s (`RECLAIM_PROOF_BOUND_MS`, `reclaimProofBoundMs` of the composition) and never kills. At the bound `reclaim` and `handOff` fail with `unavailable` and no reason, the record and the checkout stay, and the worker reports the workspace (coordinator decision Q1).
6. **Failed program.** A non-zero exit or a signal is a failure: the record gets `reclaimFailed: true`, `reclaim` fails with `precondition-failed` and reason `reclaim-failed`, and every later `reclaim`, also after a restart, fails so without a start. A crash at `WS8.after` runs the program once more after the proof, the window section 3 accepts.
7. **Program semantics.** Below the checkout, never the checkout itself: `lstat` each entry, skip a symbolic link, set `2770` on a directory it owns before it descends, set `0660` or `0770` (owner execute bit) on any other entry it owns, then replace every regular file with another hard link, whatever its owner, by a copy: the source opened with `O_NOFOLLOW | O_NONBLOCK` and checked by `fstat` to be the regular file seen, the copy created exclusively under a fresh name with the exact mode and renamed over the entry. No agent process runs during a reclaim (section 3, step 7), so the path `chmod` after `lstat` meets no race.
8. **Execution account.** `GitWorkspacesOptions.reclaimHost` is required: `LinuxReclaimHost` carries the containment parent and the execution account, `ProcessGroupReclaimHost` none. With an account, `prepare` gives the attempt directory and the checkout the execution group (`chown(path, -1, gid)`, allowed without `CAP_CHOWN` to a member of the group; deviation B, accepted by the coordinator and now stated in contract section 2), and the hand-off and the reclaim change the checkout's mode; on one account they change no mode, as section 2, "Same identity", says. A test without root declares its own account as the execution account (`simulatedSeparateAccount`). 16e composes the worker's host.
9. **Configuration mode.** The Linux tests showed that the harness's Git could not read `.git/config`, which 16b's rewrite created with mode `0600`; section 2 gives the group the owner's bits in a checkout, and the file holds only the repository format, so it is now `0660`. This changes 16b's code (`repository-config.ts`), outside 16d's scope as briefed; the coordinator accepted it as deviation A, with its fail-before evidence in `verification.md`.
10. **Umask.** The tests set umask `0007` for the worker process; making it the worker's is 16e's ("clone umask", 16c proposal).
11. **Linux tests.** `make verify-linux-git-workspace` builds the worker image with `installation.sh build-worker` and runs `test/linux-git-workspace.privileged.ts` with the repository mounted read-only, through the image's entrypoint (root with `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL`, the cgroup layout), plus the execution group and umask `0007`. It is opt-in like `verify-linux-cgroup`, as the brief says ("as existing Linux suites do"; coordinator decision Q2). Its data roots are under `/var/lib/taskelith-git-workspace-tests`, never under `TMPDIR`. It covers section 13: the image's pin; the whole conformance suite with the real execution account; real identities; the surviving program and the containment; the failed and the killed program; the program without `go` in its window or with a dead worker; the held slot while a program runs; each Git process's uid and cgroup; no secret in a result or a file of the data root; submodules; inherited settings.
12. **Image.** The worker stage installs `git=1:2.43.0-1ubuntu7.4` with `--no-install-recommends`, checks the package version with `dpkg-query` and `git --version`, removes the apt lists, logs, and caches, and clamps mtimes, as the stage's other steps do.
13. **Skip list.** It is empty, so it and its count test are retired; a test now checks that the second run holds both separate-account cases.
14. **API.** `GitWorkspaces` implements `WorkspaceProvider`; `GitWorkspaceOperations` is removed, a change of a private package only.

## Coordinator decisions (2026-10-28)

The coordinator Niki answered the open questions and the deviations on 2026-10-28.

1. **Q1, result at the proof's bound: (a).** A reclaim or a hand-off whose recorded containment is still populated at the bound answers `unavailable` without a reason, as implemented (decision 5). Contract amendment: section 9 now says that such a call answers `unavailable` and the caller may retry. It adds no reason.
2. **Q2, Linux suite in `make verify`: (a).** The suite stays opt-in as `make verify-linux-git-workspace` (decision 11); `verification.md` records its run with the image and its Git version.
3. **Q3, "before it starts": (a), with a condition.** The program keeps entering its containment before the record names it, provided a program that was launched but never got `go` does not outlive its launcher: when its worker dies, or no `go` arrives within a bound, it exits without acting and leaves its cgroup empty. The parent's death was already handled through the closed input; the bound was missing, and a program that missed it would have been recorded as a failed reclaim. Decision 4 now has the window of 60 s (`RECLAIM_GO_BOUND_MS`, injectable through `--go-within-ms`) and the `abandoned` outcome. Contract amendment: section 3, step 7, states the window and the retry.
4. **Deviation A, accepted.** The `.git/config` mode `0660` (decision 9) is a scope note on 16b's code, kept with its fail-before evidence.
5. **Deviation B, accepted.** The execution group that `prepare` gives the attempt directory and the checkout (decision 8) is now stated in contract section 2, "Modes where the identities differ".
6. **Reviewer efforts.** The review runs at the brief's efforts, reviewer A `codex gpt-6.1-sol` at medium and reviewer B `claude claude-opus-5-5` at high; `route.json` recommended high and xhigh, and "Routed effort" is not authorized yet.

## Review pass 1 resolutions (2026-10-28)

Reviewer A, Codex CLI `gpt-6.1-sol` at medium, reviewed `dcfdf821` against `7efc48d3` (High 1, Medium 6, Low 1); the records are in `findings.jsonl`, the evidence in `verification.md`.

1. **Finding 1, High, fixed in `fe994aa7`.** `launch` resolved at the `spawn` event, before the Linux program had joined its cgroup and dropped root, so a worker killed after the record write could prove an empty cgroup while the old program still started and later ran a buffered `go`. The program now writes `ready` on its output (`RECLAIM_READY`) after it joined its cgroup and switched to the execution account, and `launch` resolves only on that signal; output that ends or differs fails the launch with `unavailable` and closes the program's input. The process-group host gets the same handshake: its group exists from the spawn, so it closed no race there, but every program now has one start protocol. A program that hangs before its signal keeps `launch` waiting; the fixed program does nothing before it but a synchronous `cgroup.procs` write and three identity calls.
2. **Finding 2, fixed in `4f620a33`.** Each of the 13 crash points `WS5.before` to `WS10.after` runs the operation in a separate worker process (`test/crash-worker.ts`) that the armed point kills by `SIGKILL`, so neither the exception path nor `abandon` runs, and a new worker over the same data root recovers. `WS10.after` has its own case, the waiting program of a worker killed at `WS7.after` or `WS8.before` is shown to exit unchanged on its closed input, and the worker image's surviving program crashes the same way (`e1a5d52a`). `tasks.md` 2.4 states this coverage.
3. **Finding 3, fixed in `e1a5d52a`.** The Linux test of a program without `go` uses a checkout and a `0600` file that the execution account made (the image's root has no `CAP_CHOWN` or `CAP_DAC_OVERRIDE`), checks as a control that a program which ignores `go` makes the file `0660`, reads the exit code `3` of the timed-out and of the orphaned program from a FIFO that a root shell around the program writes, and checks the file's content and mode.
4. **Finding 4, fixed in `e1a5d52a`.** The uid and cgroup checks follow the readiness signal, the timeout case waits for the reported exit code with a 3 s window instead of polling for a short-lived state, and `processesOf` leaves out a process that exits while it is read.
5. **Finding 5, fixed in `e1a5d52a`.** The test observes the runner's output after the redaction boundary (wrapping `GitRunner`'s public `run`, `runChecked`, and `runParsed`), the worker's own stdout and stderr, the argv of every Git process, the results, and every file of the data root, for prepare, remote read, and push, each also against a remote that echoes the credential; it checks that the echoed credential reached the runner as `<redacted>`. The adapter has no logger; that limitation stays in `verification.md`.
6. **Finding 6, fixed in `962c500d`.** The spec delta modifies "Reclaim program containment" and "Reclaim program on one account": the containment is recorded after the program entered it and signalled readiness and before `go`, a program changes nothing before `go`, and it exits unchanged when its worker dies or no `go` comes within 60 s (coordinator decision Q3 (a), not a new amendment). Contract section 3, step 7, and the two other mentions say the same.
7. **Finding 7, declined.** No fixture or adapter Git process runs in a directory where discovery reaches past the scratch directory: the adapter's Git runs in `/` or in a checkout with its own `.git`, the fixture's native Git in its own repositories, and the wrapper's upward search stops at the checkout's `.git`. All 189 host adapter tests pass with the default `TMPDIR` (this host's `/tmp/.git` is empty) and with `TMPDIR` inside a valid Git repository whose configuration sets `core.hooksPath`; the code is unchanged.
8. **Finding 8, Low, fixed in `10a95669`.** `parseHandOffRecord` requires the `containment` key and reads only an explicit `null` as none; the parser test refuses `{"reclaimFailed":false}`.

## Risks

- A process group identifier can be reused after its group ends; 16e decides the macOS proof's details (16a design, risks).
- The image installs the pinned Git from the Ubuntu archive, which drops a superseded revision, so a later build fails until the pin moves. Two builds without cache gave one image manifest with the Git step; `make verify-worker-image-reproducible` still fails on a host with the containerd image store, since its index digest holds the default provenance attestation (`verification.md`).
- The new Linux tests use their own data roots, but the host's adapter tests still put theirs under `TMPDIR` (carried from 16c).
