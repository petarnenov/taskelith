## Context

G3 item 16 implements the Git workspace contract (`docs/contracts/git-workspace.md`) with the pinned `git` CLI in sub-changes 16a to 16e (`docs/g3-plan.md`, row 16). 16b ([design](/openspec/changes/archive/2026-10-28-implement-git-runner-and-snapshot/design.md), decisions 11 and 13) and 16c ([design](/openspec/changes/archive/2026-10-28-implement-git-remote-operations/design.md), decision 10) left the hand-off, the reclaim, the crash points `WS5` to `WS10`, the 6 conformance cases that need them, and the Linux tests in the worker image to this change. The coordinator's brief settles the scope; 16e keeps the worker wiring and admission, item 38 the delegated-child half of "One handed-off workspace".

## Decisions

1. **Hand-off record.** `worker/workspaces/<name>/handed-off` holds JSON `{ containment, reclaimFailed }`: `containment` is null, `{ kind: 'cgroup', name }`, or `{ kind: 'process-group', id }`. It is written with `replaceFileAsync` of `@taskelith/data-root` (a new `0600` file, synced, renamed into place, the directory synced), read with `O_NOFOLLOW`, and removed with a directory sync. Its presence alone is the hand-off state (contract section 3, step 6), so `inspect`, `snapshot`, `push`, and `remove` keep 16b's refusal; a malformed record fails `handOff` and `reclaim` with `internal`, and an unreadable one rejects `handedOff`, never reads as absent (section 9).
2. **One hand-off at a time.** With an execution account, `handOff` refuses while another workspace's record exists (`other-workspace-handed-off`). The check and the write of the record run as one step of a promise chain per workspace root, shared by every adapter of the process, so of two concurrent hand-offs exactly one succeeds (the checklist's concurrency-race finding of 16a's double). One worker process owns a data root (its root lock), so a chain in the process is atomic per worker. A repeated hand-off keeps its record, a recorded failure included, after it proves a recorded containment empty, and opens the checkout again.
3. **Reclaim order.** `reclaim` reads the record (absent: done; `reclaimFailed`: `reclaim-failed` without a start), proves a recorded containment empty, launches the program, writes the containment into the record (`WS7`), lets the program run (`WS8.before`, `WS8`, `WS8.after`), proves its containment empty and frees it, sets the checkout `2700` (`WS9`), and removes the record last (`WS10`). A failure of the record write, or a crash before `go`, abandons the program.
4. **Program start.** The program starts waiting on its input for `go` and changes nothing before it; the worker writes `go` only after the record names the containment, so the record is durable before the program does anything (section 3, step 7). On Linux the program, started as root by the worker, writes its own process identifier into `<parent>/reclaim-<name>/cgroup.procs`, drops every supplementary group, and switches to the execution account (`setgroups([])`, `setgid`, `setuid`) before it reads `go`; on one account it is the leader of its own process group, whose identifier the record names. A worker that dies before `go` closes the input, and the program exits with code 3 without a change. So on Linux a waiting program sits in its cgroup for the moment between the launch and the record write (open question 3).
5. **Proof.** `ReclaimHost.populated` reads the cgroup's `cgroup.events` (`populated 1`; a missing cgroup is empty) or `kill(-pgid, 0)` (`ESRCH` is empty, `EPERM` populated). The adapter polls every 200 ms (`RECLAIM_PROOF_INTERVAL_MS`) up to 30 s (`RECLAIM_PROOF_BOUND_MS`, `reclaimProofBoundMs` of the composition) and never kills. At the bound `reclaim` and `handOff` fail with `unavailable` and no reason, the record and the checkout stay, and the worker reports the workspace (open question 1).
6. **Failed program.** A non-zero exit or a signal is a failure: the record gets `reclaimFailed: true`, `reclaim` fails with `precondition-failed` and reason `reclaim-failed`, and every later `reclaim`, also after a restart, fails so without a start. A crash at `WS8.after` runs the program once more after the proof, the window section 3 accepts.
7. **Program semantics.** Below the checkout, never the checkout itself: `lstat` each entry, skip a symbolic link, set `2770` on a directory it owns before it descends, set `0660` or `0770` (owner execute bit) on any other entry it owns, then replace every regular file with another hard link, whatever its owner, by a copy: the source opened with `O_NOFOLLOW | O_NONBLOCK` and checked by `fstat` to be the regular file seen, the copy created exclusively under a fresh name with the exact mode and renamed over the entry. No agent process runs during a reclaim (section 3, step 7), so the path `chmod` after `lstat` meets no race.
8. **Execution account.** `GitWorkspacesOptions.reclaimHost` is required: `LinuxReclaimHost` carries the containment parent and the execution account, `ProcessGroupReclaimHost` none. With an account, `prepare` gives the attempt directory and the checkout the execution group (`chown(path, -1, gid)`, allowed without `CAP_CHOWN` to a member of the group), and the hand-off and the reclaim change the checkout's mode; on one account they change no mode, as section 2, "Same identity", says. A test without root declares its own account as the execution account (`simulatedSeparateAccount`). 16e composes the worker's host.
9. **Configuration mode.** The Linux tests showed that the harness's Git could not read `.git/config`, which 16b's rewrite created with mode `0600`; section 2 gives the group the owner's bits in a checkout, and the file holds only the repository format, so it is now `0660`.
10. **Umask.** The tests set umask `0007` for the worker process; making it the worker's is 16e's ("clone umask", 16c proposal).
11. **Linux tests.** `make verify-linux-git-workspace` builds the worker image with `installation.sh build-worker` and runs `test/linux-git-workspace.privileged.ts` with the repository mounted read-only, through the image's entrypoint (root with `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL`, the cgroup layout), plus the execution group and umask `0007`. It is opt-in like `verify-linux-cgroup`, as the brief says ("as existing Linux suites do"; open question 2). Its data roots are under `/var/lib/taskelith-git-workspace-tests`, never under `TMPDIR`. It covers section 13: the image's pin; the whole conformance suite with the real execution account; real identities; the surviving program and the containment; the failed and the killed program; the held slot while a program runs; each Git process's uid and cgroup; no secret in a result or a file of the data root; submodules; inherited settings.
12. **Image.** The worker stage installs `git=1:2.43.0-1ubuntu7.4` with `--no-install-recommends`, checks the package version with `dpkg-query` and `git --version`, removes the apt lists, logs, and caches, and clamps mtimes, as the stage's other steps do.
13. **Skip list.** It is empty, so it and its count test are retired; a test now checks that the second run holds both separate-account cases.
14. **API.** `GitWorkspaces` implements `WorkspaceProvider`; `GitWorkspaceOperations` is removed, a change of a private package only.

## Open questions for the coordinator

1. **Result at the proof's bound.** Section 9 names no failure for a containment still populated at the bound. Options: (a) `unavailable` without a reason, as implemented; (b) a new reason, such as `reclaim-pending`, amending sections 3 and 9. Recommendation: (a), since no caller distinguishes it before item 21.
2. **Linux suite in `make verify`.** The brief says "as existing Linux suites do", which are opt-in; the worker's prompt said "a make target that `make verify` runs". Options: (a) opt-in, as implemented; (b) run it in `make verify`, which needs privileged Docker and a worker image build with network on every push and in CI. Recommendation: (a).
3. **"Before it starts".** On Linux the waiting program enters its cgroup before the record names it, and acts only after. Options: (a) keep, as implemented; (b) write the record first on Linux, where the name is known. Recommendation: (a), one protocol for both platforms.

## Risks

- A process group identifier can be reused after its group ends; 16e decides the macOS proof's details (16a design, risks).
- The image installs the pinned Git from the Ubuntu archive, which drops a superseded revision, so a later build fails until the pin moves; `make verify-worker-image-reproducible` did not run with the new step.
- The new Linux tests use their own data roots, but the host's adapter tests still put theirs under `TMPDIR` (carried from 16c).
