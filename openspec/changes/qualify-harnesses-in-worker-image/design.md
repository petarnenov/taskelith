## Context

The macOS x86_64 records of 2026-10-24 pin `@anthropic-ai/claude-agent-sdk@0.3.308` and `@openai/codex@0.164.0` and give the SHA-256 of their darwin-x64 binaries. Each record leaves "Linux x64 and arm64 in the planned worker container image" open. Item 23a built the worker image from a `git archive` of the tracked files on the digest-pinned Ubuntu 24.04 base, with checksummed Node.js tarballs for linux/amd64 and linux/arm64. D11 (a) selects all four matrix entries and names the GitHub-hosted runner `ubuntu-24.04-arm` for native linux/arm64, where no local host exists. The qualification host is macOS 26 on x86_64 with Docker, so linux/amd64 runs natively and linux/arm64 only under QEMU.

## Decisions

- **Variant, not a change to the worker.** A `worker-harnesses` target builds `FROM worker`, so the default worker image is the same as before. A separate `harnesses` stage installs the packages, and the variant copies the result into `/opt/harnesses`, owned by root. The worker user can run the harnesses but cannot change them, so an auto-updater cannot replace a binary in place. The variant also sets `DISABLE_AUTOUPDATER=1`, as the Claude Code record requires. Codex has no such environment switch: `check_for_update_on_startup` is read from `CODEX_HOME`, which is per run, so the qualification run writes it there, and a Codex plugin must do the same.
- **Lockfile pins.** `infra/installation/harnesses/package.json` names the two exact versions. Its `package-lock.json` pins every package, including the SDK's peer dependencies and both harnesses' platform packages, by registry URL and `sha512` integrity. `npm ci --ignore-scripts` fails when a downloaded tarball does not match. The lockfile is separate from the root one: the harnesses are not dependencies of the published package, and only the opt-in image installs them. The dependency inventory therefore does not cover them. The lockfile pins every package; the qualification records state the integrity hashes of the two harness packages and their Linux platform packages, not of the transitive ones. The darwin-x64 tarballs at these versions match the lockfile integrity and contain binaries with the SHA-256 values of the macOS records, which ties this lock to the qualified artifacts.
- **Credential-free steps only.** This is the owner's decision of 2026-10-25. The steps are in `infra/installation/harnesses/qualify.sh` and run with `--network none` as the `taskelith` user. Their home is under the data root, with dedicated `CLAUDE_CONFIG_DIR` and `CODEX_HOME` directories. The steps record platform, OS, Node.js, user, and each binary's path, SHA-256, and version. They check that no `auth.json` or `.credentials.json` exists in the image, that the SDK's glibc package was installed and its musl package was not, and that both harnesses report no login. They generate the Codex app-server schema and hash it. They check that writes to the binaries are refused. Each step has an expected exit status, and any other status fails the run. The steps need no network because every scenario with network traffic also needs a login.
- **Side-effect check.** The harness-qualification spec names at least the harness's home and its binary directory. Here they are the qualification home, which holds both configuration directories, and `/opt/harnesses`. Before and after the steps, `qualify.sh` lists their entries with type, mode, and link target, plus the SHA-256 of every file. The script stores both listings and their difference, and `docker diff` adds every changed path in the container except the generated schema files. In the container only the steps run, so each difference is attributed to the step that writes it.
- **Not run, by reason.** No login is authorized, so all model-calling scenarios are not run: chat, correlation, resume, approvals, interruption, the crash scenario, outcomes, and egress with telemetry on and off. They stay open for G3 item 35 (Claude Code) and the G4 admission (Codex). linux/arm64 is not run. Its emulated build fails on this host, because GNU tar fails under Docker Desktop's QEMU. A native run needs an arm64 host or D11's runner, and by the coordinator's decision this item adds no workflow.
- **Pin check in `make verify`.** `test/harness-image-pins.test.ts` reads only tracked files. It checks the manifest's exact versions and that every locked package has a registry URL and an integrity hash. It checks that both harnesses lock their linux-x64 and linux-arm64 packages, and the Dockerfile stages. It also checks that each record states the locked integrity of the harness and its Linux packages. The existing composition test also checks that the variant runs unprivileged.
- **Opt-in heavy target.** `make qualify-harnesses OUT=<dir>` runs `scripts/harness-qualification.sh`. The script builds the variant for each platform from the tracked files, runs the steps, writes `steps.txt`, `changes.txt`, and `image.txt` per architecture, and removes the container and image.

## Risks and limitations

- The evidence is one run, on linux/amd64 only. Even a successful emulated arm64 run would not be support evidence, because emulation can hide architecture-specific faults.
- The Codex Linux binary is linked against musl and runs on the glibc base. Its startup and schema generation ran here; its runtime behavior under load did not.
- Both releases move fast; a later pin needs a new lockfile, a new run, and new records.
