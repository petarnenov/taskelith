## Context

`bindRepository` and `readRepositoryBinding` are declared in `control-plane.openapi.json` with the roles of [control-plane wire contracts](/docs/contracts/control-plane-wire-contracts.md) section 3 (`ACCESS_REQUIREMENTS`: `PROJECT_READ` and `PROJECT_MAINTAINER`), but `ROUTES` has neither, so both fell through to the 500 of `#dispatchBoard`. Sub-change 11a (`implement-project-setup`, #427) stores projects in `@taskelith/access`; sub-change 20f (`manage-scm-integrations`) stores SCM integrations in `@taskelith/integrations` and registers the GitHub plugin. The plugin's provider has `resolveRemoteUrl` and `capabilities.mergeMethods` ([source control contract](/docs/contracts/source-control.md) sections 2 and 4.1).

## Goals / Non-Goals

Goals: serve both operations over a store of their own, resolve the remote URL through the plugin, and declare the contract break of an output-only `remoteUrl`.

Non-goals: the audit events of SCM integrations (11b2), `createRun` and the G2 bridge (11c), any UI, live GitHub calls, and the per-run credential issue that re-checks the binding (item 21).

## Decisions

The coordinator (Niki) decided Q1 to Q7 on 2026-11-03; each decision below names its question.

1. **One binding per project (Q1).** `project_repository_bindings` has the primary key `project_id` and foreign keys to `projects` and `scm_integrations`. `@taskelith/integrations` owns it: the domain's `RepositoryBinding`, the port `RepositoryBindings`, its conformance suite `REPOSITORY_BINDINGS_CONFORMANCE`, an in-memory store, and the PostgreSQL store. The module does not depend on `@taskelith/access`; the port `BindableProjects` answers whether a project exists, and the composition adapts it from `ProjectSetupService.readProject`.
2. **Remote URL from the plugin (Q7).** The request names the integration, the repository, the integration branch, and the merge method; `remoteUrl` is output-only. `RepositoryBindingInput` keeps `additionalProperties: false`, so an old client that still sends `remoteUrl` gets 400 `invalid`. `RemoteUrlCandidate` has no other reference and is removed.
3. **Order of a bind.** The service checks, in order: the project exists (404); the integration exists (404); its plugin is registered (503) and builds a provider from the stored configuration (503 with the reason `integration-configuration-unusable` and no plugin message, coordinator decision Q2 after pass 1); `resolveRemoteUrl` succeeds (the mapping of decision 4); the resolved value has the `RemoteUrl` shape and names the requested repository (500 otherwise); its origin, the scheme and authority as written and normalized as an allowed origin is, without URL canonicalization, equals the integration's allowed origin (422 `remote-origin-mismatch`; an origin that does not normalize is a plugin defect, 500); and the plugin's `capabilities.mergeMethods` holds the merge method (422 `merge-method-undeclared`). The two 422 reasons keep the order that `BindingRefusal` documents. The store write comes last (decision 5). Each plugin result envelope, of the provider factory and of the resolver, is read once inside the boundary that catches the plugin's throws, into a plain snapshot; a throwing getter or a broken envelope is the plugin defect, 500, and its message reaches no answer or log.
4. **Resolver failures (Q4).** `not-found` becomes 422 `repository-not-visible`; `forbidden` becomes 422 `integration-credential-refused`, never a 401, which would tell the client that its own credential failed; `unavailable` stays 503 and `invalid` 400; `internal` and every other code become 500. A resolved value that is not a `RemoteUrl`, or names another repository, is a plugin defect and also 500. The four format reasons (`remote-not-https`, `remote-userinfo`, `remote-query`, `remote-fragment`) applied to a URL the client sent; a plugin URL of that kind is a 500, so they are removed from `BindingRefusal`.
5. **Stale resolution (Q6).** The resolver call runs before and outside the store's transaction, so a slow service holds no lock. The store's `put` takes the integration revision that the service resolved against and, inside its transaction, fails with `conflict` (409) when the integration is gone or its revision moved, so no binding is stored against an origin or plugin configuration that changed meanwhile. In PostgreSQL the check and the write run in one SERIALIZABLE transaction, so a concurrent `updateScmIntegration` either commits before the check or makes one of the two retry. In memory, the put and every integration write run in one exclusive section of `InMemoryScmIntegrations`, so an update that starts after a put's snapshot waits for the put, as the row lock makes it wait.
6. **Compare-and-set (Q5).** A first bind names no `expectedRevision` and fails with 409 when the project is bound; a later bind names the current revision and fails with 409 when it moved. Any field may change. A bind at the current revision that changes nothing, the resolved remote URL included, answers 200 with the stored binding and keeps its revision. The shared function `nextBinding` gives every store this meaning, as `changedConfiguration` does for integrations.
7. **Reads (Q6).** `readRepositoryBinding` returns the binding as stored, without resolving or re-checking it; an unbound project answers 404, as the document declares.
8. **Roles.** The server checks the path project's role before the body (`requirementBeforeBody`): a non-member gets the same 403 for an existing and a missing project, before any 404, as in 11a. `bindRepository` needs `project-maintainer`; an `installation-owner` without that role is refused, as for the other maintainer commands.
9. **Rebind and running attempts (Q2).** A rebind changes only the stored binding; running attempts keep the remote URL they were sent. The next credential issue or re-delivery reads the current binding and re-checks its origin (wire contracts section 4.1, "Credential issue"); item 21 serves that path.
10. **Contract break.** `control-plane.openapi.json` goes from 0.4.0 to 0.5.0, and `packages/contracts/breaking-changes.json` declares the changes that `make contract-breaking-changes` lists against the base `634080a0`. No client binds a repository before this change serves the operation, which until now answered 500. The web client `apps/web/src/generated/control-plane.ts` is regenerated.

## Risks / Trade-offs

- The resolver call can be slow; it runs outside any transaction, and the integration revision check closes the window it opens.
- A plugin that maps a missing repository to another code than `not-found` gives a 500 or 503 rather than the typed 422; the conformance suite of the SCM port checks `not-found`.
- An integration whose plugin is no longer registered answers 503 for a bind; a read still returns the stored binding.
