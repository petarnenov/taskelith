## Context

G1 left the SDLC module with workflow runs, gates, and task admission, and deferred attempts, assignments, and the ownership generation to G2. Items 3 to 6 fixed the execution facts as reviewed contracts: the launch authorization transaction and its rejection reasons (item 3), the facts a worker may report about an execution (item 4), the journal's observation identities and per-producer sequence (item 5), and capacity reservations with their justified release (item 6). Architecture section 6 places tasks, attempts, transitions, and cancellation semantics in the Execution module, and placement, reservations, and assignment policy in the Scheduling module, which uses Execution's contracts.

## Goals / Non-Goals

Goals: pure domain values and transitions with kernel results and compare-and-set generations, without I/O, for every fact and state the four contracts name for item 7, and the ownership generation bound into admission. Non-goals: application services, ports, repositories, adapters, wire schemas, quotas and delegation budgets, retry policy, sessions, and anything that runs a process.

## Decisions

- **Packages.** `@taskelith/execution` depends on the kernel and on `@taskelith/sdlc` (admission, gates, workflow definition, evidence references); `@taskelith/scheduling` depends on both and on Execution, so Scheduling reads Execution's facts and never the reverse. Each package has only `src/domain/` and a root export; there is no port entry, since no plugin implements anything here.
- **Task aggregate.** A task holds its admission identifier, its ownership generation, and its attempts, and each attempt holds its executions with their grants. The ownership rule (one owning execution per attempt) and invariant 2 (one active attempt per task) are then checked on one record, which a repository compares by its generation, as G1 records are. Execution facts are kept as history in the attempt, so a late start of an exited execution is recorded without a transition.
- **Ownership generation.** It is the version of a task's active ownership, held by the task. Opening an attempt and claiming ownership for a new placement raise it; the assignment created for that placement carries it, so a command or a launch request of an earlier owner is stale (`stale-ownership-generation`). Grants, starts, exits, and cancellation requests do not change it. A claim needs no execution that can still run: superseding an assignment with a grant is not an ownership change (capacity contract section 6).
- **Binding into admission.** The admission record gains an optional `ownershipGeneration`, set by `useAdmission` when the dispatch passes one, and kept by later changes. A task opens only from a used admission that binds one, at exactly that generation, and a re-admission binds an admission dispatched at the next generation. The parameter is optional so that the G1 API and tests stay compatible; the frozen `SdlcFramework` port does not see admissions.
- **Derived attempt phase.** An attempt's phase (`awaiting-launch`, `launch-authorized`, `running`, `ended`) is derived from its owning execution and its outcome (invariant 6). Item 3's "move the attempt to `launch-authorized`" is the new owning execution in state `authorized`. After an exit or `not-started`, the attempt awaits a new launch or its end, because item 3 allows another execution after `exited` and item 21 decides the outcome; the attempt ends only by `endAttempt`, by an operator reconciliation, or by a cancellation once nothing can run.
- **Assignments stay in Scheduling.** Placement and acceptance are the assignment's states (`offered`, `accepted`, `ended`), not the attempt's, so that acceptance, start, and outcome remain distinct facts (invariant 3). The launch check reads plain views (`LaunchAssignment`, `LaunchReservation`) that Scheduling produces, so Execution does not import Scheduling.
- **Launch authorization.** `authorizeLaunch` runs the checks of item 3 section 9 in its order, derives the relied-on gates from the run's workflow as item 3 section 2 states, applies the ownership rule of section 4, and returns the next task and the grant, or a typed `LaunchRejection`. `operation-mismatch` belongs to `replayLaunchOperation`, and `unavailable` to the service. Expiry is computed from `issuedAt` and the ttl; the worker's monotonic deadline is the worker runtime's (item 20).
- **Start observations.** `decideStartObservation` follows item 3 section 7. Its first check protects other workers: a grant or execution of another worker gives `foreign` and writes nothing. A start already recorded for the execution is a `duplicate` only when the observation names a grant bound to the execution. Quarantine and another epoch come next, and then a start without a grant of that execution, whether unknown or bound to another execution, is an `unauthorized-start`, as the contract's tests require; only a bound grant reaches `historical` or `started`. An `unauthorized-start` of an execution the task holds is kept in a separate list of unauthorized starts, once per grant identity, so it never occupies or blocks the accepted start; the service writes the cancellation for that execution only.
- **Immutability.** Launch parameters are a branded type that only `parseLaunchParameters` creates, so a grant cannot carry an unparsed ttl or skew. Every recorded value is a frozen copy: grant parameters, exit statuses, and reservation scopes and requests share nothing with their inputs, so a caller cannot change a recorded fact without a transition.
- **Refusals.** A worker refusal ends an offered assignment for any worker-side reason; an accepted assignment is not refused for admission pressure, because capacity contract section 8 makes it wait with its reservation, and bounded supersession applies to it instead.
- **Version-based acceptance.** Transitions accept a fact only from a state that allows it; a repeated fact is a `duplicate` that changes nothing; a fact a terminal state forbids is rejected for the caller to keep as evidence. Across observations, the producer cursor classifies a sequence as new, duplicate, rollback, or new incarnation, and confirms only the contiguous prefix (item 5 sections 6 and 8).
- **Cancellation.** A request is a field on the attempt, never a state. The attempt ends as cancelled when no execution of it can run, at once or when the owning execution's terminal fact is recorded. Revocation by an invalidating writer revokes every grant of the owning execution, keeps each grant's first reason, and requests cancellation.
- **Outcomes.** An ended attempt's outcome is that of its last exit (`exited`, or `operator-resolved` when an operator recorded it) or `not-started`, with whether cancellation was requested and the ownership generation the attempt ended in, so a later owner never relabels it. The task outcome fact reports it; acceptance of the task's work stays with its gates (invariant 11).
- **Reservation and release.** The reservation is embedded in its assignment, because an assignment has exactly one for its whole life. Ending an assignment releases only when no execution under it can run, which Execution reports through `executionsUnderAssignment`; otherwise the reservation stays held until `releaseAfterTerminalFact`. Supersession needs an assignment that never received a grant.
- **Reachability.** A worker's reachability is a Scheduling record of contacts, since placement reads it; heartbeat ingestion belongs to the Fleet module later. No execution or assignment transition takes it as input, so loss of contact cannot change an execution or release capacity (invariant 4). An older contact changes nothing, and contact is lost only against the latest contact.
- **Sessions.** Sessions are not modeled in G2, so this domain does not establish that a session has at most one active attempt; under capacity contract section 10, G3 counts sessions explicitly unless its session model establishes it.

## Risks / Trade-offs

- One task record holds all attempts and executions, so its history grows with retries and re-authorizations; item 11 may store it in several rows as long as the same generation guards each change.
- `authorizeLaunch` reads plain views of other modules' state; the launch authority (item 17) must fill them inside the authorization transaction, or the comparison is not linearized.
- The optional `ownershipGeneration` of `useAdmission` lets a G2 caller forget it; `openTask` rejects such an admission, so the omission cannot dispatch work.
