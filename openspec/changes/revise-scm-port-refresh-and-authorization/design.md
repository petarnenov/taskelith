## Context

The brief of the coordinator assigns part of G3 plan item 20: revise the item 7 port so that a refresh keeps the previous secret until the run confirms adoption, as item 26 does for worker credentials, add `authorization` to the run credential, and add the port operation that [control-plane wire contracts](/docs/contracts/control-plane-wire-contracts.md) section 4.1 assigns to item 20. The pattern of item 26 is `confirmCredentials` and `expirePredecessors` of `packages/modules/fleet` (`src/domain/enrollment.ts`, `src/ports/fleet-conformance.ts`): the predecessor stays valid until the successor is confirmed or the rotation's deadline passes.

## Decisions

1. **Versions on the port.** A refreshed credential keeps its `credentialId`, and each returned secret is a version, 1 at issue and one more at each refresh. [Execution wire contracts](/docs/contracts/execution-wire-contracts.md) section 8.7 already numbers versions this way, and its notice and fetch name a credential and a version, so the port's number and the wire's number are the same and item 21 needs no mapping. Without a version on the port, a confirmation could not say which of several live secrets the run adopted.
2. **Adoption ends earlier versions only.** `confirmRunCredentialAdoption({ credentialId, version })` ends every version below the named one and keeps it and later ones. [Worker messages and terminal](/docs/contracts/worker-messages-and-terminal.md) section 6 ends a version only once every attempt confirmed it or a later one, so item 21 confirms the lowest version that all holders adopted; ending later versions would break an attempt that already holds them. A repeated or stale confirmation succeeds and ends nothing more, because confirmations can arrive late or twice; it never restores an ended version.
3. **The deadline is the version's expiry.** Item 26's rotation names its own deadline. A plugin cannot end a secret at a future time by itself, because it acts only when called, so the port takes each version's own `expiresAt` as its deadline, which the service enforces where it can (GitHub's installation tokens expire after an hour). A module that wants an earlier deadline confirms a later version at that time. The contract's Forgejo column records that Forgejo enforces a deadline only by revocation.
4. **Unknown versions fail.** A confirmation of a version above the latest one fails with `not-found`, as does one for an unknown or revoked credential, so a confirmation from a confused caller cannot end the current version.
5. **Revocation ends every version.** Otherwise a revoked credential would leave a refreshed but unconfirmed predecessor usable.
6. **`authorization` checked as a header value.** The reader accepts a scheme of token characters, one space, and visible ASCII credentials with inner spaces only, at most 65536 characters, the bound of `ScmAuthorization` in `execution.openapi.json`, whose pattern only excludes control characters; the port's form is stricter, so every value it accepts fits the wire. A line break would let a plugin inject a second header into Git's `http.extraHeader`; a bare secret without a scheme is no `Authorization` value. The suite compares `authorization` across refreshes and runs as it compares secrets, and its findings never carry the value. Its form stays the plugin's, so the module names no SCM.
7. **`WorkspaceCredential` derived from `RunCredential`.** It becomes `Pick<RunCredential, 'credentialId' | 'secret' | 'authorization' | 'repositories' | 'permissions'>`, the same fields as before, so the workspace port, its adapters, and the `git-workspace-port` capability are unchanged, and a run credential passes to the workspace without a conversion.
8. **Remote URL as its own narrow port.** `RepositoryRemoteResolver.resolveRemoteUrl({ repository })` returns `{ repository, remoteUrl }`, checked with the pattern and the 2048-character bound of `RemoteUrl` in `execution.openapi.json`: HTTPS, a host name rather than an IPv6 literal, an optional port from 1 to 65535, and no white space, user information, query, or fragment, so that the URL also passes the conditions that `bindRepository` checks. The suite compares the project's URL with the fixture's new `projectRemoteUrl`, which the fixture knows natively, so a plugin cannot pass with a plausible but wrong URL. Making `remoteUrl` output-only in the wire contract and the binding handlers is not part of the port and stays with later item 20 work.
9. **Fixture code access through `authorization`.** The fixture's code read and write send the credential's `authorization`, as the Git workspace does, so a wrong header form fails the access probes; the in-memory SCM looks up code access by `authorization` and the other permissions by the secret.

## Wire contract text that the revision makes stale

[Execution wire contracts](/docs/contracts/execution-wire-contracts.md) section 8.7, "Version", answers `credential-ended` for "a version whose secret a refresh, a revocation, or its expiry ended". Under port `0.2.0` a refresh ends no version; a confirmed adoption of a later version does. The brief excluded the wire contracts; the coordinator widened the scope on 2026-11-03 to this wording only, because the port change created the drift. The sentence now says that a version ends when a confirmed adoption of a higher version ends it, when its own `expiresAt` passes, or on a revocation. No wire schema, OpenAPI or AsyncAPI document, reason code, or wire version changes; `execution.openapi.json` enumerates `credential-ended` without that wording. The same decision covers scenario "Ended version" of the `execution-wire-contracts` spec, which a MODIFIED delta rewords the same way.

## Risks

- A live service may not let a plugin end one of several tokens without the token itself; the GitHub plugin keeps each version's secret until it is ended, which is item 20's design.
- The suite now probes more accesses against a live service, about twice as many credential probes as before.
