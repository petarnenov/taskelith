## Context

G3 item 43 (`docs/g3-plan.md`, row 43) asks for the G2 native acceptance rows that ADR 0015 decision 5 ("Containment and platforms", "Cancellation race g and the 24c-dependent rows on macOS and Linux") defers to G3. This change takes the Linux x86_64 parts only, as the coordinator scoped it: the system-level cancellation part and the connectivity part of the Cancellation and Connectivity (G2) rows on `linux-ubuntu-24.04-x86_64`, run through the worker's Linux cgroup supervisor instead of the test-side process-group launch host. The macOS rows, race g, the `macos-26-arm64` re-run, and the `linux-ubuntu-24.04-arm64` entry stay with item 43, which stays open.

Before this change the G2 scenario workers composed `processGroupHost` (`test/g2-scenarios/scenario-worker.ts:154` at `3f23516a`, `test/g2-scenarios/process-group-supervision.ts:38-52`): a detached test supervisor on a platform without containment, signalling the child's process group. The scenarios ran only under `make verify`, unprivileged, so no record of 24c came from the cgroup supervisor.

## Decisions

1. **Export the product launch host.** `supervisionHost` moves from `apps/worker/src/main.ts` into `apps/worker/src/execution-supervision.ts`, beside `fileSupervision`, `fileRecordListing`, and `containmentScan`, which it composes, and the package index exports it. The move is cleaner than exporting it from `main.ts`, the process entry. Behavior is unchanged; three Linux-only unit tests cover it.
2. **One switch: the Linux launch environment.** When `TASKELITH_CONTAINMENT_PARENT`, `TASKELITH_EXECUTION_UID`, and `TASKELITH_EXECUTION_GID` are all set on Linux, as the privileged runner sets them, `ScenarioWorker` passes a containment parent and the execution account in its `WorkerSettings` and composes `supervisionHost` through `cgroupHost` (`test/g2-scenarios/scenario-launch.ts`). Otherwise it keeps `processGroupHost`, so `make verify` runs as before. The crash-before-ack fixture builds a `ScenarioWorker` in its own process from the inherited environment, so it switches with it.
3. **A containment parent per scenario worker.** On start the worker reports every populated containment under its parent that has no record as an unrecorded process (`apps/worker/src/launch-orchestrator.ts:173-180`). The three scenario files run in parallel in one container, and some scenarios run two workers, so each worker gets `<delegated parent>/<installation base name>-<worker name>`, created on start. A restarted worker of the same name, as in race e, gets the same parent. The directories are not removed: a cgroup with live or killed processes cannot be removed at once, and the container is removed with `--rm`.
4. **The supervisor start hold.** Race c holds the supervisor start until the cancel is journaled. The product host has no such hook, so `cgroupHost` wraps each `ExecutionSupervision` in `HeldStart`, which awaits the hold before `start()` and delegates every other method.
5. **Shared Linux launch helpers.** `linuxLaunchFromEnvironment`, `executionAccountOf`, and `admitExecutionAccount` move from `apps/control-plane/test/harness-composition.ts` to `@taskelith/testing` (`packages/testing/src/linux-launch.ts`), with unit tests. The crash-window harness admits the account to its spawns and order trace files; the scenario installation only opens its base for passage (mode 0711), because the held scripted process, running as the execution account, polls a release file there.
6. **Guard and cancel signal.** `assertContained` reads `/proc/<pid>/cgroup` of each started scripted process and fails unless it lies under the delegated parent; races c (when the seed cancels after the start) and h call it. It does nothing without the Linux launch environment. Under the cgroup supervisor a cancel kills the containment (`worker-supervisor` "Cancellation of the process set"), so the process ends by `SIGKILL`; the process-group host sends `SIGTERM` first. `CANCEL_SIGNAL` follows the environment, not the observed host, so that a run with the environment but the old host fails (fail-before evidence).
7. **Generalized runner, same names.** `tools/linux-cgroup/crash-windows.sh` runs the test files among its arguments and falls back to the crash windows when there are none; `scripts/linux-crash-windows.sh` also forwards `TASKELITH_TOXIPROXY_URL`, `TASKELITH_POSTGRES_PROXY_URL`, and `TASKELITH_NATS_PROXY_URL`, which `scripts/services.sh run` exports. On this branch NATS is plain `nats://` and its trust is in `TASKELITH_SERVICES_SECRETS`, which the script already mounts. The script names are kept, so `make verify-linux-crash-windows` and its tests are unchanged; a rename would touch the image, the `Makefile`, and archived citations for no behavior.
8. **Target and proofs.** `make verify-linux-g2-scenarios` runs the three 24c files through that runner against its own services project; `FILES` and `PATTERN` select. The Linux entry of `make native-acceptance` runs `acceptance-cancellation-races` (row cancellation: the races and the stale generations, which the row names) and `acceptance-partition` (row connectivity: the partitions), each recorded like every other proof; off Linux both are not applicable, as the crash-window proofs are. The stale writes of the connectivity row are the stale-epoch scenarios of the stale-generations file, recorded under the cancellation proof; the acceptance table cites them for both rows.
9. **Evidence on this host only.** Two `make native-acceptance ENTRIES=linux` runs with the seeds `20261026` and `7`, the two seeds of 24c's evidence. The Intel iMac is not applicable for the Docker-Engine worker-image row: Docker Desktop gives no host network outside its virtual machine (`run-g2-crash-windows-on-linux` design decision 3). The hosted `ubuntu-24.04` runner of `.github/workflows/linux-acceptance.yml` is the Docker-Engine evidence; it is re-dispatched after the merge as a follow-up.

## Hosted arm64 runner

`gh api repos/petarnenov/taskelith` gives a public repository owned by a user, and the repository has no self-hosted runner (`actions/runners`, total 0). GitHub's reference of standard hosted runners (`github/docs`, `data/reusables/actions/supported-github-runners.md`, last changed by `eb5a6158a3` on 2026-10-16) lists `ubuntu-24.04-arm` among the arm64 Linux labels for public repositories, free and unlimited there. No dispatch on it ran; adding a `linux-ubuntu-24.04-arm64` hosted dispatch is a follow-up, not part of this change.

## Risks

- A run of `make native-acceptance` on Linux takes about two minutes longer, and the hosted workflow's 60-minute bound has less slack.
- The guard covers races c and h only; the other scenarios rely on the same host composition.
- Each scenario worker's containment parent stays until the container ends; outside the `--rm` container of the runner nobody sets the Linux launch environment.
