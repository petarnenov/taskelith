## Context

G3 item 12 implements the account pool contract (`docs/contracts/account-pool.md`). The coordinator's split (contract section 11): 12a the slot records, the credential store, the add-slot command, and the `new-session` selection; 12b, this change, the cooldown from plugin signals, affinity on resume, and the selection after a limit; 12c the per-run delivery; 12d `wire-account-pool-into-control-plane`. 12a refused `resumed-session` and `after-limit` requests with `invalid` and asked 12b to replace that refusal (12a design, answer Q1). The agent harness port (`docs/contracts/agent-harness-port.md` section 4.1) defines the `limit` signal, `account-signal` with `signal: 'limit'`, and its optional `resetsAt`, which `parseHarnessEvent` of `@taskelith/execution` parses into `HarnessEvent`. No new third-party dependency is needed.

## Decisions

1. **Resumed session.** `selectResumedSessionSlot` takes the session's own slot with its held reservations and applies the eligibility of section 3.2: an eligible slot is reserved, even when another slot is less loaded; `unhealthy`, `cooling-down`, and `at-concurrency-limit` wait with `provider-concurrency-exhausted`, with the slot's cooldown end when its first obstacle is the cooldown; `revoked`, `removed`, and `not-allowed` reject with `session-slot-withdrawn` (section 4.3). No other slot is read, so none is chosen.
2. **After a limit.** `selectAfterLimitSlot` tries each alternative harness's pool in the request's order with the least-loaded rule (section 4.2) and reserves the first winner; otherwise the limited slot when eligible, which after a limit means once its cooldown ended; otherwise it waits with `provider-concurrency-exhausted` and the earliest cooldown end among the slots it waits for, the alternatives' pools and the limited slot, each counted only when its first obstacle is its cooldown. A limited slot that was revoked or removed is ineligible and its cooldown is not counted, so the request waits only for another harness (section 4.4). It never rejects. `selectSlotInTransaction` reads no pool of the limited harness, so another slot of that harness is never chosen.
3. **Stored session slot.** A `resumed-session` or `after-limit` request reads its pinned or limited slot with `AccountSlots.get`, in any state, because `pool` holds only active slots. A stored slot of another harness than the request names is `invalid` (section 4.1); a slot that was never added is the `not-found` of `get`, which ends the placement like any failure, before any write.
4. **Shared helpers.** `least-loaded-selection.ts` exports `eligibleStandings`, `reservedSlot`, `slotWait`, and `earliestCooldownEnd`, which take the standings instead of a `NewSessionPool`, so the three selections build their outcomes one way; `selectNewSessionSlot` behaves as in 12a.
5. **Selection stays in the reservation transaction.** All three kinds are selected by `selectSlotInTransaction` inside `placeInTransaction`, at the transaction's `now`, before `decidePlacement`, which decides the credential step as in 12a; only the insert of a placement writes the slot (section 4.7).
6. **Cooldown rule.** `cooldownAfterLimit(stored, report, now, default)` is pure: a reported reset after `now` gives `reported-reset` until that time, else `default` for the default minutes after `now`; the result replaces the stored cooldown only when it ends later, so an equal or shorter one keeps the stored cooldown and its source, and a stored cooldown that already ended is replaced (section 5). A cooldown stays stored after its end; eligibility compares its end with `now`, inclusive as in 12a, so no sweep clears it.
7. **Limit command.** `applySlotLimitInTransaction(tx, { assignmentId, signal, defaultCooldown })` runs in the caller's SERIALIZABLE capacity transaction, like the other capacity operations, and needs only `assignments`, `accountSlots`, and `now` (`SlotSignalTransaction`). It reads the assignment and its reservation's `providerCredentials`; a reservation that names no slot, or more than one, is `precondition-failed`, and an unknown assignment `not-found`. It applies the cooldown to the stored slot by `replace` at the read revision, and writes nothing when the cooldown does not change. It does not check the reservation's or the slot's state (questions Q3 and Q4).
8. **Reset time.** The port's `resetsAt` allows up to nine fraction digits, and `Instant` holds milliseconds; the command rounds a reset inside a millisecond up, so the cooldown never ends before the reported time, and refuses a `resetsAt` that is no instant with `invalid`.
9. **Rereads.** Section 5 rereads the slot after a lost compare-and-set and applies the report again. The command does so up to `SLOT_LIMIT_APPLICATIONS` applications, 3, and then returns the `conflict` (question Q6). On PostgreSQL a concurrent writer is a serialization failure instead, which `PostgresDatabase` retries as a whole transaction that rereads too.
10. **Races on PostgreSQL.** `account-pool-selection.integration.test.ts` runs four races through `gatedStore`, whose first attempt waits after the gated read until both racers read, while a retry passes the gate (the 12a pass 1 lesson): a resumed and a new session for the last unit of the resumed slot; two `after-limit` placements for an alternative's last unit; a limit and a placement that selects its slot; and two limits on one slot. Each identifies the racer that committed second, from the outcome or the slot's revision, and asserts that it ran at least two attempts.
11. **Neutrality and secrecy.** The neutrality test's file list gains the new files, and a test checks that the limit command's outcomes and failures hold no slot credential; the command reads no credential, and its failures name only the assignment, the slot, and the reset time.

## Open coordinator questions

The contract leaves these open; the change takes the conservative option named in each and does not decide them. They are pending the coordinator's answer.

1. **Q1, usage and health.** Contract section 5 also applies usage reports (window end from a usage window length per harness) and authentication failures (`unhealthy`), and section 9 tests them, but the brief scopes 12b to the limit and cooldown signals and no sub-change of section 11 names them. Conservative choice: 12b applies only the `limit` signal. Which sub-change applies usage reports and authentication failures?
2. **Q2, default cooldown setting.** The default is an installation setting from 1 to 1440 minutes, provisionally 60, and no installation setting store exists. Conservative choice: the caller passes it, parsed by `parseDefaultCooldownMinutes`, and stores nothing. Where is the setting kept, and is 12d's composition to pass 60 until an operator command exists?
3. **Q3, signal key.** Section 5 applies a signal to the slot of "the attempt's reservation", and item 18 relays a signal with its attempt. An attempt can have several assignments over time. Conservative choice: the command takes the `AssignmentId`, which names exactly one reservation. Is the assignment the key item 18 relays?
4. **Q4, late signals and withdrawn slots.** A limit can arrive after the reservation was released, or for a revoked or removed slot. Conservative choice: it is applied whatever the reservation's or the slot's state, since a cooldown only withholds new reservations and a reinstatement keeps it (section 8). Is that intended, or should a released reservation or a removed slot refuse it?
5. **Q5, far reported reset.** Section 5 bounds the default but not a reported reset, and no signal ends a cooldown early. Conservative choice: a reported reset is applied as reported, however far ahead. Should the pool bound it, for example to the default's maximum of 1440 minutes?
6. **Q6, bound on rereads.** Section 5 rereads after a lost compare-and-set without a bound. Conservative choice: at most 3 applications, then the `conflict` returns to the caller, who may apply the signal again. Is a bound acceptable?

## Risks

- An `after-limit` selection reads every alternative's pool and one held count per slot inside the placement transaction; pools are small, as in 12a.
- Nothing relays a signal yet (item 18) and nothing passes a slot request (12d), so the behavior runs only in tests until then.
