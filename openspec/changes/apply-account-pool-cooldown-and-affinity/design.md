## Context

G3 item 12 implements the account pool contract (`docs/contracts/account-pool.md`). The coordinator's split (contract section 11): 12a the slot records, the credential store, the add-slot command, and the `new-session` selection; 12b, this change, the cooldown from plugin signals, affinity on resume, and the selection after a limit; 12c the per-run delivery; 12d `wire-account-pool-into-control-plane`. 12a refused `resumed-session` and `after-limit` requests with `invalid` and asked 12b to replace that refusal (12a design, answer Q1). The agent harness port (`docs/contracts/agent-harness-port.md` section 4.1) defines the `limit` signal, `account-signal` with `signal: 'limit'`, and its optional `resetsAt`, which `parseHarnessEvent` of `@taskelith/execution` parses into `HarnessEvent`. No new third-party dependency is needed.

## Decisions

1. **Resumed session.** `selectResumedSessionSlot` takes the session's own slot with its held reservations and applies the eligibility of section 3.2: an eligible slot is reserved, even when another slot is less loaded; `unhealthy`, `cooling-down`, and `at-concurrency-limit` wait with `provider-concurrency-exhausted`, with the slot's cooldown end when its first obstacle is the cooldown; `revoked`, `removed`, and `not-allowed` reject with `session-slot-withdrawn` (section 4.3). No other slot is read, so none is chosen.
2. **After a limit.** `selectAfterLimitSlot` tries each alternative harness's pool in the request's order with the least-loaded rule (section 4.2) and reserves the first winner; otherwise the limited slot when eligible, which after a limit means once its cooldown ended; otherwise it waits with `provider-concurrency-exhausted` and the earliest cooldown end among the slots it waits for, the alternatives' pools and the limited slot, each counted only when its first obstacle is its cooldown. A limited slot that was revoked or removed is ineligible and its cooldown is not counted, so the request waits only for another harness (section 4.4). It never rejects. `selectSlotInTransaction` reads no pool of the limited harness, so another slot of that harness is never chosen.
3. **Stored session slot.** A `resumed-session` or `after-limit` request reads its pinned or limited slot with `AccountSlots.get`, in any state, because `pool` holds only active slots. A stored slot of another harness than the request names is `invalid` (section 4.1); a slot that was never added is the `not-found` of `get`, which ends the placement like any failure, before any write.
4. **Shared helpers.** `least-loaded-selection.ts` exports `eligibleStandings`, `reservedSlot`, `slotWait`, and `earliestCooldownEnd`, which take the standings instead of a `NewSessionPool`, so the three selections build their outcomes one way; `selectNewSessionSlot` behaves as in 12a.
5. **Selection stays in the reservation transaction.** All three kinds are selected by `selectSlotInTransaction` inside `placeInTransaction`, at the transaction's `now`, before `decidePlacement`, which decides the credential step as in 12a; only the insert of a placement writes the slot (section 4.7).
6. **Cooldown rule.** `cooldownAfterLimit(stored, report, now, default)` is pure: a reported reset after `now` gives `reported-reset` until that time, capped at `SLOT_REPORTED_RESET_MAXIMUM_MINUTES`, 10080 minutes (7 days), after `now` (answer Q5), else `default` for the default minutes after `now`; the result replaces the stored cooldown only when it ends later, so an equal or shorter one keeps the stored cooldown and its source, and a stored cooldown that already ended is replaced (section 5). A cooldown stays stored after its end; eligibility compares its end with `now`, inclusive as in 12a, so no sweep clears it.
7. **Limit command.** `applySlotLimitInTransaction(tx, { assignmentId, signal, defaultCooldown })` runs in the caller's SERIALIZABLE capacity transaction, like the other capacity operations, and needs only `assignments`, `accountSlots`, and `now` (`SlotSignalTransaction`). It reads the assignment and its reservation's `providerCredentials`; a reservation that names no slot, or more than one, is `precondition-failed`, and an unknown assignment `not-found`. It applies the cooldown to the stored slot by `replace` at the read revision, and writes nothing when the cooldown does not change. It applies a limit for a released reservation and for a revoked slot, which a reinstatement returns with its cooldown (section 8), and accepts one for a `removed` slot as a no-op: it returns the slot unchanged, with no error and no write (answers Q3 and Q4).
8. **Reset time.** The port's `resetsAt` allows up to nine fraction digits, and `Instant` holds milliseconds; the command rounds a reset inside a millisecond up, so the cooldown never ends before the reported time, and refuses a `resetsAt` that is no instant with `invalid`. `SlotLimitReport` carries the reset as epoch milliseconds, and `cooldownAfterLimit` caps it before it becomes an `Instant`, so the latest reset that the port accepts, `9999-12-31T23:59:59.999999999Z`, which rounds up into the year 10000 that `Instant` refuses, is capped like any other (review pass 1, finding 1).
9. **Rereads.** Section 5 rereads the slot after a lost compare-and-set and applies the report again. The command does so up to `SLOT_LIMIT_REREADS` times, 3, so at most four applications in all, and then returns the `conflict`, which is retryable: the caller may apply the signal again (answer Q6). On PostgreSQL a concurrent writer is a serialization failure instead, which `PostgresDatabase` retries as a whole transaction that rereads too.
10. **Races on PostgreSQL.** `account-pool-selection.integration.test.ts` runs four races through `gatedStore`, whose first attempt waits after the gated read until both racers read, while a retry passes the gate (the 12a pass 1 lesson): a resumed and a new session for the last unit of the resumed slot; two `after-limit` placements for an alternative's last unit; a limit and a placement that selects its slot; and two limits on one slot. Each identifies the racer that committed second, from the outcome or the slot's revision, and asserts that it ran at least two attempts.
11. **Neutrality and secrecy.** The neutrality test's file list gains the new files, and a test checks that the limit command's outcomes and failures hold no slot credential; the command reads no credential, and its failures name only the assignment, the slot, and the reset time.

## Coordinator answers

The design's open questions Q1 to Q6 asked the coordinator what the contract leaves open. The coordinator Niki (architect) answered on 2026-10-29, verbatim:

> Q1 New sub-change 12e `apply-account-pool-load-and-health-signals` (usage reports, authentication-failure health, the section 9 tests). If 12d later splits key rotation off, that becomes 12f. Name 12e as a follow-up in the proposal and in g3-plan item 12.
> Q2 Yes: 12d's composition supplies the default cooldown from an installation setting in the control-plane installation settings (default 60 min, range 1-1440). 12b keeps it a caller parameter.
> Q3 Keep AssignmentId. One attempt runs under one reservation, so item 18 carries the attempt's AssignmentId with each relayed signal; note that obligation for item 18 in the design.
> Q4 Keep it applied for a released reservation and for a revoked slot (the provider limit is real; a reinstated slot inherits the cooldown). For a removed slot: accept the signal as a no-op, no error, with a test.
> Q5 Cap the reported reset at 7 days (10080 min) from DB now, to cover weekly provider limits while keeping a bogus far-future value from locking a slot indefinitely; a later signal re-applies. Test at and past the cap.
> Q6 3 re-reads accepted; `conflict` is retryable by the caller, state it in the design.

How the change applies them:

1. **Q1.** 12b applies only the `limit` signal. Usage reports, the `unhealthy` health of an authentication failure, and their section 9 tests belong to the follow-up 12e `apply-account-pool-load-and-health-signals`; key rotation, if 12d splits it off, becomes 12f. The proposal, `docs/g3-plan.md` item 12, and contract sections 11 and 12 say so.
2. **Q2.** No code change. `applySlotLimitInTransaction` keeps the default cooldown a caller parameter, parsed by `parseDefaultCooldownMinutes`; 12d's composition supplies it from the control-plane installation settings, default 60 minutes, range 1 to 1440.
3. **Q3.** No code change. The command stays keyed by the `AssignmentId`. Obligation for item 18: it carries the attempt's `AssignmentId` with each signal it relays, since one attempt runs under one reservation. Contract section 12 states the key and the obligation.
4. **Q4.** A limit for a released reservation or a revoked slot is applied (decision 7; a reinstated slot keeps its cooldown, contract section 8). A limit for a `removed` slot is accepted as a no-op, with no error and no write; the test "a limit for a removed slot is accepted and writes nothing" failed before the change.
5. **Q5.** A reported reset after `now` is capped at 10080 minutes after the database time `now` (decision 6), and a later limit applies again by the rule of decision 6. Two tests failed before the change: "a reported reset is capped at seven days after now", which checks a reset at the cap, kept as reported, and two past it, and "a limit past the cap cools the slot for seven days", through the command. The spec delta, with "Least-loaded selection with cooldown" of `harness-account-pools` modified (review pass 1, finding 2), and contract sections 5 and 12 state the cap.
6. **Q6.** After 3 rereads, the first application and three more, the command returns `conflict`, which the caller may retry by applying the signal again (decision 9). The change first stopped after 3 applications in all; review pass 1 (finding 3) corrected it to the accepted 3 rereads.

## Risks

- An `after-limit` selection reads every alternative's pool and one held count per slot inside the placement transaction; pools are small, as in 12a.
- Nothing relays a signal yet (item 18) and nothing passes a slot request (12d), so the behavior runs only in tests until then.
- A limit past the cap leaves the slot eligible again after 7 days, before the provider's reported reset; a later limit cools it again.
