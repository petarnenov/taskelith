## Context

G3 item 12 implements the account pool contract (`docs/contracts/account-pool.md`) of item 5. The coordinator's brief splits it: 12a (this change) the slot records, the encrypted credential store, the selection inside the reservation transaction, and the slot limit of section 7.1; 12b cooldown from plugin signals, affinity on resume, and the selection after a limit; 12c the per-run delivery to the worker. The port types, the contract values, and the conformance suites exist since item 5; the in-memory doubles lived in the scheduling test. No new third-party dependency is allowed without asking the coordinator; none is needed.

## Decisions

1. **Slot count read.** Contract section 7.1 says that `AccountSlots` has no read that counts a harness's slots and leaves the check to item 12. `AccountSlots.countNotRemoved(harnessId)` counts the harness's slots in every project that are not `removed`, revoked ones included, so the slot limit counts exactly what section 7.1 counts. The conformance suite gains a case, and a test double that counts tombstones fails only that case.
2. **Admitted pairs.** `AdmittedDeliveries.find(harnessId, mechanismId)` answers the admitted pair's delivery (`subscription-token`, the only one of `SLOT_DELIVERIES`) and an optional `slotLimit`, or nothing. The control plane keeps the pairs outside the pool (section 7.1); the pool names no harness, so 12a registers no pair. `StaticAdmittedDeliveries` holds a fixed list. Claude Code's pair with limit 1 is registered by the item that admits the harness (open question Q3).
3. **Add-slot command.** `addAccountSlot` reads the pair and refuses a mechanism without one with `invalid`; it parses the record with version 1 first, so an invalid record stores nothing; it stores the credential, then runs one capacity transaction that reads `countNotRemoved`, refuses a count at the limit with `invalid`, and adds the record that names the stored version. An `Err` of that transaction discards the stored version. A rejected transaction promise (an unreachable store) may have committed, so the version is kept, as contract section 8.1 foresees for an add-slot command that crashes between its store and its `add`; the sweep of section 8.1 is not in 12a. On PostgreSQL the count and the insert run at `SERIALIZABLE`, so of two concurrent adds for the last allowed slot one loses a serialization race, is retried by `PostgresDatabase`, and then sees the count; the test runs it.
4. **Slot store on PostgreSQL.** One row per slot in `account_slots`, with a column per record field and checks that repeat `parseAccountSlot`'s invariants; rows are parsed back through `parseAccountSlot`. `replace` reads the row for the contract's order of `not-found` and `invalid`, then updates `WHERE revision = expectedRevision`, so a lost compare-and-set is `conflict`, and a concurrent writer in another transaction is a serialization failure that the retry turns into `conflict`. The pool orders by `slot_id COLLATE "C"`.
5. **Encrypted credential store.** The ciphertext lives in PostgreSQL and the key in `control-plane/` (contract section 1 allows the key or the whole store there). This keeps versions transactional: `slot_credential_counters` holds each slot's last version and a destroyed mark, so a store is one `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` of the counter followed by the insert of the ciphertext unless destroyed, and concurrent stores serialize on the counter row. `destroy` marks the counter and deletes every version, so a later or concurrent store keeps nothing and versions are never reused. Each operation commits in a `SERIALIZABLE` transaction of its own (`PostgresSlotCredentials` takes the transaction runner), because `SlotCredentials` is outside `CapacityTransaction` (section 6.2); a failed transaction rejects the promise with a message that holds no credential.
6. **Cipher and key.** AES-256-GCM from `node:crypto` (`AesGcmSlotCredentialCipher` in `@taskelith/secrets`): a random 96-bit nonce per seal, a 128-bit tag, and `taskelith-slot-credential`, the slot identifier, and the version as authenticated data, so a ciphertext copied to another slot or version, read with another key, or changed fails to open. `reveal` then fails with `internal` and names only the slot. The cipher prints, serializes, and inspects as `[redacted]`. The 32-byte key is the document `control-plane/slot-credential-key` (`openSlotCredentialKey` in `@taskelith/control-plane-store`), written once with the namespace's owner-only create, and a concurrent creator's key wins. A malformed key file is refused with `precondition-failed`, naming the file and not its content. The PostgreSQL adapter declares the cipher interface it needs (`SlotCredentialCipher`), which the secrets cipher satisfies, so `@taskelith/postgres` gains no runtime dependency. Key rotation is not implemented (open question Q4).
7. **Selection in the placement transaction.** `PlacementRequest.slotRequest` replaces `providerCredentials` (section 4.7: the caller never passes a credential). `selectSlotInTransaction` parses the request with `parseSlotRequest`, reads the pool and each slot's `heldForCredential`, and selects at the transaction's `now` with the pure `selectNewSessionSlot`: eligibility in the order of section 3.2, the least-loaded rule of section 4.2, and the policy of section 4.5; a wait carries the earliest cooldown end of the slots whose first obstacle is their cooldown. The selection runs before `decidePlacement`, which reads everything first as before, and decides its credential step (after the quota check, before the charge check). The insert of a placement records the selected slot as the only entry of `providerCredentials` and replaces the slot with `lastReservedAt = now` at the next revision, after the assignment insert, so a candidate declined for its worker writes no slot. The selection reruns for each candidate of a task in one transaction; it reads only and gives the same result, which section 4.7 allows.
8. **Request kinds of 12b.** `resumed-session` and `after-limit` fail the placement with `invalid` until 12b implements sections 4.3 and 4.4, so no session is placed against the affinity rules (open question Q1).
9. **Rejecting reasons and the board.** `REJECTING_REASONS` spreads `SLOT_REJECTING_REASONS` (section 4.5). The Scheduling test that keeps the board's reasons equal to Scheduling's (product ports contract section 3.8) and the contract test that keeps the `rejected` obstacle enumeration equal to the board's then require both mirrors, so `PLACEMENT_REJECTING_REASONS` of `@taskelith/execution` and the obstacle schema of `control-plane.openapi.json` gain `no-eligible-slot` and `session-slot-withdrawn`. `make contract-compatibility` reports the added response enumeration values as breaking, so the document goes to 0.4.0 and `packages/contracts/breaking-changes.json` declares the six changes (open question Q2).
10. **Neutrality.** A test reads the pool's source and test files and finds no harness or vendor name; it holds the list of names it forbids and removes that list from its own text before the scan.

## Open coordinator questions

1. **Q1, request kinds.** The pure selection of `resumed-session` and `after-limit` (sections 4.3 and 4.4) is small and reads the same pool, but the brief places affinity and the selection after a limit in 12b. Conservative choice: 12a selects `new-session` only and refuses the other kinds with `invalid`. Should 12a include them instead?
2. **Q2, wire version.** Adding the slot rejecting reasons to Scheduling (contract section 4.5) forces the board mirror and the OpenAPI obstacle enumeration, a breaking change by `make contract-compatibility`, so `control-plane.openapi.json` goes to 0.4.0. Conservative choice: keep every mirror equal, as the existing tests require, and declare the change. Is this wire change wanted in 12a, or should it be its own change?
3. **Q3, Claude Code's pair.** The pool cannot name a harness, and the control plane has no list of admitted pairs yet. Conservative choice: 12a provides the `AdmittedDeliveries` port, the limit check, and `StaticAdmittedDeliveries`, and registers no pair; item 19 (or its wiring) registers Claude Code's `subscription-token` pair with limit 1. Which change registers it?
4. **Q4, unassigned work.** None of 12a, 12b, or 12c names the slot commands other than adding (allowed projects and concurrency limit, revoke, reinstate, rotate, remove), the sweep of section 8.1, the HTTP operations of 9a's account slots, the composition of the key and `PostgresSlotCredentials` in the control plane, and key rotation. Conservative choice: none of them is in 12a. Where do they go?

## Risks

- The selection reads every slot of the pool and one held count per slot inside the placement transaction; pools are small, and each count uses the held-credential index of the resource admission migration.
- A slot write of every placement makes concurrent placements that select the same slot serialize; that is the contract's intent (section 4.7) and the race test covers it.
