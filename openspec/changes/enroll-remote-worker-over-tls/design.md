## Context

Decision D11 (b) of the [G3 plan](/docs/g3-plan.md#owner-decisions) says that workers pin the installation authority at enrollment. Sub-change 26a ([archived change](/openspec/changes/archive/2026-10-28-issue-installation-certificates/design.md)) created the installation CA, served the worker API over HTTPS and NATS over TLS on certificates it issued, and left pinning to 26b (its decision 10): the local Linux worker trusts the CA through `TASKELITH_NATS_CA` and `NODE_EXTRA_CA_CERTS`, which adds it to the system roots. The away delegate's decisions of away run `20261027T221048Z-claude-63826`, as the coordinator's brief carries them, set 26b: decision 3, workers keep the bearer secret and the NATS user JWT over TLS that authenticates the server only, without mutual TLS; decision 4, the enrollment bundle carries the CA's fingerprint, with no trust on first use.

Before this change, `HttpEnrollmentClient` posted the token with the global `fetch`, which trusts the system roots and `NODE_EXTRA_CA_CERTS`, and the worker connected to the broker with the CA of `TASKELITH_NATS_CA`, or plain without it.

## Decisions

1. **The bundle.** `issue-enrollment-token` prints `{"enrollmentToken": ..., "installationCaSha256": ...}`. The fingerprint is the SHA-256 of the CA certificate's DER, 64 lowercase hexadecimal digits, computed from `installation-ca.pem`, read under the namespace's owner, mode, and link checks after the operator is authorized and before the token is issued, so a missing or invalid file issues no token and an unauthorized operator gets `forbidden` whatever the file's state. The operator hands the worker both values; the worker reads the fingerprint from `TASKELITH_INSTALLATION_CA_SHA256`. The worker also accepts the colon-separated or uppercase form that `openssl x509 -fingerprint -sha256` prints, so an operator can compare it with that output; it normalizes before it compares. Two fields rather than one encoded string keep the token's existing variable and redaction shape (`tken_`) unchanged.
2. **A public CA operation.** `readInstallationCa`, `GET /installation/ca`, declares no credential (`security: []`) and answers `InstallationCa`, whose only property `certificate` is one PEM certificate block; the schema's pattern admits nothing else, so no key block can pass the response check. The execution OpenAPI document goes from 0.4.0 to 0.5.0: a new operation and schema, no change to an existing one. The control plane reads `installation-ca.pem` once at start, under the namespace's checks, and refuses to start when it is missing or is not exactly one CA certificate; a failure names the file and never quotes it. Reading at start, not per request, keeps the operation free of file access and its failures; `make installation-certificates` restarts the control plane after it rewrites the file (26a decision 11).
3. **The check before the token.** The worker reads the CA before it sends anything secret. That read uses TLS that does not verify the server, because the worker trusts nothing yet; what makes the answer trustworthy is that its SHA-256 equals the fingerprint the operator handed over out of band, so this is not trust on first use. The answer must be one CA certificate (`basicConstraints` CA); otherwise, or on a different fingerprint, the start fails with `precondition-failed` and reason `installation-ca-mismatch`. The order is the root claim, the CA read and check, then the token. A failure at any of them abandons the claim, so no `worker/` subtree remains. The comparison runs in the worker's application layer (`apps/worker`), and the HTTP adapter only reads and parses.
4. **Where the pin lives.** `worker/installation-ca.pem`, mode `0600`, created once by the durable file rule after the journal and before `worker/identity`, like the credential files; an identity therefore implies the pin. A later start reads it through the control-record path checks and fails with reason `corrupt` when it is missing or empty. Roots enrolled before this change have no such file and so fail closed, with a message that names the missing pin and says to remove `worker/` and enroll again. No migration, pre-release: no deployed installation exists, and a local one is re-enrolled.
5. **HTTPS pinning with `undici`.** The client's `HttpFetch` port carries a `ServerTrust`, the pinned CA or no verification for the CA read, and only `undici-fetch.ts` maps it to an `undici` `Agent`, so a `node:https` `HttpFetch` can replace it and no `undici` type leaves the module. The pinned `Agent` sets `rejectUnauthorized: true`, because Node otherwise takes it from `NODE_TLS_REJECT_UNAUTHORIZED`; every request carries `redirect: 'error'`, because a redirect could lead to plain HTTP. `@nats-io/transport-node` 3.4.0 sets `rejectUnauthorized: true` before it merges the endpoint's `tls`, so the broker needs no change; a test covers it. Every control-plane call of the worker, the enrollment, the launch authorization, and the evidence publication, passes an `undici` `Agent` whose `connect.ca` is the pinned CA. Node's TLS replaces the default roots, `NODE_EXTRA_CA_CERTS` included, when a CA is given, so a certificate that the system trusts but the installation CA did not issue fails the handshake before a request, and its bearer, is sent. `undici@7.30.1` is the version Node.js 24.22.1 bundles (`process.versions.undici`); it becomes a runtime dependency of the private adapter `@taskelith/worker-control-plane-client`. The lockfile already held it for `@semantic-release/github`, with the same integrity. Rejected alternative: `node:https` requests, which would also pin without a new package but would need the multipart body of `publishEvidence` encoded by hand and would leave `fetch`'s response handling.
6. **Broker pinning.** The worker's broker endpoint carries `tls: {ca: <pinned CA>}`, which `@nats-io/transport-node` passes to `tls.connect`, so the pinned CA is its only CA. The worker no longer reads `TASKELITH_NATS_CA`. Test harnesses whose broker is the integration services' NATS, whose certificate comes from a test CA, replace the endpoint's CA with that test CA in their injected `connect`; that is test composition, not a worker setting.
7. **HTTPS only.** `TASKELITH_CONTROL_PLANE_URL` must be `https:`; a plain URL would send the token in the clear and pin nothing. Adapter tests still use plain local servers where TLS is not under test.
8. **Outbound only.** The worker still opens no listening socket. The existing test checked only that no `TCPServerWrap` existed in a process with no server; the new test enrolls over pinned TLS against a local HTTPS server in the same process and records, through an `async_hooks` hook, every listening handle (`TCPSERVERWRAP`, `PIPESERVERWRAP`, or `UDPWRAP`) created during the start; it requires none. The hook also sees an unreferenced handle, which `process.getActiveResourcesInfo` omits.
9. **Out of scope.** Mutual TLS (rejected by 26a decision 3), delivery of a rotated generation (26c), CA rollover (G6), the private-network bind and the acceptance worker (26d).

## Review checklist

The coordinator's brief listed the checklist in [checklist.json](checklist.json) (dev commit `1c73e1a7`): the most frequent review categories are contract-drift, error-handling, redaction, docs, spec-wording, evidence-mismatch, and missing-fail-before-test; the most frequent record-quality categories are evidence-mismatch, docs, spec-wording, stale-citation, and contract-drift.

How the change guards against them: the OpenAPI document, the route table, the specs, and the contracts change together, and the route table's operation is checked against the document by its response schema (contract-drift, docs); every new failure is a `Result` that names a variable or file, and a failed check abandons the root claim (error-handling); the CA operation's schema admits one certificate block only, and failures never quote the token, a fingerprint input, or PEM text (redaction); each scenario states an observable outcome (spec-wording); each required behaviour has a test shown to fail on the base, recorded in `verification.md` with real counts (missing-fail-before-test, evidence-mismatch).

## Risks and limitations

- An operator who copies a wrong fingerprint gets `installation-ca-mismatch` and must issue a new token only if the old one has expired; the token is not spent by the failed start.
- The CA read's unverified TLS lets a man in the middle learn that a worker is enrolling and answer another CA; the check then refuses it, so the attacker gets no token, but the worker cannot enroll until the path is clean.
- A Linux worker container and the native scenario run depend on hosts this change could not fully exercise (see `verification.md`).
