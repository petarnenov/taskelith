## Context

Item 4 defined workflow definitions, run bindings (which carry the policy revision), work items, and artifact revisions; item 5 defined gates, evidence, invalidation of gates, and stage progress, and left admission and application services to this item. Architecture section 6 describes admission records and their invalidation; section 9 binds a task to its SDLC run and stage when it is created. Decision D4 (a) of the G1 plan keeps attempts and assignments, and with them the ownership generation, in G2.

## Goals / Non-Goals

Goals: pure admission rules that compose the gate and stage rules, and one application service with a repository port and an in-memory adapter that exercise them. Non-goals: the ownership generation, launch authorization, attempts, events, wire contracts, durable persistence, and task kinds other than planning and implementation.

## Decisions

- **Capability.** A new capability `sdlc-task-admission`. Admission is a separate concern from gate and stage transitions, which it reads but does not change, and the wire contracts of item 13 will reference it on its own.
- **Task kind from the stage.** A stage that covers `implementation` takes implementation tasks; a stage that covers `intake` or `specification` and not `implementation` takes planning tasks; a stage covering neither, such as a review stage, takes neither kind in this item. The caller states the kind by calling the matching operation, and a mismatch is `precondition-failed`, so a planning admission cannot open an implementation stage.
- **Record.** An admission holds its identifier, the task identifier, the kind, the workflow identifier and version and the stage, the work item identifier when there is one, the artifact revisions it is bound to (at most one per artifact), the policy revision of the run, the revisions a planning task created, its state, a generation, the time of its last change, and, once invalidated, the revision that invalidated it. The run binding must name the same workflow and version as the stage progress; otherwise the request is `precondition-failed`. The ownership generation is not modeled until assignments exist (G2).
- **Implementation rule.** An implementation task needs a work item and a stage with at least one prerequisite stage, every one of which has passed under the `sdlc-gates` rule (at least one gate, all passed). A stage without prerequisites therefore admits no implementation task, because no gate could have validated its inputs. The admission is bound to the union of the subjects of the prerequisite gates; if two of them judged different revisions of the same artifact, the inputs are inconsistent and the request is `precondition-failed` naming the artifact.
- **Planning rule.** A planning task needs neither a specification nor a work item, since it may create both, and no prerequisite gate. It is bound to the revisions the caller says it starts from, possibly none. Once used (dispatched), it records each revision it creates; an admitted, invalidated, or implementation admission records none.
- **States.** `admitted` to `used` when the task is dispatched, and `admitted` to `invalidated` when a bound artifact changes; `used` and `invalidated` are final. Only unused admissions are invalidated, as architecture section 6 says; started work is the stop and reconcile policy of G2. Every transition takes the generation its writer read and fails with `conflict` before any other rule, as in `sdlc-gates`.
- **Invalidation.** A revision outdates an admission exactly when the admission is bound to a revision of the same artifact with a different digest; the same content read elsewhere does not. The service invalidates every unused admission the revision outdates, both when a planning task records a created revision and on request for revisions from elsewhere.
- **Ports.** `AdmissionRepository` (get, add, compare-and-set replace, and listing the unused admissions bound to an artifact) and `Clock` are outbound ports owned by the module in `src/ports/`, separate files from the `SdlcFramework` port of item 6. The repository is asynchronous so that a database adapter can implement it unchanged. Domain rules still take the time as an argument; only the service reads the clock.
- **Concurrent invalidation.** The service writes each invalidation with compare-and-set. When a concurrent writer changed one of the admissions, it stops with `conflict`; running it again is safe and completes the rest, because invalidated and used admissions are no longer listed as unused. Recording a created revision invalidates first and stores the planning admission last, so that a failed invalidation leaves it at the generation the caller read and the same call can be repeated without recording the revision twice.
- **Type-only modules and coverage.** The ports are interfaces, so their compiled files are empty modules that no test can load, and the coverage scope check would report them as missing. The check now skips a module whose compiled file contains only `export {};` after comments are removed; a module with any statement must still appear in the report.
- **In-memory adapter.** `InMemoryAdmissionRepository` lives in `src/adapters/` of the module, as the plan asks for an in-memory repository in `@taskelith/sdlc`; durable adapters belong in `packages/adapters/` with G2.

## Risks / Trade-offs

- The caller supplies the gates of the run. Marking gates stale when an artifact changes is a separate `sdlc-gates` operation; until a run aggregate owns both, a caller that does not mark them could admit new implementation work against the old revisions. Omitting a gate never admits more, because a stage needs at least one gate and all of them passed.
- Invalidation over several admissions is not atomic in memory or in the port; it is idempotent and repeatable instead. A durable adapter may do it in one transaction.
