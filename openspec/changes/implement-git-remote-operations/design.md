## Decisions

1. **Order of refusals.** `readRemoteHead` checks the workspace record (`not-found`), the kind (`invalid`, `read-only-workspace`), and the credential's `read-code` scope (`forbidden`), and then reads only the remote, so it works while the workspace is handed off (contract section 3, step 6). `push` checks the record, the kind, the `write-code` scope, the hand-off record (`workspace-handed-off`), the Git directory (`unsafe-checkout`, then the `.git/config` rewrite), and the clean state (`workspace-dirty`), then the remote. The shared `#boundTaskBranch` reads the record and checks kind and scope; `#openedAt` keeps 16b's hand-off, directory check, and rewrite. Every refusal before the remote makes no remote call (tests "the remote head read checks ..." and "the push checks ...").
2. **Remote head.** `git ls-remote <binding remote> refs/heads/<branch>`, started in `/` (`GIT_NEUTRAL_DIRECTORY`) with the credential's header, so no repository configuration acts. `ls-remote` matches patterns by their tail, so the adapter takes only the line whose ref is exactly `refs/heads/<branch>`; none is `null`. A failed process is `unavailable`; a line that is not `<object>\t<ref>` or an object name that is not 40 or 64 lowercase hexadecimal characters is `internal`.
3. **Lease and ancestry.** As contract section 8 and the brief settle it: the push reads the remote head first and fails with `remote-moved` when it differs from the expected head, which covers an expected head that the remote never had. With an expected head, the workspace's head must descend from it, else `not-fast-forward`. The ancestry is read from verified commits (`readVerified` with the new `parseCommitParents`), generation by generation, never with `merge-base --is-ancestor`, which reads whatever object a forged pack gives a name (test "a commit whose bytes do not hash to its name fails the push ancestry check"). First `git cat-file --batch-check` asks whether the clone holds the expected head as a commit; when it does not, the head cannot descend from it and the walk is skipped, which is the usual case of a remote that another party moved. That shortcut can only refuse: a hidden ancestor makes the push fail closed. Then the push runs exactly `taskBranchPushArguments(branch, expected, binding remote)` in the checkout with the credential. When it fails, the remote head is read again: a head other than the expected one means the lease refused a branch that moved after the read (`remote-moved`, test "a remote that moves between the head read and the push ..."); otherwise the push is `unavailable`.
4. **Planted remotes.** The push names the binding's remote URL from the workspace record, never a remote of the checkout, and runs after the rewrite of `.git/config`; the remote head read starts in `/`. A test plants `remote.origin.url`, `remote.origin.pushurl`, `remote.pushDefault`, `branch.<task>.remote`, and a `url.<other>.insteadOf` rewrite of the binding's origin, then reads the remote head and pushes: the other origin receives no request.
5. **Redirects (coordinator decision Q1 (a)).** See "Coordinator decisions". Git's default `http.followRedirects=initial` follows a redirect of the first request, the advertisement, and then sends every later request, with the header, to the new origin. With `false`, Git stops at the first redirect of any request.
6. **Time limit (coordinator decision Q2 (a)).** `GitRunner` spawns every Git process with `detached: true`, so it leads a process group of its own (Node calls `setsid`), and after its time limit kills the group with `process.kill(-pid, 'SIGKILL')`, which also reaches `git-remote-http` and any other helper Git started. The runner resolves on `close`, after every process holding its pipes has exited. The bound is `GIT_TIME_LIMIT_MS`, 10 minutes, the runner's default; `GitWorkspacesOptions.gitTimeLimitMs` sets another through `GitRunner.withTimeLimit`, and a bound that is not a positive safe integer is a `RangeError` at construction. A process that carries a credential is the one that reaches the remote (16b D3), so its timeout is `unavailable`; any other is `internal`. The gate's `git --version` and 16b's prepare run under the same runner, so every Git process has the limit.
7. **Crash points.** Contract section 3 names `WS1` to `WS10` for the lifecycle steps: clone, rename into place, removal, hand-off, and reclaim. `readRemoteHead` and `push` reach none of them: the remote head read changes nothing, and the push changes only the remote, atomically, with its outcome read back from the remote. So 16c adds no crash point.
8. **Smart-HTTP test server.** `SmartHttpRemote` in the test fixture serves the bare repository through `git http-backend` as CGI on `127.0.0.1` (`REMOTE_USER` enables `receive-pack`), so clone, `ls-remote`, and push use Git's smart protocol, version 2 included. Its own credential check answers `401` unless the request's `Authorization` header is the read credential's (upload-pack) or the write credential's (upload-pack and receive-pack); the foreign credential names another repository and gets nothing. It keeps every request with its headers, and can redirect one request kind of one service to another origin, stall, or answer the advertisement with an `ERR` packet that repeats the request's `Authorization` value, which Git prints on standard error. It replaces the dumb-HTTP server everywhere; one 16b test that picked the only pack file now picks the one it wrote, because a smart clone leaves a pack.
9. **Redaction.** Tests check every non-empty form of every fixture credential (`credentialForms`): no argument and no environment variable except the header holds one; every request the server received carries exactly the read or write credential's value and no other header or URL holds a form; and the failure messages of a prepare, a remote head read, and a push whose remote repeats the header hold `<redacted>` and no form. The adapter has no logger of its own: its failure messages are the text a worker log receives.
10. **Conformance.** The 9 cases deferred with "sub-change 16c" now run; the skip list holds the 6 hand-off cases of 16d, and its test also checks their count.

## Coordinator decisions (Niki, 2026-10-28)

- **Q1 (a), redirects.** Add `http.followRedirects=false` to `GIT_COMMAND_SCOPE_SETTINGS` after `core.multiPackIndex=false` and before the header, for every Git process; update contract section 7, the section 13 test, the `@taskelith/workspace` constant, and the modified requirement "Git configuration scope". Test a cross-origin `302` of the advertisement and of the following request, asserting that the other origin receives no request at all. The contract states the consequence: a remote that redirects, such as a renamed repository, fails as `unavailable`, so the control plane must send the canonical remote URL (item 20's follow-up from 9a). No `http.<url>.extraHeader` scoping. The redirect reproduction is recorded in `verification.md`.
- **Q2 (a), time limit.** One "Time limit" sentence in contract section 7: a 10-minute wall-clock default, configurable through `GitWorkspacesOptions`; a detached process group, the whole group killed with `SIGKILL`; a timeout maps to `unavailable` for a process that reaches the remote and to `internal` for a local one, with no new reason. A test proves the group gone (`kill(-pgid, 0)` fails with `ESRCH`, waited on as a condition), with an injected bound so it runs in seconds and wide slack. No `http.lowSpeedLimit`; listed as a follow-up.

## Risks

- The ancestry walk starts one `cat-file --batch` process per generation; when the clone holds the expected head but the head does not descend from it, such as after the agent rewrote the branch, it reads the whole history, one process per generation, bounded only by the time limit of each process.
- A remote that trickles bytes keeps a process alive until the 10-minute limit; `http.lowSpeedLimit` would end it sooner (follow-up).
- A push that the remote applied but whose report was lost reads the remote head as moved and fails with `remote-moved`; the caller's next `readRemoteHead` shows its own head.
