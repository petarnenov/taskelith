# ADR 0013: Intents, campaigns, and proposal graphs

Date: 2026-10-25
Status: Decided by the owner on 2026-10-25 in the project conversation. Recorded; no campaign model, blueprint artifact, dispatcher, or branch handling exists yet. Implementation is not authorized: it starts only when the owner authorizes it, and the decisions then become work items of that gate's plan under "Delivery and authorization". The forward-compatibility obligations apply to G3 and G4 designs now.

## Context

- The owner described the intended use of Taskelith: submit an intent or idea, run the full SDLC lifecycle, implement by gates, generate a blueprint of tasks with a dependency map, and dispatch tasks automatically in the order the map allows.
- The architecture already models a project, a workflow run, its stages, tasks, and attempts (sections 5 and 6), and G1 delivered the framework-neutral stage graph, admission, and gate rules. It has no unit above a change, no dependency graph between changes, no automatic dispatch of a sequence of changes, and no priority field; the owner described priority as the dependency graph itself, not a separate scalar.
- The constraints that bound the design are: native framework artifacts are the source of truth for specification content; a changed artifact revision invalidates unused admissions; the knowledge graph is advisory and rebuildable; auto-merge merges one change at a time per target branch ([ADR 0008](0008-product-ui-and-integration-authority.md) decision 2); and an agent cannot authorize its own integration.
- In the conversation the owner decided the hierarchy, the recursive proposal generation, the override rules, the graph persistence, and the merge ladder. This ADR records those decisions; it does not implement them.

## Decisions

1. **Vocabulary and containment.** Intent, campaign, change, stage, task. An intent is a goal and contains one or more campaigns; a campaign is a sub-goal around which a set of changes is grouped; a change is one workflow run with its own worktree, branch, stages, gates, and merge; a stage and its tasks are the existing model. Campaigns are siblings; no campaign contains another. Platform specifications and contracts use only these words for these units.
2. **Proposals generate proposals.** The intent is itself a proposal of the selected SDLC framework. Its approved implementation generates campaign proposals; each campaign proposal generates change proposals; a change generates its native tasks. Every level keeps the same lifecycle, gates, and evidence rules; only the scale changes. The framework plugin maps the native artifacts of a parent proposal to the generated campaign or change proposals and records the generation edges.
3. **Two kinds of edge.** Generation edges connect a parent to the proposals it generated. Dependency edges connect two nodes of the same parent and state that one is dispatched only after the other is integrated. The platform validates both: generation forms an acyclic tree over the intent; dependencies form a DAG with no self-edge, duplicate, unknown node, or cycle; every generated node is reachable from its parent. A new revision of a parent's blueprint is a new artifact revision and invalidates the unused admissions of the affected children, as the admission rules already require.
4. **The blueprint is a platform artifact in Git.** The dependency graph and the list of generated nodes are a framework-neutral manifest committed to the repository and generated by the framework plugin from the parent proposal. Git is the source of truth; PostgreSQL mirrors the manifest for queries and authorization; Neo4j holds a query and visualization projection behind a `BlueprintGraph` port, with an in-memory implementation for tests and a PostgreSQL fallback. No kernel or module names Neo4j, and dispatch never reads the projection: readiness is computed from canonical admission and gate state, so a stale or unavailable graph projection can neither dispatch nor block work.
5. **Readiness is the only ordering rule, and it is necessary rather than sufficient.** Integration is defined per node: a change is integrated when it merged into its intent branch and its gates passed; a campaign is integrated when every change in it is integrated and its own campaign-level gates passed; an intent is integrated when every campaign is integrated and its gates passed. A node is graph-ready when every dependency is integrated. It is dispatchable only when it is graph-ready, no hold applies to it or to a dependency ancestor, it has a valid admission whose artifact, code, and policy revisions are current and whose gates passed, and a capacity reservation and budget are available. Independent graph-ready nodes dispatch in parallel, within capacity reservations, account slots, and the campaign's budget. A numeric priority is not introduced; the graph is the priority.
6. **Overrides only add constraints.** An operator may `hold`, `release`, or `order` nodes. `hold` makes a node and every node that depends on it, transitively, not dispatchable, and never its prerequisites or siblings; a hold is rejected when a node the operator has already requested or queued for dispatch depends on it, naming that dependent. `release` removes a hold. `order(a, b)` adds a dependency edge and is rejected if it creates a cycle. A request to run a node under a held dependency ancestor is rejected and names the ancestor. Containment, an intent containing a campaign, is not a dependency and never makes a sibling wait. A hold never cancels a running attempt; cancellation is its own audited action. No override can remove a dependency or make a dependent runnable while its prerequisite is held.
7. **The merge ladder.** Each change merges into the intent's integration branch, which is created from the project's integration branch when the intent is approved. A change that has no intent, a standalone task, keeps the existing rule and merges into the project's integration branch. When every campaign is integrated and the intent's gates pass, the intent branch is promoted into the project's integration branch through a promotion gate: verification, independent review of the promotion diff, and the conflict flow with its three-attempt budget. Only the owner merges the project's integration branch into `main`: no integrator authority, auto-merge setting, or council approval authorizes that merge. Release and deployment stay outside autonomy.
8. **Parent approval covers children.** The approval of an intent proposal is the semantic approval of every campaign and change generated from it, so generated work does not wait for a separate spec approval. Verification evidence and independent review are still required per change. A change that departs from the approved blueprint returns to its parent for a new revision instead of silently redefining the graph.
9. **The council decides the boundary questions.** The decision body of [ADR 0014](0014-decision-council-and-delegated-approval.md) approves the intent, ratifies the outcome of verification and review, and approves promotion and merge up to the integration branches, never into `main`. It never replaces the independent reviewer and never waives evidence.

## Forward-compatibility obligations

The following apply to G3 and G4 designs now, so that introducing campaigns later is a bounded change rather than a rewrite:

- Approval of a stage runs through an approver port or decision body, not a hard-coded human call, so the council can be inserted without changing the lifecycle.
- Project settings include an integration branch, and the workspace contract keeps a per-change branch and does not assume the project branch is the only target.
- The scheduling module computes readiness from canonical admission and gate state, so a dispatcher can be added above it without changing assignment or reservation semantics.
- Board and inbox read models stay centrally aggregated views over stable task and stage identities, so a campaign grouping can be added without a second data path.
- The blueprint mapping is a new versioned operation of the SDLC framework plugin, added under the frozen port's versioning rules; the frozen contract is not changed silently.
- Capacity budgets nest from the first implementation of each level: intent, campaign, change, attempt.

## Consequences

- The model adds two levels above a change. A campaign of N changes is N worktrees, N branches, and one serial merge stream per target branch; the conflict surface moves to the intent branch.
- The blueprint manifest is a new contract to version and validate. Neither OpenSpec nor SpecKit has a native graph between changes, so the manifest is the platform's normalized form, generated by the plugin and reviewed like any artifact.
- Parallelism is bounded by slots and budgets, not by the graph. An intent with a wide graph runs only as wide as its reservations allow.
- The graph projection is optional infrastructure: an installation without Neo4j keeps dispatching, because readiness never depends on it.
- This ADR authorizes no implementation. Until the owner authorizes it, intents and campaigns are a recorded design only.

## Delivery and authorization

Implementation starts only on an explicit owner authorization. When it starts, the decisions above are work items of that gate's plan, tracked through the selected SDLC framework. The council of [ADR 0014](0014-decision-council-and-delegated-approval.md) cannot be constituted before Claude Code, Codex, and OpenCode are admitted, so the full model follows those admissions and a separate owner authorization; the delivery gate is not fixed here. Until then, the obligations of "Forward-compatibility obligations" keep the G3 and G4 work compatible.
