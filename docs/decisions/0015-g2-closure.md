# ADR 0015: G2 closure and deferrals

Date: 2026-10-27
Status: Proposed. Draft of [G2 work plan](../g2-plan.md) item 27 (change `close-g2`), prepared while items 24 and 25 were still running and updated on 2026-10-27 from `dev` at `2a26714b` and the branches handed off for integration. Work that is on a branch and not on `dev` is named with its branch and head and stays a gate until it is integrated. The marked placeholders that remain are filled from those integrations and from a fresh-clone reproduction before the owner accepts this ADR. Each deferral names the decision or record it follows; where none names a gate, the entry is marked as the author's assignment for the owner to confirm. Closing G2 starts no G3 implementation item: G3 item 0 runs first ([G3 work plan](../g3-plan.md)).

## Context

G2, "Durable execution vertical slice", is defined in [architecture section 13](../architecture.md#delivery-sequence). Its exit evidence: submit an admitted task, assign it, execute it, and persist its result, and exercise duplicate delivery, process-launch crash windows, partition, cancellation races, stale generations, and disk loss. The [G2 work plan](../g2-plan.md) decomposed the gate into items 1 to 27; several items were split by the coordinator into parts, each one OpenSpec change merged into `dev` and archived under `openspec/changes/archive/`. Decision D11 (a) scoped native acceptance to all four matrix entries and asked this ADR to record as open any entry or row that the available hosts cannot establish.

- **24c `run-g2-partition-and-races`.** A G2 plan item. It was handed off and returned to its worker (Zaki), because its tests hang on macOS in the coordinator's integration `make verify`; no record of the hang is in the repository yet. Its integration into `dev` is pending after that fix (decision 2).
- **Linux CP9 defect L1.** After an unknown exit with a proven start, the control plane opens an automatic retry, although section 6 of the supervisor identity contract and the retry budget of `0` for an uncertain execution allow one attempt. Found by `run-g2-crash-windows-on-linux` (branch head `07568a20`, its verification, "Candidate defect L1"); on Linux only, because on macOS CP9 ends `uncertain` without an exit. The fix `stop-automatic-retry-of-unknown-exit` is pending and is not in the repository yet.
- **ReDoS in the failure-cause redaction** (below, "Records and contracts"). The fix is pending until it lands on `dev`.
- **macOS arm64 process ownership re-run.** The row failed on D1 in 25b and has not been re-run on `macos-26-arm64` since the fix (decision 3); Maki re-runs it before the closure.

- **Assignment age on a database-stamped column** (option A of `stamp-assignment-age-on-database-clock`, rejected for G2): a G3-or-later candidate if more writers of offered rows appear (its design).
- **Relaunch without back-off after a launch fails before W2.** `LaunchOrchestrator` relaunches at once when a launch ends before W2, for example when the deadline clock cannot be read: the clock read returns `end` without a back-off (`apps/worker/src/launch-orchestrator.ts:514-515`), the tracked launch's cleanup wakes the loop (`:296`), and the next pass continues the launch again (`:143-144`). Every step is a microtask, so the loop starves the event loop. Found by Zaki in 24c, where on macOS the G2 harness composed the Linux process-group launch host, whose deadline clock reads `/proc`; Desi's diagnostic on the Intel iMac on 2026-10-27 confirmed it: the worker child ran at about 99% CPU in a JIT loop and never serviced `SIGUSR2` (coordinator's statement; no record in the repository yet). 24c's fix `e5db6610` (on its branch, not on `dev`) skips the G2 scenario suites outside Linux and bounds every wait and cleanup; it does not change the orchestrator. Follow-up change `back-off-relaunch-after-pre-w2-failure`, not in the repository yet. Gate, set by the coordinator: assigned after the G2 closure unless it lands first; not a blocker.
- **Safe-to-retry rule against the supervisor identity contract.** The capacity reservation contract lets an automatic retry follow an earlier attempt that `exited` with a proven start and counts a proven exit as safe (`docs/contracts/capacity-reservation.md:242`, section 13), so `isSafeToRetry` treats every such exit as certain, an unknown exit status included (`packages/modules/scheduling/src/application/capacity-operations.ts:268`, `:270`). Section 6 of the supervisor identity contract keeps the outcome of an exit with an unknown status unknown, with the retry budget of `0` for uncertain execution (`docs/contracts/supervisor-identity.md:107`). Found by Liki. Once the fix of L1, `stop-automatic-retry-of-unknown-exit`, lands, an unknown exit no longer reaches that path. Follow-up change `align-safe-to-retry-with-supervisor-identity`, contract-first, not in the repository yet. Gate, set by the coordinator: after the G2 closure; contract-first; not a blocker.
- **Snapshot `assignment.age` is offered-only.** The signal counts only offered assignments, not accepted ones (`packages/modules/observability/src/domain/signals.ts:21`, `packages/adapters/postgres/src/control-plane-signals.ts:25`). The owner's delegate kept that meaning for G2 in away run `20261027T045006Z-opencode-96871` (OpenCode `opencode-go/kimi-k2.7-code`); its record is in the coordinator's local away run directory, not in the repository. A separate accepted-age signal was that decision's option B, a G3-or-later candidate. Resolved for G2; no gate.
- **Fair-order rotation.** The placement service offered a batch in an order that undid the project rotation of its own read. `align-fair-order-rotation` (Zaki; branch head `d5f3baf3`, integration pending) lets the domain own the rotation. Its record leaves two items open (its design and verification, limitations): a cursor at the last row's project still starves the rotation when reads end with the same project, queued as `advance-placement-rotation-cursor` (Zaki), not in the repository yet; and the rotation cursor `#after` of `PlacementService` lives in memory only (`apps/control-plane/src/application/placement-service.ts:47`, `:78`), so a control plane restart starts the rotation again. The tie-breaks of the same order are fixed by `break-fair-order-ties-by-task-id` (integration pending). Whether these must land before the closure: author's assignment, follow-ups without a G2 gate (owner to confirm).
