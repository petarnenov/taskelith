# ADR 0005: Harness subscription account pools

Date: 2026-10-24
Status: Decided by the owner on 2026-10-24 in the project conversation. Decisions 1, 2, and 8 record the owner's request; decisions 3 to 7 were proposed by the author and approved by the owner the same day. Decisions 4 and 5 were amended by the owner on 2026-10-25, and decision 2 on 2026-10-27. Recorded; not implemented. Provider terms for pooled subscriptions are not yet verified.

## Context

The [Claude Code qualification](../qualification/claude-code.md) used one subscription through device authentication. In the tested arrangement, the login is bound to a configuration directory on one worker host, not to a workspace, which conflicted with the [trust model](../trust-model.md)'s per-workspace provider credentials. Managing many accounts this way would need a manual login per account and host; broader limits of device authentication were not tested. The owner asked for pools to which many subscriptions can be added, per harness and project, each used on a least-loaded basis. Authentication must always use a subscription.

## Decisions

1. **Account pools.** Taskelith manages harness accounts, called slots. Each slot belongs to exactly one harness plugin and lists the projects it is explicitly allowed to serve. A slot may serve several projects. A project's pool for a harness is the set of slots allowed for that project.
2. **Subscription authentication only.** Every slot authenticates with a subscription supported by its harness plugin's declared mechanism. API-key billing is not used. Each harness plugin declares in its manifest the subscription mechanisms it supports, for example a long-lived subscription token or a device login stored per slot, and each slot uses one of them. *Amendment, 2026-10-27 (owner decision in the project conversation, after the [provider terms recheck](../qualification/claude-code.md#consequences-for-d15) quoted the Usage Policy clauses on routing requests through consumer subscriptions and on bypassing restrictions, and the conditions of hosting Claude Code):* Taskelith does not pool or rotate Claude subscriptions until a further owner decision. Support for the user's own API key comes first, which replaces "API-key billing is not used" for Claude Code ([G3 work plan](../g3-plan.md) item 45). Subscription use stays limited to the owner's own account, with no rotation to another account. Other harnesses are unchanged.
3. **Least-loaded selection.** A new session gets a slot from the project's pool for the chosen harness. Eligible slots are allowed for the project, healthy, not in cooldown, and below their concurrency limit. Among them, the slot with the fewest active sessions wins. Ties go to the slot with the lowest usage, then to the least recently used slot. Usage is a harness-neutral fraction of the slot's current usage-window limit, reported by the plugin within the current window; the usage tie-breaker is applied only when every tied slot has such a report, otherwise ties go directly to the least recently used slot. If no slot is eligible, the session waits for a slot or is rejected by policy. The selection reserves the slot transactionally together with the other run resources (architecture section 8).
4. **Cooldown.** When a plugin reports a rate-limit or usage-limit signal, the slot enters cooldown until the reported reset time, or a bounded default when none is reported, and receives no new sessions until then. *Amendment, 2026-10-25 (owner decision in the project conversation):* a session whose slot reports such a limit writes a handoff and stops. Its work continues in a new session that reads the handoff and runs on a different harness of the project; another slot of the same harness is never chosen because of a limit, since that is the clearest case of "rotating accounts". If no other harness is eligible, the task waits for that slot's cooldown to end and continues on it.
5. **Session affinity.** A session stays on the slot that started it. Resume uses the same slot. If that slot is unavailable (cooldown, revocation, or removal), the session waits or is explicitly reconciled by policy or an operator; it is never silently moved to another slot. *Amendment, 2026-10-25 (owner decision in the project conversation, after the [provider terms reviews](../qualification/codex.md#consequences-for-d15) quoted the prohibition of "rotating accounts"):* a session also keeps the harness that started it, and resume uses the same harness. Its harness and its slot stay fixed until its work is finished and the session and its agent are closed; neither is switched during the session. A limit is handled as decision 4 sets out; any other unavailable slot is still handled as above, but explicit reconciliation drains or ends the session instead of moving it; its work may continue in a new session. The binding is per session, not per task: a new session of the same task gets its harness and slot by the normal selection, and may get different ones.
6. **Credential handling.** Slot credentials are stored encrypted by the control plane. A worker receives a slot's credential only for the run that reserved it, inside the worker container on Linux. Credentials never enter logs, prompts, lessons, or error payloads. Each slot can be revoked or removed on its own; removal drains or rejects its in-flight sessions.
7. **Trust model.** For subscription slots, provider credentials are scoped to the slot and its allowed projects and are injected per run. This replaces "scoped to the specific workspace/project" for harness provider credentials; Git and SCM credentials stay per workspace.
8. **Microkernel.** The account pool is a harness-neutral kernel capability behind a port. Plugins only inject a slot's credential into their harness and report load, limits, and resets as declared capabilities. No kernel code, type, schema, or test names a harness or vendor (ADR 0003 decision 8).

## Risks

- Provider terms: subscriptions are usually personal accounts. Whether each vendor's terms allow pooled subscriptions for automated use has not been verified. Per ADR 0003 decision 2, each harness plugin records these terms before admission; the owner decides whether any remaining risk is acceptable.
- Credential exposure: whether an agent's own commands can read an injected credential has not been tested. Each harness qualification must test it.
- Load signals: harnesses may not report usage or reset times. A plugin without them falls back to active-session counts and a bounded default cooldown.

## Consequences

The architecture, trust model, foundation ledger, and Claude Code qualification record are updated to match. Implementation belongs to G2 (reservation and credential storage) and G3 (harness plugins). Every harness qualification adds tests for its subscription mechanism, load and limit signals, and credential exposure.
