# Bootstrap governance policy

Policy version: 5 (2026-10-24: version 2 added the independent review process; version 3 added auto-merge as integration authority and the selectable SDLC framework, [ADR 0008](decisions/0008-product-ui-and-integration-authority.md); 2026-10-25: version 4 adds the decision council as delegated approval authority up to the integration branch, [ADR 0014](decisions/0014-decision-council-and-delegated-approval.md); 2026-10-27: version 5 replaces one reviewer per task with two alternating reviewers per task). Status: repository bootstrap policy; runtime enforcement is not implemented.

Owner acceptance: Petar Nenov accepted the SDLC policy on 2026-10-24 in the project conversation. On 2026-10-24, the owner explicitly authorized a separate Codex reviewer agent (`gpt-6.1-sol` with `model_reasoning_effort = "medium"`) for independent review of the current and subsequent G0 changes, and later the same day the further reviewers listed under [Independent review process](#independent-review-process). Integration and release authorization remain distinct.

## Authority

The owner, Petar Nenov, defines scope and accepts product and architecture decisions. Contributors and agents may propose work, inspect the repository, and implement authorized changes. An instruction to continue authorizes the next bounded work item; it does not authorize the entire architecture roadmap.

The implementer records author checks. An independent reviewer must be a person or separately authorized agent that did not author the change; self-review is never independent review. The owner may explicitly accept a documented review exception for bounded bootstrap work. Never infer an exception from silence or mark the review as passed because an exception was granted.

The owner or an explicitly authorized integrator controls merging and pushing. Finishing local work does not itself authorize integration. In a project managed by Taskelith, an enabled auto-merge setting, which only a project-maintainer changes, is that explicit authorization: pushing to the task's own branch is covered by a standing rule, a change whose gates have all passed is merged without a further human step, and where an earlier rule conflicts with auto-merge, auto-merge wins ([ADR 0008](decisions/0008-product-ui-and-integration-authority.md) decisions 2 and 3). One merge has no delegated authority at all: merging the project's integration branch into `main` is owner-only, and no integrator, auto-merge setting, or decision-council approval authorizes it. Release authority follows [the release policy](releases.md): qualifying changes integrated into main may publish automatically after verification. Deployment requires separate owner authorization.

In a managed project, a decision council constituted under [ADR 0014](decisions/0014-decision-council-and-delegated-approval.md) may exercise the delegated approval authority up to an integration branch: it approves an intent, ratifies verification and independent review, and approves merges into the project's integration branch. It can never waive verification evidence, approve its own work, change policy or project settings, release an operator hold, merge into `main`, or release or deploy. It does not fall back to a partial bench: when all three seats cannot convene, the question escalates to a human. The owner can disable the council at any time, returning approvals to the human roles.

- **Two alternating reviewers per task** (owner, 2026-10-27, replacing version 4's "One reviewer per task"). The coordinator assigns each task two reviewers, reviewer A and reviewer B, of different harnesses unless no reviewer of another harness is available ("Rotation" and "Unavailable reviewer" below). Pass 1 is A's full review. Pass 2 is B's full, independent review, which also checks the pass 1 fixes. Pass 3 is A's confirmation of the pass 2 fixes only, with no new scope. A Low-only pass ends the review under "Low findings are fixed" below, so after a Low-only pass 1, B is not used. No other reviewer cross-reviews the task; a switch under "Unavailable reviewer" below replaces A or B and is not a cross-review. A rule that names the task's assigned reviewer without a pass, such as the review of a returned branch, means reviewer A. `verification.md` and `passes.jsonl` record which reviewer, A or B, ran each pass.
- **Tasks under the previous rule** (owner, 2026-10-27). A task briefed before version 5 reached `dev`, including one already in review, finishes under version 4's "One reviewer per task": one assigned reviewer makes every pass, no second reviewer cross-reviews it, and a replacement under "Unavailable reviewer", chosen as version 4 chose it, the next reviewer in the rotation that is not paused and meets the task's review requirements, with no harness test, takes over the remaining passes, its first pass confirming the earlier passes' findings and then reviewing the whole task.
- **Rotation** (approved by the owner). Consecutive tasks go to different reviewers in turn, unless a task needs a particular reviewer. The turn (coordinator, 2026-10-25) follows the order of the list above, returning to the first after the last, and skips a reviewer that is unavailable, paused, or unable to meet the task's review requirements. Unless a task needs a particular reviewer, a new task goes to the reviewer after the one most recently assigned, for whatever reason that one was assigned. Its reviewer A is that reviewer, and its reviewer B the next reviewer in the turn after A whose harness differs from A's (coordinator, 2026-10-27); B then counts as the most recently assigned. When no authorized reviewer of a harness different from A's is available, because each is paused, unavailable, or unable to meet the task's review requirements, B may be another model of A's harness, as "Unavailable reviewer" allows for a replacement (coordinator, 2026-10-27). Reviewers of the same harness are never next to each other in the list, including from the last back to the first (owner, 2026-10-26), so any reordering keeps them apart; the turn is Codex CLI (gpt-6.1-sol), OpenCode CLI (kimi-k3.1-pro), Antigravity CLI, OpenCode CLI (deepseek-v4-pro), Claude Code (claude-fable-5-1), OpenCode CLI (kimi-k2.7-code), Codex CLI (gpt-6-astra), OpenCode CLI (qwen3.8-max), Claude Code (claude-opus-5-5), then Codex CLI (gpt-6.1-sol) again. The rule binds the list, not the effective turn (owner, 2026-10-26): when the turn skips a reviewer, for example a paused one, two reviewers of the same harness may follow each other.
- **Unavailable reviewer** (owner, 2026-10-25). A reviewer that is unavailable for any reason is not used for the next 30 minutes, and the next reviewer is proposed instead. Applying the two-reviewer, rotation, and three-pass rules (coordinator, 2026-10-25; two-reviewer since 2026-10-27): unavailable means that a review attempt does not run to a report, for example an error, a run that opens no session, a quota limit, or an outage; a pass that runs and reports findings is not unavailability. The 30 minutes run from the failed attempt, whether or not the reviewer is assigned, and it is not retried inside them. The replacement is the next reviewer in the rotation that is not paused, meets the task's review requirements, such as network access under "External facts", and, for a task with reviewers A and B, has a harness different from the task's other reviewer: from B's for a replacement of A, and from A's for a replacement of B (2026-10-27); a task under the previous rule has no other reviewer and no harness test. The worker proposes it and the coordinator assigns it; when the coordinator develops the task itself, it chooses the replacement and records why. The replacement takes the replaced reviewer's role, A or B, with that role's remaining passes and their scope, and is briefed with the earlier passes: a replacement of A before pass 1 makes the full pass 1, a replacement of B makes pass 2, and a replacement of A after pass 2 confirms only the pass 2 fixes in pass 3. When no reviewer of a harness different from the task's other reviewer is available, that is, not paused or unavailable and meeting the task's review requirements, the coordinator may assign a reviewer of the same harness with a different model and records the reason in `verification.md` (coordinator, 2026-10-27). Failed attempts do not count toward the pass cap, and the pass count carries over. `verification.md` records each failed attempt with its time, and the switch. A longer pause is listed under "Reviewer pauses" in the [agent task protocol](agent-task-protocol.md#reviewer-pauses) until it ends.
- **External facts** (approved by the owner). A task whose review depends on external facts goes to reviewers with network access, A and B alike.
- **Proof of read-only review** (approved by the owner). Take a SHA-256 snapshot of all tracked and untracked files before and after each pass, plus any external evidence directory shared with the reviewer. A change made by the reviewer invalidates the pass.
- **Review prompt** (approved by the owner; ADR 0004). The prompt names the [ADR 0004](decisions/0004-first-class-engineering-principles.md) principles as criteria and asks for every instance of a problem, not examples. `verification.md` records the reviewer, model, effort, session ID, findings, and their resolution. Each finding is also recorded as one line of the change's `findings.jsonl`, the structured [review findings record](agent-task-protocol.md#review-findings-record) that later briefs draw on (owner, 2026-10-27).
- **Before the first pass** (approved by the owner). The author self-checks the change against the review criteria and runs the evidence check, and `verification.md` records both. In this repository the evidence check means that every external link is pinned to a tag, commit, or exact version, or labeled as an unversioned page, and that every repository link of the change's records follows the record link rule of [agent task protocol](agent-task-protocol.md#worker-steps) step 6 and resolves, as `npm run verify:links` checks. The generated part of `verification.md` passes `make record-check` (2026-10-27).
- **At most three passes per task** (owner). If Critical, High, or Medium findings remain after the third pass, the author stops and presents options to the owner: fix them without review (recorded as unreviewed fixes), accept them as a known risk, or defer them. Any further pass needs the owner's permission.
- **Low findings are fixed** (owner). If a pass finds only Low findings, they are fixed and recorded as unreviewed fixes, and the reviewer is not called again. Low findings reported together with higher-severity findings are fixed with them and checked in the next pass or, after the third pass, recorded as unreviewed fixes.

## Lifecycle and records

Every task, including inspection, documentation, maintenance, emergency work, and delegated work, binds to a change of the selected SDLC framework, without exception; OpenSpec is the default and this repository's framework ([ADR 0004](decisions/0004-first-class-engineering-principles.md) principle 8 as amended by [ADR 0008](decisions/0008-product-ui-and-integration-authority.md)). Record inspection as a task in that change when it determines the scope. Use OpenSpec 1.14.3 through `npm run openspec -- ...`; the lockfile pins its dependency tree. A future framework upgrade is its own tracked change.

| Stage | Required record and transition |
| --- | --- |
| Propose and inspect | Owner request or authorized parent scope, bounded proposal, impacted capability, and exclusions. |
| Specify and design | Testable requirements and design; documentation-only work declares no runtime impact. Record unresolved decisions rather than inventing approval. |
| Implement | Task checklist and changes within the recorded scope. Material scope expansion returns to proposal. |
| Verify | Exact commands, results, environment, relevant revision or reviewed diff, limitations, and remaining gates in `verification.md`. Run `make verify`, which includes `npm test` and strict validation of all OpenSpec artifacts. |
| Review | Record author review separately from independent findings, reviewer identity, reviewed revision, and resolution. Structural validation is not semantic approval. |
| Accept and integrate | Owner acceptance or explicit delegated authority (in a managed project, an enabled auto-merge setting and, where constituted, a decision-council approval under [ADR 0014](decisions/0014-decision-council-and-delegated-approval.md)), required review or recorded exception, and current verification. Record the integrated revision when integration occurs; in this repository the merge pull request records the integration checks, its merge commit is the integrated revision, and the coordinator does not edit the archived record. |
| Close | Reconcile tasks and evidence; archive using the pinned CLI. In this repository, since 2026-10-26 (owner), the author archives after review and verification, in the last commit of the change's branch, records the checks of the archived tree in that commit, and names integration as the remaining gate of the archived `verification.md`. The coordinator merges `dev` with `git merge --no-commit --no-ff origin/dev`, commits the merge only when it will integrate, and on any return runs `git merge --abort`, so a returned branch never carries a coordinator merge. On any return of a branch that carries its archive commit, the worker restores the active change by reverting that commit, merges `dev`, reconciles each restored delta with `dev`'s current requirement text, keeping others' edits, has reviewer A review the resolved diff and the reconciliation, records it, and archives again as the last commit; a branch without an archive commit only needs step 7. ([agent task protocol](agent-task-protocol.md#worker-steps)) Local completion may leave these gates pending. |

The proposal, design, capability specification, tasks, and verification record form the bootstrap evidence set. Reference the originating issue when one exists; no issue is required merely to duplicate an already recorded owner request. Task checkboxes show progress, not approval authority.

## Evidence freshness

Tie review to the actual source revision, or to a base revision and explicitly identified working-tree diff before a commit exists. Record commands against the resulting tree. Changes to requirements, policy, implementation, or verification inputs invalidate affected evidence; repeat the relevant checks and obtain renewed review before acceptance, except where the [independent review process](#independent-review-process) allows unreviewed fixes, which are recorded as such. Documentation-only edits need editorial and reference checks, not invented runtime coverage.

Do not rewrite historical records as if this policy applied before it existed. The existing bootstrap and automated-release verification records remain author evidence with their stated limits. Passing local checks does not prove CI execution, external deployment, distributed recovery, or independent review.

## Framework independence

OpenSpec is the default framework for developing Taskelith, but it is not a product kernel dependency: every project, Taskelith included, selects its framework through replaceable SDLC plugins ([ADR 0004](decisions/0004-first-class-engineering-principles.md), [ADR 0008](decisions/0008-product-ui-and-integration-authority.md)). G1 delivered the framework-neutral models and the SpecKit fixtures ([ADR 0010](decisions/0010-g1-closure.md)); runtime workflow selection, immutable per-run framework bindings, semantic admission, and evidence enforcement are G2–G4 work. See [ADR 0001](decisions/0001-bootstrap-governance.md) and [foundation status](foundation.md).
