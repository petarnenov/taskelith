# G1 work plan

Date: 2026-10-24. Status: the owner started G1 on 2026-10-24 ("започваме G1") and, the same day, authorized merging each completed and reviewed task into `dev` and starting the next one without a separate approval ("Разрешавам да мърджваш и да започваш следваща задача"). Items therefore start in dependency order without a per-item approval, except that an item blocked by an open owner decision below starts only after the owner decides it. No G1 product code exists yet.

G1, "Domain and SDLC contracts", is defined in [architecture section 13](architecture.md#delivery-sequence). Its exit evidence: domain tests reject invalid transitions and unbound implementation tasks, planning tasks can create missing specs, and structural validation and semantic approval remain distinct. Section 13 requires each gate to be decomposed through the SDLC framework into reviewed, independently verifiable work items. This plan lists those items. Each item is one OpenSpec change, developed in its own git worktree and merged into `dev`.

## Starting point

- Product code is the 28-line CLI in `src/cli.ts`; there are no runtime dependencies.
- `scripts/check-boundaries.ts` already recognises `src|packages/modules/<module>/{domain,application,ports}`, bans infrastructure SDKs from modules, limits cross-module imports to a module's `index`, and forbids modules and the SPA from importing plugins. It has no rules yet on what kernel or plugin packages themselves may import.
- Tests run from a flat `test/*.test.ts` glob, coverage is measured over `dist/`, and the coverage scope check enumerates only `src/`, so code in other packages would be outside the 75% gate until item 1 extends it.
- The [SDLC framework mapping](sdlc-framework-mapping.md) inspects native OpenSpec 1.14.3 and SpecKit 1.2.3 artifacts, one of the steps section 13 names for G1. It finds that SpecKit's specify, plan, tasks, and implement steps are agent prompts run by a harness, not CLI operations, and lists claims still to verify by running SpecKit.
- The pinned OpenSpec CLI already offers `--json` output on `list`, `show`, `validate`, `status`, and `instructions`; its `spec-driven` schema instructions use `show --json` and `instructions --json`.
