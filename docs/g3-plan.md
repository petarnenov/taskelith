# G3 work plan

Date: 2026-10-25. Status: final, finalized on 2026-10-27 on the G2 closure ([ADR 0015](decisions/0015-g2-closure.md)). Accepted by the owner through the away delegate on 2026-10-27. On 2026-10-25 the owner approved drafting this plan and decided every owner decision below except D15, which waited for item 2, and added D18; the owner decided D15 the same day, after item 2. The draft authorized no implementation, and no item started from it except the wave 1 contracts that the owner started on 2026-10-26 (below). On 2026-10-27, after the G2 closure, the owner started G3: from then on, by D16 (a), items start in dependency order and by the waves below, item 0 first, and are merged without a per-item approval, except items blocked by an open decision. The draft was to be finalized when G2 closed, because the G2 closure ADR might carry deferrals into G3, by adding those deferrals and correcting the starting point to what G2 actually delivered. G2 closed on 2026-10-27 (ADR 0015), and this version does both: the [Starting point](#starting-point) describes G2 as built, and [G2 closure deferrals](#g2-closure-deferrals) attaches each deferral to the G3 item that owns it. Finalizing the plan itself adds no owner decision and starts no item. On 2026-10-26 the owner started G3 for the contracts of the first wave only: items 3, 5, 6, 7, and 8 started then, in parallel with G2, and every other item waited for the G2 closure (see [Dependency order and parallel work](#dependency-order-and-parallel-work)). On 2026-10-26 the owner also decided that, after the G2 closure, item 0 re-reviews the merged items 1, 2, 3, 5, 6, 7, and 8 against G2 as built before any other G3 item starts, and that every other item not yet merged also depends on item 0.

G3, "Usable web product and first real agent", is defined in [architecture section 13](architecture.md#delivery-sequence): the React SPA, self-hosted login, project, task, and session views, chat and approvals, the Git workspace adapter, and the selected real agent and SCM plugins. Its exit evidence: from a fresh installation, an operator enrolls a remote worker and completes a real repository task with inspectable artifacts, independent review, and verification evidence; closing the browser does not stop execution; and turn retries and native approval responses survive a restart without silently repeating side effects. Section 13 requires each gate to be decomposed through the SDLC framework into reviewed, independently verifiable work items; this plan lists them. Each item is one OpenSpec change, developed in its own git worktree and merged into `dev`.

## Starting point

- G3 follows the recovery foundation of G2 (architecture section 13). G2 closed on 2026-10-27 ([ADR 0015](decisions/0015-g2-closure.md), accepted by the owner): items 1 to 26 of the [G2 work plan](g2-plan.md) are merged and archived through the changes that ADR 0015 decision 1 lists, and the exit evidence was reproduced from a fresh clone of `dev` at `bd6108d4` (decision 4; [foundation ledger, "G2 status"](foundation.md#g2-status)). G3 builds most directly on G2 item 13 (installation bootstrap and enrollment), item 16 (control-plane API), item 19 (`EvidenceStore`), item 20 (worker agent runtime), and item 23 (minimal local installation), and on item 26, which added the pinned harness packages to the Linux worker image. Closing G2 claims a durable execution vertical slice on one installation with a scripted test process, not a real agent harness, SCM integration, remote worker, TLS, or supported matrix entry (ADR 0015, "Consequences").
- G2 as built has these limits, which the G3 items below meet (ADR 0015 decisions 2, 3, and 5):
  - The process-launch crash windows and duplicate delivery ran on macOS with the native supervisor, 28 of 28 on `macos-26-x86_64` (25c), and outside macOS only on Linux, in the privileged test composition of `make verify-linux-crash-windows` on one x86_64 host, 29 of 29 after the fix of L1 (decisions 2 and 3). The one `macos-26-arm64` run, 25b, predates `fix-launch-recovery-reauthorization`: 15 windows passed and 11 failed on D1.
  - The partition, cancellation race, and stale generation scenarios of 24c `run-g2-partition-and-races` run on Linux only: since `6d40c0c4` they skip outside Linux (`SCENARIO_HOST`, `test/g2-scenarios/scenario-run.ts:16`). Their 34 records are Linux x64 runs on a test-side composition whose workers launch through the test-side process-group launch host, not the Linux cgroup supervisor or a native worker, and race g, an adopting macOS supervisor that ignores a cancel, has no record (decisions 2 and 5).
  - No native acceptance row is fully accepted on any of the four matrix entries (decision 3).
  - The installation runs plain HTTP, NATS, and PostgreSQL on localhost ports, with no TLS and no installation certificate authority, and a rotated worker credential is never delivered to the worker (decision 5).
  - No production code calls the Linux containment self-check, so worker admission does not use it (`harden-worker-linux-self-check-home-layout`, design D3).
  - G2 has no writer of gates, artifact revisions, or policy revisions: `submitTask` seeds `current_revisions` from the admission, and each such writer must call `invalidateLaunches` when it is added ([launch authorization contract](contracts/launch-authorization.md) sections 5 and 11). A launch rejected under a stale admission is released, not re-admitted, and no HTTP or CLI surface reads the reconciliation queue (`wire-launch-authority-reconciliation`).
  - Evidence download takes the installation-wide operator credential, and evidence retirement has no HTTP or admin entry point (`implement-evidence-store`, decision Q2).
  - The execution protocol version 1 exception ended with the closure: [execution wire contracts](contracts/execution-wire-contracts.md) section 3 applies strictly (decision 5, "Records and contracts").
  - At the closure the placement rotation cursor lived in memory only, so a control plane restart started the project rotation again; keeping it so was owner-confirmed at the acceptance of ADR 0015 (decision 5, "Fair-order rotation"). The non-blocking follow-up `persist-placement-rotation-cursor` (#349, merge `eda6c283`) stores it per installation: a `PlacementRotation` port, a one-row PostgreSQL table `placement_rotation`, and capacity reservation contract section 13, "Durable cursor", so the rotation survives a restart. Control-plane instances share the one cursor and the last writer wins, and a move by declines alone is lost when an outage stops its pass or its end-of-pass write fails (its verification, "Limitations").
  - Two other placement changes landed after `bd6108d4`, the revision the closure reproduced: #344 `placement-backoff-preserves-rotation` (merge `21f399a5`), before the closure's own merge (#347), and #348 `stop-placement-pass-at-fleet-decline` (merge `56346d92`), after it. Since #344 a decline for lack of fleet capacity no longer backs the task off, so the task keeps its wait and its place in the rotation. Since #348 a placement pass makes no offer after its first such decline, so capacity that frees during a pass is offered in the next pass, in rotation order, where another replica or a task earlier in the rotation may take it first, and a full fleet costs at most one rolled-back placement transaction per pass instead of up to 100. No load test measured either cost, and the rule of #348 relies on equal requests and eligibility that does not depend on the task, which per-task requests or hard controls must revisit (their verification, "Limitations").
- G2 hands two extension points to G3. The [capacity reservation contract](contracts/capacity-reservation.md) section 10 reserves subscription account slots as provider credential units and leaves the account pool port and slot selection to G3. G2 item 15 runs a test-only scripted process, and the agent harness port belongs to G3; the [execution wire contracts](contracts/execution-wire-contracts.md) join the harness invocation to the offer in G3, and the [supervisor identity contract](contracts/supervisor-identity.md) makes "a harness supported on macOS keeps its processes in its process group" a G3 harness qualification obligation.
- [ADR 0010](decisions/0010-g1-closure.md) defers the code-head identity for head-bound verification and review to G3, with the Git workspace adapter and the first real repository task.
- [ADR 0007](decisions/0007-g0-closure.md) puts the review of the Anthropic, OpenAI, and GitHub terms before admission in G3, and completes the native acceptance rows that need real harness and SCM workflows in G3.
- [ADR 0008](decisions/0008-product-ui-and-integration-authority.md) fixes the product UI and the [product UI specification](../openspec/specs/product-ui/spec.md) records it: the project board as the landing page, task detail, board states, design rules, the "Needs you" inbox, intake with defaults and write-back, delegated spec approval, automatic worker admission, the session activity indicator, and auto-merge as the integration authority, with its conflict flow and the maintainer's standing rules. Decision 6 defines the board, inbox, intake, write-back, and auto-merge port contracts in G3, and the worker admission port in G2; the G2 work plan had no item for the worker admission port, and the G2 closure deferred the wiring of the worker self-check into admission to item 27 (ADR 0015 decision 5).
- [ADR 0005](decisions/0005-harness-subscription-account-pools.md) fixes the account pools: slots per harness and allowed projects, subscription authentication only, least-loaded selection, cooldown, session affinity, encrypted slot credentials injected per run, and a harness-neutral kernel port. Claude Code is the first real harness ([ADR 0003](decisions/0003-first-integrations-and-plugin-kernel.md) decision 1); its port and conformance suite are written for the port, not for Claude Code, and Codex checks them in G4 before the port is frozen.
- [ADR 0006](decisions/0006-github-first-scm.md) makes GitHub.com the first SCM, through one GitHub App per installation and per-run installation tokens. The [GitHub qualification](qualification/github.md) states the SCM port's consequences: per-run scoped credentials, merge blocking that the plugin's own identity cannot bypass, a reviewer identity separate from the identity that opens a change, signed webhooks verified on the raw body, and token refresh for runs longer than an hour.
- Architecture sections 6, 7, and 11 fix the rules G3 implements: durable chat turns with client idempotency keys, native permission and input requests persisted before display and consumed once, runtime approval distinct from SDLC approval, same-origin HTTPS with server-side sessions and CSRF protection, SSE with a durable cursor for UI updates, and WebSocket only for bidirectional flows such as terminals. Section 15 requires the first provider's chat and approval semantics and evidence storage to be resolved before G3 acceptance. The [trust contract](trust-model.md) section 3 defines the `installation-owner`, `project-maintainer`, `project-operator`, and `project-viewer` roles; G2 decision D10 left login, sessions, and project roles to G3.
- The [Claude Code qualification](qualification/claude-code.md) and the GitHub qualification list what remains before admission. Claude Code and GitHub.com stay `candidate` in the [dependency register](dependencies.md), and no SPA, login, or Git library is registered.
