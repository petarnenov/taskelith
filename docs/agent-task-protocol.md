# Agent task protocol

Status: working protocol for agent sessions that develop Taskelith in parallel, set by the owner on 2026-10-24. It applies the [governance policy](governance.md) and the [release flow](releases.md) to several sessions working at once, on one or more machines. It summarizes the operational steps and points to those documents for the full rules; where this page and they differ, they win.

The named sessions, their roles, and how the owner changes the coordinator are in the [fleet roster](fleet.md).

## Roles

- **Owner.** Defines scope and decides product, architecture, dependency, promotion, publication, and deployment questions, review exceptions, and findings left after the third review pass ([governance "Authority"](governance.md#authority), [review process](governance.md#independent-review-process)).
- **Coordinator.** One session that plans the work items, assigns them to workers, and integrates finished work. On 2026-10-24 the owner authorized the coordinator to merge each completed and reviewed task into `dev` and start or assign the next one without a separate approval.
- **Worker.** A session that develops one assigned task at a time and hands it back to the coordinator. Since 2026-10-26 (owner) the worker archives its change on its own branch before the handoff, so that the coordinator integrates it with one pull request; a worker does not open pull requests or merge. UI tasks (SPA, board, inbox, intake and write-back screens, plugin and settings UI) go to the worker that holds the UI proof of concept.

The coordinator may also develop tasks itself, following the worker steps, and then integrates its own work.

## Worker steps

1. **Worktree.** Develop each task in its own worktree on its own branch, created from a fresh `origin/dev` as in [releases "Parallel work with worktrees"](releases.md#parallel-work-with-worktrees), then `nvm use` and `npm ci --ignore-scripts`. To pick up newer `dev` work, merge `origin/dev` into the branch with a merge commit; when the `post-merge` hook or `make verify` reports a stale dependency inventory, run `make dependency-inventory` and commit the regenerated files ([merging parallel branches](dependency-inventory.md#merging-parallel-branches)). Do not rebase a pushed branch, and never force push. A merge that changes the task's requirements, contracts, implementation, or verification inputs invalidates the affected evidence ([evidence freshness](governance.md#evidence-freshness)): repeat the checks and the review.
2. **Change.** Bind the task to an OpenSpec change named after it: `npm run openspec -- new change <change>`, with `proposal.md`, `design.md`, a spec delta, `tasks.md`, `verification.md`, an empty `findings.jsonl` and `passes.jsonl`, and the brief's checklist saved as `checklist.json` ([review findings record](#review-findings-record)). A delta that creates a capability starts with a `## Purpose` of at least 50 characters, because `archive` otherwise writes a placeholder that fails strict validation; `make verify` archives every active change in a temporary copy and fails on such problems. Documentation-only work under an existing requirement may instead set `skip_specs: true` in `.openspec.yaml` and add no `specs/` files. `npm run openspec -- validate <change> --strict` must pass.
3. **Scope and content.** Implement only the assigned scope. Write all repository content in English, and paraphrase non-English owner quotes. Keep every comment in tracked authored source, script, build, and configuration files to at most two lines of at most 80 characters each, counting block-comment delimiters, indentation, and markers, as `AGENTS.md` states. Generated files, lockfiles, captured third-party artifacts under `docs/qualification/`, and fixture copies of those captures are exempt; `make verify` enforces the rule through `npm run verify:comments`. Use conventional commit messages with no AI attribution, `Co-Authored-By` trailer, or session link. Use `feat`, `fix`, or `perf`, or a revert, only for changes to the published `taskelith` package, because they can trigger a release ([releases](releases.md)); work in private workspace packages, documentation, and tooling uses `chore`, `build`, `ci`, `docs`, or `test`.
4. **Checks.** Once the implementation is committed, and before the `make verify` run that `make record` records for pass 1, run `make findings ARGS="route --change <change>"` and commit the change's `route.json` unedited ([route record](#review-findings-record)); if that run's fixes change the diff, delete `route.json`, route again, and record why in `verification.md`. Run `make verify` before the first review pass and again after each round of fixes. On a branch whose changes since its merge base with `origin/dev` touch only `docs/**` other than `docs/review-findings/**` and `docs/qualification/**`, which tests read, `openspec/**`, or root-level Markdown other than `CHANGELOG.md`, it runs its docs-only profile, which skips only `make test`; every other branch runs the full profile. A run that passes on a clean committed tree writes a stamp of that tree and its merge base with `origin/dev`, which the `pre-push` hook and `make integrate` reuse; a detached HEAD always gets the full profile. `make test` takes the host-wide Docker slot by itself, first in, first out, and prints who holds it while it waits (`make docker-slot` shows the queue), so a worker no longer asks the coordinator for the slot; a run whose `make test` was killed keeps the slot until every process of its command has ended.
5. **Review.** Follow the [independent review process](governance.md#independent-review-process) with the reviewer of each pass that the coordinator assigns, at the effort that governance "Routed effort" allows, reporting to the coordinator a reviewer of pass 1 or 3 in `route.json` other than the brief's. The passes run in the order of governance "Review sequence" until a pass reports only Low findings or none: pass 1, role A; pass 2, role B; and pass 3, role A, only after a pass 2 with a Medium or worse finding. Run each pass with `make review` as [reviewer invocations](#reviewer-invocations) describes. After every pass that runs to a report, append one summary line to `passes.jsonl`, filled in from the template that `make review` prints, also for a pass without findings, with its role, A or B, reviewer, session, and counts by severity, and one line per finding to `findings.jsonl` with its capability for any file outside `openspec/changes/`, its outcome once the pass's findings are resolved, and `missedBy` when an earlier pass or the integration missed it; update a line's outcome when a later pass changes it. Failed attempts add no lines ([review findings record](#review-findings-record)).
6. **Record.** Write `verification.md` as the [lifecycle table](governance.md#lifecycle-and-records) and the [review process](governance.md#independent-review-process) require: scope and source, the revision, environment, the author self-check and evidence check, the exact checks and results, each review pass with its reviewer and role, A or B, its invocation, model confirmation, session ID, snapshot result, findings with counts by severity that match its `passes.jsonl` line, and resolutions, any unreviewed fixes marked as such, with a place for the coordinator's architect check of them (governance "Architect check of unreviewed fixes"), limitations, and remaining gates. [The SpecKit capture record](../openspec/changes/archive/2026-10-24-capture-speckit-native-artifacts/verification.md) is an example. Link from the change's records only inside the change directory, such as `design.md` or `specs/<capability>/spec.md`, or root-relative, such as `/docs/governance.md`, never with `../` out of it or to an active change, because archiving moves the directory; a spec delta, whose text archiving copies into `openspec/specs/`, links only root-relative. `make verify` runs `npm run verify:links`, which checks this at the change's future archived path and checks that every link target and anchor under `openspec/changes/`, `openspec/specs/`, and `docs/` exists, archived records included. The mechanical part, the `make verify` result with its profile, tree, test counts, and coverage, the strict OpenSpec and findings validations, the spec diff stat against the merge base, and the passes of `passes.jsonl`, is generated: after a passing `make verify` on the committed tree, run `make record CHANGE=<change> LOG=<make verify log>`, which reads the log's last complete run, refuses a log that does not end with its stamped result or whose totals contradict each other, rewrites only the text between its markers, and stores the `make verify` line next to the run's stamp; before pass 1 run `make record-check CHANGE=<change>`, which fails when that text no longer matches the tree, when the tree differs from the verified one outside the change's `verification.md`, `tasks.md`, `findings.jsonl`, and `passes.jsonl`, or when the `make verify` line differs from the stored one; reviewers check the hand-written rest. Before step 7 the record is complete except for the results of step 7's own checks, which step 7 adds. Its remaining gates name `Integration into dev by the coordinator (single pull request)`. The coordinator does not edit the archived record: the merge pull request records the integration checks, and its merge commit is the integrated revision.
7. **Archive.** After the last review pass and its fixes, tick every task in `tasks.md` and archive the change in the last commit of the branch:
    1. Run `npm run openspec -- archive <change> --yes`.
    2. On the resulting working tree, run `npm run openspec -- validate --all --strict`, which checks the active changes and the living specs, and `make verify`. Check this change's line in `npm run openspec -- validate --archived --no-interactive`, which checks that archived changes have every task done; the command fails as a whole on older archived changes, so only this change's line counts. Check that `git diff "$(git merge-base HEAD origin/dev)" -- openspec/specs` shows only this change's intended edits. Check that the moved change has its `findings.jsonl`, empty if the review found nothing, and its `passes.jsonl`, and that `make findings ARGS="validate"`, which `make verify` runs, passes; validation requires the files only in active changes, so this check covers the archived one.
    3. Write those results into the moved `verification.md`, naming the checked state as the tree of the archive commit, which is the working tree the checks ran on; then commit everything as `docs: archive the <title> change`.

    The archive commit only applies the reviewed deltas with the pinned CLI, so it needs no further review pass.
8. **Handoff.** Push the branch with `git push -u origin <change>`; the `pre-push` hook runs `make verify`, unless the clean HEAD tree has a stamp of a passing run of its profile. Send the coordinator the branch, the head commit (the archive commit), a short summary, the `make verify` result, and the review result. Then return to the main clone and stop.
9. **After integration.** When the coordinator reports the merge, update the main clone (`git switch dev && git pull --ff-only`). If the task's worktree or local branch still exists on the worker's machine, remove them (`git worktree remove ../taskelith-worktrees/<change>` and `git branch -D <change>`). Then take the next brief in the same session: since 2026-10-27 (owner) the owner does not clear a worker's session after each task, and the worker keeps it thin as [context size](#context-size) describes.
10. **Return.** The coordinator returns a task when merging `dev` into its branch conflicts in any file other than the dependency inventory, when that merge invalidates its evidence, or when the branch lacks its archive commit. The coordinator merges `dev` only on a local integration branch in its own worktree (`make integrate`), pushes the merge only when it will integrate, and on any return discards that branch and worktree, so a returned branch never carries a coordinator merge. On any return of a branch that carries its archive commit, the worker restores the active change by reverting that commit, merges `dev`, reconciles each restored delta with `dev`'s current requirement text, keeping others' edits, has the reviewer of pass 1 review the resolved diff and the reconciliation, records it, and archives again as the last commit; a branch without an archive commit only needs step 7. In the task's worktree:
    1. `git revert --no-commit <archive commit>`, which restores the active change directory and the living specs from before the archive, and commit as `docs: restore the active <title> change to merge dev`.
    2. Note the merge base of the archive commit and `dev` (`base="$(git merge-base <archive commit> origin/dev)"`), which stays right even if the branch already carries a later merge of `dev`, then `git merge origin/dev`. The living specs then come from `dev`, because the branch changes them only through the archive; resolve any other conflict.
    3. Reconcile every restored delta with `dev`'s current living specs. The pinned OpenSpec replaces a whole `MODIFIED` requirement, keeping no edit made since under the same scenario names, so a stale delta would silently undo `dev`'s edits. For each requirement that a delta modifies, removes, or renames and that `dev` changed (`git diff "$base" origin/dev -- openspec/specs`), rewrite the delta from `dev`'s current text and keep those edits.
    4. Run `make verify`, have the reviewer of pass 1 review the resolved diff and the reconciliation, and record it in the restored `verification.md`.
    5. Archive again under step 7, whose spec diff must show only this change's intended edits, and hand off under step 8.

    A merge without such a conflict or invalidated evidence never comes back: the coordinator completes it, including a regenerated dependency inventory. This mirrors the conflict flow of [ADR 0008](decisions/0008-product-ui-and-integration-authority.md) decision 3, including its spec-conflict and escalation rules.

Questions that belong to the owner (see Roles) go to the coordinator with options and a recommendation. The worker does not decide them.

## Coordinator steps

1. **Assign.** Assign only tasks without an open owner decision. When a worker is idle and such a task exists, send it a complete brief: the task and its plan row, scope and exclusions, the tasks it depends on, the assigned reviewer of each pass, as governance "Reviewer assignment" names them, a pointer to this protocol, and the review checklist that `make findings ARGS="checklist --capability <capabilities> --files <globs>"` prints for the capabilities and files the task is expected to touch, with that exact invocation, the dev commit that its last line names, and the task's size (S, S-M, M, M-L, or L), so that the worker can save it. Assign reviewers as the [review process](governance.md#independent-review-process) requires, including reviewers with network access for tasks that depend on external facts. Skip a reviewer that is [unavailable](governance.md#independent-review-process), paused, unable to meet the task's review requirements, or barred from the role by governance "Reviewer assignment". When the reviewer of a pass becomes unavailable, assign the replacement that the worker proposes from the rotation, that may review the pass under governance "Reviewer assignment" and whose harness differs from the reviewers of the adjacent passes unless governance "Unavailable reviewer" allows otherwise. Before integration, check every fix that no later pass reviewed as solution architect and record the check (governance "Architect check of unreviewed fixes"): one line in the change's `verification.md` or, for an archived branch, in the pull request body. Bring owner questions to the owner with options and a recommendation.
2. **Integrate.** Integrate one task at a time, through one pull request that carries the archived change, with `make integrate BRANCH=<change> TITLE=<title> BODY=<body>` from the main clone ([`scripts/integrate.sh`](../scripts/integrate.sh)). Before it, check with `git diff "$(git merge-base origin/<change> origin/dev)" origin/dev --stat` whether `dev` changed the task's requirements, contracts, implementation, or verification inputs; if so, return the task to its worker under worker step 10 without running it. The command:
   - first checks that the main clone is on `dev`, has no uncommitted or untracked change, and fast-forwards to `origin/dev`, and otherwise prints `MAIN NOT READY <main clone> <reason>` and exits with status 8 before it changes anything.
   - creates the integration worktree `../taskelith-worktrees/itg-<change>` on the local branch `itg-<change>` from `origin/<change>`, and stops with `NOT ARCHIVED <change>` (exit status 5) unless the branch carries its archived change: `openspec/changes/<change>/` is gone and `openspec/changes/archive/<date>-<change>/` exists. Return such a task to its worker under worker step 10.
   - merges `origin/dev` there with a merge commit on the local branch. On a conflict it aborts the merge, lists the conflicting files, prints `CONFLICT <change>`, and exits with status 3. Conflicts in the generated dependency inventory resolve themselves; any other conflict returns the task to its worker under worker step 10.
   - runs `make setup`, stops with `NOT CLEAN <change>` (exit status 7) when the integration worktree has an uncommitted or untracked change, and requires a full `make verify` stamp of the merged tree, running the full `make verify` as its own process group under a 2400 s alarm (`TASKELITH_INTEGRATE_TIMEOUT`) when none exists; on the alarm, and when the command gets `INT`, `TERM`, or `HUP`, it stops the whole group and waits until it is gone; an interrupted run prints `INTERRUPTED <change>` and exits with 128 plus the signal number. On a failure, or when a passing run left no full stamp of the merged tree, it prints `VERIFY FAIL <change>` and the end of the log and exits with status 4; nothing is pushed. When `make verify` reports the inventory stale, run `make dependency-inventory` in the integration worktree, commit the regenerated files, and continue with `RESUME=1` (no other value resumes), which needs no return to the worker. When the failure is the task's, remove the integration worktree and its local branch and return the task the same way.
   - after the verify step prints the integration line `Integration: tree <tree>; verify <ran, or reused stamp of <time>>; profile full; verify seconds <seconds>; change <archived change directory>; branch <change>; started <time>`, with the run's start time after any pause in UTC to the second and the verify step's whole seconds, adds it after `BODY` to the body of a pull request it opens or appends it to the body of an open pull request a resume continues, and appends it as one JSON line to `${XDG_STATE_HOME:-~/.local/state}/taskelith/integrations.jsonl`, the integration log, where a failed append only warns.
   - pushes the merge to the task's branch, where the `pre-push` hook reuses the stamp, opens a pull request into `dev`, and merges it with a merge commit; a resume continues with the open pull request of the branch, or skips the merge when its pull request is already merged at the pushed commit. When the integration HEAD is already in `origin/dev`, because an earlier attempt's pull request was merged, a run or a resume only cleans up and opens no second pull request. There is no separate archive pull request, and the coordinator does not edit the archived `verification.md`: the pull request records the integration checks, and its merge commit is the integrated revision.
   - removes the integration worktree and its local branch, updates the main clone with `git pull --ff-only` and `npm ci`, deletes the remote branch, and checks that it is gone: exit status 6 with `DELETE FAILED <change>` when it remains, and exit status 9 with `DELETE UNCONFIRMED <change>` when origin cannot be asked. Then it prints `LANDED <change> <url> <head>`.

   `TITLE` and `BODY` reach the script exactly as typed: `make` expands neither.
   While the file `${XDG_STATE_HOME:-~/.local/state}/taskelith/integrate.pause` exists, the command waits before it starts. It replaces the coordinator's former scratch scripts.
   - If a commit type would trigger a release that the change does not warrant, recommit it with the right type on a new branch with the same author, instead of rewriting the pushed branch.
3. **Clean up.** `make integrate` updates the main clone, removes the integration worktree and local branch, and deletes the remote branch ([releases](releases.md#parallel-work-with-worktrees)); after a return, remove the integration worktree and local branch yourself. Remove a worker's worktree only on the worker's own machine, by the worker (worker step 9).
4. **Release the worker.** Tell the worker that its task is merged, so that it cleans up, and brief its next task right after the landing report; the worker keeps its session.

## Task progress

`make progress` prints, for every task worktree on this host and on the SSH hosts listed in `~/.config/taskelith/progress-hosts.json` (a JSON list of `{"name", "ssh", "repo"}`, for example `[{"name": "Zaki", "ssh": "petar@hpz600", "repo": "~/taskelith"}]`, kept outside the repository), its stage from 1 brief to 11 landed, derived only from the records these steps already create: the checklist, code commits, the verify stamp, `route.json`, `passes.jsonl`, the archive commit, the coordinator's integration queue, and the merge into `origin/dev`; an unreachable host is reported and never fails the run. `make progress-refresh` writes the same view atomically to `~/.config/taskelith/progress.json`, which the coordinator's status line reads and refreshes in the background when it is older than 60 seconds; its lock only de-duplicates refreshes, best-effort, so a rare overlap runs two refreshes, and the atomic write keeps the cache whole. Workers take no extra step for it.

## Subagent execution

The owner set this rule on 2026-10-26; it applies to tasks assigned from that day on.

- **Implementation in a subagent.** A session that develops a task, a worker or the coordinator, delegates the work of the worktree (code, tests, documentation, and OpenSpec artifacts) to a subagent that it briefs with the task, its scope, and the rules that apply. The session reviews and checks the subagent's result itself before review and handoff.
- **Protocol in the session.** The session keeps the protocol steps: messages to the coordinator or the owner, owner questions, the independent review, whose results the subagent may record as the session provides them, and the handoff. A subagent does not hand off, open pull requests, or decide owner questions.
- **Fresh subagents** (owner, 2026-10-27). A session does not resume a subagent that has been idle for more than five minutes, because a resumed subagent rereads its whole context. For a round of review fixes it starts a fresh subagent with a short brief: the findings, the files they name, the checks to run, and where the task's records are.

## Test authoring

The owner set this rule on 2026-10-27 to stop flaky tests where they are written, not in follow-up changes:

- **No sleeps for synchronization.** A test that waits for concurrent work waits on a barrier, an event, or a condition the work signals, or drives an injected clock; it never waits a fixed time and hopes the work is done.
- **Wide timing bounds.** A bound on stubbed work is at least six times that work, for example at least 600 ms for 100 ms of stubbed work, because loaded hosts such as the coordinator's iMac stretch timings.
- **No scheduling luck.** A test does not depend on the order in which the runtime happens to schedule timers, promises, or processes, or on state shared with another test.

Reviewers file a breach as the category `test-flakiness` of [`categories.txt`](review-findings/categories.txt), which the plan checklist of every brief already ranks.

## Context size

The owner set this rule on 2026-10-25. Since 2026-10-27 (owner) sessions keep their context thin so that they rarely reach the limit:

- **Coordinator.** It offloads polling, such as waiting for an integration or a review, to background scripts and their notifications instead of repeated checks in its context, and keeps briefs and notes in files that it names in its messages.
- **Worker.** It does all task work in subagents ([subagent execution](#subagent-execution)) and keeps only the protocol steps in its main session.
- **Warning hook.** The tracked [`.claude/settings.json`](../.claude/settings.json) runs [`scripts/context-warning.ts`](../scripts/context-warning.ts) on every prompt. It estimates the context from the transcript, from the usage of the newest response or, without one, from the transcript size at four bytes per token, and prints one warning line at 140,000 tokens or more (`TASKELITH_CONTEXT_WARN_TOKENS` changes the threshold). It is an estimate, never blocks a prompt, and never prints transcript content.

When a session's context approaches 150,000 tokens, the session tells the owner and recommends `/compact` or `/clear`, because only the owner can run them in the session's window. It warns before the limit, not after.

- **Record first.** Before it warns, the session records what a reset would lose. A worker commits its work and notes its state and open questions in the change's `tasks.md` or `verification.md`; the coordinator updates its notes on assignments and pending integrations.
- **Recommend one.** It recommends `/compact` while a task is in progress or decisions are not yet recorded, and `/clear` when everything needed is recorded. A worker in the middle of a task recommends only `/compact`; it recommends `/clear` only between tasks, when nothing it needs is unrecorded.
- **Worker.** A worker also tells the coordinator, which sends it no work until the worker reports that it is ready again.
- **Coordinator.** The coordinator also says whether any handoff is waiting for integration.

## Review findings record

The owner set this record on 2026-10-27 so that past review findings inform new briefs. It lives in the repository; there is no database.

- **Format.** Each OpenSpec change keeps `findings.jsonl` next to `verification.md`: one JSON object per line and per finding, as [`docs/review-findings/finding.schema.json`](review-findings/finding.schema.json) defines it, with the change, optional artifact, pass, reviewer (harness, model, variant or effort, in the canonical key that "Validation" names), session, severity, category, title, file, optional line, capability, outcome (`fixed`, `fixed-unreviewed`, `declined`, `deferred`, or `owner-accepted`), resolution, and optional commit. A change that reviews several artifacts, each with its own review sequence of passes 1 to 3, names the reviewed artifact in `artifact`, an identifier; a change that reviews one artifact omits it. A change without findings has an empty file. The capability is the OpenSpec capability the finding concerns. A finding whose file is under `openspec/changes/`, for example the change's own `verification.md`, is a record finding and may omit it; every other finding names it, and a change that skips specs names the closest capability under `openspec/specs`. Lines are bounded, unknown properties are rejected, and a value shaped like a token or credential fails validation, because reviewer text is untrusted: write titles and resolutions in your own words.
- **Pass summaries.** Each OpenSpec change also keeps `passes.jsonl` next to `findings.jsonl`: one JSON object per line and per review pass that ran to a report, also one without findings, as [`docs/review-findings/pass.schema.json`](review-findings/pass.schema.json) defines it, with the change, optional artifact, pass, role (`A` or `B`), reviewer, session, and counts by severity (`critical`, `high`, `medium`, `low`). A pass is identified by its artifact and number; an absent artifact is its own. A change not yet reviewed has an empty file. Failed attempts are not passes and have no line. The summaries are a separate file so that every line of `findings.jsonl` stays one finding and the archived findings need no rewrite.
- **Missed findings.** A finding may name what missed it in `missedBy`: an earlier pass of the change and of the finding's own artifact with that pass's role, for example `{"pass": 1, "role": "A"}`, or `"integration"` for work already integrated into `dev`.
- **Commands.** `make findings ARGS="<command>"` runs the tool with the pinned Node.js and passes globs in `ARGS` unexpanded; `npm run findings -- <command>` is its implementation and takes the same commands.
- **Categories.** [`docs/review-findings/categories.txt`](review-findings/categories.txt) is the controlled vocabulary, one category per line; adding a category is adding one line there.
- **Validation.** `make findings ARGS="validate"`, which `make verify` runs as `npm run verify:findings`, checks every `findings.jsonl` and `passes.jsonl` under `openspec/changes`, active and archived, against the schemas and the vocabulary and reports each problem with its file and line. Pass summaries get the same line bound, unknown-property, and secret-like-value checks as findings, and a `missedBy` pass must be earlier than the finding's pass. Where a change has `passes.jsonl`, with a missing `findings.jsonl` taken as empty, each pass of each artifact is summarized once, every finding's pass of its artifact has a summary with the same reviewer and session, the summary's counts equal the findings of that artifact's pass by severity, and a `missedBy` pass of the finding's artifact has a summary with the named role; messages name the artifact when there is one. Every active change must have both files, and in an active change a finding outside `openspec/changes/` must name a capability that exists as a directory under `openspec/specs`, as must any capability a record finding names. In an active change every reviewer of both files must use the canonical key: harness `claude`, `codex`, `opencode`, or `agy`; the model as the harness CLI takes it, for an OpenCode model only, `<provider>/<model>` with both parts non-empty, for example `opencode-go/kimi-k2.7-code`, and no other model with a prefix; and `variant`, the effort, `default` when the harness default ran. Validation reports any other key with its file and line. Archived findings are checked without this capability rule and archived records without the reviewer key rule, because they predate them. Changes archived before these records existed have none and are not backfilled; worker step 7 checks that a newly archived change has its files.
- **Legacy reviewer keys.** Archived records are not rewritten. `index`, `reviewers`, and `checklist` read the legacy spellings of their reviewers as the canonical key through one alias table, `LEGACY_REVIEWER_ALIASES` in [`scripts/reviewer-keys.ts`](../scripts/reviewer-keys.ts), so that each reviewer has one row.
- **Index.** `make findings ARGS="index [--json]"` counts archived findings by category, capability, file, and reviewer, with the shares fixed (`fixed` and `fixed-unreviewed`), declined, and other (`deferred` and `owner-accepted`).
- **Reviewer statistics.** `make findings ARGS="reviewers [--json]"` counts archived review passes per reviewer and per role, A or B, where role A covers passes 1 and 3, since policy version 8 the Codex reviewers of both, and role B pass 2, so that the counts stay comparable with earlier records: passes, findings by severity, findings per pass, the share of passes with at least one Medium or worse finding, and the misses that later findings attribute to the reviewer's passes through `missedBy`, plus the misses attributed to the integration and, apart, those that name a pass without a record, for example a pass without findings of an archived change without `passes.jsonl`. An archived change without `passes.jsonl` counts only its passes with findings, derived from `findings.jsonl`, with role `(unknown)`, and the output says so; it also states how many archived changes have neither file and are therefore not counted.
- **Checklist.** `make findings ARGS="checklist --capability <a,b> --files <globs> [--top N]"` lists the most frequent archived categories, seven by default and at most ten, each with its newest example title. An archived finding matches when its capability is one of the given ones or its file matches one of the globs (Node.js `path.posix.matchesGlob`); with neither option every archived finding matches. Whatever the options, a "Record quality" section follows: the same ranking over archived record findings, whose file is under `openspec/changes/`. Where git has the merge base of `HEAD` and `origin/dev` and can read its archive, the command ranks the archived findings as of that dev commit and a last line names it, so that `--at` with that commit reproduces the checklist; otherwise it ranks the working tree's archive and names no commit. `--at <commit>` ranks the archive as of the given commit, read through git, and fails on an unknown commit. The coordinator pastes both sections and the dev commit line into the brief, with the invocation. `--json` prints both sections and the dev commit as JSON.
- **Checklist record.** When the worker creates the change, before the first review pass, it saves the brief's checklist as the change's `checklist.json` by running the brief's exact invocation with `--save <change> --at <dev commit>`, the dev commit that the brief's checklist names, and, when the brief gives a size, `--size <S|S-M|M|M-L|L>`: `make findings ARGS="checklist --files scripts/** --save <change> --at 0123abc --size S-M"`. Because `--at` ranks the archive as of the brief's dev commit, the record equals the brief's checklist even if `dev` moved since. [`docs/review-findings/checklist.schema.json`](review-findings/checklist.schema.json) defines the file: the query (capabilities, file globs, top), the generation time, the dev commit, the size, and both ranked lists with their counts and baselines. The review baseline counts every archived finding outside `openspec/changes/`, the record quality baseline every archived record finding, all and Medium or worse, and how many of them have a listed category. `--save` refuses an unknown commit, a name that is not an active change directory (`archive` included), and an existing file, and the worker does not edit the file; the archive keeps it. Validation checks every `checklist.json`, active and archived, against the schema, its change, and the vocabulary, and that it is consistent: a real generation time, unique categories ranked by count and at most `top` of them, and baselines whose listed and Medium or worse counts do not exceed their totals. It requires one in every active change opened after this rule landed: once git has the commit that first added `openspec/changes/archive/<date>-measure-checklist-effect/`, an active change needs `checklist.json` when the commit that first added its `.openspec.yaml` descends from that commit, or when its `.openspec.yaml` is not committed. A shallow clone, such as the CI checkout, requires none, because its boundary commit appears to add every file; `make verify` in a full clone, which the `pre-push` hook runs, enforces the rule. Changes opened earlier, and archived changes, are not backfilled, because the brief text is not kept in the repository.
- **Route record.** Before pass 1 (worker step 4) the worker runs `make findings ARGS="route --change <change> [--json] [--no-shadow]"`, which derives structured features of the committed change against its merge base with `origin/dev`, decides a tier, `standard` or `elevated`, with the deterministic rule, asks the shadow router, TypeSafe AI's Jev model, unless `--no-shadow` is given, and writes the change's `route.json`. The shadow router gets one yes-or-no question, whether the change will need review pass 3 under governance "Review sequence", that is whether the reviewer of pass 2 will find a Medium or worse issue, with the features except the rule's path flags, a context that explains the fields, the review process, and the third pass rates of the other archived reviewed changes, overall and by lines changed, and the proposal's Why and What Changes, with secret-like strings redacted and clipped at 1,200 and 1,500 characters, and its task and spec requirement counts; it records P(third) and the shadow tier, `elevated` at 0.4 or more, defined by [`docs/review-findings/route.schema.json`](review-findings/route.schema.json). Since rule version 2 its reviewer table plans passes 1, 2, and 3 of governance "Reviewer assignment", with the networked reviewers of passes 1 and 3 for a change with external facts, and keys the efforts of each tier per pass; the record only recommends (governance "Routed effort"). The shadow router reads its credential from the environment variable `JEV_MAF_LAB`, which the owner sets on the host; the value never reaches output or records. Without it, when its input cannot be built, or on a timeout or error, the rule decides alone, the command exits 0, and `route.json` records the reason code; without the credential it reads no archive or proposal for its input. The command refuses an existing `route.json`, an archived or unknown change, and uncommitted changes outside the change directory. Validation checks every `route.json`, active and archived, against the schema, its change, the secret-like value check, and the trigger thresholds and reviewer table of its rule version, for its features and tier, so that a later version leaves archived records valid; a change without one is not reported. `make findings ARGS="route-evaluation [--at <revision>] [--rule-only] [--save <change>] [--json]"` routes the archived reviewed changes as of a revision, for a one-time evaluation of the routers.
- **Checklist effect.** `make findings ARGS="effect [--json]"` measures, over archived changes with `checklist.json`, per change and per archive date, the share of pass-1 findings outside `openspec/changes/`, all and Medium or worse, whose category the review list names, and the same for pass-1 record findings and the record quality list, each beside the expected share of its baseline; a day's expected share is the findings-weighted mean of its changes. An observed share below the expected one suggests that the checklist prevented findings it warns about. Pass-1 findings are normalized per size point (S 1, S-M 1.5, M 2, M-L 2.5, L 3) or, without a recorded size, per 100 lines changed outside `openspec/changes/` between the dev commit and the archive commit. Archived changes without `checklist.json` are listed and excluded. A routing section follows: per archived change with `route.json`, the rule's tier and triggers, the shadow router's tier and P(third), or P(`elevated`) for a record routed before the third pass question, or its failure code, the recommended reviewers and those that ran passes 1 and 2, whether they followed the route, the passes needed, and the findings of passes 1 and 2 by severity; then, per router and tier, the third pass share, the agreement of the two tiers, the Brier score and AUC of P(third) against the third passes that ran, and the share of changes that followed the route. A review that ended after pass 2 counts two passes.

## Reviewer invocations

The coordinator assigns the reviewer of each pass as governance "Reviewer assignment" under ["Review sequence"](governance.md#independent-review-process) sets out (owner, 2026-10-28): Codex CLI (gpt-6-astra) for pass 1, Claude Code (claude-opus-5-5) at effort `medium` for pass 2, and Codex CLI (gpt-6.1-sol) for pass 3; for a task that needs network access Claude Code (claude-fable-5-1) for passes 1 and 3; an OpenCode reviewer never for pass 1 or 3, and for pass 2 only of a documentation-only task once its pause has ended. Governance holds the rule, its reasons, and the replacements; the other reviewers below serve as replacements.

Run each pass from the task's worktree with `make review`, which takes the reviewer's key, an authorized reviewer of governance "Authorized reviewers" at its configured effort, and a prompt and a log outside the worktree. Keep prompt files, logs, and snapshot files outside the worktree, for example in a scratch directory, so that they do not change the snapshot; `make review` takes no snapshot, so the worker takes the snapshots below before and after it:

```bash
make review CHANGE=<change> PASS=<1-9> [ROLE=<A|B>] REVIEWER='<reviewer key>' PROMPT=<prompt file> LOG=<log file>
```

The exit statuses below are those of [`scripts/review-run.ts`](../scripts/review-run.ts); `make` reports a failing one as `Error <status>` and itself exits 2. Without `ROLE` the command takes the role of the pass, A for passes 1 and 3 and B for pass 2, and a later pass needs `ROLE`. A wrong argument, also a given `ROLE` other than the role of its pass, exits 2 with the usage and the reviewer keys.

- **Route gate.** Before pass 1, when the change's `route.json` is missing or was made for another tree (another merge base with `origin/dev`, or a routed commit whose tree differs from `HEAD` outside the change's directory), the command routes the change, as `make findings ARGS="route --change <change>"` does, only when the clean tree has a passing `make verify` stamp, deleting a stale `route.json` first and restoring it when routing fails; it then stops with exit status 3, so that the worker commits `route.json`, records why a stale one was routed again, and runs `make verify`, `make record`, and `make review` again. Without the stamp it refuses with exit status 1. Later passes never route.
- **Clean environment.** The reviewer CLI starts through `env -i` with an empty environment, so that no variable that Node.js adds to child processes reaches it either, plus only `PATH`, `HOME`, `USER`, `LANG`, `TERM`, and `TMPDIR` and the variables that its row of the table in [`scripts/reviewer-invocations.ts`](../scripts/reviewer-invocations.ts) declares (`CODEX_HOME`; `CLAUDE_CONFIG_DIR`; the `XDG_*` directories and `OPENCODE_CONFIG`), each only when set. No secret, `JEV_MAF_LAB` included, reaches a reviewer; reviewers must still not read the shell profile, because a login shell restores the variable.
- **Fixed invocation.** That table holds each reviewer's command with its mandatory flags and the effort that governance "Authorized reviewers" configures; the reviewer that `route.json` recommends for the pass, the plan of the same pass number or, for pass 3 of a rule version 1 record, pass 1's plan, is printed beside it: another effort as `recommends effort <effort>; the authorized <effort> applies`, which replaces it only once governance "Routed effort" authorizes it, and, for passes 1 and 3, another reviewer with the request to report it to the coordinator. The log takes the reviewer's stdout and stderr; Antigravity also writes its own log next to it, with the suffix `.cli.log`, which the command empties before each run. The prompt and both logs must resolve outside the worktree, and a log that is a symbolic link, has other hard links, is no regular file, or is the prompt file is refused with exit status 1.
- **Record.** Before the reviewer starts, the command prints the route gate's result, the recommendation, the invocation, the environment's names, the log, and the start time, so that a failed attempt keeps them. After a run that exits 0 and reports a valid session ID and the reviewer's model (for OpenCode in the assistant messages of `opencode session export --standalone --sanitize <session>`, for Antigravity in the model label of its own log), and, for Codex, the effort and the `read-only` sandbox of the key in its header, the command prints the session and the model confirmation, for Codex also the effort and sandbox, for `verification.md`, and a `passes.jsonl` line template with the change, pass, role, reviewer, and session filled and a placeholder for each count, which fails validation until filled. It writes no line, because a line with counts not yet counted would be a false record: after the report, replace the placeholders with the counts of the findings you record in `findings.jsonl` and append the line, as step 5 says. It refuses a pass that already has a line before the reviewer runs. A failed attempt exits 4.
