# Agent task protocol

Status: working protocol for agent sessions that develop Taskelith in parallel, set by the owner on 2026-10-24. It applies the [governance policy](governance.md) and the [release flow](releases.md) to several sessions working at once, on one or more machines. It summarizes the operational steps and points to those documents for the full rules; where this page and they differ, they win.

## Roles

- **Owner.** Defines scope and decides product, architecture, dependency, promotion, publication, and deployment questions, review exceptions, and findings left after the third review pass ([governance "Authority"](governance.md#authority), [review process](governance.md#independent-review-process)).
- **Coordinator.** One session that plans the work items, assigns them to workers, and integrates finished work. On 2026-10-24 the owner authorized the coordinator to merge each completed and reviewed task into `dev` and start or assign the next one without a separate approval.
- **Worker.** A session that develops one assigned task at a time and hands it back to the coordinator. Since 2026-10-26 (owner) the worker archives its change on its own branch before the handoff, so that the coordinator integrates it with one pull request; a worker does not open pull requests or merge. UI tasks (SPA, board, inbox, intake and write-back screens, plugin and settings UI) go to the worker that holds the UI proof of concept.

The coordinator may also develop tasks itself, following the worker steps, and then integrates its own work.

## Worker steps

1. **Worktree.** Develop each task in its own worktree on its own branch, created from a fresh `origin/dev` as in [releases "Parallel work with worktrees"](releases.md#parallel-work-with-worktrees), then `nvm use` and `npm ci --ignore-scripts`. To pick up newer `dev` work, merge `origin/dev` into the branch with a merge commit; when the `post-merge` hook or `make verify` reports a stale dependency inventory, run `make dependency-inventory` and commit the regenerated files ([merging parallel branches](dependency-inventory.md#merging-parallel-branches)). Do not rebase a pushed branch, and never force push. A merge that changes the task's requirements, contracts, implementation, or verification inputs invalidates the affected evidence ([evidence freshness](governance.md#evidence-freshness)): repeat the checks and the review.
2. **Change.** Bind the task to an OpenSpec change named after it: `npm run openspec -- new change <change>`, with `proposal.md`, `design.md`, a spec delta, `tasks.md`, and `verification.md`. A delta that creates a capability starts with a `## Purpose` of at least 50 characters, because `archive` otherwise writes a placeholder that fails strict validation; `make verify` archives every active change in a temporary copy and fails on such problems. Documentation-only work under an existing requirement may instead set `skip_specs: true` in `.openspec.yaml` and add no `specs/` files. `npm run openspec -- validate <change> --strict` must pass.
3. **Scope and content.** Implement only the assigned scope. Write all repository content in English, and paraphrase non-English owner quotes. Keep every comment in tracked authored source, script, build, and configuration files to at most two lines of at most 80 characters each, counting block-comment delimiters, indentation, and markers, as `AGENTS.md` states. Generated files, lockfiles, captured third-party artifacts under `docs/qualification/`, and fixture copies of those captures are exempt; `make verify` enforces the rule through `npm run verify:comments`. Use conventional commit messages with no AI attribution, `Co-Authored-By` trailer, or session link. Use `feat`, `fix`, or `perf`, or a revert, only for changes to the published `taskelith` package, because they can trigger a release ([releases](releases.md)); work in private workspace packages, documentation, and tooling uses `chore`, `build`, `ci`, `docs`, or `test`.
4. **Checks.** Run `make verify` before the first review pass and again after each round of fixes.
5. **Review.** Follow the [independent review process](governance.md#independent-review-process) with the reviewer the coordinator assigns, using the invocations below.
6. **Record.** Write `verification.md` as the [lifecycle table](governance.md#lifecycle-and-records) and the [review process](governance.md#independent-review-process) require: scope and source, the revision, environment, the author self-check and evidence check, the exact checks and results, each review pass with its invocation, model confirmation, session ID, snapshot result, findings, and resolutions, any unreviewed fixes marked as such, limitations, and remaining gates. [The SpecKit capture record](../openspec/changes/archive/2026-10-24-capture-speckit-native-artifacts/verification.md) is an example. Complete the record before step 7; afterwards only step 10 adds to it. Its remaining gates name `Integration into dev by the coordinator (single pull request)`; the coordinator does not edit the archived record, and the merge pull request and its merge commit record the integrated revision.
7. **Archive.** After the last review pass and its fixes, archive the change in the last commit of the branch: run `npm run openspec -- archive <change> --yes`, then `npm run openspec -- validate --all --strict` and `make verify`, and commit as `docs: archive the <title> change`. The archive commit only applies the reviewed change with the pinned CLI, so it needs no further review pass.
8. **Handoff.** Push the branch with `git push -u origin <change>`; the `pre-push` hook runs `make verify`. Send the coordinator the branch, the head commit (the archive commit), a short summary, the `make verify` result, and the review result. Then return to the main clone and stop.
9. **After integration.** When the coordinator reports the merge, update the main clone (`git switch dev && git pull --ff-only`). If the task's worktree or local branch still exists on the worker's machine, remove them (`git worktree remove ../taskelith-worktrees/<change>` and `git branch -D <change>`). Then clear the session's context (`/clear` in Claude Code) before taking the next task.
10. **Conflicts.** When the coordinator returns a task because its branch conflicts with `dev`, merge `origin/dev` and resolve the conflict in the task's worktree, run `make verify` again, have the assigned reviewer review the resolved diff, record it in `verification.md` (the archived one, or the restored one under step 11), and hand off again. A merge without such a conflict or invalidated evidence never comes back: the coordinator completes it, including a regenerated dependency inventory. This mirrors the conflict flow of [ADR 0008](decisions/0008-product-ui-and-integration-authority.md) decision 3, including its spec-conflict and escalation rules.
11. **Re-archive.** When the conflict is under `openspec/specs/` or `openspec/changes/archive/`, undo the archive before the merge, so that the change is archived again onto `dev`'s specs:
    1. `git revert --no-commit <archive commit>`, which restores the active change directory and the living specs from before the archive, and commit as `docs: restore the active <title> change to merge dev`.
    2. `git merge origin/dev`, which now leaves the living specs to `dev`, because the branch changes them only through the archive; resolve any other conflict, run `make verify`, have the assigned reviewer review the resolved diff, and record it in the restored `verification.md`.
    3. Archive again under step 7, which applies the change's deltas to `dev`'s specs, and hand off under step 8.

Questions that belong to the owner (see Roles) go to the coordinator with options and a recommendation. The worker does not decide them.

## Coordinator steps

1. **Assign.** Assign only tasks without an open owner decision. When a worker is idle and such a task exists, send it a complete brief: the task and its plan row, scope and exclusions, the tasks it depends on, the assigned reviewer, and a pointer to this protocol. Choose and rotate reviewers as the [review process](governance.md#independent-review-process) requires, including a reviewer with network access for tasks that depend on external facts. Skip a reviewer that is [unavailable](governance.md#independent-review-process), paused, or unable to meet the task's review requirements. When the assigned reviewer becomes unavailable, assign the replacement that the worker proposes from the rotation. Bring owner questions to the owner with options and a recommendation.
2. **Integrate.** Integrate one task at a time, through one pull request that carries the archived change. After `git fetch origin`, check out the reported branch in a worktree (`git worktree add ../taskelith-worktrees/<change> origin/<change> -b <change>` when the coordinator has none, then `nvm use` and `npm ci --ignore-scripts`).
   - Check that the branch carries its archived change: `openspec/changes/<change>/` is gone and `openspec/changes/archive/<date>-<change>/` exists. Otherwise return the task to its worker for worker step 7.
   - If the branch is behind `origin/dev`, merge `origin/dev` into it. Conflicts in the generated dependency inventory resolve themselves; when the `post-merge` hook or `make verify` reports the inventory stale, run `make dependency-inventory` and commit the regenerated files, which needs no return to the worker. If that merge conflicts under `openspec/specs/` or `openspec/changes/archive/`, abort it (`git merge --abort`) and return the task to its worker for worker step 11. If it conflicts in another file, or changes the task's requirements, contracts, implementation, or verification inputs, return the task to its worker under worker step 10. Otherwise run `make verify` and push the merge.
   - Open a pull request into `dev` and merge it with a merge commit (`gh pr merge <change> --merge`). There is no separate archive pull request, and the coordinator does not edit the archived `verification.md`: the pull request records the integration.
   - If a commit type would trigger a release that the change does not warrant, recommit it with the right type on a new branch with the same author, instead of rewriting the pushed branch.
3. **Clean up.** Update the main clone with `git pull --ff-only`. Remove the coordinator's worktree and local branch, and delete the remote branch from the main clone ([releases](releases.md#parallel-work-with-worktrees)). Remove a worker's worktree only on the worker's own machine, by the worker (worker step 9).
4. **Release the worker.** Tell the worker that its task is merged, so that it cleans up and clears its context, and assign the next task.

## Subagent execution

The owner set this rule on 2026-10-26; it applies to tasks assigned from that day on.

- **Implementation in a subagent.** A session that develops a task, a worker or the coordinator, delegates the work of the worktree (code, tests, documentation, and OpenSpec artifacts) to a subagent that it briefs with the task, its scope, and the rules that apply. The session reviews and checks the subagent's result itself before review and handoff.
- **Protocol in the session.** The session keeps the protocol steps: messages to the coordinator or the owner, owner questions, the independent review, whose results the subagent may record as the session provides them, and the handoff. A subagent does not hand off, open pull requests, or decide owner questions.

## Context size

The owner set this rule on 2026-10-25. When a session's context approaches 150,000 tokens, the session tells the owner and recommends `/compact` or `/clear`, because only the owner can run them in the session's window. It warns before the limit, not after.

- **Record first.** Before it warns, the session records what a reset would lose. A worker commits its work and notes its state and open questions in the change's `tasks.md` or `verification.md`; the coordinator updates its notes on assignments and pending integrations.
- **Recommend one.** It recommends `/compact` while a task is in progress or decisions are not yet recorded, and `/clear` when everything needed is recorded. A worker in the middle of a task recommends only `/compact`; `/clear` stays at worker step 9.
- **Worker.** A worker also tells the coordinator, which sends it no work until the worker reports that it is ready again.
- **Coordinator.** The coordinator also says whether any handoff is waiting for integration.

## Reviewer invocations

Run each reviewer from the task's worktree, read-only, with the model and effort set in the invocation ([governance](governance.md#independent-review-process)). Keep prompt files, logs, and snapshot files outside the worktree, for example in a scratch directory, so that they do not change the snapshot.

Always pass `-s read-only`, because a local configuration may default to full access. No network access. |
| Antigravity CLI | `agy -p "<prompt>" --model gemini-4-argon-medium --effort medium --mode plan --output-format json --log-file <log>` | Model in the log; `conversation_id` in the JSON output. Has network access. |

It denies the common forms of reading outside the worktree: its read tool outside the worktree, and shell commands with absolute paths, `~`, `..`, `$`, or input redirection. These are pattern rules, not a sandbox, so they cannot be relied on for secrecy. Every deny rule must come after the last allow rule, because the last matching rule wins. Share no external evidence directory with it. |

If a review attempt does not run to a report for any reason, for example an error, no session, or a quota limit, the worker does not use that reviewer for any task for 30 minutes and proposes the next reviewer in the rotation that is not paused and meets the task's review requirements to the coordinator (a coordinator that develops the task itself chooses it and records why), as the governance rule "Unavailable reviewer" sets out. The replacement is briefed with the earlier passes. Failed attempts do not count as passes, and the pass count carries over.

Snapshot before and after each pass, and compare the two. Include any external evidence directory shared with the reviewer as well.

```bash
git ls-files -co --exclude-standard | xargs shasum -a 256 | shasum -a 256
```

The prompt names the criteria (`AGENTS.md`, [ADR 0004](decisions/0004-first-class-engineering-principles.md), the governance review process, and the specifications the change touches). It asks for every instance of a problem with its severity, file and line, and a fix, and for counts per severity at the end. For a later pass, it names the earlier pass's session and asks the reviewer to confirm each finding's resolution before reviewing the whole change again.
