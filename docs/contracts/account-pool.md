# Account pool contract

Date: 2026-10-26. Status: contract for G3 ([G3 work plan](../g3-plan.md) item 5, `define-account-pool-contract`), reviewed and merged; G3 item 0 (`revalidate-g3-foundations`) re-reviewed it, and the follow-up changes of that review align it. On 2026-10-27 the owner amended ADR 0005 decision 2 for Claude Code, which section 7.1 applies. G3 sub-change 12a (`implement-account-pool-slot-store`) implements the slot records, the encrypted credential store, the add-slot command with its slot limit, and the `new-session` selection in the placement transaction (section 11). G3 sub-change 12b (`apply-account-pool-cooldown-and-affinity`) implements the `resumed-session` and `after-limit` selection and the cooldown of a slot from a `limit` signal (section 12). G3 sub-change 12c (`deliver-slot-credential-per-run`) implements the per-run delivery of a slot credential and its delivery record (section 13). It defines the harness-neutral account pool port of [ADR 0005](../decisions/0005-harness-subscription-account-pools.md): subscription account slots per harness with allowed projects, eligibility, least-loaded selection inside the reservation transaction, cooldown, session affinity, the selection after a limit, encrypted slot credentials delivered only to the run that reserved the slot, and revocation and removal. The [harness account pools specification](../../openspec/specs/harness-account-pools/spec.md) states the behavior; this contract fixes the records, values, ports, and invariants that implement it. It extends the [capacity reservation contract](capacity-reservation.md) section 10. G3 item 12 implements it, item 9 maps its commands and views onto the OpenAPI document, item 18 delivers the credential inside the worker, and item 33 shows the pools.

## 1. Purpose and parties

The account pool is a capability of the Scheduling module, because a slot is a provider credential unit of a capacity reservation (capacity reservation contract section 2) and is selected inside the reservation transaction (section 4 of that contract). No type, value, schema, or test of the pool names a harness or vendor ([ADR 0003](../decisions/0003-first-integrations-and-plugin-kernel.md) decision 8, ADR 0005 decision 8): a harness appears only as an opaque harness plugin identifier, and a subscription mechanism only as the opaque identifier of one that the plugin declares in its agent harness port `capabilities`.

| Port | Owner | Implemented by |
| --- | --- | --- |
| `AccountSlots`: slot records, read and written inside the reservation transaction | Scheduling | The item 12 adapter in the installation's PostgreSQL database |
| `SlotCredentials`: encrypted slot credential material | Scheduling | The item 12 adapter, whose encryption key, or whole store, lives in the `control-plane/` namespace ([installation and enrollment contract](installation-and-enrollment.md) section 3), never in the database; the encryption and key management choice belongs to item 12 |

Harness plugins never call these ports, and the control plane never queries a harness plugin: the worker's harness host calls a plugin, inside the execution of a session (agent harness port contract sections 1 and 5). A plugin declares its subscription mechanisms in its `capabilities`, and within a session it reports usage and limit signals, a limit with an optional reset time, and authentication failures of the slot's credential through the agent harness port (item 3); the control plane turns those reports into slot updates (section 5). A plugin receives a slot's credential only through the run that reserved the slot (section 7).

This item adds the port types, the contract values, and a conformance suite for both ports. It adds no adapter, no selection or scheduler code, no encryption, and no wire schema.

## 2. Common rules

1. **Authorization.** The Access module checks the caller's role before a port is called ([trust model](../trust-model.md) section 3); a port never decides authorization itself. Slots are installation resources: setting a harness's usage window length (section 5), adding a slot, changing its allowed projects or concurrency limit, storing or rotating its credential, and revoking, reinstating, or removing it are `installation-owner` commands. A `project-viewer` reads the pool state of its own project, never a credential; a slot shared with other projects is shown without their names (a requirement on items 9 and 33).
2. **Opaque identities.** A slot is identified by a `ProviderCredentialId`, the identifier that a reservation records in `providerCredentials`. The harness is a `HarnessPluginId` and the mechanism a `SubscriptionMechanismId`, both opaque to the pool. `HarnessPluginId` is the Execution module's type (`@taskelith/execution`), whose value is the harness plugin's manifest `id`; the agent harness port identifies a plugin by the same type ([agent harness port contract](agent-harness-port.md) section 4.1). `SubscriptionMechanismId` stays the pool's own opaque type: its values are drawn from the subscription mechanisms that the plugin declares through the agent harness port, and they are validated outside the pool. Wherever this contract orders by `id`, it means the code-unit order of the identifier, the order of PostgreSQL's `"C"` collation for ASCII identifiers, as the capacity reservation contract section 13 orders project and task ids, so that every replica and adapter agrees.
3. **Compare-and-set.** Every slot change replaces the record at an expected revision, inside the transaction that decides it, and fails with `conflict` when the revision has moved. A slot's revision starts at `1` and grows by one with each change. Because the reservation transaction reads slots, every slot change runs at `SERIALIZABLE`, as capacity reservation contract section 4 requires of its writers: adding a slot, a usage or limit signal or a credential authentication failure applied to it (section 5), a change of the allowed projects or the concurrency limit, a revocation, reinstatement, or removal, and a rotation's switch and revision advance (section 8).
4. **Failures.** Every operation that can fail for a domain reason returns a kernel `Result`: `invalid` for malformed input, `not-found`, and `conflict` for a duplicate or a lost compare-and-set. A read without a domain failure, such as `pool`, returns its value, as the capacity ledger does. A store that cannot be reached rejects the operation's promise, which aborts the reservation transaction.
5. **Secrecy.** A slot credential never enters a log, a prompt, a lesson, an error payload, an event, an outbox record, a view, or a wire response (ADR 0005 decision 6), nor the worker journal, an execution directory, or the worker's local outbox (section 7.3). Only `SlotCredentials` holds it at rest, and only the delivery to the reserving run reveals it. A subscription token has no shape that the shape rules of `@taskelith/secrets` match, so a run is redacted by the value of its credential (section 7.4).

## 3. Slots

### 3.1 Record

| Field | Meaning |
| --- | --- |
| `id` | The slot's `ProviderCredentialId` |
| `harnessId` | The harness plugin the slot belongs to; never changes |
| `mechanismId` | One subscription mechanism that the plugin declares in its agent harness port `capabilities` (section 2, rule 2). The control plane's add-slot command checks it, before `add`, against the admitted pairs of harness plugin and mechanism that the control plane keeps (section 7.1), never by querying the plugin; a pair is admitted only for a mechanism the plugin declares as a subscription. It rejects with `invalid` a mechanism without an admitted pair for the slot's harness: one the plugin does not declare as a subscription, such as an API key, and one without an admitted delivery, such as a `device-login` slot of Claude Code; `add` itself treats it as opaque |
| `credentialVersion` | The `SlotCredentialVersion`, a positive integer, under which `SlotCredentials` holds the slot's current credential (section 6.2); only a rotation changes it (section 8.1) |
| `allowedProjects` | The projects the slot may serve, at least one, without duplicates |
| `concurrencyLimit` | The slot's provider credential concurrency (capacity reservation contract section 2), a positive integer, by default `DEFAULT_PROVIDER_CREDENTIAL_CONCURRENCY` (`4`) |
| `state` | `active`, `revoked`, or `removed` (section 8) |
| `health` | `healthy` or `unhealthy` (section 5) |
| `cooldown` | Absent, or the end of the cooldown and its source: `reported-reset` or `default` (section 5) |
| `usage` | Absent, or the last usage report: a fraction from `0` to `1` of the slot's usage-window limit and `windowEndsAt`, the end of the window that the pool derives for the report (section 5) |
| `lastReservedAt` | Absent, or the time of the slot's latest reservation |
| `revision` | Section 2, rule 3 |

`parseAccountSlot` checks these invariants: at least one allowed project and none twice, a positive integer concurrency limit, credential version, and revision, and a usage fraction from `0` to `1`. Every command builds its record through it, and the ports store parsed records without checking them again.

A project's **pool for a harness** is the set of `active` slots of that harness whose `allowedProjects` include the project. Revoked and removed slots belong to no pool.

### 3.2 Eligibility

A slot is eligible for a reservation at the database time `now` when all of these hold. The first failing check, in this order, is the slot's ineligibility reason:

| Check | Reason |
| --- | --- |
| The slot is not removed | `removed` |
| The slot is not revoked | `revoked` |
| The project is in `allowedProjects` | `not-allowed` |
| The slot is `healthy` | `unhealthy` |
| No cooldown, or its end is at or before `now` | `cooling-down` |
| Its held reservations are below `concurrencyLimit` | `at-concurrency-limit` |

Held reservations are counted by the capacity ledger's `heldForCredential`, inside the same transaction, and compared with the slot's own `concurrencyLimit`; `DEFAULT_PROVIDER_CREDENTIAL_CONCURRENCY` is only the default of a new slot's limit. This check is the reservation's credential concurrency check (section 4.7). That count equals ADR 0005's active sessions only if a session has at most one active attempt; this contract relies on G3 item 4 establishing that, as capacity reservation contract section 10 requires.

## 4. Selection

### 4.1 Requests

Selection runs inside the reservation transaction (capacity reservation contract section 4), at the credential step that section 4.7 fixes, and the reservation records the selected slot in `providerCredentials`. A request has one of three kinds:

| Kind | Fields | Used when |
| --- | --- | --- |
| `new-session` | project, `harnessId`, policy for no eligible slot | A session starts, including a new session of a task whose earlier session closed for a reason other than a limit |
| `resumed-session` | project, the session's `harnessId` and `slotId` | A session continues, for example after a restart; the session's harness and slot are fixed (section 4.3) |
| `after-limit` | project, the limited session's `harnessId` and `slotId`, the other harnesses allowed for the task in the project's order of preference | A new session continues the work of a session whose slot reported a limit (section 4.4) |

Which harnesses a task may use, and in which order, comes from the project's defaults and the task (G3 item 11); the pool takes them as given. Every request is built through `parseSlotRequest`, which rejects with `invalid` an `after-limit` request whose alternatives include the limited harness or name a harness twice. A request whose pinned or limited `harnessId` differs from the stored slot's `harnessId` is also `invalid`; `parseSlotRequest` cannot see the store, so the item 12 selection checks it against the stored slot inside the reservation transaction. A `new-session` request also names the project's policy for no eligible slot: `wait` or `reject` (section 4.5).

### 4.2 Least-loaded rule

Among the eligible slots of the requested pool, the slot with the fewest held reservations wins. Remaining ties go to the lowest usage fraction, then to the least recently reserved slot, then to the lowest `id` (section 2, rule 2), so that the rule is deterministic. The usage step applies only when every tied slot has a usage report whose derived window end (section 5) is after `now`; otherwise, when a tied slot has no report, its harness has no usage window length, or its report's window has ended, it is skipped. A slot never reserved counts as least recently reserved. For a `reserved` outcome, of any request kind, the insert of the reservation sets the slot's `lastReservedAt` to `now` in the same transaction (section 4.7).

### 4.3 Session affinity

A session keeps the harness and slot that started it until its work is finished and the session and its agent are closed (ADR 0005 decision 5 as amended). A `resumed-session` request considers only its own slot:

- If the slot is eligible, it is reserved again, even when another slot is less loaded.
- If the slot is `unhealthy`, `cooling-down`, or `at-concurrency-limit`, the request waits with `provider-concurrency-exhausted`. A limit that the session's own slot reported does not lead here: that session writes a handoff and stops (section 4.4).
- If the slot is `revoked` or `removed`, or no longer allows the project (`not-allowed`), the request is rejected with `session-slot-withdrawn`. The session is drained or ended by policy or an operator, never moved to another slot or harness; its work may continue only in a new session.

No request kind moves a running session to another slot or harness, and no explicit reconciliation does either.

### 4.4 After a limit

When a session's slot reports a usage or rate limit, the slot enters cooldown (section 5), and the session writes a handoff and stops (G3 items 4 and 18). The new session that reads the handoff is selected by an `after-limit` request, which never chooses another slot of the limited harness, because that is "rotating accounts":

1. Each other allowed harness is tried in the given order with the least-loaded rule over its pool. The first harness with an eligible slot wins.
2. If no other harness has an eligible slot, the limited slot itself is reserved when it is eligible again, that is, when its cooldown has ended.
3. Otherwise the request waits with `provider-concurrency-exhausted`, and each later placement try of the task repeats steps 1 to 3. Those tries follow the capacity reservation contract's fair order and backoff (sections 5 and 13): a decline with `provider-concurrency-exhausted` backs off up to `60s` with jitter, and the rotation across projects decides when the task is offered again. The work therefore runs on another harness at the first try after one has an eligible slot, or on the limited slot at the first try after its cooldown ends, not at the moment either becomes eligible.

If the limited slot is revoked or removed while the request waits, step 2 no longer applies, and the request waits only for another harness. When no other harness has an eligible slot either, that wait has no end of its own: policy or an operator ends the request, which keeps ADR 0005 decision 4, because the pool still never switches to another slot of the limited harness. An `after-limit` request names no policy and never rejects, because ADR 0005 decision 4 makes the task wait.

### 4.5 No eligible slot

For a `new-session` request with no eligible slot in its pool, the policy decides: `wait` waits with `provider-concurrency-exhausted`, and `reject` rejects with `no-eligible-slot`. A slot outside the pool is never used. The reason values that this contract adds, `session-slot-withdrawn` and `no-eligible-slot`, are listed in the capacity reservation contract section 11. Item 12 derives the module's rejecting reasons from `SLOT_REJECTING_REASONS` instead of copying them; the waiting reason is already the capacity contract's `provider-concurrency-exhausted`, and the type system checks it against the waiting reasons. Sub-change 12a keeps `SLOT_REJECTING_REASONS` apart from `REJECTING_REASONS`; 12d joins them (section 11).

### 4.6 Outcomes

A selection returns one of: `reserved`, with the slot and its harness; `waiting`, with `provider-concurrency-exhausted` and, when known, the earliest cooldown end among the slots it waits for; or `rejected`, with `no-eligible-slot` or `session-slot-withdrawn`. A selection itself changes no slot, whatever its outcome; only the insert of the reservation writes the selected slot (section 4.7).

### 4.7 In the placement transaction

As G2 built the reservation transaction, the caller supplies the credentials: `placeInTransaction` reserves the `providerCredentials` of its `PlacementRequest`, the control plane's placement service passes none, and each credential is checked against the fixed default `DEFAULT_PROVIDER_CREDENTIAL_CONCURRENCY` (capacity reservation contract section 13, "Provider credentials"). Item 12 changes that as follows:

- **Selection replaces the caller's set.** The caller passes the attempt's slot request (section 4.1), or none for an attempt that uses no provider credential, such as G2's scripted process, and never a credential. `placeInTransaction` runs the selection, and the reservation records the selected slot as the only entry of `providerCredentials`, or none without a request. The request's project is the project that the reservation records, the task's; a request for another project is `invalid`.
- **Credential step.** The selection decides the credential step of the transaction's checks (`decidePlacement`): after the installation, attempt, request, worker, and quota checks, and before the charge check. A worker or fleet without room and a full project or run quota therefore give their own reasons before any slot is considered, so a `reject` policy rejects only an attempt that passed the installation, attempt, request, worker, and quota checks; the charge check follows the credential step, so a rejection by the policy precedes a charge reason such as `delegation-budget-exhausted`. A selected slot is checked against its own `concurrencyLimit` (section 3.2), so a slot whose limit is `8` admits eight held reservations.
- **Waiting.** A `waiting` selection is the waiting reason `provider-concurrency-exhausted`. It is not a reason about one worker, so the placement tries no further candidate, because the selection depends on no worker. It is not a decline for lack of fleet capacity (capacity reservation contract section 13, "Fair order"), so the pass goes on to the next task, the task backs off (section 5 there), and the control plane writes the task's `waiting` record with that reason in a transaction of its own (section 13 there, "Recorded outcome").
- **Rejected.** A `rejected` selection is a rejecting reason, `no-eligible-slot` or `session-slot-withdrawn`: the placement transaction ends the attempt and writes the task's `rejected` record with that reason, as for any rejecting reason. Item 12 adds `SLOT_REJECTING_REASONS` to the module's rejecting reasons (section 4.5), so that the placement and the record accept them. Sub-change 12a keeps them apart from `REJECTING_REASONS`, so its placement transaction ends as `rejected` without that record; 12d joins them (section 11).
- **One write.** The selection only reads. The one slot write, `lastReservedAt`, is made with the insert of the reservation, its assignment, and its command, so a candidate declined for a reason about its worker leaves no slot write in a transaction that later commits on another candidate. All candidates of one task are tried in one transaction, which reads one database clock `now`, the transaction's start, and changes no slot before that insert, so every selection in it has the same result; item 12 may select once per transaction and reuse the result.

## 5. Signals, health, and cooldown

The agent harness port (item 3) defines the `usage` and `limit` signals, the `reset-time` of a limit, and the `authentication` and `forbidden` failures that a plugin reports within a session; this contract defines only their effect on a slot. The pool never queries a harness plugin outside a session (section 1). An `account-signal` event and a failure name no slot: each belongs to the session of one attempt, and the control plane applies it to the slot that the attempt's reservation records in `providerCredentials`, the one slot that the selection reserved for the session (section 4.1). It applies each as a compare-and-set change of that slot. A change whose compare-and-set loses with `conflict` rereads the slot and applies the report again to the fresh record, up to three rereads, after which the change returns `conflict`, which the caller may retry (section 12), so that the rules below, such as a later limit never shortening a cooldown, hold against the latest record rather than a stale one.

- **Limit.** A usage or rate limit puts the slot in cooldown until the reported reset time when that time is after `now` (source `reported-reset`), capped at `10080` minutes (7 days) after `now`, which covers weekly provider limits and keeps a bogus far reset from locking a slot indefinitely, or for the bounded default otherwise (source `default`). The default is an installation setting from `1` to `1440` minutes, provisionally `60` minutes. A later limit extends a cooldown and never shortens it. A cooldown ends only at its stored end: no signal ends it earlier.
- **Load.** The usage window is a pool concern: the `usage` signal carries a fraction and no window. The pool configuration sets a usage window length per harness plugin, a positive whole number of minutes. A usage report replaces `usage` with its fraction and `windowEndsAt`, the database time at which the control plane applies it plus that length. When the configuration sets no length for the slot's harness, the window end is unknown, and the report clears `usage`. The tie-breaker skips a slot without `usage` or whose window has ended (section 4.2).
- **Health.** A slot becomes `unhealthy` when a session on it reports that the slot's credential fails authentication: a turn that ends `failed` with the failure `authentication`, or a start or resume that fails with `forbidden` (agent harness port contract section 9). It becomes `healthy` again only when a rotation switches it to a new credential (section 8.1); no credential check runs outside a session.

Cooldown and ill health make a slot ineligible for new reservations and release no held reservation (capacity reservation contract section 10). A plugin that reports no usage, or a harness without a usage window length, falls back to the held-reservation count, and a limit without a reset time to the default cooldown (ADR 0005 "Risks").

## 6. Ports

### 6.1 `AccountSlots`

Read and written inside the reservation transaction; item 12 adds it to `CapacityTransaction`.

| Operation | Contract |
| --- | --- |
| `add(slot)` | Stores a new slot; `conflict` when the identifier exists, and `invalid` when the revision is not `1` |
| `get(id)` | The slot in any state; `not-found` when it was never added |
| `pool(projectId, harnessId)` | The project's pool for the harness (section 3.1), ordered by `id`; empty when there is none |
| `replace(slot, expectedRevision)` | Replaces the slot when its stored revision equals `expectedRevision`. Checked in this order: `not-found` for an unknown slot, `invalid` for a new revision other than `expectedRevision` plus one, a `harnessId` change, or a slot leaving `removed`, then `conflict` when the stored revision differs |
| `countNotRemoved(harnessId)` | The number of the harness's slots in every project that are not `removed`, revoked ones included; the add-slot command's slot limit reads it (section 7.1). Added by sub-change 12a |


### 6.2 `SlotCredentials`

| Operation | Contract |
| --- | --- |
| `store(slotId, secret)` | Stores the credential, encrypted at rest, under a new version that it assigns and returns; it never replaces a stored version. The version is the next value of a counter that the adapter stores per slot, so the versions of a slot strictly increase, concurrent stores included, and a version is never reused, even after a discard or `destroy`; it is never one more than the highest surviving version. After `destroy(slotId)`, a store keeps nothing, even one that runs at the same time as the destroy, and still returns a new version. It has no domain failure: the add-slot command stores before it adds the record that names the returned version and discards the version when `add` fails, and the rotate command stores before the transaction that switches the slot to the version (section 8.1) |
| `reveal(slotId, version)` | The credential of that version for the delivery of section 7; `not-found` when it is not stored. It checks no reservation, attempt, or slot state: the delivery checks them and reads the slot's `credentialVersion` before it calls `reveal` |
| `discard(slotId, version)` | Destroys one version, the one an add-slot command stored before its `add` failed; discarding a missing one succeeds, and it has no domain failure |
| `discardOlderThan(slotId, version)` | Destroys every version of the slot lower than `version`: after a rotation's switch, the replaced version and every lower version that a failed or stopped rotation left (section 8.1). It keeps `version`, every higher version, and other slots' versions, succeeds when nothing is stored, so that a retry is safe, and has no domain failure |
| `destroy(slotId)` | Destroys every version of the slot and every later store for it (section 8); destroying a missing credential succeeds, so that a retry is safe, and it has no domain failure |

`SlotCredentials` is not part of `CapacityTransaction`, because its key and possibly its store live outside the database (section 1).

A `SlotCredentialVersion` is a positive integer that `store` assigns. It is ordered, so that a rotation can discard only the versions older than its own (section 8.1). It comes from the stored per-slot counter, not from the record, which would let two concurrent rotations derive the same version, and not from the highest surviving version, which would reuse a discarded or destroyed one. A `SlotSecret` is the text of one `subscription-token` credential (section 7.1). It reveals its text only through its `reveal()` method. Its string and JSON forms are the kernel's `REDACTED`, `[redacted]`, so that a logged or serialized secret discloses nothing. The adapter encrypts the material at rest with a key kept in the `control-plane/` namespace, never in the database (section 1); this item states the requirement and leaves the algorithm and the key management to item 12.

## 7. Credential delivery

A credential is revealed only to deliver it to the run that reserved its slot. The delivery, not `SlotCredentials`, makes the checks: in a capacity transaction, it checks that the reservation is `held`, names the slot in `providerCredentials`, and belongs to the attempt that the worker launches, that the slot is `active`, and that its `mechanismId` has an admitted delivery for its `harnessId` (section 7.1), and it reads the slot's `credentialVersion`. It calls `reveal` for that version only after that transaction commits, because `SlotCredentials` is outside `CapacityTransaction` (section 6.2), and sends the credential only with a valid launch authorization for that attempt ([launch authorization contract](launch-authorization.md)) over a confidential transport (section 7.2). At the first delivery to an `authorized` execution, that launch authorization is the execution's grant, unexpired and not `revoked`; a re-delivery replaces this condition with the ownership checks of section 7.3. The credential travels only in the control plane's API response to the worker's delivery request after its launch authorization or for a re-delivery (`fetchSlotCredential`, [execution wire contracts](execution-wire-contracts.md) section 8.6), never in a broker message or stream, which would keep it at rest in the broker. The worker receives the credential with the launch of that attempt, inside the worker container on Linux, and the harness plugin injects it into its harness (item 18). A credential is never sent to another run, another worker, or another plugin.

A revoke or removal serialized after the delivery transaction commits but before the credential is sent does not stop that delivery: the attempt already checked receives the credential. Section 8 covers this window: a revocation cancels the in-flight attempts on the slot (section 8.1), and a removal drains or rejects them, that attempt among them.

### 7.1 Admitted deliveries

A slot's credential is delivered only through a delivery admitted for the slot's harness and mechanism. A harness plugin's mechanism gets an admitted delivery when the item that admits the harness defines how that mechanism's credential is delivered and checks that the plugin declares the mechanism in its `capabilities`; the control plane keeps the admitted pairs of harness plugin and mechanism outside the pool, which stays neutral (section 1), and reads them, not the plugin, when it checks a slot. A session start or resume whose credential names a mechanism that the plugin does not declare still fails with `invalid` (agent harness port contract section 4.1). The add-slot command rejects a slot whose mechanism has no admitted delivery for its harness with `invalid` (section 3.1), and the delivery reveals nothing for such a slot.

This contract defines one delivery, `subscription-token` (agent harness port contract section 4.1): one text per slot, which the harness reads and never changes, so the run has nothing to write back. A `device-login` slot holds a per-slot state directory that the harness updates during a run, for example a rotating refresh token; delivering it needs a state directory format and a write-back that only the reserving run makes, by compare-and-set, and neither is defined. G3 admits one harness, Claude Code (item 19), and G3 decision D6 chose a subscription token per slot for it, if item 35 confirms it ([G3 work plan](../g3-plan.md), "Owner decisions"), so Claude Code's only admitted delivery is `subscription-token`, and a `device-login` slot of Claude Code is rejected. Another harness gets the delivery of its own mechanism when it is admitted, for example a later harness whose subscription state is a file per home directory.

ADR 0005 decision 2, as amended by the owner on 2026-10-27, stops the pooling and rotation of Claude subscriptions until a further owner decision and limits subscription use to "the owner's own account", in the words of the decision, with no rotation to another account. Because Taskelith cannot check which account a credential belongs to, this contract applies the decision as a limit of one slot: an admitted pair may carry a limit on the slots of its harness that are not `removed`, kept with the pair outside the pool, and the add-slot command rejects a slot beyond it with `invalid`; Claude Code's `subscription-token` pair allows one slot, which the operator adds for the account that the decision allows, a fact that Taskelith cannot check. This contract does not map that account to a role of the [trust model](../trust-model.md); a further owner decision does. Sub-change 12a adds the read `countNotRemoved(harnessId)` to `AccountSlots` (section 6.1): the add-slot command reads it and adds the slot in one `SERIALIZABLE` capacity transaction (section 2, rule 3), so of two concurrent adds for the last allowed slot at most one commits (section 11). A rotation (section 8.1) replaces that account's token and never moves the slot to another account, which Taskelith cannot check either. The user's own API key, which the amendment puts first, gets its mechanism and delivery from G3 item 45; until then no delivery is admitted for it.

### 7.2 Transport

Since G3 sub-change 26a the API and the broker use TLS from the installation CA ([installation and enrollment contract](installation-and-enrollment.md) section 7), and since 26b a worker pins that CA at enrollment; the installation binds a private network only with 26d. Because item 26 gives every installation its certificate authority, a credential is delivered only over the TLS of G3 item 26, also to a worker co-located with the control plane on its host, and never over plain HTTP (coordinator, 2026-10-29, sub-change 12c). A remote worker receives no slot credential before item 26 completes that TLS.

### 7.3 The credential on the worker

The worker holds a delivered credential only in its host's memory, for the execution it was delivered to, and gives it to the harness plugin to inject. It never writes it to the worker journal, a launch authorization request or grant included, to the execution directory `worker/executions/<executionId>/`, to `worker/logs/`, or to the local outbox ([worker journal contract](worker-journal.md) sections 2, 5, and 6); a launch authorization grant carries no credential. The worker keeps no copy when the execution ends or when the attempt's ownership generation or the worker's recovery epoch changes, uses no delivery that arrives after one of these, and no execution reuses the credential of another. Every execution after its W3 commit, one that recovery starts with a new `executionId` and one that recovery adopts included, requests the credential again through a new delivery with the checks of section 7; an adopted execution requests it before it redacts or injects anything with it. Because a rotation switches a slot's `credentialVersion` only while the slot is revoked and no held reservation names it, and a delivery reveals the version that the slot record names (section 8.1), every delivery to a run reveals the credential that the run started with.

**Re-delivery to an adopted execution.** An adopted execution has no usable launch authorization: its grant expires after `ttl`, and another authorization of the same `executionId` is allowed only while it has not started ([launch authorization contract](launch-authorization.md) sections 4 and 7). Its re-delivery therefore replaces section 7's launch authorization condition with an ownership check, made in the same `SERIALIZABLE` capacity transaction as the reservation and slot checks: the installation is not in restore quarantine; the authenticated worker is enrolled, unrevoked, at its current credential generation, and at the current recovery epoch; it holds the execution's assignment at the current ownership generation, and the attempt is not cancelled or terminal; and the execution is the attempt's owning execution, `authorized` or `started`, with no `revoked` grant. A failing check reveals nothing and refuses the re-delivery with the reason that launch authorization contract section 9 assigns to the same check: `quarantined`, `stale-recovery-epoch`, `worker-not-authorized`, `assignment-not-active`, `stale-ownership-generation`, `attempt-not-launchable`, `execution-conflict` for an execution that is not the owning one, is terminal, or has a `revoked` grant, and `capacity-not-reserved` for a reservation that is released, held for another attempt, or does not name the slot. A slot that is not `active` refuses it with its ineligibility reason, `revoked` or `removed` (section 3.2), and a slot whose mechanism has no admitted delivery for its harness with `invalid`, which the wire form answers as the typed reason `delivery-not-admitted` (execution wire contracts section 8.6). The checks run in that order, so a cancelled attempt gives `attempt-not-launchable` before its revoked grant is checked. A worker whose re-delivery is refused cannot redact the run by value, so it writes none of the run's harness output, terminal stream, or log text to any record of section 7.4 and never sends it off its host, even after the run ends: it discards that text and keeps only the run's facts that hold no run text, such as its exit and its cancellation.

### 7.4 Redaction for the run

The shape rules of `@taskelith/secrets` ([installation and enrollment contract](installation-and-enrollment.md) section 8) match only Taskelith's own secrets, and a subscription token has no known shape. From the delivery to the end of the run, every text of the run, whatever its channel, its harness output, terminal stream, logs, and failures included, is therefore redacted by value before it is written to the worker journal, `worker/executions/<executionId>/`, `worker/logs/`, or the local outbox, and before it leaves the harness host: `redactSecrets(text, revealed)` and `redactFailure(failure, revealed)` find every occurrence of each revealed credential text in the original text, overlapping ones included, and replace each run of occurrences that overlap or touch with one `[redacted]`. A whitespace-free word that holds both an occurrence and a secret that the shape rules match is replaced whole, so that neither secret leaves a visible part; the shape rules then apply to the rest. Both functions redact one whole text, so a stream is redacted over a sliding window: the worker holds back the stream's trailing whitespace-free word, and at least its last `max(len(value)) - 1` characters, until the next chunk or the end of the stream, so that a credential split across chunks is still found, and it truncates text only after redacting it. `redactFailure` redacts a failure's detail keys as well as its values, and joins, with `, ` and in their order, the values of keys that become equal. The worker keeps the revealed value for the run until the run ends, after a revocation or removal of its slot too (section 8). Item 18 applies them on the worker, and the control plane applies them to a failure of the delivery. Whether the agent's own commands can read the injected credential is a qualification result (agent harness port contract section 4.1; item 35), which this redaction does not change.

## 8. Revocation, reinstatement, and removal

| Command | From | To | Effect |
| --- | --- | --- | --- |
| Revoke | `active` | `revoked` | The slot leaves every pool and no credential is revealed for it; the stored credential is kept encrypted |
| Reinstate | `revoked` | `active` | The slot returns to its pools with its health, cooldown, and usage as they were |
| Remove | `active` or `revoked` | `removed` | Every version of the credential is destroyed, one that a concurrent rotation stores included (section 6.2); the record stays as a tombstone for the reservations and audit records that name it |

A held reservation blocks neither revocation nor removal. A revocation cancels the in-flight attempts on the slot as section 8.1 says, and that cancellation is the justifying fact that releases their reservations as the capacity reservation contract section 6, "Cancellation", says; a removal releases none by itself. A removal drains or rejects them by policy or an operator (ADR 0005 decision 6); a removal of a revoked slot finds them already cancelled by the revocation, so an operator who must stop a compromised credential's runs at once revokes the slot before removing it. In-flight attempts, including one whose credential delivery committed before the command and is still being sent (section 7), release their reservations only by a justifying fact (capacity reservation contract section 6); their sessions are never moved to another slot or harness. A drained attempt keeps the credential delivered to it, but its re-delivery is refused with `removed`, because the slot is no longer `active` and the removal did not cancel the attempt (section 7.3). Each command is audited with its actor and time.

### 8.1 Rotation and emergency revocation

A run keeps the credential it started with, because redaction by a new value would miss output that holds the old one (section 7.4). The rotate command therefore never changes a stored credential: it reads the slot's `credentialVersion` and revision, then stores the new credential, which returns a new version (section 6.2), and then, in one capacity transaction, checks that the slot is `revoked`, that `heldForCredential` counts no held reservation of it, and that its `credentialVersion` is still the one it read, and switches the slot to the new version by compare-and-set on the revision it read, setting it `healthy` (section 5). It refuses the rotation with `conflict` when a check fails, and leaves the new version as an orphan that no record names, for a later rotation to discard (below). The switch is the only change of the credential that a delivery sees, so a reinstatement or removal can run at any time: one serialized before the switch makes it fail, and the slot keeps its version; one serialized after it finds the new version. A delivery holds a reservation, so the version it read is never switched or discarded before it reveals it, and a removal's `destroy` removes every version, one that a rotation stores afterwards included. A rotation that fails or stops between its store and its switch leaves a version that no record names, which no delivery reveals; the operator runs the rotation again.

A successful rotation discards the superseded versions. After its switch commits, the rotate command calls `discardOlderThan(slotId, newVersion)`, which discards every version lower than its own: the replaced version and every lower orphan of a failed or stopped rotation. It then advances the slot's revision by one in a capacity transaction that changes nothing else; a `conflict` of that advance means another command already moved the revision. The cleanup never discards a version that a record names or will name, because versions are ordered and a rotation reads the record before it stores: a later switch is made by a rotation that read the record after this switch, so its version is higher and kept, and a rotation that read the record before this switch fails its compare-and-set with `conflict`, because this switch moved the revision. An orphan higher than the version current after a switch, left by a rotation that stored after the switching rotation and then failed, is kept, encrypted at rest, until a later successful rotation that stored after it discards it, because that rotation's own version is higher. A rotate command that crashes after its switch leaves the replaced version until the next rotation of the slot or its removal, and an add-slot command that crashes between its store and its `add` leaves a version under a slot identifier that no record names (section 6.2). Item 12 must therefore add a sweep that calls `discardOlderThan` with the `credentialVersion` that it reads from each slot record, which never discards a current or higher version, and discards every stored version under a slot identifier that no record names (section 9); until then such a crash can leave one encrypted version at rest. An operator rotates an active slot by revoking it, waiting until its reservations are released, rotating, and reinstating it.

A held reservation never blocks a revocation or a removal, so a compromised credential can always be withdrawn. In its `SERIALIZABLE` transaction, the revoke command cancels the assignment of every attempt whose held reservation names the slot. That cancellation is an invalidating writer of the [launch authorization contract](launch-authorization.md) section 5: it revokes the attempt's grants and writes a cancellation command for the attempt to the outbox, and the reservation is released as the capacity reservation contract section 6, "Cancellation", says: by the revoke transaction itself when no execution under the assignment is `authorized` or `started`, for example a reserved attempt not yet launched, and otherwise by the transaction that records that execution's terminal fact. The worker journals the command as a cancellation request and forwards it to the execution's supervisor ([worker journal contract](worker-journal.md) section 5). Until the run ends, the worker keeps redacting it by the value delivered to it (section 7.4); a re-delivery after a worker restart is refused with `attempt-not-launchable`, because the revocation cancelled the attempt, a check that section 7.3 makes before the slot's state.

## 11. Sub-change 12a

G3 item 12 is split into sub-changes (the coordinator's brief of 12a and the coordinator's answers recorded in its design): 12a the slot records, the encrypted credential store, the add-slot command with its slot limit, and the least-loaded selection of a `new-session` request inside the placement transaction; 12b cooldown from plugin signals, affinity on resume, and the selection after a limit; 12c the per-run delivery of the slot credential to the worker; 12d `wire-account-pool-into-control-plane`, listed below. 12a implements:

- **Slot records.** `PostgresAccountSlots` of `@taskelith/postgres` stores a slot as one row of `account_slots`, whose checks repeat the invariants of `parseAccountSlot` (section 3.1), distinct allowed projects included, and is the `accountSlots` member of `CapacityTransaction`. `InMemoryAccountSlots` of `@taskelith/scheduling` is the test double. Both pass the `AccountSlots` conformance suite.
- **Encrypted credentials.** `PostgresSlotCredentials` keeps each version's ciphertext in `slot_credentials` and the per-slot counter, with its destroyed mark, in `slot_credential_counters`, and commits each operation in a `SERIALIZABLE` transaction of its own, outside the reservation transaction (section 6.2). It encrypts with AES-256-GCM (`AesGcmSlotCredentialCipher` of `@taskelith/secrets`, from `node:crypto`): a random 96-bit nonce per version and a 128-bit tag, with the slot identifier and the version as authenticated data, so a row copied to another slot or version does not open. The 256-bit key is the document `control-plane/slot-credential-key` (`openSlotCredentialKey` of `@taskelith/control-plane-store`), created once, owner-only, and never in the database. A ciphertext that does not open, for example after the key file was replaced, makes `reveal` fail with `internal`, which names the slot and no credential text. Both `SlotCredentials` adapters pass the conformance suite. Key rotation is not implemented; it belongs to 12d.
- **Add-slot command.** `addAccountSlot` reads the admitted pair of the slot's harness and mechanism from `AdmittedDeliveries`, which the control plane keeps outside the pool (section 7.1), and rejects a slot without one with `invalid` before it stores anything. It parses the record, stores the credential, and in one capacity transaction checks the pair's slot limit with `countNotRemoved` and adds the record that names the stored version; when the transaction returns an `Err`, it discards that version. A transaction that rejects, or returns `unavailable` with the detail `outcome` `unknown` because its `COMMIT` reply was lost, may have committed, so the command keeps the version, which the sweep of section 8.1 later removes if no record names it. A discard that fails leaves the version to that sweep too, and the command still returns its own failure. Its failures name identifiers and limits, never the credential.
- **Selection.** `placeInTransaction` takes the attempt's `slotRequest` instead of `providerCredentials` (section 4.7) and fails with `invalid`, before any selection, a request whose project is not the project of the task's lineage, which the reservation records. For a `new-session` request it reads the pool, counts each slot's held reservations with `heldForCredential`, and selects by sections 3.2, 4.2, and 4.5; the selection decides the credential step of `decidePlacement`, and a reservation of the selected slot records it in `providerCredentials` and sets its `lastReservedAt` in the same transaction. 12a failed a `resumed-session` or `after-limit` request with `invalid`; sub-change 12b replaces that refusal with its selection (section 12). ## 12. Sub-change 12b

Sub-change 12b, `apply-account-pool-cooldown-and-affinity`, implements, inside `@taskelith/scheduling`:

- **Resumed session.** `selectSlotInTransaction` reads a `resumed-session` request's pinned slot with `get`, in any state, and `selectResumedSessionSlot` applies section 4.3: the slot is reserved when eligible, even when another slot is less loaded; it waits with `provider-concurrency-exhausted` when it is `unhealthy`, `cooling-down`, or `at-concurrency-limit`, with its cooldown end when the cooldown is its first obstacle; and it is rejected with `session-slot-withdrawn` when it is `revoked`, `removed`, or `not-allowed`. No other slot is read.
- **After a limit.** For an `after-limit` request it reads the pool of each alternative harness, in the request's order, and the limited slot with `get`, never a pool of the limited harness, and `selectAfterLimitSlot` applies section 4.4: the least-loaded eligible slot of the first alternative that has one, else the limited slot when eligible, else a wait with `provider-concurrency-exhausted` and the earliest cooldown end among the alternatives' slots and the limited slot whose first obstacle is their cooldown. It never rejects.
- **Stored slot.** A pinned or limited slot whose stored `harnessId` differs from the request's is `invalid` (section 4.1), and one never added is `not-found`; both end the placement before any write. The selection stays inside the placement transaction, and only the insert of a placement writes the slot (section 4.7).
- **Limit signal.** `applySlotLimitInTransaction` applies a plugin's parsed `limit` event (agent harness port contract section 4.1) in the caller's `SERIALIZABLE` capacity transaction to the one slot that the reservation of the given assignment records, by compare-and-set (section 5): until the reported reset when it is after the database time `now`, rounded up to the millisecond, capped at `SLOT_REPORTED_RESET_MAXIMUM_MINUTES` (10080) minutes after `now`, otherwise for the default minutes that the caller passes, parsed by `parseDefaultCooldownMinutes` within section 5's bounds; a cooldown that would end no later than the stored one leaves the slot unwritten. A lost compare-and-set rereads the slot and applies the limit again, up to `SLOT_LIMIT_REREADS` (3) rereads after the first application, and then returns `conflict`, which the caller may retry. A reservation that names no slot or more than one is `precondition-failed`. A limit is applied for a released reservation and for a `revoked` slot, which a reinstatement returns with its cooldown (section 8); one for a `removed` slot is accepted as a no-op, with no error and no write.
- **Races.** PostgreSQL tests race, each through a gate after the first attempt's read, a resumed and a new session for the last unit of a slot, two `after-limit` placements for an alternative's last unit, a limit and a placement that selects the slot, and two limits on one slot.

The coordinator's answers recorded in 12b's design settle what section 5 does not state. The key of a limit is the attempt's `AssignmentId`, because one attempt runs under one reservation, so item 18 carries the attempt's `AssignmentId` with each signal it relays. 12d's composition supplies the default cooldown from the control-plane installation settings, default `60` minutes, range `1` to `1440`. Usage reports and authentication failures (section 5, "Load" and "Health") are not applied by 12b; sub-change 12e, `apply-account-pool-load-and-health-signals`, applies them and adds their section 9 tests.
