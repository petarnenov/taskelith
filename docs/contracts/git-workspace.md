# Git workspace contract

Date: 2026-10-26. Status: proposed contract for G3 ([G3 work plan](../g3-plan.md) item 6, `define-git-workspace-contract`), under independent review. It defines the workspace lifecycle under `worker/workspaces/` with the layout of G3 plan decision D4 (a), a fresh clone per attempt; the task branch name; the code-head identity (repository, commit, and tree) that head-bound verification and review record; dirty-state detection; the use of the per-run SCM credential; an evidence snapshot of the head; and cleanup that never removes a control record. Revised on 2026-10-27 (change `align-git-workspace-with-execution-boundary`) to fit the execution boundary: the identities and modes of section 2, the hand-off and reclaim of the checkout in section 3, and the Git process rules of section 7. Revised again on 2026-10-27 (change `derive-workspace-names-from-task-ids`) to derive workspace and task branch names from any identifier (section 2). Revised on 2026-10-28 (change `align-git-workspace-adapter-contract`, sub-change 16a of item 16) to settle what the adapter needs before its Git code: the crash point names (section 3), the read of handed-off workspaces, the reclaim program's containment name and its proof after a restart (section 3), the single slot of a Linux worker with a separate execution account (section 3), the pinned Git client, the credential transport, and HTTPS remotes (section 7), the meaning of "never forced" and the push options (section 8), the snapshot format (section 10), the fixture hooks (section 12), and which tests move to item 38 (sections 13 and 14). Revised on 2026-10-28 (change `implement-git-remote-operations`, sub-change 16c) by coordinator decisions Q1 and Q2: the header goes only to the bound remote, never through a redirect, and every Git process has a time limit (sections 7 and 13). Revised on 2026-10-28 (change `implement-workspace-handoff-and-reclaim`, sub-change 16d) by coordinator decisions Q1 and Q3 and the accepted deviation B: the reclaim program's window for `go` (section 3), the retry after `unavailable` from `reclaim` (section 9), and how `prepare` gives the execution group (section 2). It closes the code-head deferral of [ADR 0010](../decisions/0010-g1-closure.md) at the contract level, and it fills in the workspace rules that the [worker journal contract](worker-journal.md) section 2 leaves to G3. G3 item 16 implements it with the pinned `git` CLI (decision D3 (a)), item 17 binds verification and review evidence to the code head, and item 18 runs harnesses in the workspaces.

## 1. Purpose and parties

The architecture's Workspace module owns workspace ownership, placement, preparation, and cleanup; Git is one adapter, and the lifecycle rules stay in the module ([architecture section 6](../architecture.md#modules)). This item adds the module as `@taskelith/workspace`, with the port types, contract values, and pure rules below, and a conformance suite.

| Port | Client | Implemented by |
| --- | --- | --- |
| `WorkspaceLifecycle`: prepare, list, remove, sweep, hand off, reclaim, and the handed-off workspaces | The worker runtime (item 18) | The item 16 Git workspace adapter on the worker |
| `WorkspaceHeads`: status, code head, and head snapshot | Verification, review, and the evidence path (items 17 and 21) | The item 16 adapter |
| `TaskBranchPublisher`: the remote task branch head and the push | The implementation flow (items 18 and 21) | The item 16 adapter |
| `WorkspaceProvider`: the three ports together | The worker's composition root | The item 16 adapter |

Each client depends on the narrowest port it uses ([ADR 0004](../decisions/0004-first-class-engineering-principles.md) principle 2). The ports run only in the worker process, the only writer of `worker/workspaces/` and of the checkouts' Git work (worker journal contract section 2, where supervisors write only execution records). This item adds no adapter, no Git call, no worker runtime wiring, and no wire schema.

## 2. Layout

Paths are relative to `dataRoot` ([storage contract](../storage.md)). By D4 (a), every attempt gets its own fresh clone; G6 and G7 measure a mirror per repository with a worktree per attempt (D4 (b)).

| Path | Content |
| --- | --- |
| `worker/workspaces/` | The workspace root (`WORKSPACE_LAYOUT.root`), created by enrollment with the rest of `worker/` (worker journal contract section 2) |
| `worker/workspaces/<name>/` | One attempt's workspace; nothing else lives in it |
| `worker/workspaces/<name>/workspace` | The worker's record of the workspace (`WORKSPACE_LAYOUT.metadata`): its attempt identifier, kind, task branch, repository binding, and the clone's repository format (section 7). `prepare` writes it after the clone and the checkout of the target, inside the staging entry (section 3). Git work takes them from this record, never from the checkout, which the agent can change |
| `worker/workspaces/<name>/handed-off` | The worker's hand-off record (`WORKSPACE_LAYOUT.handOffRecord`), present while the checkout is handed off (section 3); before a reclaim program starts, it names that program's containment, `reclaim-<name>` (`reclaimContainmentName`), or on macOS its process group |
| `worker/workspaces/<name>/checkout/` | The clone: its working tree and its `.git` directory. It is the `workingDirectory` that a harness runs in |
| `worker/workspaces/.staging-<name>/` | A prepare in progress (section 3) |
| `worker/workspaces/.removing-<name>/` | A removal in progress (section 3) |

- **Names.** Attempt and task identifiers are opaque identifiers of 1 to 128 printable ASCII characters other than space (`Identifier` in the OpenAPI documents), and a client chooses its task identifiers, so an identifier may hold `/`, `.`, or `:` or be `..`. The workspace therefore never uses an identifier as a name; it derives one (`WORKSPACE_NAME_RULES`):
    - **Form.** A name is a readable prefix, a `-`, and a digest, or the digest alone when the prefix is empty. The prefix is the identifier with every character other than an ASCII letter, a digit, `-`, or `_` replaced by `_`, without its leading `-` and `_`, cut to at most 40 characters. The digest is the SHA-256 of the identifier's UTF-8 bytes, as lowercase hexadecimal, cut to its first 32 characters (128 bits). So `feature/login` gives `feature_login-` and 32 hexadecimal characters, and `..` gives the digest alone.
    - **Safe.** A name has at most 73 characters, only letters, digits, `-`, and `_`, and starts with a letter or a digit, so that it is a single path segment, never `.` or `..` and never a staging or removing entry, and a valid Git branch name component: it holds no `.`, so no `..` and no `.lock`, and none of the characters that `git check-ref-format` refuses. Every identifier has a name, so no identifier is refused.
    - **Distinct and stable.** The same identifier always gives the same name, so every attempt of a task finds its branch. Two names are equal only when their digests are, because the digest is the fixed last 32 characters; identifiers that share a prefix, such as `a/b` and `a_b`, get different digests. Two distinct identifiers collide only on a 128-bit collision of truncated SHA-256: among a billion identifiers its probability is about 1.5 × 10^-21, and a client that chooses identifiers to collide needs about 2^64 hash computations.
    - **Digest.** The domain does not compute SHA-256 itself: `workspaceDirectoryName` and `taskBranchName` take an `IdentifierDigest`, a synchronous function that the adapter supplies, for example with `createHash('sha256')` of `node:crypto`, and that returns the full SHA-256 of the identifier's UTF-8 bytes as 64 lowercase hexadecimal characters; the domain keeps its first 32.
    - **Use.** `<name>` in the paths above is the attempt's name (`workspaceDirectoryName`), and the workspace record holds the attempt identifier, from which `list` reports it.
- **One repository.** A workspace holds one clone of the project's bound repository (item 11). A project with several repositories is outside G3.
- **Project content.** Everything under `worker/workspaces/` is project content with its own modes and symbolic links; nothing in it is read as a control record (worker journal contract section 2).
- **Identities.** The *worker identity* is the account the worker process runs as. On Linux it is root (uid 0) in the worker container, under the entrypoint's `setpriv` with only `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL`, so without `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, or `CAP_FOWNER` ([local installation](../local-installation.md#worker-container)); the data root is owned by uid and gid 0. On macOS it is the worker's own account. The *execution identity* is the account an execution runs as: on Linux the execution account `taskelith-exec` (uid and gid 10003, [supervisor identity contract](supervisor-identity.md) section 8), whose processes get no supplementary group, because Node.js clears them when it sets a user ID; on macOS the worker's account.
- **Modes where the identities differ (Linux).** The worker identity cannot change an entry's owner, so the execution reaches its checkout through the *execution group*, the execution identity's primary group, and the worker identity holds that group as a supplementary group, which lets it give its own directories that group without `CAP_CHOWN`. `prepare` gives the staging entry and its `checkout/` that group when it creates them, with `chown(path, -1, gid)` of the execution group, before it sets their modes and before the clone writes. `WORKSPACE_MODES` holds the values:

| Path | Owner and group | Mode |
| --- | --- | --- |
| `dataRoot`, `worker/`, `worker/workspaces/` | Worker identity, execution group | `0710`: the group passes through and can neither list nor create an entry (worker journal contract section 2) |
| `worker/workspaces/<name>/` and its staging and removing entries | Worker identity, execution group | `0710` |
| `worker/workspaces/<name>/workspace` and `handed-off` | Worker identity | `0600` |
| `worker/workspaces/<name>/checkout/` | Worker identity, execution group | Set-group-ID from its creation, before the clone writes into it: `2700` while reclaimed; `2770` while handed off (section 3) |
| Entries in the checkout | The worker identity for what the clone writes, the execution identity for what the agent writes; the execution group, inherited through the checkout's set-group-ID, which every new directory also inherits | The group gets the owner's bits: the clone runs with umask `0007`, so what Git writes read-only, such as object files, is read-only for both; a reclaim sets the modes of what the agent wrote (section 3) |

- **What stays closed.** Every control record and control-record directory keeps mode `0600` or `0700` without group bits, so the traversal opens none of them. The execution group can list no directory on the path to a checkout and no control-record directory; the only directories it can list are those of a handed-off checkout. The workspace records are `0600`, and a reclaimed checkout is `2700`, so an execution can reach only a checkout that is handed off.
- **Hard links.** On Linux the kernel setting `fs.protected_hardlinks` must be `1`, so that the execution account cannot hard-link into its checkout a file it can neither read nor write, such as a control record. A worker whose executions run under a separate account checks it on start and refuses to start otherwise.
- **Residual risk: names under `worker/`.** The execution group can test whether a path it names under `worker/` exists and read its metadata (size, times, owner, mode), but can neither list nor read it. This is accepted (owner's delegate, 2026-10-27, open question 2 (a) of the change `align-git-workspace-with-execution-boundary`); therefore no name under `worker/`, of a file or a directory, may encode a secret.
- **Same identity (macOS).** Where the two identities are the same account, every directory above keeps mode `0700`, the hand-off and the reclaim change no mode, and nothing separates the execution from the worker's records; this is the boundary that the trust model accepts for macOS today. The hand-off record holds the hand-off state there as everywhere (section 3). The reclaim program runs there as the worker identity, without a containment, in a process group of its own (section 3, step 7).

## 3. Lifecycle

A workspace is `absent`, `preparing`, `ready`, or `removing`. Only `ready` workspaces are listed and used. A prepare names the attempt, its project and task, the target, the run credential, and the repository binding: the repository identifier, its remote URL, and the base branch, from the project's repository binding (item 11).

1. **Prepare.** `prepare` checks the target, the credential (section 7), and the sources, in the order of section 9, then creates `.staging-<name>/checkout/` reclaimed, with the execution group and mode `2700` (section 2), clones the bound repository into it as the worker identity (section 7), so that every entry the clone writes gets that group, checks out its target, and writes the workspace record into `.staging-<name>/`, then renames `.staging-<name>/` to `<name>/`. The rename is the moment the workspace becomes `ready`, so a crash leaves either no workspace or a complete one. A failure before the rename, a file system fault included, deletes `.staging-<name>/`; a failure to make the rename durable afterwards fails the prepare with `unavailable` and keeps the ready workspace, which `list` reports. An existing `<name>/` fails with `conflict` and leaves it unchanged. An `at-head` target whose tree is not the tree of its commit fails with `invalid` and reason `head-mismatch`, so a workspace never claims a code head it does not hold.
2. **Targets.** A `task-branch` workspace checks out the task branch (section 4): the remote task branch at its head when it exists, so that a later attempt continues the task's work, or a new task branch at the head of the binding's base branch. An `at-head` workspace checks out a given code head, detached, for review at the same head (G3 plan decision D7 (a)); it never pushes.
3. **Ready.** A ready workspace survives a worker restart; `list` returns the attempts with a ready workspace, handed off or not, from their workspace records, in UTF-16 code unit order of their identifiers, the order of JavaScript's default array sort, and an attempt continues in its own workspace after a restart.
4. **Remove.** `remove` refuses a dirty workspace (section 6) with `precondition-failed` and reason `workspace-dirty` and keeps it, because a dirty worktree is never force-deleted as recovery or cleanup ([architecture section 5](../architecture.md#5-domain-vocabulary-and-invariants), invariant 7). A clean workspace is renamed from `<name>/` to `.removing-<name>/`, and that entry is then deleted, so a crash leaves either a ready workspace or a removal to finish. A handed-off workspace is refused (step 6). Removing an absent workspace succeeds. Discarding a dirty workspace on an operator's explicit decision is a later policy, defined separately; this contract offers no way to do it.
5. **Sweep.** `sweep` deletes every staging and removing entry left by a crash. The worker sweeps on start, before it prepares a workspace. This never deletes a dirty worktree: a staging entry is an incomplete clone that no attempt has used, because a workspace is handed out only after its rename into place, and a removing entry was clean when `remove` renamed it, after the attempt's terminal fact, so nothing writes to it afterwards.
6. **Hand off.** Before an execution of the attempt starts, the worker runtime calls `handOff`, which writes the hand-off record durably and then sets the checkout to mode `2770`. The record is the hand-off state on every platform, so that a restart keeps it also where no mode changes (macOS). While it exists, `inspect`, `snapshot`, `push`, and `remove` fail with `precondition-failed` and reason `workspace-handed-off`, after the checks that come before it in section 9, because the agent may still be writing; `readRemoteHead` reads only the workspace record and the remote, and works. A repeated hand-off succeeds. `handedOff` returns the listed attempts whose hand-off record exists, in the order of `list`, read from the records, so it is the same after a restart; the worker counts the slot it holds through it (below), and `list` does not say which workspace is handed off.
    - **One handed-off workspace per Linux worker.** All executions of a Linux worker share the execution account, so while two checkouts are handed off, each execution could reach the other's, and a later execution could signal or trace a reclaim program, which runs as that account too. A Linux worker whose executions run under a separate account therefore holds at most one handed-off workspace at a time: it declares a slot count of `1` ([capacity reservation contract](capacity-reservation.md) section 8, "Declared capacity"), so a second attempt waits for placement. Beside the attempts that section 8 counts, it counts a workspace whose hand-off record exists as holding its slot until the reclaim removes the record, refuses an assignment beyond that slot with `worker-slots-exhausted`, and declares its capacity again after the reclaim, so that it becomes eligible for placement. Its `handOff` refuses while another workspace is handed off, with `precondition-failed` and reason `other-workspace-handed-off`; it checks for that workspace and writes its own hand-off record atomically per worker, so of two concurrent hand-offs exactly one succeeds. A delegating parent keeps its reservation and its handed-off workspace while it waits (capacity reservation contract section 7), so its worker refuses the child, and the child runs only on another worker with a free slot, in its own workspace. This is the owner's delegate's decision of 2026-10-27 (open question 1 (a) of the change `align-git-workspace-with-execution-boundary`); an execution account per slot, a uid pool, lifts the cap later.
    - **One slot.** Such a worker has one slot: it refuses to start when `TASKELITH_WORKER_SLOTS` is set to more than `1`, with an error that names the variable and the execution account, and it declares one slot when the variable is unset. A worker whose executions run as its own account keeps the slot count it is given. This is the owner's delegate's decision of 2026-10-28 (16a decision 9); item 16 implements it in 16e.
7. **Reclaim.** `reclaim` runs only after the process set of every execution of the attempt is proven empty (supervisor identity contract section 8); an unproven termination keeps the workspace handed off, and it is reported for reconciliation (item 21). The worker launches the reclaim program, which enters its containment, `reclaim-<name>` (`reclaimContainmentName`) under the worker's containment parent, switches to its identity, and signals that it is ready while it waits for `go`; only after that signal does the worker write the containment into the hand-off record durably, and before that write the program may change nothing. The worker's scan for unrecorded processes (supervisor identity contract sections 9 and 11) skips a containment that a hand-off record names, because no execution record names it. A worker that finds a containment named there, after a restart or an interrupted reclaim, proves that containment's process set empty before it reclaims again, runs Git on the workspace, or hands it off, because a surviving program could still be writing. It proves it by polling until the process set is empty, never by killing it, within a bound that item 16 fixes and tests; a process set still populated at the bound leaves the workspace handed off, and the worker reports it for reconciliation (item 21). It first runs a fixed program of the worker image, never one from the repository, as the execution identity in that containment. Where the identities are the same (macOS), the program runs as the worker identity, without a containment, in a process group of its own; the record names that process group instead, and it is proven empty when no process belongs to it. The program waits for the worker's `go`, which the worker sends only once that record is durable, and changes nothing before it; a program whose worker dies before `go`, or that gets no `go` within its window of 60 seconds (`RECLAIM_GO_BOUND_MS`), exits without a change and leaves its containment empty, and a `reclaim` whose program so ended fails with `unavailable`, keeps the record, and may be retried. Without following a link, the program replaces each regular file that has another hard link with a copy, checking that an entry is a regular file before it opens it, so that no link outside the checkout reaches its content and no special file, such as a named pipe, blocks it; and it sets exactly `0660`, or `0770` when the owner may execute, on every file it owns and `2770` on every directory it owns, which clears any set-user-ID, sticky, or other bit that the agent set. Then the worker sets the checkout back to `2700` and removes the hand-off record last. With the attempt's processes and the program gone and the checkout closed, no execution of the attempt can change it any more. A repeated reclaim, or one that a worker crash interrupted, runs again from the start, after that proof. A program that exits with a failure or is killed leaves the record and the checkout handed off: `reclaim` fails with `precondition-failed` and reason `reclaim-failed`, and the worker reports the workspace for reconciliation (item 21) and never runs the program again by itself. The record keeps that outcome, so a later `reclaim` of the workspace, also after a restart, fails with `reclaim-failed` without starting the program. A crash after the program failed and before the outcome is durable in the record (`WS8.after`) runs the program once more after a restart, after the proof above; this window is accepted, because the program is idempotent, as for an interrupted reclaim, and a program that fails again then records its outcome.

Item 16 makes each step a named crash point of the G2 test harness (`CrashPoints` of `@taskelith/testing`), `.before` and `.after` the step, and for the reclaim program also the bare name while it runs:

| Point | Step |
| --- | --- |
| `WS1` | The clone into the staging entry (prepare, step 1) |
| `WS2` | The rename of the staging entry into place (prepare, step 1) |
| `WS3` | The rename of a workspace to its removing entry (remove, step 4) |
| `WS4` | The deletion of the removing entry (remove and sweep, steps 4 and 5) |
| `WS5` | The durable write of the hand-off record (hand off, step 6) |
| `WS6` | The hand-off's mode change of the checkout to `2770` (step 6) |
| `WS7` | The durable write of the reclaim program's containment into the hand-off record (step 7) |
| `WS8` | The reclaim program: `WS8.before` before its `go`, `WS8` while it runs, `WS8.after` after it exits (step 7) |
| `WS9` | The reclaim's mode change of the checkout to `2700` (step 7) |
| `WS10` | The removal of the hand-off record (step 7) |

A crash test kills the worker at each point and checks the state that section 3 promises after a restart: no workspace or a complete one around `WS1` and `WS2`, a ready workspace or a removal that `sweep` finishes around `WS3` and `WS4`, a handed-off workspace from `WS5.after` on, and from `WS7.after` to `WS10.before` a workspace that stays handed off until the containment that the record names is proven empty.

## 4. Task branch

- A task's branch is `taskelith/<taskName>` (`taskBranchName`: `TASK_BRANCH_PREFIX` followed by the name that section 2 derives from the task identifier). Every attempt of the task uses it, so that a retry or a conflict resolution (ADR 0008 decision 3) continues the same branch.
- The adapter pushes only the task branch, only to `refs/heads/taskelith/<taskName>`, and never the base branch, a tag, or another ref (section 7).

## 5. Code-head identity

The code head that head-bound verification and review record is `CodeHeadIdentity`:

| Field | Meaning |
| --- | --- |
| `repository` | The repository's opaque identifier, the same string the SCM port uses (`RepositoryId`) |
| `commit` | The full object name of the head commit |
| `tree` | The full object name of that commit's root tree |

- Object names are full lowercase hexadecimal: 40 characters for SHA-1 or 64 for SHA-256, with one format for both. `parseCodeHeadIdentity` rejects anything else with `invalid`; abbreviated names are never recorded.
- Two heads are the same only when all three fields are equal (`isSameCodeHead`). A new commit is a new head even when its tree is unchanged, such as an amended message or an empty commit, so head-bound evidence goes stale ([architecture section 6](../architecture.md#first-class-sdlc-with-replaceable-frameworks), R21). The tree lets a reader check that two heads hold the same content, and lets item 17 show it; it never makes a stale approval current again.
- A head is recorded for verification, review, or a snapshot only from a clean workspace (section 6): `cleanHead` returns it, and a dirty workspace fails with `precondition-failed` and reason `workspace-dirty`.
- The SDLC module owns the code head that gates and evidence compare: `CodeHeadIdentity`, `RepositoryId`, and `isSameCodeHead` of `@taskelith/sdlc`, with opaque `CodeObjectId` names it never parses. This module's `CodeHeadIdentity` extends it with `GitObjectId` names, which `parseCodeHeadIdentity` validates, and re-exports `isSameCodeHead` and `RepositoryId`, so a workspace head is an SDLC head without a conversion.

## 6. Dirty state

`inspect` returns the workspace's current code head, its current branch (null when detached), and its dirty reasons, in this order:

| Reason | Meaning |
| --- | --- |
| `modified` | A tracked file differs from the head in the working tree or in the index, including a deleted tracked file and a staged change that the working tree no longer shows |
| `untracked` | A file that is neither tracked nor ignored by the repository's ignore rules |
| `operation-in-progress` | An unfinished merge, rebase, cherry-pick, revert, or bisect, or an unresolved conflict |
| `off-branch` | A `task-branch` workspace whose current branch is not its task branch |

A workspace is clean when no reason applies. Before it reads the status, the adapter writes every index entry anew from its mode, object, stage, and path (`git update-index --index-info`), so no stat data, assume-unchanged or skip-worktree flag, or cache tree the agent forged in the index makes Git skip a tracked file or a staged change. A workspace is also `modified` when its merged index entries, gitlinks included, are not exactly the files, links, and gitlinks of the head's tree as the adapter reads it from verified objects (section 10), so a gitlink added only to the index, which Git's status ignores, never hides a directory of work. Ignored files do not make a workspace dirty and are never part of a head or a snapshot; review runs in a fresh `at-head` workspace (D7 (a)), so ignored build output of the implementation does not reach it.

## 7. Run credential

The per-run SCM credential is the `RunCredential` of the [source control contract](source-control.md) section 3, issued by `RunCredentialIssuer` for the run. This contract uses it and does not redefine it.

- **Per operation.** The caller passes the credential (`WorkspaceCredential`: its identifier, secret, repositories, effective permissions, and `authorization`, the complete value of the `Authorization` header that the SCM plugin's credential binding forms from the secret, section 14) to each operation that reaches the remote: `prepare`, `readRemoteHead`, and `push`. The workspace never keeps it, so a refreshed credential is simply the one passed next.
- **Scope first.** Before any remote call, including one in the synchronous part of the operation, `checkCredentialScope` requires the bound repository among the credential's repositories and the permission among its effective permissions: `read-code` for `prepare` and `readRemoteHead`, `write-code` for `push`. Otherwise the operation fails with `forbidden` and reason `credential-out-of-scope` before it makes any remote call, so the secret never reaches a service it is not scoped to. The service checks the credential again.
- **Never stored.** The secret is never written into the workspace: not in `.git/config`, a remote URL, a credential store, a reflog, or a file of the working tree. It is never passed on a command line, where other processes can read it, and never logged; item 16 hands it to Git for the one call only and tests that no log line holds it (section 13).
- **Transport.** The header's form belongs to the SCM plugin: its credential binding supplies the complete, already encoded `Authorization` value as the credential's `authorization`, and the GitHub plugin, the first instance, forms `Basic ` followed by the base64 of `x-access-token:<secret>`. The adapter does not parse or build it: it places `Authorization: <authorization>` as the setting `http.extraHeader` (`GIT_CREDENTIAL_SETTING`) into the environment of the one Git process that reaches the remote, as command-scope configuration (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`), after the settings below (`gitConfigEnvironment`). The whole value is as secret as the secret itself: it is scrubbed wherever the secret is, never an argument, such as `-c`, never in a file, such as a credential store or a configuration file, never given to a credential helper, and never logged. The environment of a process running as the worker identity is readable only by that identity (on Linux root), not by the execution account. Where the identities are the same (macOS), an agent can read a Git process's environment, and so the header, while the process runs; this is an accepted residual risk of the one-account composition, as the agent there runs as the account that holds the worker's own credentials anyway.
- **Built environment.** Every Git process gets an environment built from an allowlist, never extended from the worker's: exactly `PATH=/usr/bin:/bin`, `HOME=/nonexistent`, a directory that does not exist, `LC_ALL=C`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, and `GIT_NO_REPLACE_OBJECTS=1`, so that no replace ref the agent made under `refs/replace/` changes a blob, tree, or commit that Git reads (`GIT_BUILT_ENVIRONMENT`), and as command-scope configuration exactly, in this order, `core.hooksPath=/dev/null`, an empty `credential.helper`, which clears the list, `diff.ignoreSubmodules=all`, `status.submoduleSummary=false`, `submodule.recurse=false`, `fetch.recurseSubmodules=false`, `push.recurseSubmodules=no`, `core.untrackedCache=false`, so that no untracked cache the agent forged in the index hides an untracked file, `core.commitGraph=false` and `core.multiPackIndex=false`, so that no commit-graph or multi-pack-index the agent forged gives Git another root tree or object, and `http.followRedirects=false`, so that the header never follows a redirect to another origin (`GIT_COMMAND_SCOPE_SETTINGS`), then the header toward the remote only. It inherits no other variable: no other `GIT_*` variable, such as `GIT_CONFIG_PARAMETERS`, another `GIT_CONFIG_KEY_<n>`, or a `GIT_TRACE*` variable, so that no trace of the header reaches a log, no `SUDO_UID`, no `XDG_*` variable, which with a real `HOME` would bring `git/config`, `git/ignore`, and `git/attributes`, and so could hide untracked work that `remove` would then delete as clean, no `*ASKPASS` program, which Git runs on a refused credential despite `GIT_TERMINAL_PROMPT=0`, no proxy or certificate variable, such as `https_proxy`, `ALL_PROXY`, `SSL_CERT_FILE`, or `CURL_CA_BUNDLE`, and no variable that the worker's runtime adds to a child on its own, such as Node's `NODE_V8_COVERAGE`, which the adapter names as unset so that Node does not add it.
- **Outside every repository.** Git reads the configuration of the repository it finds from its working directory, also for `ls-remote` with a URL. So a Git process that needs no checkout, the `ls-remote` and the clone of `prepare` and the `ls-remote` of `readRemoteHead` and `push`, starts in `/` (`GIT_NEUTRAL_DIRECTORY`), which no agent can write and above which there is nothing; a remote head read while the workspace is handed off thus never reads a `url.<base>.insteadOf`, `http.proxy`, or `http.sslVerify` the agent planted, which would send the header elsewhere. Only a process that works on a reclaimed checkout starts in it, after the rewrite below.
- **Bound remote only.** The worker sends the header only to the remote URL that the control plane supplied with the run, the binding's remote: never to a URL from the workspace's configuration, which the rewrite below removes and which no process that starts in `/` reads, and never to a redirect's target, because `http.followRedirects=false` stops Git at the first redirect, of the advertisement as of a later request. A remote that redirects, such as a renamed repository, therefore fails as `unavailable`, so the control plane sends the canonical remote URL (item 20).
- **Time limit.** Every Git process runs in a process group of its own and is killed, with its whole group, by `SIGKILL` after a wall-clock limit of 10 minutes by default, which the adapter's composition can set (`gitTimeLimitMs`); a process that reaches the remote then fails its operation as `unavailable`, a local one as `internal`, with no new reason.
- **HTTPS remotes.** A binding's remote URL is HTTPS without user information, so that no secret can be part of a URL and the header travels encrypted. `prepare` refuses any other remote, before its credential check, with `invalid` and reason `insecure-remote` (`checkRemoteTransport`, policy `https-only`). Plain `http://` to `127.0.0.1` is allowed only where a test composes the adapter with the policy `https-or-loopback-http`, for its local Git server; the worker's composition never does.
- **Pinned Git client.** The adapter runs Git only through the explicit path that the worker's tool manifest records, never the first `git` in `PATH`, and accepts it only when `git --version` prints exactly the recorded version string (`checkGitClient` with a `GitClientPin`); otherwise the worker refuses to start with `precondition-failed` and reason `git-client-mismatch`. The pin is injected into the adapter, so a test can give it another, such as a wrapper that records each process; the suite's fixture names the pin it composed, and the suite compares each Git process's first argument with that pin's path. The pins (`GIT_CLIENT_PINS`, G3 plan decision D3, [G3 dependencies](../g3-dependencies.md) section 4): on Linux `/usr/bin/git` of the package `git=1:2.43.0-1ubuntu7.4`, which prints `git version 2.43.0`, so the image build checks the package version (16d); on macOS Apple's `/usr/bin/git`, `git version 2.50.1 (Apple Git-155)`. The worker image installs the Linux pin and checks its package at build time since 16d.
- **No repository-controlled settings.** An agent can edit the workspace's `.git`. Once per operation, before its first Git call on a reclaimed checkout, after the checks of the Git directory below, the adapter therefore writes `.git/config` anew, without following a link, holding only the repository format version and object format that the workspace record keeps from the clone, and deletes `.git/info`, whose `exclude`, `attributes`, and `grafts` Git reads beside the tracked files, so that no ignore rule there hides untracked work that `remove` would delete as clean. So no repository-local setting the agent wrote acts on the worker's Git, whatever its key: a credential helper, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.askPass`, a filter driver, `include.path`, `http.proxy`, `remote.<name>.pushurl`, or `url.<base>.insteadOf` among them. The adapter also runs Git with hooks disabled and pushes to the binding's remote URL, never to a remote the workspace configures. The agent's own repository-local settings do not survive a reclaim.
- **The agent.** Whether a harness process receives an SCM credential is the harness host's rule (item 18, [trust model](../trust-model.md) section 5); this contract gives it none.
- **Git processes.** Every Git process of the adapter, for prepare, `inspect`, `snapshot`, `readRemoteHead`, `push`, and every other operation, and the deletion of `remove` and `sweep`, runs as the worker identity in the worker's home cgroup (on Linux `init/` of the worker container), started by the worker process itself: never through an execution supervisor, never as the execution identity, and never in an execution's containment or another cgroup under the containment parent. Only the reclaim program of section 3 runs as the execution identity, in its own containment, and it runs no Git; where the identities are the same (macOS), it runs as the worker identity, without a containment, in a process group of its own, and runs no Git either.
- **Git directory.** The worker identity can write every control record, so a link the agent leaves in `.git` would let the worker's Git read or write one. Once per operation, before its first Git call on a reclaimed checkout, the adapter checks, without following a link, that the checkout and `.git` are owned by the worker identity, that `.git` exists and is a directory that holds only directories and regular files, so no symbolic link and no FIFO, socket, or device that a Git process would block on, and no `commondir` or `objects/info/alternates`, not a `gitdir:` file, and that no entry below the checkout's top, and none at the top but `.git` itself, is named `.git` in any case, as the gitfile of a submodule is, which no tracked path can be, and which macOS finds as `.git` in another case; a file system error other than absence fails the operation with `unavailable`, never as an absent or unsafe entry; otherwise the operation fails with `precondition-failed` and reason `unsafe-checkout`, the workspace is kept, and it is reported for reconciliation (item 21).
- **Submodules.** The adapter's Git never enters a nested repository: it passes `--ignore-submodules=all` to every status and diff, and sets `diff.ignoreSubmodules=all`, `status.submoduleSummary=false`, `submodule.recurse=false`, `fetch.recurseSubmodules=false`, and `push.recurseSubmodules=no` as command-scope configuration. A tree that holds a gitlink is never snapshotted (section 10).
- **`safe.directory`.** The adapter never sets `safe.directory`, and runs Git in an environment it builds: without system and global configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`), without inherited `GIT_CONFIG_*` values, and without `SUDO_UID`, which Git running as root would trust as the owner. So no inherited `safe.directory`, `*` included, admits a checkout whose top directory or `.git` the agent replaced with its own, and its own owner check above refuses that as `unsafe-checkout` in any case. The harness's Git runs as the execution identity in a checkout the worker identity owns, so it needs `safe.directory` for exactly that checkout: the harness host (item 18) passes it as command-scope configuration in the harness's environment (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`), first with an empty value, which resets the list, then the checkout's path, never the value `*` and never in a file the agent can change.

## 8. Push

`readRemoteHead` returns the remote task branch head now, or null while the branch does not exist, so a caller tells an absent branch from one at the base commit. It fails with `invalid` and reason `read-only-workspace` for an `at-head` workspace. A caller reads it before a first push, in a continuing attempt, and after a `remote-moved` refusal; it is the port's only view of the remote, and the caller never needs native access.

`push` publishes a clean `task-branch` workspace's head to its task branch:

- It fails with `invalid` and reason `read-only-workspace` for an `at-head` workspace, with `forbidden` for a credential without `write-code` on the repository, and with `precondition-failed` and reason `workspace-dirty` for a dirty workspace.
- It names the remote task branch head the caller last saw through `readRemoteHead` or a successful push, or none. A remote head that differs fails with `conflict` and reason `remote-moved`; a head that does not descend from the remote head fails with `conflict` and reason `not-fast-forward`. A push is never forced, and a refused push leaves the remote unchanged.
- **Never forced** means that the remote task branch never moves to a commit that does not descend from the leased head, the expected remote head the caller named; on a first push, with none expected, the branch is only created. A lease alone does not ensure it, because Git lets a push with a matching lease replace the branch with any commit. So the adapter checks before the push that the workspace's head descends from the expected head, failing with `not-fast-forward` otherwise, and the lease makes the push fail with `remote-moved` if the branch moved after that check.
- **Ancestry check and lease.** Both are required. Before the push, the adapter checks that the workspace's head descends from the expected head, and refuses with `not-fast-forward` otherwise; on a first push there is nothing to descend from. Then it pushes with exactly `git push --atomic --force-with-lease=refs/heads/<branch>:<expected-sha> <remote> HEAD:refs/heads/<branch>` (`taskBranchPushArguments`, after at most `-C <checkout>`), where `<expected-sha>` is the expected head's full object name, empty on the first push, which requires the branch to be absent, and `<remote>` the binding's remote URL. No other argument follows: never `--force`, `-f`, a bare `--force-with-lease`, a lease on another ref, `--force-if-includes`, an option that cancels one before it, such as `--no-atomic` or `--no-force-with-lease`, or a refspec that starts with `+`.
- On success it returns the pushed `CodeHeadIdentity`, which is the workspace's current head.

## 9. Failures

Every operation returns a kernel `Result`, except `list`, `handedOff`, and `sweep`, which return values and reject their promise when the disk cannot be read, so `handedOff` never reports a workspace as not handed off because its record could not be read, as the account pool's reads do. Failures carry a `reason` detail where this table names one (`WORKSPACE_FAILURE_REASONS`). `prepare` checks in this order: the target's repository (`invalid`), the remote URL (`invalid`, `insecure-remote`), the credential (`forbidden`), the sources (`not-found`), the target's tree (`invalid`, `head-mismatch`), then an existing workspace (`conflict`). The other operations check in this order: the workspace (`not-found`), the kind (`invalid`, `read-only-workspace`), the credential (`forbidden`), the hand-off (`workspace-handed-off`), the Git directory (`unsafe-checkout`), the clean state (`workspace-dirty`), then, for `snapshot`, the tree (`gitlink-in-tree`, `non-utf8-path`, `unsafe-tree-path`), and for `push` and `readRemoteHead` the remote (`conflict`, `unavailable`); so a handed-off `at-head` workspace still answers `push` with `read-only-workspace`, and a foreign credential with `forbidden`. `handOff` and `reclaim` check the workspace first; `handOff` then refuses while another workspace is handed off (`other-workspace-handed-off`, section 3), and `reclaim` fails after a failed reclaim program (`reclaim-failed`). A refusal creates no new workspace and leaves an existing one unchanged. A `reclaim` or `handOff` that finds the recorded containment still populated at the bound of its proof (section 3) answers `unavailable` without a reason and leaves the workspace handed off, and the caller may retry.

| Code | Reason | When |
| --- | --- | --- |
| `invalid` | — | An `at-head` target of another repository |
| `invalid` | `head-mismatch` | An `at-head` target whose tree is not its commit's tree |
| `invalid` | `read-only-workspace` | `push` or `readRemoteHead` for an `at-head` workspace |
| `invalid` | `insecure-remote` | `prepare` with a remote URL that is not HTTPS or holds user information (section 7) |
| `forbidden` | `credential-out-of-scope` | A credential without the repository or the permission |
| `not-found` | — | A missing base branch or head commit, or an absent workspace for `inspect`, `snapshot`, `readRemoteHead`, `push`, `handOff`, or `reclaim` |
| `conflict` | — | `prepare` for an attempt that has a ready workspace |
| `conflict` | `remote-moved`, `not-fast-forward` | Section 8 |
| `precondition-failed` | `workspace-dirty` | `snapshot`, `push`, or `remove` of a dirty workspace |
| `precondition-failed` | `workspace-handed-off` | `inspect`, `snapshot`, `push`, or `remove` of a handed-off workspace (section 3) |
| `precondition-failed` | `other-workspace-handed-off` | `handOff` while another workspace is handed off, on a worker whose executions share a separate account (section 3) |
| `precondition-failed` | `reclaim-failed` | `reclaim` whose program exited with a failure or was killed (section 3) |
| `precondition-failed` | `gitlink-in-tree` | `snapshot` of a head whose tree holds a gitlink (section 10) |
| `precondition-failed` | `non-utf8-path` | `snapshot` of a head whose tree holds a path or link target that is not valid UTF-8 (section 10) |
| `precondition-failed` | `unsafe-tree-path` | `snapshot` of a head whose tree holds a path that Git refuses, a duplicate, or a file that is also a directory (section 10) |
| `precondition-failed` | `git-client-mismatch` | The worker's start, when the Git client is not the pinned one (section 7) |
| `precondition-failed` | `unsafe-checkout` | `inspect`, `snapshot`, `push`, or `remove` of a checkout whose owner or `.git` fails the checks of section 7, a missing `.git` included |
| `unavailable` | — | The remote cannot be reached, or a file system call of `prepare`, `inspect`, `snapshot`, or `remove` fails |
| `internal` | — | A malformed workspace record, Git output the adapter cannot read, a Git object whose bytes do not hash to its name, or a failed Git process that is not a refusal above |

## 10. Evidence snapshot

Architecture section 6 requires content-addressed snapshots, because mutable workspace paths alone cannot reproduce an admission after a branch moves, and R31 requires accepted evidence to survive the deletion of a workspace.

- `snapshot` returns the clean head's `CodeHeadIdentity`, a content type, and bytes that contain exactly the entries of the head's tree: each file with its path, Git mode (`100644` or `100755`), and exact bytes, whether or not they are valid text, and each symbolic link with its path and target, and nothing else: no `.git`, no commit metadata, no ignored or untracked file, and no credential.
- The bytes depend only on the tree: the same tree gives the same bytes in every workspace, on every run, and for every commit that has that tree, so their SHA-256 digest is stable.
- **Format.** The bytes are Taskelith's own tar archive, content type `application/x-tar` (`HEAD_SNAPSHOT_CONTENT_TYPE`), built by `encodeHeadSnapshot` from a map of the head's tree, so that any path, `__proto__` included, is an entry, as the adapter reads it from verified objects (below) and its blobs, never by `git archive`, so `export-subst` and `export-ignore` attributes do not apply and the bytes are the same for every Git version. Its rules:
    - one entry per file and per symbolic link of the tree, and no directory entry, in byte order of the paths' UTF-8 bytes;
    - ustar headers: a file has type `0` and mode `0644`, or `0755` for Git mode `100755`, and its exact bytes; a link has type `2`, mode `0777`, and its target; owner and group `0`, time `0`, and empty user and group names;
    - a pax extended header of type `x`, named `PaxHeader`, before an entry whose path or target exceeds 100 bytes or whose size exceeds the ustar field, with the records `path`, `linkpath`, and `size` that it needs;
    - two zero blocks at the end, and no further padding.
- **Text.** A path and a link target are UTF-8 text. Git stores them as bytes, so the adapter decodes each with `decodeGitPath`, and `encodeHeadSnapshot` checks the strings it gets; a path or target that is not valid UTF-8, or a string with a lone surrogate, makes `snapshot` fail with `precondition-failed` and reason `non-utf8-path`, so no byte is changed on the way into the archive.
- **Verified objects.** Git does not check an object's bytes against its name when it reads them, and an agent can add a pack, a loose object, or an index of objects that gives an existing name other bytes. The adapter therefore reads the head's commit, every tree below it, and every blob of the snapshot itself (`git cat-file --batch`) and checks that each hashes to its name with the clone's object format, as `<type> <size>\0` and its bytes; an object that does not fails the operation with `internal`. The tree that `inspect` and `snapshot` report and compare with the index (section 6) is the one read so.
- **Paths.** Each name of a path must be one that Git accepts in a path (`verify_path` with its HFS+ and NTFS rules): not empty, `.`, `..`, or `.git` in any case or spelling, such as `.GIT`, `.git.`, or `git~1`; no path may occur twice or be both a file and a directory. Otherwise `snapshot` fails with `precondition-failed` and reason `unsafe-tree-path`, after the gitlink and UTF-8 checks, so the archive never holds a `..` or `.git` entry.
- **Gitlinks.** A tree that holds a gitlink (Git mode `160000`, a submodule's entry) has no content to archive, so `snapshot` refuses it with `precondition-failed` and reason `gitlink-in-tree`.
- The evidence path stores the bytes in the `EvidenceStore` under their `ContentDigest` and publishes them through `EvidencePublisher` with kind `code-head-snapshot` (`HEAD_SNAPSHOT_EVIDENCE_KIND`). Accepted evidence is kept for its retention period, whatever happens to the workspace or the branch.

## 11. Cleanup and control records

- `remove` and `sweep` touch only entries directly under `worker/workspaces/` that belong to the workspace layout. They never remove, rename, or follow a path to the journal, the identity, a credential file, the root lock, the journal fault record, an execution record, or the logs (worker journal contract section 2), and never the workspace root itself.
- Deletion never follows a symbolic link, whether it is inside a workspace or a leftover entry that is itself a link: the link is removed as a link, and its target stays.
- `remove` deletes as the worker identity, after a reclaim gave its group every entry that the agent wrote, so that no entry of the checkout is closed to it.
- The worker runtime removes a workspace only when it is clean and after the attempt's terminal fact is confirmed (worker journal contract section 6) and every head the attempt must keep is pushed or its snapshot is accepted as evidence. A workspace is never removed for disk pressure, which truncates only `worker/logs/` (worker journal contract section 7).
- A ready workspace whose attempt the journal does not know is reported for reconciliation (item 21), and is removed only once the control plane confirms that attempt is terminal, or by an operator.
