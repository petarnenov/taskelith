# Git workspace contract

Date: 2026-10-26. Status: proposed contract for G3 ([G3 work plan](../g3-plan.md) item 6, `define-git-workspace-contract`), under independent review. It defines the workspace lifecycle under `worker/workspaces/` with the layout of G3 plan decision D4 (a), a fresh clone per attempt; the task branch name; the code-head identity (repository, commit, and tree) that head-bound verification and review record; dirty-state detection; the use of the per-run SCM credential; an evidence snapshot of the head; and cleanup that never removes a control record. Revised on 2026-10-27 (change `align-git-workspace-with-execution-boundary`) to fit the execution boundary: the identities and modes of section 2, the hand-off and reclaim of the checkout in section 3, and the Git process rules of section 7. It closes the code-head deferral of [ADR 0010](../decisions/0010-g1-closure.md) at the contract level, and it fills in the workspace rules that the [worker journal contract](worker-journal.md) section 2 leaves to G3. G3 item 16 implements it with the pinned `git` CLI (decision D3 (a)), item 17 binds verification and review evidence to the code head, and item 18 runs harnesses in the workspaces.

## 1. Purpose and parties

The architecture's Workspace module owns workspace ownership, placement, preparation, and cleanup; Git is one adapter, and the lifecycle rules stay in the module ([architecture section 6](../architecture.md#modules)). This item adds the module as `@taskelith/workspace`, with the port types, contract values, and pure rules below, and a conformance suite.

| Port | Client | Implemented by |
| --- | --- | --- |
| `WorkspaceLifecycle`: prepare, list, remove, and sweep | The worker runtime (item 18) | The item 16 Git workspace adapter on the worker |
| `WorkspaceHeads`: status, code head, and head snapshot | Verification, review, and the evidence path (items 17 and 21) | The item 16 adapter |
| `TaskBranchPublisher`: the remote task branch head and the push | The implementation flow (items 18 and 21) | The item 16 adapter |
| `WorkspaceProvider`: the three ports together | The worker's composition root | The item 16 adapter |

Each client depends on the narrowest port it uses ([ADR 0004](../decisions/0004-first-class-engineering-principles.md) principle 2). The ports run only in the worker process, the only writer of `worker/workspaces/` and of the checkouts' Git work (worker journal contract section 2, where supervisors write only execution records). This item adds no adapter, no Git call, no worker runtime wiring, and no wire schema.

## 2. Layout

Paths are relative to `dataRoot` ([storage contract](../storage.md)). By D4 (a), every attempt gets its own fresh clone; G6 and G7 measure a mirror per repository with a worktree per attempt (D4 (b)).

| Path | Content |
| --- | --- |
| `worker/workspaces/` | The workspace root (`WORKSPACE_LAYOUT.root`), created by enrollment with the rest of `worker/` (worker journal contract section 2) |
| `worker/workspaces/<attemptId>/` | One attempt's workspace; nothing else lives in it |
| `worker/workspaces/<attemptId>/workspace` | The worker's record of the workspace (`WORKSPACE_LAYOUT.metadata`): its kind, task branch, repository binding, and the clone's repository format (section 7). Git work takes them from this record, never from the checkout, which the agent can change |
| `worker/workspaces/<attemptId>/handed-off` | The worker's hand-off record (`WORKSPACE_LAYOUT.handOffRecord`), present while the checkout is handed off (section 3); it names the containment of a started reclaim program |
| `worker/workspaces/<attemptId>/checkout/` | The clone: its working tree and its `.git` directory. It is the `workingDirectory` that a harness runs in |
| `worker/workspaces/.staging-<attemptId>/` | A prepare in progress (section 3) |
| `worker/workspaces/.removing-<attemptId>/` | A removal in progress (section 3) |

- **Names.** `<attemptId>` is the attempt identifier itself. A workspace name is a single safe path segment and Git ref component: letters, digits, `-`, and `_`, starting with a letter or digit, so that it is never `.` or `..`, never contains `/`, and never collides with a staging or removing entry. An attempt or task identifier outside that form fails with `invalid` and reason `unsafe-name`; the identifiers that the control plane mints for G3 use that form (an obligation on item 9).
- **One repository.** A workspace holds one clone of the project's bound repository (item 11). A project with several repositories is outside G3.
- **Project content.** Everything under `worker/workspaces/` is project content with its own modes and symbolic links; nothing in it is read as a control record (worker journal contract section 2).
- **Identities.** The *worker identity* is the account the worker process runs as. On Linux it is root (uid 0) in the worker container, under the entrypoint's `setpriv` with only `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL`, so without `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, or `CAP_FOWNER` ([local installation](../local-installation.md#worker-container)); the data root is owned by uid and gid 0. On macOS it is the worker's own account. The *execution identity* is the account an execution runs as: on Linux the execution account `taskelith-exec` (uid and gid 10003, [supervisor identity contract](supervisor-identity.md) section 8), whose processes get no supplementary group, because Node.js clears them when it sets a user ID; on macOS the worker's account.
- **Modes where the identities differ (Linux).** The worker identity cannot change an entry's owner, so the execution reaches its checkout through the *execution group*, the execution identity's primary group, and the worker identity holds that group as a supplementary group, which lets it give its own directories that group without `CAP_CHOWN`. `WORKSPACE_MODES` holds the values:

| Path | Owner and group | Mode |
| --- | --- | --- |
| `dataRoot`, `worker/`, `worker/workspaces/` | Worker identity, execution group | `0710`: the group passes through and can neither list nor create an entry (worker journal contract section 2) |
| `worker/workspaces/<attemptId>/` and its staging and removing entries | Worker identity, execution group | `0710` |
| `worker/workspaces/<attemptId>/workspace` and `handed-off` | Worker identity | `0600` |
| `worker/workspaces/<attemptId>/checkout/` | Worker identity, execution group | Set-group-ID from its creation, before the clone writes into it: `2700` while reclaimed; `2770` while handed off (section 3) |
| Entries in the checkout | The worker identity for what the clone writes, the execution identity for what the agent writes; the execution group, inherited through the checkout's set-group-ID, which every new directory also inherits | The group gets the owner's bits: the clone runs with umask `0007`, so what Git writes read-only, such as object files, is read-only for both; a reclaim sets the modes of what the agent wrote (section 3) |

- **What stays closed.** Every control record and control-record directory keeps mode `0600` or `0700` without group bits, so the traversal opens none of them. The execution group can list no directory on the path to a checkout and no control-record directory; the only directories it can list are those of a handed-off checkout. The workspace records are `0600`, and a reclaimed checkout is `2700`, so an execution can reach only a checkout that is handed off.
- **Hard links.** On Linux the kernel setting `fs.protected_hardlinks` must be `1`, so that the execution account cannot hard-link into its checkout a file it can neither read nor write, such as a control record. A worker whose executions run under a separate account checks it on start and refuses to start otherwise.
- **Residual risk: names under `worker/`.** The execution group can test whether a path it names under `worker/` exists and read its metadata (size, times, owner, mode), but can neither list nor read it. This is accepted (owner's delegate, 2026-10-27, open question 2 (a) of the change `align-git-workspace-with-execution-boundary`); therefore no name under `worker/`, of a file or a directory, may encode a secret.
- **Same identity (macOS).** Where the two identities are the same account, every directory above keeps mode `0700`, the hand-off and the reclaim change no mode, and nothing separates the execution from the worker's records; this is the boundary that the trust model accepts for macOS today. The hand-off record holds the hand-off state there as everywhere (section 3).

## 3. Lifecycle

A workspace is `absent`, `preparing`, `ready`, or `removing`. Only `ready` workspaces are listed and used. A prepare names the attempt, its project and task, the target, the run credential, and the repository binding: the repository identifier, its remote URL, and the base branch, from the project's repository binding (item 11).

1. **Prepare.** `prepare` checks the attempt and task names for every target, the target, the credential (section 7), and the sources, in the order of section 9, then writes the workspace record into `.staging-<attemptId>/`, creates `.staging-<attemptId>/checkout/` reclaimed, with the execution group and mode `2700` (section 2), clones the bound repository into it as the worker identity (section 7), so that every entry the clone writes gets that group, and checks out its target, then renames `.staging-<attemptId>/` to `<attemptId>/`. The rename is the moment the workspace becomes `ready`, so a crash leaves either no workspace or a complete one. An existing `<attemptId>/` fails with `conflict` and leaves it unchanged. An `at-head` target whose tree is not the tree of its commit fails with `invalid` and reason `head-mismatch`, so a workspace never claims a code head it does not hold.
2. **Targets.** A `task-branch` workspace checks out the task branch (section 4): the remote task branch at its head when it exists, so that a later attempt continues the task's work, or a new task branch at the head of the binding's base branch. An `at-head` workspace checks out a given code head, detached, for review at the same head (G3 plan decision D7 (a)); it never pushes.
3. **Ready.** A ready workspace survives a worker restart; `list` returns the attempts with a ready workspace, handed off or not, in the code point order of their identifiers, and an attempt continues in its own workspace after a restart.
4. **Remove.** `remove` refuses a dirty workspace (section 6) with `precondition-failed` and reason `workspace-dirty` and keeps it, because a dirty worktree is never force-deleted as recovery or cleanup ([architecture section 5](../architecture.md#5-domain-vocabulary-and-invariants), invariant 7). A clean workspace is renamed from `<attemptId>/` to `.removing-<attemptId>/`, and that entry is then deleted, so a crash leaves either a ready workspace or a removal to finish. A handed-off workspace is refused (step 6). Removing an absent workspace succeeds. Discarding a dirty workspace on an operator's explicit decision is a later policy, defined separately; this contract offers no way to do it.
5. **Sweep.** `sweep` deletes every staging and removing entry left by a crash. The worker sweeps on start, before it prepares a workspace. This never deletes a dirty worktree: a staging entry is an incomplete clone that no attempt has used, because a workspace is handed out only after its rename into place, and a removing entry was clean when `remove` renamed it, after the attempt's terminal fact, so nothing writes to it afterwards.
6. **Hand off.** Before an execution of the attempt starts, the worker runtime calls `handOff`, which writes the hand-off record durably and then sets the checkout to mode `2770`. The record is the hand-off state on every platform, so that a restart keeps it also where no mode changes (macOS). While it exists, `inspect`, `snapshot`, `push`, and `remove` fail with `precondition-failed` and reason `workspace-handed-off`, after the checks that come before it in section 9, because the agent may still be writing; `readRemoteHead` reads only the workspace record and the remote, and works. A repeated hand-off succeeds.
    - **One handed-off workspace per Linux worker.** All executions of a Linux worker share the execution account, so while two checkouts are handed off, each execution could reach the other's, and a later execution could signal or trace a reclaim program, which runs as that account too. A Linux worker whose executions run under a separate account therefore holds at most one handed-off workspace at a time: it declares a slot count of `1` ([capacity reservation contract](capacity-reservation.md) section 8, "Declared capacity"), so a second attempt waits for placement. Beside the attempts that section 8 counts, it counts a workspace whose hand-off record exists as holding its slot until the reclaim removes the record, refuses an assignment beyond that slot with `worker-slots-exhausted`, and declares its capacity again after the reclaim, so that it becomes eligible for placement. Its `handOff` refuses while another workspace is handed off, with `precondition-failed` and reason `other-workspace-handed-off`. A delegating parent keeps its reservation and its handed-off workspace while it waits (capacity reservation contract section 7), so its worker refuses the child, and the child runs only on another worker with a free slot, in its own workspace. This is the owner's delegate's decision of 2026-10-27 (open question 1 (a) of the change `align-git-workspace-with-execution-boundary`); an execution account per slot, a uid pool, lifts the cap later.
7. **Reclaim.** `reclaim` runs only after the process set of every execution of the attempt is proven empty (supervisor identity contract section 8); an unproven termination keeps the workspace handed off, and it is reported for reconciliation (item 21). Before it starts the reclaim program, the worker writes the program's containment into the hand-off record durably. A worker that finds a containment named there, after a restart or an interrupted reclaim, proves that containment's process set empty before it reclaims again, runs Git on the workspace, or hands it off, because a surviving program could still be writing; an unproven one keeps the workspace handed off and reported for reconciliation. It first runs a fixed program of the worker image, never one from the repository, as the execution identity in its own containment under the containment parent. Without following a link, the program replaces each regular file that has another hard link with a copy, checking that an entry is a regular file before it opens it, so that no link outside the checkout reaches its content and no special file, such as a named pipe, blocks it; and it sets exactly `0660`, or `0770` when the owner may execute, on every file it owns and `2770` on every directory it owns, which clears any set-user-ID, sticky, or other bit that the agent set. Then the worker sets the checkout back to `2700` and removes the hand-off record last. With the attempt's processes and the program gone and the checkout closed, no execution of the attempt can change it any more. A repeated reclaim, or one that a worker crash interrupted, runs again from the start, after that proof. A program that exits with a failure or is killed leaves the record and the checkout handed off: `reclaim` fails with `precondition-failed` and reason `reclaim-failed`, and the worker reports the workspace for reconciliation (item 21) and never runs the program again by itself.

Item 16 makes each step a named crash point: before and after the staging clone, before and after the rename into place, before and after the rename to removing and the deletion, before and after the hand-off record's write and the hand-off's mode change, and before, during, and after the reclaim's containment record, program, mode change, and the record's removal.

## 4. Task branch

- A task's branch is `taskelith/<taskId>` (`TASK_BRANCH_PREFIX` followed by the task identifier, which section 2 restricts). Every attempt of the task uses it, so that a retry or a conflict resolution (ADR 0008 decision 3) continues the same branch.
- The adapter pushes only the task branch, only to `refs/heads/taskelith/<taskId>`, and never the base branch, a tag, or another ref (section 7).

## 5. Code-head identity

The code head that head-bound verification and review record is `CodeHeadIdentity`:

| Field | Meaning |
| --- | --- |
| `repository` | The repository's opaque identifier, the same string the SCM port uses (`RepositoryId`) |
| `commit` | The full object name of the head commit |
| `tree` | The full object name of that commit's root tree |

- Object names are full lowercase hexadecimal: 40 characters for SHA-1 or 64 for SHA-256, with one format for both. `parseCodeHeadIdentity` rejects anything else with `invalid`; abbreviated names are never recorded.
- Two heads are the same only when all three fields are equal (`isSameCodeHead`). A new commit is a new head even when its tree is unchanged, such as an amended message or an empty commit, so head-bound evidence goes stale ([architecture section 6](../architecture.md#first-class-sdlc-with-replaceable-frameworks), R21). The tree lets a reader check that two heads hold the same content, and lets item 17 show it; it never makes a stale approval current again.
- A head is recorded for verification, review, or a snapshot only from a clean workspace (section 6): `cleanHead` returns it, and a dirty workspace fails with `precondition-failed` and reason `workspace-dirty`.

## 6. Dirty state

`inspect` returns the workspace's current code head, its current branch (null when detached), and its dirty reasons, in this order:

| Reason | Meaning |
| --- | --- |
| `modified` | A tracked file differs from the head in the working tree or in the index, including a deleted tracked file and a staged change that the working tree no longer shows |
| `untracked` | A file that is neither tracked nor ignored by the repository's ignore rules |
| `operation-in-progress` | An unfinished merge, rebase, cherry-pick, revert, or bisect, or an unresolved conflict |
| `off-branch` | A `task-branch` workspace whose current branch is not its task branch |

A workspace is clean when no reason applies. Ignored files do not make a workspace dirty and are never part of a head or a snapshot; review runs in a fresh `at-head` workspace (D7 (a)), so ignored build output of the implementation does not reach it.

## 7. Run credential

The per-run SCM credential is the `RunCredential` of the [source control contract](source-control.md) section 3, issued by `RunCredentialIssuer` for the run. This contract uses it and does not redefine it.

- **Per operation.** The caller passes the credential (`WorkspaceCredential`: its identifier, secret, repositories, and effective permissions) to each operation that reaches the remote: `prepare`, `readRemoteHead`, and `push`. The workspace never keeps it, so a refreshed credential is simply the one passed next.
- **Scope first.** Before any remote call, including one in the synchronous part of the operation, `checkCredentialScope` requires the bound repository among the credential's repositories and the permission among its effective permissions: `read-code` for `prepare` and `readRemoteHead`, `write-code` for `push`. Otherwise the operation fails with `forbidden` and reason `credential-out-of-scope` before it makes any remote call, so the secret never reaches a service it is not scoped to. The service checks the credential again.
- **Never stored.** The secret is never written into the workspace: not in `.git/config`, a remote URL, a credential store, a reflog, or a file of the working tree. It is never passed on a command line, where other processes can read it, and never logged; item 16 hands it to Git for the one call only and tests that no log line holds it (section 13).
- **No repository-controlled settings.** An agent can edit the workspace's `.git`. Before each Git call on a reclaimed checkout, after the checks of the Git directory below, the adapter therefore writes `.git/config` anew, without following a link, holding only the repository format version and object format that the workspace record keeps from the clone. So no repository-local setting the agent wrote acts on the worker's Git, whatever its key: a credential helper, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.askPass`, a filter driver, `include.path`, `http.proxy`, `remote.<name>.pushurl`, or `url.<base>.insteadOf` among them. The adapter also runs Git with hooks disabled and pushes to the binding's remote URL, never to a remote the workspace configures. The agent's own repository-local settings do not survive a reclaim.
- **The agent.** Whether a harness process receives an SCM credential is the harness host's rule (item 18, [trust model](../trust-model.md) section 5); this contract gives it none.
- **Git processes.** Every Git process of the adapter, for prepare, `inspect`, `snapshot`, `readRemoteHead`, `push`, and every other operation, and the deletion of `remove` and `sweep`, runs as the worker identity in the worker's home cgroup (on Linux `init/` of the worker container), started by the worker process itself: never through an execution supervisor, never as the execution identity, and never in an execution's containment or another cgroup under the containment parent. Only the reclaim program of section 3 runs as the execution identity, in its own containment, and it runs no Git.
- **Git directory.** The worker identity can write every control record, so a link the agent leaves in `.git` would let the worker's Git read or write one. Before each Git call on a reclaimed checkout, the adapter checks, without following a link, that the checkout and `.git` are owned by the worker identity, that `.git` exists and is a directory that holds no symbolic link, `commondir`, or `objects/info/alternates`, not a `gitdir:` file, and that no entry below the checkout's top is named `.git`, as the gitfile of a submodule is, which no tracked path can be; otherwise the operation fails with `precondition-failed` and reason `unsafe-checkout`, the workspace is kept, and it is reported for reconciliation (item 21).
- **Submodules.** The adapter's Git never enters a nested repository: it passes `--ignore-submodules=all` to every status and diff, and sets `diff.ignoreSubmodules=all`, `status.submoduleSummary=false`, `submodule.recurse=false`, `fetch.recurseSubmodules=false`, and `push.recurseSubmodules=no` as command-scope configuration.
- **`safe.directory`.** The adapter never sets `safe.directory`, and runs Git in an environment it builds: without system and global configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`), without inherited `GIT_CONFIG_*` values, and without `SUDO_UID`, which Git running as root would trust as the owner. So no inherited `safe.directory`, `*` included, admits a checkout whose top directory or `.git` the agent replaced with its own, and its own owner check above refuses that as `unsafe-checkout` in any case. The harness's Git runs as the execution identity in a checkout the worker identity owns, so it needs `safe.directory` for exactly that checkout: the harness host (item 18) passes it as command-scope configuration in the harness's environment (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`), first with an empty value, which resets the list, then the checkout's path, never the value `*` and never in a file the agent can change.

## 8. Push

`readRemoteHead` returns the remote task branch head now, or null while the branch does not exist, so a caller tells an absent branch from one at the base commit. It fails with `invalid` and reason `read-only-workspace` for an `at-head` workspace. A caller reads it before a first push, in a continuing attempt, and after a `remote-moved` refusal; it is the port's only view of the remote, and the caller never needs native access.

`push` publishes a clean `task-branch` workspace's head to its task branch:

- It fails with `invalid` and reason `read-only-workspace` for an `at-head` workspace, with `forbidden` for a credential without `write-code` on the repository, and with `precondition-failed` and reason `workspace-dirty` for a dirty workspace.
- It names the remote task branch head the caller last saw through `readRemoteHead` or a successful push, or none. A remote head that differs fails with `conflict` and reason `remote-moved`; a head that does not descend from the remote head fails with `conflict` and reason `not-fast-forward`. A push is never forced, and a refused push leaves the remote unchanged.
- On success it returns the pushed `CodeHeadIdentity`, which is the workspace's current head.

## 9. Failures

Every operation returns a kernel `Result`, except `list` and `sweep`, which return values and reject their promise when the disk cannot be read, as the account pool's reads do. Failures carry a `reason` detail where this table names one (`WORKSPACE_FAILURE_REASONS`). `prepare` checks in this order: the attempt and task names and the target's repository (`invalid`), the credential (`forbidden`), the sources (`not-found`), the target's tree (`invalid`, `head-mismatch`), then an existing workspace (`conflict`). The other operations check in this order: the attempt name and the workspace (`invalid`, `not-found`), the kind (`invalid`, `read-only-workspace`), the credential (`forbidden`), the hand-off (`workspace-handed-off`), the Git directory (`unsafe-checkout`), the clean state (`workspace-dirty`), then the remote (`conflict`, `unavailable`); so a handed-off `at-head` workspace still answers `push` with `read-only-workspace`, and a foreign credential with `forbidden`. `handOff` and `reclaim` check the attempt name and the workspace first; `handOff` then refuses while another workspace is handed off (`other-workspace-handed-off`, section 3), and `reclaim` fails after a failed reclaim program (`reclaim-failed`). A refusal creates no new workspace and leaves an existing one unchanged.

| Code | Reason | When |
| --- | --- | --- |
| `invalid` | `unsafe-name` | An attempt or task identifier outside the safe form of section 2 |
| `invalid` | — | An `at-head` target of another repository |
| `invalid` | `head-mismatch` | An `at-head` target whose tree is not its commit's tree |
| `invalid` | `read-only-workspace` | `push` or `readRemoteHead` for an `at-head` workspace |
| `forbidden` | `credential-out-of-scope` | A credential without the repository or the permission |
| `not-found` | — | A missing base branch or head commit, or an absent workspace for `inspect`, `snapshot`, `readRemoteHead`, `push`, `handOff`, or `reclaim` |
| `conflict` | — | `prepare` for an attempt that has a ready workspace |
| `conflict` | `remote-moved`, `not-fast-forward` | Section 8 |
| `precondition-failed` | `workspace-dirty` | `snapshot`, `push`, or `remove` of a dirty workspace |
| `precondition-failed` | `workspace-handed-off` | `inspect`, `snapshot`, `push`, or `remove` of a handed-off workspace (section 3) |
| `precondition-failed` | `other-workspace-handed-off` | `handOff` while another workspace is handed off, on a worker whose executions share a separate account (section 3) |
| `precondition-failed` | `reclaim-failed` | `reclaim` whose program exited with a failure or was killed (section 3) |
| `precondition-failed` | `unsafe-checkout` | `inspect`, `snapshot`, `push`, or `remove` of a checkout whose owner or `.git` fails the checks of section 7, a missing `.git` included |
| `unavailable` | — | The remote cannot be reached |

## 10. Evidence snapshot

Architecture section 6 requires content-addressed snapshots, because mutable workspace paths alone cannot reproduce an admission after a branch moves, and R31 requires accepted evidence to survive the deletion of a workspace.

- `snapshot` returns the clean head's `CodeHeadIdentity`, a content type, and bytes that contain exactly the entries of the head's tree: each file with its path, Git mode (`100644` or `100755`), and exact bytes, whether or not they are valid text, and each symbolic link with its path and target, and nothing else: no `.git`, no commit metadata, no ignored or untracked file, and no credential.
- The bytes depend only on the tree: the same tree gives the same bytes in every workspace, on every run, and for every commit that has that tree, so their SHA-256 digest is stable. Item 16 chooses the format and declares its content type, for example a tar archive with fixed metadata.
- The evidence path stores the bytes in the `EvidenceStore` under their `ContentDigest` and publishes them through `EvidencePublisher` with kind `code-head-snapshot` (`HEAD_SNAPSHOT_EVIDENCE_KIND`). Accepted evidence is kept for its retention period, whatever happens to the workspace or the branch.

## 11. Cleanup and control records

- `remove` and `sweep` touch only entries directly under `worker/workspaces/` that belong to the workspace layout. They never remove, rename, or follow a path to the journal, the identity, a credential file, the root lock, the journal fault record, an execution record, or the logs (worker journal contract section 2), and never the workspace root itself.
- Deletion never follows a symbolic link, whether it is inside a workspace or a leftover entry that is itself a link: the link is removed as a link, and its target stays.
- `remove` deletes as the worker identity, after a reclaim gave its group every entry that the agent wrote, so that no entry of the checkout is closed to it.
- The worker runtime removes a workspace only when it is clean and after the attempt's terminal fact is confirmed (worker journal contract section 6) and every head the attempt must keep is pushed or its snapshot is accepted as evidence. A workspace is never removed for disk pressure, which truncates only `worker/logs/` (worker journal contract section 7).
- A ready workspace whose attempt the journal does not know is reported for reconciliation (item 21), and is removed only once the control plane confirms that attempt is terminal, or by an operator.

## 12. Conformance suite

`WORKSPACE_CONFORMANCE` runs against an adapter through a `WorkspaceFixture` that its test supplies, fresh for each case: the provider, a repository binding, a read-only, a writing, and a foreign credential, the base branch's tree with a tracked and an ignored path, a second provider over the same data root as after a restart, and native helpers that write text and binary files, executables, and links, stage a path in the index, link to a control record, commit, leave an operation unfinished, switch branches, read and advance remote branches, count the remote calls the service has seen, read a workspace's head commit and tree natively, read every byte of a workspace, read every control record kind of the worker journal contract section 2, decode a snapshot into its tree entries, interrupt a prepare or the removal of a clean workspace with links to control records inside, and leave a leftover entry that is itself a link to a control record directory, leave a hard link outside the workspace to a file of the checkout, leave a symbolic link in the checkout's `.git`, delete the checkout's `.git`, and leave a gitfile below the checkout's top; the fixture also says whether the adapter's executions share a separate account. It checks that:

- a `task-branch` workspace starts at the base head on the task branch, or at the remote task branch when it exists, is listed, and a second prepare leaves it unchanged; an `at-head` workspace opens detached at the given head and can neither push nor read a task branch;
- unsafe names, including an unsafe task with an `at-head` target and a foreign credential, a head of another repository, an unknown head, a tree that is not the commit's, and a missing base branch fail with their codes and reasons and leave nothing;
- a foreign credential cannot prepare, read the remote head, or push, a read-only credential cannot push, each refusal makes no remote call, and no credential's secret appears anywhere in the workspace;
- every head that `prepare` and `inspect` return is the commit and tree that Git reports for the workspace; each dirty reason is reported, a change staged and then reverted in the working tree is `modified` and makes `snapshot`, `push`, and `remove` refuse and keep the workspace, an ignored file is not, and a commit makes the workspace clean with a new commit and tree; a new commit with an unchanged tree is a new head;
- `readRemoteHead` reports an absent branch as null; a first push, a continuing attempt's push, and the recovery after a moved remote all use the head it reports; a push needs a clean workspace and the expected remote head, refuses a moved or diverged remote, leaves the base branch unchanged, and returns the head it pushed;
- every snapshot's head is the workspace's current head, repository, commit, and tree; a snapshot needs a clean head, holds exactly the base and committed entries with their modes, link targets, and bytes, including bytes that are not valid UTF-8, and no ignored file, has the same bytes after an empty commit and in a fresh workspace opened at the same pushed head, and changes with the tree;
- a handed-off workspace refuses `inspect`, `snapshot`, `push`, and `remove` with `workspace-handed-off`, also after a restart, and stays listed, while a push with a foreign credential fails with `forbidden` and a push of a handed-off `at-head` workspace with `read-only-workspace`; a hand-off and a reclaim can be repeated, and those of an absent workspace fail with `not-found`; after a reclaim, a write through a hard link that the agent left outside the workspace does not reach the checkout;
- a symbolic link in the checkout's `.git`, a deleted `.git`, and a gitfile below the top that names another workspace's `.git` make `inspect`, `snapshot`, `push`, and `remove` refuse with `unsafe-checkout`, keep the workspace, and leave every control record unchanged;
- where the executions share a separate account, a second workspace's hand-off fails with `other-workspace-handed-off` while one is handed off, also after a restart, and succeeds after its reclaim;
- a dirty workspace is refused and kept; the removal of a clean one is idempotent, removes no other workspace, and leaves the target of an ignored link inside it and every control record unchanged; after a restart, interrupted prepares and removals are not listed and are swept without following any link, every control record stays unchanged, and ready workspaces remain.

## 13. Required tests

- This item: the contract values, the parsers and rules, and the suite against a test-only double with real directories under a temporary data root and a fake Git service, and against defective variants of it that the suite must report: one that stores the credential in the workspace, one that calls the remote before checking the scope, one that does so in the synchronous part of a prepare only, one that checks the task name only for a task branch, one that accepts a mismatched tree, one that misses untracked files, one that puts the commit into the snapshot, one that loses modes and link targets, one that returns a stale tree with a snapshot, one that removes a dirty workspace, one that ignores the index, one that corrupts binary content in a snapshot, one whose removal reaches beyond its workspace, one that follows links when it sweeps, one that runs Git on a handed-off checkout, one whose reclaim keeps outside hard links, one that follows a link in the Git directory, and one that hands off a second workspace. Tests of the double also check its modes, that the clone writes into a checkout that is set-group-ID already, that a reclaim gives the group read and write on what the agent wrote, closed files included, never writes through or over an entry the agent named, never opens a hard-linked named pipe, that the hand-off record survives a restart without a mode change, and that a Git state the agent rewrites cannot make an `at-head` workspace publish. The worker journal adapter tests the traverse-only modes of section 2 and refuses a linked workspace root, also on Linux as root with only the worker's three capabilities and the execution account (`make verify-linux-cgroup`), where the account reads and edits nested entries that the worker wrote into a `2700` checkout after its hand-off.
- Item 16: the suite through `make` against the Git adapter with a local bare repository, on Linux in the worker image and natively on macOS; the crash points of section 3; a test that a hook, a credential helper, a filter driver, an `include.path`, an `insteadOf` rewrite, and a changed remote URL planted in the workspace's `.git` neither run nor redirect a push, and that the secret never appears in a process's arguments; snapshot bytes that are equal across two clones and two runs; and these Linux tests, which need Git in the Linux test image or a run in the worker image:
    - **Real identities.** With the worker as root holding only `CAP_SETUID`, `CAP_SETGID`, and `CAP_KILL` and the execution group, and the agent as the execution account (uid and gid 10003, no supplementary group): the clone, the hand-off, an agent that reads and edits nested files of the clone, commits with the harness's Git through `safe.directory`, and leaves a mode `0700` directory and a hard link outside, the reclaim, then `inspect`, `snapshot`, `push`, and `remove`; and that the agent can list no directory on the path to its checkout and no control-record directory, read no control record or workspace record, and reach no reclaimed checkout, while it can list its handed-off checkout.
    - **Surviving reclaim program.** A worker killed while its reclaim program runs, and restarted while that program still runs, neither reclaims again, nor runs Git on the workspace, nor hands it off until the program's containment is proven empty.
    - **Failed reclaim program.** A reclaim program that exits with a failure leaves the workspace handed off, `reclaim` fails with `reclaim-failed`, and the program does not run again; a worker with a separate execution account refuses to start while `fs.protected_hardlinks` is not `1`.
    - **Submodules.** A committed gitlink with a gitfile below the top that names another workspace's `.git` is refused with `unsafe-checkout`, and that other `.git` stays unchanged.
    - **Inherited Git settings.** With `safe.directory=*` in the system and global configuration, inherited `GIT_CONFIG_*` values, and `SUDO_UID` naming the execution account, a checkout whose `.git` the agent replaced is refused with `unsafe-checkout`, and the harness's Git trusts only its own checkout; an inherited `GIT_CONFIG_COUNT` that sets `core.hooksPath` and a global `url.<base>.insteadOf` neither run a hook nor redirect the adapter's push.
    - **One handed-off workspace.** A Linux worker with a separate execution account declares one slot and refuses a second assignment with `worker-slots-exhausted`, also after the execution's exit while its reclaim program runs, and declares its capacity again after the reclaim. A parent that waits for its delegated child keeps its handed-off workspace, so its worker refuses the child, and the child runs on a second worker with a free slot, in its own workspace.
    - **Git process cgroup.** For every Git process that prepare, `inspect`, `snapshot`, `readRemoteHead`, `push`, and `remove` start, `/proc/<pid>/status` shows the worker identity and `/proc/<pid>/cgroup` the worker's home cgroup, never a cgroup under the containment parent.
    - **No secret in a log.** After a prepare, a `readRemoteHead`, and a push with a run credential, no worker log line and no captured Git output holds the secret. This test depends on Desi's change `align-scm-port-with-g2-credentials`, which aligns the run credential with the G2 credentials.
- Item 17: a changed commit or tree makes head-bound verification and review stale, and editing an artifact cannot restore them.
