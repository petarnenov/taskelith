# Execution wire contracts

Date: 2026-10-25. Status: proposed wire contract for G2 ([G2 work plan](../g2-plan.md) item 8), under independent review. It states the rules of the execution documents that their schemas cannot express. The documents are the source of the field definitions; this page never repeats a field list. G3 sub-change 9c (`extend-execution-http-contracts`) extends the OpenAPI document with the operations of section 8.

## 1. Documents

| Document | Version | Content |
| --- | --- | --- |
| [`execution.asyncapi.json`](../../packages/contracts/documents/execution.asyncapi.json) | 0.7.0 | Commands to a worker and observations from it, over NATS JetStream, and its heartbeats over core NATS |
| [`execution.openapi.json`](../../packages/contracts/documents/execution.openapi.json) | 0.6.0 | The public installation CA certificate (`readInstallationCa`, which declares no credential; G3 sub-change 26b), enrollment, launch authorization, delegation with its 500 and 503 failures (item 21), task results, evidence with its 400, 500, and 503 failures (item 19), the quarantine with its redrive (item 16), and, since G3 sub-change 9c, evidence retirement, delegation results, the reconciliation queue and re-admission, and the slot and per-run SCM credential deliveries (section 8), over HTTPS; G2 served it as plain HTTP on loopback, and since G3 sub-change 26a the installation serves it over HTTPS on a certificate of the installation CA (D11; [installation contract](installation-and-enrollment.md) section 7) |

Both live in `@taskelith/contracts` beside the SDLC documents and the [control-plane document](control-plane-wire-contracts.md). The package generates one type and one validator per schema name from all its documents, so a name that several documents define must name the same schema, and a security scheme name the same scheme; the build and the package tests fail otherwise. The execution documents reuse `CommandMetadata`, the identifiers, `ArtifactRevision`, and `Admission` of the SDLC documents. `Admission` gains the optional `ownershipGeneration` that a used admission carries ([`sdlc-task-admission`](../../openspec/specs/sdlc-task-admission/spec.md)), which the SDLC documents declare with version 0.2.0.

## 2. Transport

By decision D3 (a), each worker has its own command subject, read through its own durable pull consumer, and its own observation subject; by D12 (a), launch authorization is the HTTPS operation `authorizeLaunch`, and commands and observations stay on NATS.

- **Subjects:** `taskelith.<installationId>.workers.<workerId>.commands` and `taskelith.<installationId>.workers.<workerId>.observations`. The per-worker broker credentials of D9 (a) let a worker read only its own command subject and publish only on its own observation and heartbeat subjects ([trust model](../trust-model.md)). The subject names are the author's proposal; item 2 confirms the topology, and item 12 owns the streams and consumers.
- **Heartbeats:** `taskelith.<installationId>.workers.<workerId>.heartbeats` carries `worker.heartbeat` (section 6) over core NATS. No stream holds it, so a heartbeat sent while no control plane listens is lost and the next one replaces it. Only the worker publishes on its own heartbeat subject.
- **Deduplication:** every command, observation, and inventory part is first published with the `Nats-Msg-Id` header set to its `commandId`, its `observationId`, or its `reportId` followed by `.` and its `part`. A redrive from quarantine needs a new header value inside the broker's window ([JetStream spike](../g2-jetstream-spike.md#consequences-for-later-items)), so the header is only a broker hint: the message's identity is the field in its body, which never changes. A confirmation has no identity and no header: it is cumulative, so a duplicate changes nothing. The broker window is an optimization; receivers deduplicate by the body identities for their whole lifetime (architecture section 9). The broker's stream sequence is not the producer sequence: a repeat after the window or a redrive gets a new one, so no rule depends on it.
- **Size:** a message's JSON encoding is at most `1 MiB`, the broker's maximum payload ([operational targets](../operational-targets.md)). The array bounds keep every message below it; a test checks the largest one, an inventory part with every identifier at its maximum length.
- **Malformed messages:** a message that fails its schema is not acted on and goes to quarantine with diagnostics (item 12); it is not rejected by an observation, because none of its fields can be trusted. A malformed heartbeat, which no stream holds, is dropped and logged instead.

## 3. Protocol version

Architecture section 13 requires compatible server and worker version windows and a worker that fails closed when it cannot execute the assigned protocol.

- **Version:** the execution protocol version is a positive integer, `1` in this contract, exported as `EXECUTION_PROTOCOL_VERSION`. Every execution command carries it as `payload.protocolVersion`, and every observation and report as `protocolVersion`.
- **Stable part:** `CommandMetadata` and `payload.protocolVersion` keep their meaning in every protocol version. The worker validates a delivered command against `VersionedCommand` first, then checks the version against its window, and only then validates the command's own schema.
- **Fail closed:** a worker that does not support the version, or that finds another `workerId` in the metadata, executes nothing of the command, an offer included. It rejects the command with `execution.command.rejected`, which names the command only by `commandId` and `commandType`, so that no field of an unknown payload is needed, and which carries the worker's window. It acknowledges the command only after that observation is committed, as for every rejected command ([worker journal](worker-journal.md) W1). For an offer, the control plane finds the assignment by its `commandId` and refuses it with `protocol-not-supported`, which ends it and releases its reservation (capacity reservation section 6).
- **Windows:** the worker declares its window at enrollment and in every `worker.capacity.declared` observation. The control plane stamps each command with the highest version both windows contain (`commonProtocolVersion`) and places no assignment on a worker whose window has no common version; enrollment of such a worker fails with 422.
- **Compatibility window:** the control plane supports the current and the previous protocol version, so that workers can be upgraded after the control plane. A worker that supports neither is drained and upgraded before it receives work (architecture section 13). Whatever its protocol version, a worker that sends no `worker.self-check.reported` is never admitted, so it gets no placement and no new launch grant ([worker admission](worker-admission.md) section 7).
- **New versions:** a change that a worker of the current version could not execute correctly, such as a new required field or a changed meaning, needs the next protocol version. A change that the breaking-change check reports for a document also needs a new `info.version` of that document, as for every contract document. Since `declare-contract-breaking-changes`, a new major version, or a new minor version while the major version is 0, declares only the breaking changes that `packages/contracts/breaking-changes.json` lists for that document and version, so that each one is visible: bump `info.version`, run `make contract-breaking-changes` (it needs Docker for oasdiff and never writes the file), copy the printed entry into the file at its sorted place, and write its reason. `make contract-compatibility` fails on every unlisted or stale change, on an entry for a version that declares no breaking change, and on a malformed file; entries of versions up to the merge-base version stay as history.

## 4. Commands

Each command is a `CommandMetadata` envelope that also requires `attemptId`, `workerId`, and `ownershipGeneration`, with a fixed `commandType` and its own payload.

| Command | `commandType` | Written by |
| --- | --- | --- |
| Assignment offer | `execution.assignment.offer` | The assignment's creation, with its reservation (capacity reservation section 4); the requested CPU and memory are each at most `2147483647`, the largest PostgreSQL `integer`, and the per-attempt ceiling of capacity reservation section 8 still applies |
| Cancellation | `execution.cancellation.request` | A cancellation request, a revocation after authorization (launch authorization section 5), an `unauthorized-start` for that execution only, or an assignment end while an execution under it can run |
| Assignment end | `execution.assignment.end` | The cancellation and supersession transactions (capacity reservation section 6) |

- An offer names the `recoveryEpoch` the worker uses in its launch requests and in the observations about its executions. The admission and its generation are `metadata.sdlc.admissionId` and `metadata.sdlc.admissionGeneration`, which the worker journals with the launch intent ([worker journal](worker-journal.md) section 5).
- A cancellation without `executionId` targets the attempt; with it, only that execution. A cancellation is never proof of termination.
- What an offer executes is not part of G2: item 15 runs a test-only scripted process chosen by the worker's test configuration, and the harness invocation joins the offer with the agent harness port in G3.

The control plane also sends `execution.observations.confirmed` and `worker.inventory.requested` (section 6) on the command subject. Neither is a command: they have no `commandId`, the worker does not journal them in its inbox, and receiving either twice changes nothing.

## 5. Observations

Each observation is an `ObservationMetadata` envelope with a fixed `observationType` and its own payload. An observation about an attempt also requires `attemptId` and `ownershipGeneration`, the generation of the offer the worker journaled; only `execution.command.rejected`, which names its command by `commandId` alone (section 3), `execution.unrecorded-process`, `worker.capacity.declared`, `worker.admission-pressure.changed`, and `worker.self-check.reported` are about no attempt. Its producer is the pair `(workerId, journalId)`, and `sequence` is gapless per that pair ([worker journal](worker-journal.md) section 6). `observationId` is deterministic from its source: the `commandId` for a command outcome, the `executionId` and the fact for an execution fact, the `executionId`, the fact, and an evidence counter for a repeated `uncertain`, the `executionId`, the fact, and the cancellation's `commandId` for `cancellation.not-applied`, and the `journalId` and the containment for `execution.unrecorded-process`, which therefore has one identity per journal incarnation: a derivation after confirmation is published again under the same identity, and the receiver applies it without effect ([worker journal](worker-journal.md) section 6). `occurredAt` is the worker's clock and is informational only; no safety rule depends on it.

| Observation | `observationType` | Source |
| --- | --- | --- |
| Assignment accepted | `execution.assignment.accepted` | The offer was journaled and accepted |
| Assignment refused | `execution.assignment.refused` | A worker-side reason of capacity reservation section 11 |
| Command rejected | `execution.command.rejected` | Section 3 |
| Launch rejected | `execution.launch.rejected` | A non-retryable launch rejection (launch authorization section 9) |
| Started, exited, not started, uncertain, termination unproven, unrecorded process | `execution.started`, `execution.exited`, `execution.not-started`, `execution.uncertain`, `execution.termination-unproven`, `execution.unrecorded-process` | The facts of supervisor identity section 11 |
| Cancellation not applied | `execution.cancellation.not-applied` | An adopting supervisor on macOS (supervisor identity section 8) |
| Capacity declared | `worker.capacity.declared` | At enrollment and whenever the slot count, CPU, memory, enforceable controls, or protocol window change; each of the slot count, CPU, and memory is at most `2147483647`, the largest PostgreSQL `integer` |
| Admission pressure changed | `worker.admission-pressure.changed` | The causes of admission pressure changed; an empty list clears it |
| Self-check reported | `worker.self-check.reported` | Once per worker start, after the capacity declaration and the pressure report ([worker admission](worker-admission.md)) |

The schemas also fix the dependencies between fields:

- A refusal is `retryable` exactly when its reason is `worker-admission-pressure`, and then it names at least one `pressureCauses` entry, such as `journal-backlog` or `disk-floor`; no other refusal names causes. A refusal with `worker-self-check-failed` is not retryable.
- A self-check result that `passed` has no `details`; one that `failed` has one to eight; one that is `not-applicable` has exactly one recognised reason, `platform-not-covered` or `no-launch-command`; a report with another reason is malformed. A report that names a check more than once passes the schema, and the control plane decides it as one failed result ([worker admission](worker-admission.md) section 4a).
- An exit with `spawnFailed` has `startProven` false, a `spawnFailure`, and the termination evidence `never-spawned`; an exit without `spawnFailed` has no `spawnFailure` and another termination evidence. That it is `containment-empty` on Linux and `process-group-empty` on macOS is the worker's rule; recovery on start may instead prove the end by `boot-changed` or, on Linux, `namespace-ended` (supervisor identity section 6), with status `unknown`.
- `execution.started` carries the child's process identity; the control plane checks its `launchAuthId`, `executionId`, and `recoveryEpoch` as launch authorization section 7 states.
- Every other execution observation carries `recoveryEpoch` too: `execution.exited`, `execution.not-started`, `execution.uncertain`, `execution.termination-unproven`, and `execution.cancellation.not-applied` the epoch of the launch intent their execution belongs to, and `execution.unrecorded-process` the epoch of the worker's journal. The control plane checks it, and the quarantine state, as launch authorization section 7 states for these observations. This required field was added to protocol version 1 under a pre-release exception (change `gate-stale-epoch-observations`, design D2) that ended with the G2 closure ([ADR 0015](../decisions/0015-g2-closure.md)); from then on, section 3 applies strictly, and a new required field needs the next protocol version.

## 6. Confirmation and inventory

- **Confirmation:** `confirmedThrough` is the end of the contiguous prefix of the journal's sequence that the control plane has applied. It only grows for a `(workerId, journalId)`; a lower value than the worker's local one is ignored. A broker acknowledgement confirms nothing (worker journal section 6).
- **Inventory:** on every reconnect the worker publishes `worker.inventory.reported` with the assignments it holds, their executions with their journal state and whether they are uncertain, and `throughSequence`, the last sequence the snapshot reflects. Uncertainty is evidence beside the state, as in the journal, and `launch-intended` is an execution without a journaled grant. One snapshot is sent in `parts` messages with one `reportId`, each of at most 256 assignments and 256 executions, and its `snapshot` number increases with every snapshot of the journal. The report is outside the journal sequence and is not confirmed.

  - The control plane applies a snapshot only when it has every part and every observation through `throughSequence`. A part of a lower `snapshot` than one already received from the same journal is discarded, so a delayed snapshot never replaces a later one. The parts of a fresh snapshot, defined below, are exempt from this filter until the rollback check below has run.
  - An omission proves lost local history only for an assignment whose acceptance the control plane applied from the same journal at a sequence up to `throughSequence`, and, after disk loss, for one accepted under an earlier journal of the worker; it is then reconciled as worker journal section 8 states.
  - An unfinished assignment that the snapshot omits without such an acceptance may be one the worker had not received when it took the snapshot. The control plane re-sends its offer with the same `commandId` only if no grant is recorded, which the worker's inbox makes idempotent, and draws no other conclusion from the omission.
- **Heartbeat:** the worker sends `worker.heartbeat` every `10s` ([operational targets](../operational-targets.md)) with its `workerId`, its `journalId`, and `sentAt`, which is its own clock and informational only. A heartbeat is outside the journal sequence; it is neither confirmed nor deduplicated, and it carries no capacity or pressure. The control plane records it as contact only when the subject's worker is the body's `workerId`, enrolled, not revoked, and under its enrolled `journalId` that is not retired. Unlike an observation or an inventory report, a heartbeat of a journal never seen does not replace the enrolled one: it is refused until an observation or report of the new journal has replaced it. After `30s` without any contact, a heartbeat, an observation, or an inventory report, the control plane marks the worker unreachable, which takes it out of new placement and changes no attempt, assignment, or reservation; any later contact makes it reachable again.
- **Inventory request:** `throughSequence` alone cannot tell a journal rolled back to before an applied acceptance from a delayed snapshot. When the control plane sees a worker reconnect, and whenever an unsolicited snapshot, one without a `requestId`, omits an unfinished assignment it cannot classify, it sends `worker.inventory.requested` with a fresh random `requestId` and keeps only the latest one per worker. The control plane sends no request for a snapshot that answers a request, even a superseded one: a newer request was sent, and its fresh answer handles any omission. The worker answers every request with a snapshot that carries that `requestId`, taken after the request arrived. A snapshot is **fresh** when its `requestId` is the current one of its worker, so it reflects the journal after every acceptance and grant the control plane had applied when it sent the request. An unfinished assignment that a fresh snapshot omits without an applied acceptance needs no further request: the re-sent offer above covers an offer the worker had not received.
  - When it sends a request, the control plane records the request's **bound**: the highest sequence it had applied from each journal of the worker, and the unfinished assignments whose acceptance it had applied from that journal. An observation applied after the request does not change the bound.
  - In a fresh snapshot, a `throughSequence` below the bound of its journal is a rollback, and so is the omission of an unfinished assignment the bound lists.
  - The control plane checks a complete fresh snapshot for rollback before it applies the lower-`snapshot` filter, because a journal that rolled back also rolled back its `snapshot` counter. A fresh snapshot that the filter would discard is used only for that check: a rollback starts reconciliation, and the snapshot never replaces the later one.
  - A rollback starts reconciliation as worker journal section 8 states: ownership and the capacity reservation are kept, and nothing is assumed about prior side effects.
  - A snapshot with another `requestId`, or without one, is applied only under the rules above and never proves a rollback.

## 7. HTTP operations

| Operation | Credential | Rules |
| --- | --- | --- |
| `enrollWorker` | Single-use enrollment token | The worker presents its new `journalId`, host, protocol window, and capacity, with each capacity value at most `2147483647`; the response holds the `workerId`, the credential generation, the recovery epoch, the control plane's protocol window, and both credentials, whose content item 13 defines. |
| `authorizeLaunch` | Worker credential | Status 200 carries the decision recorded for the `operationId`: a grant, a rejection, or, on a transport retry, `revoked` or `expired`. Status 503 means no decision was reached; the worker retries with the same `operationId` until its deadline. A rejection is `retryable` exactly for `quarantined` and `unavailable`, and a retry after it uses a new `operationId`. `skewMilliseconds` is less than `ttlMilliseconds`. The worker computes its deadline from its own suspend-inclusive clock (launch authorization section 7); `issuedAt` is never compared with the worker's clock. |
| `requestDelegation` | Worker credential | The worker names the delegating attempt at its ownership generation and the child task; the control plane derives the parent and root, and admits, holds, or rejects the child with the reasons of capacity reservation section 7. A repeat with the same `delegationId` returns the current state. |
| `readTaskResult` | Operator credential | `pending` until an attempt of the task ends; then the outcome of its last ended attempt, which does not accept the task's work, and the evidence records of the task. |
| `publishEvidence` | Worker credential | A multipart body of the record and its content. Every record names its input artifacts, code revision, validator or producing program with its version, and outcome (architecture section 8). The record names the `ownershipGeneration` at which the worker produced it, and the worker must have held the attempt at that generation. The control plane compares it with the current generation in the transaction that stores the record: evidence of an older generation is kept for audit with `ownershipCurrent` false and never counts as current evidence (launch authorization section 5). The control plane verifies the SHA-256 digest and size before it stores the record; a repeat of the same record returns 200. |
| `readEvidence`, `downloadEvidence` | Browser session or operator credential, since 9c (section 8.2) | The record, and the content whose SHA-256 digest is the record's `contentDigest`; content that is missing or does not match is not served. |

The operator credential is the installation bootstrap credential of decision D10 (a). Item 16 declares it on the SDLC operations in `sdlc.openapi.json` 0.3.0. Section 8 adds the operations of G3 sub-change 9c.

## 8. G3 operations

G3 sub-change 9c (`extend-execution-http-contracts`, [G3 work plan](../g3-plan.md) item 9) adds these operations to `execution.openapi.json` 0.6.0. They stay in this document, not in the [control-plane document](control-plane-wire-contracts.md): retirement shares its path with `readEvidence`, the generator refuses one path in two documents, and the other operations serve the worker or sit beside the operations they extend (architect, 2026-10-28). This sub-change adds no adapter or handler; items 10, 12, 21, 38, and 44 implement the operations.

### 8.1 Credentials and roles

- **Session.** `browserSession` and `csrfToken` are the schemes of the control-plane document, and `AuthenticationFailure`, `AccessDenial`, `CsrfRejection`, `ExternalId`, and `RemoteUrl` its schemas, all unchanged, because the generator refuses one name with two definitions ([control-plane wire contracts](control-plane-wire-contracts.md) sections 1 and 2). An operation that accepts the session takes the cookie, with the CSRF header for a mutation, or the operator bearer alone, which authenticates the first `installation-owner` (control-plane section 2). It authenticates, checks the CSRF token, and checks the role, in that order, and every failure has the control-plane schemas: 401 `AuthenticationFailure`, 403 `AccessDenial` or, for a mutation, `CsrfRejection`.
- **Worker.** The worker operations take the worker credential only, and their 401 is the kernel `Failure`, as for the G2 worker operations.
- **Roles.** The roles are those of the [trust model](../trust-model.md#3-project-scoped-authorization-roles) section 3:

| Operation | Credential | Who |
| --- | --- | --- |
| `readEvidence`, `downloadEvidence` | Session or operator bearer | `project-viewer` or above on the record's project, or an `installation-owner`; anyone else gets 404 (section 8.2) |
| `retireEvidence` | Session with CSRF, or operator bearer | `project-maintainer` on the record's project; a principal that may not read the record gets 404, and a reader below `project-maintainer` 403 (section 8.2) |
| `listUnknownExecutions` | Session or operator bearer | `project-viewer` or above on the project, or an `installation-owner` |
| `listUnrecordedProcesses` | Session or operator bearer | `installation-owner` |
| `readmitTask` | Session with CSRF, or operator bearer | `project-operator` or above on the project named in the query, checked before the task is read (section 8.5) |
| `readDelegationResult` | Worker | The worker that holds the active attempt of the delegation's parent task (section 8.3) |
| `fetchSlotCredential` | Worker | The worker that owns the execution, for a slot that its reservation names (section 8.6) |
| `issueRunScmCredential`, `fetchRunScmCredential` | Worker | The worker that holds an attempt of a task of the run (section 8.7) |

### 8.2 Evidence

- **Per-project reads, a breaking change.** G2 served `readEvidence` and `downloadEvidence` to the installation-wide operator credential alone (`implement-evidence-store`, which left per-project authorization to G3 login; [ADR 0015](../decisions/0015-g2-closure.md) decision 5; G3 plan row 10). Since 9c a `project-viewer` or above on the record's project reads them, because the trust model section 3 gives evidence reads to project roles and requires evidence downloads to be authorized by project. The project is known only from the record, so the control plane reads the record before it checks the role, and it answers a principal without a role on that project with the 404 of an unknown record, so that a record of another project is never disclosed. This differs from the control-plane rule, which checks the role before it reads anything, because every control-plane operation of a project names it in its path or query and answers a principal without the role 403 `role-required` (control-plane section 2); the evidence path names no project, and the trust model section 3 requires evidence downloads to be isolated by project. The rule covers the operations of the record's path, `readEvidence`, `downloadEvidence`, and `retireEvidence`, and no other operation of this document. The operator bearer authenticates an `installation-owner`, which reads every project, so the CLI keeps its access. A client sees the change as the session credential, the `AuthenticationFailure` body of a 401, and a 404 for a record outside its projects. A download reads the record, then its content outside that transaction (`EvidenceService.download`); when the content is missing, it reads the record again, and a record retired in between answers 404, as an unknown record, not 500, which stays for the missing or corrupt content of a record that still exists.
- **Its version.** `make contract-compatibility` compares schemas, not authorization, and reports no breaking change for this; the document still declares it with the next minor version, 0.6.0, which also covers the added operations, because a caller of the same request can now be refused. For the same reason `packages/contracts/breaking-changes.json`, which lists only the changes that the check computes (section 3), has no entry for this narrowing.
- **Retirement.** `retireEvidence` is `DELETE` on the record's path. It removes the record once 365 days have passed since its publication, its `publishedAt`, not its `capturedAt` (`EVIDENCE_RETENTION_DAYS`, `retentionEndsAt`, `checkRetentionElapsed`), and then its content once no record refers to the digest, under the digest's advisory lock that a publication of the same digest also takes, as `EvidenceService.retire` does (`implement-evidence-store` decision Q2). Before then it answers 422 `RetentionRefusal`, reason `retention-not-elapsed`, with the required `details.retainedUntil`, the `Instant` that `retentionEndsAt` computes, and changes nothing. A record never changes after it is stored, so retirement names no revision; of two concurrent retirements one removes the record and the other answers 404, as does a retirement of an already retired record. Evidence of an older ownership generation retires under the same rule. The record and its content are removed in two transactions; once the record's removal commits, the retirement answers 204 even when the content's removal fails, and the content is left to a sweep of digests that no record refers to (section 9, G3 item 10), because a repeat would answer 404 and could never remove it. A 500 or 503 therefore means that the record was not removed.
- **Roles.** A principal that may not read the record gets its 404, as for the reads, and a reader below `project-maintainer` gets 403 `role-required`, because it learns nothing that its read would not show.

### 8.3 Delegation results

- **Result.** `readDelegationResult` answers `pending` while the child task has not ended, and `ended` with the outcome that the agent harness port returns to the parent, `completed`, `rejected`, `failed`, or `cancelled` ([agent harness port](agent-harness-port.md) section 7.4), a summary of at most `MAX_HARNESS_TEXT_LENGTH` characters, and its end time. A delegation that `requestDelegation` rejected ends `rejected`. Item 38 maps the child task's end to the outcome and writes the summary, which is text of the child's run and is redacted as that run's text is ([account pool contract](account-pool.md) section 7.4).
- **Reader.** The worker that holds the active attempt of the delegation's parent task at the task's current ownership generation reads it: the delegating attempt, or a later attempt of the same task that resumed its session, to which the host delivers the result as a turn (agent harness port section 7.4). Any other worker gets the 404 of an unknown delegation.
- **And the response command.** The read does not answer the parent's native request: the response command of sub-change 9d returns the result to it ([session timeline](session-timeline.md) section 5.2). The read lets the host learn the result after a restart or a missed command. 9d reuses `DelegationResult`, `DelegationResultOutcome`, and `DelegationSummary` unchanged.

### 8.4 Reconciliation queue

The reads map the G2 `ReconciliationQueue` (`wire-launch-authority-reconciliation` decision 5) onto the reconciliation items of [product ports](product-ports.md) section 4.1.

- **Unknown executions.** `listUnknownExecutions` returns a project's executions that `isUnknownExecution` holds: not terminal, with evidence other than `cancellation-not-applied`, such as `uncertain` or `termination-unproven`. Each names its run, task, attempt with the ownership generation it holds, execution, worker, state, and evidence. The evidence list is every entry that `withEvidence` kept, without a bound, because a repeated `uncertain` adds one per observation; at least one entry is of a kind other than `cancellation-not-applied`, which the schema requires with `contains`.
- **Unrecorded processes.** `listUnrecordedProcesses` returns the processes that workers reported without a journal record. They name no project, so only an `installation-owner` reads them (product ports section 4.1; trust model section 3).
- **Pages.** Both return at most 100 items and, while more remain, a `next` position, as the control-plane lists do (control-plane section 6), but by a composite key, because neither identifier is unique alone: an `executionId` is unique only within its task, and an `observationId` only per worker, the key of `unrecorded_processes` being `(worker_id, observation_id)`. Unknown executions are in the code-unit order of the task identifier, then the execution identifier, and `next` is an `UnknownExecutionCursor` whose fields the caller passes as `afterTaskId` and `afterExecutionId`; unrecorded processes are in the order of the worker identifier, then the observation identifier, and `next` is an `UnrecordedProcessCursor` passed as `afterWorkerId` and `afterObservationId`. One parameter of a pair without the other answers 400. A page that ends between two items with the same `executionId` or `observationId` therefore resumes at the next one. The port lists by worker or by task today; item 44 adds the read by project after a position.
- **Answers.** Resolving an unknown execution (`resolve-execution`) and acknowledging a process (`acknowledge-process`) are answers to inbox items, which go to the reconciliation source that owns them (product ports section 4.2), through the inbox operations of sub-change 9b, not through this document.

### 8.5 Re-admission

- **Command.** `readmitTask` re-admits a task through the writer of admissions, binding a new admission at the task's next ownership generation (G2 `rebindAdmission`; product ports section 4.1, "After a revocation"; G3 plan row 44). The task keeps its identity (product ports section 3.3). It answers 201 with the task and its new admission.
- **Project.** The request names the task's project as the query parameter `projectId`. The control plane checks the role on that project before it reads the run or the task, as the control-plane operations do (control-plane section 2), so a principal without `project-operator` or above on it gets 403 `role-required` whether the task exists or not, and a run or task that is not of that project answers 404 only to a principal with the role. This follows the control-plane rule rather than the evidence rule of section 8.2, because the caller can name the project.
- **Compare-and-set and idempotency.** The request names the task's ownership generation as the caller read it and a `readmissionId`, the caller's idempotency key scoped to the task ([product ports](product-ports.md) section 2, rule 7). A repeat with the same key and input returns the first 201, for example after a lost response; the same key with another input answers 409 `conflict`. A generation that moved, for example by a re-admission under another key, answers 409 `conflict` and changes nothing, so of two concurrent re-admissions with different keys exactly one wins.
- **Refusals.** 422 `ReadmissionRefusal`, checked in this order: `attempt-active` while an attempt of the task is active, which includes an attempt whose execution is unknown until reconciliation resolves it, because `rebindAdmission` refuses then and the product side never dispatches the task again before the re-admission (product ports section 4.1); `admission-not-dispatched` while the task's current admission is `admitted` and not yet used, because placement still dispatches it at the current generation; and `admission-refused` when SDLC admission refuses the new admission at the current revisions, as `submitTask` answers 422.
- **Role.** A `project-operator` or above, who may trigger retries (trust model section 3).
- **Automatic re-admission.** Item 44 also re-admits, through the same writer, an attempt whose launch was rejected under a stale admission, in place of the G2 release (`wire-launch-authority-reconciliation` decision 2), and a task whose launch grant a product writer revoked under the launch invalidation protocol, a cancelled attempt (G3 plan row 44, review finding P2-M3 of `bind-product-writers-to-launch-invalidation`). That writer runs inside the control plane with the same checks and has no wire operation; `readmitTask` is the operator's command for the other cases.

### 8.6 Slot credential delivery

The architect decided on 2026-10-28 that a slot credential is delivered, first and again, by the same pattern as a refreshed SCM credential (section 8.7): a fetch over HTTPS with the worker credential, scoped to the run and the slot, written once, read only by its owner, and logged without its value. A credential travels only in an API response, never in a broker message or stream ([account pool contract](account-pool.md) section 7).

- **Fetch.** `fetchSlotCredential` takes the execution and the slot in its path and, as query parameters, the attempt, the ownership generation, and the recovery epoch that the worker holds. Its scope is the run's reservation and the slot: the control plane finds the execution by the attempt and the execution identifier together, because an execution identifier is unique only within its task, and the attempt's reservation must name the slot. It needs no notice, because the worker asks when it starts or adopts an execution (account pool section 7.3).
- **First fetch and later fetches.** One operation makes both deliveries (architect, 2026-10-28). The first fetch, after the launch authorization that made the execution `authorized`, returns the slot's current credential version; a later fetch, for example after the worker adopted the execution, re-delivers that version. `LaunchGrant` carries no credential, because the worker journals the grant (account pool section 7.3). Account pool section 7 sends the credential only with a valid launch authorization for the attempt: an `authorized` execution with no earlier delivery therefore also needs its launch grant unexpired by `issuedAt` and `ttl` and not `revoked`, found from the execution, with no query parameter ([launch authorization](launch-authorization.md) sections 4 and 7). For an execution that already had a delivery, `started` or adopted, account pool section 7.3's ownership checks stand in for that condition, because its grant may have expired (section 7.3, "Re-delivery to an adopted execution").
- **Checks.** The checks of account pool section 7.3, in its order, refuse with 422 `SlotCredentialRefusal` and reveal nothing: `quarantined`, `stale-recovery-epoch`, `worker-not-authorized`, `assignment-not-active`, `stale-ownership-generation`, `attempt-not-launchable`, `execution-conflict`, `capacity-not-reserved`, then the slot's ineligibility, `revoked` or `removed`, and `delivery-not-admitted` for a mechanism without an admitted delivery for its harness. Section 7.3 names that last refusal `invalid` and names this wire reason beside it; on this API a 400 means a malformed request, so it is a typed 422 reason. An `authorized` execution with no earlier delivery and an expired grant is `execution-conflict`, as one with a `revoked` grant. A reservation that is released or held for another attempt, or that does not name the slot, is `capacity-not-reserved`. An unknown attempt or execution is `assignment-not-active`, after the installation and worker checks, as `rejectUnknownAssignment` answers a launch, so the operation has no 404 and a worker learns nothing of another worker's executions. A revocation of a slot cancels every attempt whose held reservation names it (account pool section 8.1), so a later fetch for the execution of such an attempt answers `attempt-not-launchable`, the earlier check, not `revoked` (account pool section 7.3).
- **Written once.** The delivery carries the version that the slot record names. A rotation switches it only while no held reservation names the slot (account pool section 8.1), so every delivery to the same execution and slot carries the same version and value.
- **Owner only and never kept.** Only the worker that owns the execution passes the checks. The response has `Cache-Control: no-store`; the worker holds the credential only in memory (account pool section 7.3), and no log holds the response body (section 8.8).

### 8.7 Per-run SCM credential

A refreshed per-run SCM credential reaches the worker as a notice of sub-change 9d, which names the run, the credential, and the version, and the worker fetches the secret over HTTPS (architect, 2026-10-28); the secret never travels in a broker message.

- **Issue.** `issueRunScmCredential` returns the run's current credential version to a worker that holds an attempt of a task of the run, and the control plane issues the first one (`issueRunCredential`, [source control contract](source-control.md) section 3) when the run has none, so a repeat with no refresh between returns the same version, and a repeat after a refresh the refreshed one. A run's credential belongs to the run, so the attempts of its tasks share it. The first issue is serialized per run, by a lock or a unique key on the run's credential: of concurrent first issues one issues, and every other returns the winner's version and issues nothing, so a run never holds an untracked secret.
- **Fetch.** `fetchRunScmCredential` returns the version that a notice names. A version is the secret that one issue or refresh returned, numbered 1 at issue and one more at each refresh; it never changes once written.
- **Ownership checks.** The request names the attempt, its ownership generation, and the worker's recovery epoch. The control plane refuses with 422 `ScmCredentialRefusal` and the reasons of [launch authorization](launch-authorization.md) section 9 for the same checks, in this order: `quarantined`, `stale-recovery-epoch`, `worker-not-authorized`, `assignment-not-active` (also for an unknown run or an attempt that is not of a task of the run, after the installation and worker checks, so the operations answer no 404 for a run), `stale-ownership-generation`, and `attempt-not-launchable`.
- **Remote re-check.** Then, on every issue and every fetch, it re-checks the project's repository binding against the SCM integration's current allowed origin, as control-plane section 4.1, "Credential issue", requires: `repository-unbound` for a project without a binding, then the checks of `bindRepository` in its order, `remote-not-https`, `remote-userinfo`, `remote-query`, `remote-fragment`, and `remote-origin-mismatch` (control-plane section 4). The stored URL passed them when it was bound; the re-check catches an origin narrowed since. `merge-method-undeclared` is a binding refusal only and does not apply.
- **Version.** Only after these checks does an issue or a fetch look up the credential and its version, so a worker without an attempt of the run learns nothing of its credentials. A fetch answers 404 for an unknown credential or version, and 422 `credential-ended` for a version whose secret a refresh, a revocation, or its expiry ended (source control section 3). An issue answers 422 `credential-ended` when a revocation or its expiry ended the run's current version, because it re-delivers that version and issues no new one; the refresh of source control section 3 gives the next version before expiry.
- **Records.** On every refusal the control plane issues and reveals nothing and records the reason with the run, attempt, worker, credential, and version, never a secret. The refusal's `message` and `details` name only the reason and these identifiers, never the remote URL, which a `remote-userinfo` refusal would otherwise expose with its user information, or a secret.
- **What the worker gets.** The delivery carries the effective repositories and permissions, the expiry, the secret, the complete `Authorization` value that the SCM plugin forms from it (`authorization`, [git workspace contract](git-workspace.md) sections 7 and 14), and the bound remote URL that the re-check passed. The worker sends the credential only to that URL (control-plane section 4.1, "Worker"). The response has `Cache-Control: no-store`, the worker keeps the secret only in memory and passes it per operation (git workspace section 7), and no log holds the response body.

### 8.8 Logs and caching

A request log of these operations holds only the method, the operation, its path and query parameters, the status, and the failure, never a request or response body or the `Cookie`, `X-CSRF-Token`, or `Authorization` header, and what it holds is still redacted with `@taskelith/secrets`, as for the control-plane document (control-plane section 7). Path and query parameters hold identifiers, generations, and epochs only. The three credential deliveries are the only responses of this document that carry a secret, and each has `Cache-Control: no-store`.
