# Control-plane wire contracts

Date: 2026-10-28. Status: proposed wire contract for G3 ([G3 work plan](../g3-plan.md) item 9): sub-change 9a `define-control-plane-access-contracts` (archived) defined the access and setup operations, and sub-change 9b `define-board-session-and-event-stream-contracts`, under independent review, adds the board, task detail, inbox, agent session, and event stream operations (sections 8 to 10). It states the rules of the control-plane document that its schemas cannot express. The document is the source of the field definitions; this page never repeats a field list. Items 10 to 15 implement it; neither sub-change adds an adapter or a handler.

## 1. Document

| Document | Version | Content |
| --- | --- | --- |
| [`control-plane.openapi.json`](../../packages/contracts/documents/control-plane.openapi.json) | 0.2.0 | Login and sessions; projects with their members, defaults, auto-merge setting, repository binding, and pool slots; the workers view; enrollment tokens; account slots; SCM integrations; the webhook receiver; the board, task detail, and inbox views and inbox answers; agent sessions with their turns, native requests, responses, and output; the project and installation event streams |

It lives in `@taskelith/contracts` beside the SDLC and execution documents, and the build generates its types and validators with theirs, exported as `HttpComponents`, `HttpOperations`, and `HttpPaths` and checked by `checkHttpSchema`. It reuses, unchanged, `Failure`, `Identifier`, `Instant`, `DisplayText`, `Generation`, `Platform`, `Architecture`, `AttemptOutcome`, `ExitStatus`, and `AdmissionState` of the execution document, `ContentDigest` and `WorkflowRunBinding` of the SDLC document, and `SelfCheckResult`, `SelfCheckId`, and `NotApplicableReason` of `execution.asyncapi.json`, because the generator refuses one component name with two schemas. Since this sub-change it also refuses one security scheme name with two definitions; before it, the later document's scheme silently replaced the earlier one. `operatorToken` is therefore the scheme of the other documents, unchanged.

The control plane serves the document on the browser endpoint over HTTPS, same-origin with the SPA ([architecture section 11](../architecture.md#11-spa-authentication-and-live-traffic); [installation contract](installation-and-enrollment.md) section 7).

## 2. Authentication and CSRF

| Scheme | Kind | Used by |
| --- | --- | --- |
| `browserSession` | Cookie `__Host-taskelith-session`: a server-side session identifier of 256 random bits, set with `HttpOnly`, `Secure`, `SameSite=Strict`, and `Path=/`, without `Domain` | The SPA |
| `csrfToken` | Header `X-CSRF-Token`: the session's CSRF token, 256 random bits in base64url | The SPA, with the cookie, on every operation other than GET |
| `operatorToken` | Bearer: the installation bootstrap credential of decision D10 (a) ([installation contract](installation-and-enrollment.md) section 4) | The CLI and the owner |

- **Sessions.** Sessions are server-side (G3 decision D2 (a)). `readSession` needs no credential: without a valid session cookie it starts an anonymous session, sets its cookie, and returns its CSRF token. `logIn` is a mutation like any other, so it needs that anonymous session's cookie and token, which protects the login itself against cross-site requests. A successful login gives the session a new identifier and a new CSRF token, so an identifier known before the login is worthless after it. `logOut` ends the session and expires its cookie. Item 10 sets the session lifetime, the password policy, and the hashing.
- **Mutations.** Every operation other than GET, the receiver of section 5 aside, accepts the session cookie together with the CSRF header. Every one of them except the session operations `logIn` and `logOut` also accepts the operator bearer alone, and none accepts another credential. The tests `every operation other than GET requires the CSRF header with the session cookie` and `every mutation but the session operations also accepts the operator bearer alone` check the document. A bearer request needs no CSRF token, because a browser never adds the bearer by itself. The control plane compares the token with its session's in constant time.
- **Operator credential.** The bearer authenticates the principal that item 10 creates from the G2 bootstrap credential, the first `installation-owner`; authorization then checks that principal's roles like any other principal's (section 3). It is not accepted by the session operations.
- **Order and failures.** For every operation with a session or bearer requirement, the control plane authenticates first, then checks the CSRF token, then the role, and only then reads the request body, so a caller without access learns nothing about the resource. The webhook receiver authenticates by a signature over the body, so it reads the body first, in the order of section 5. Every failure is the kernel `Failure` shape with code `forbidden` and a `details.reason`:

| Status | Schema | Reason | When |
| --- | --- | --- | --- |
| 401 | `AuthenticationFailure` | `unauthenticated` | No valid session cookie or bearer, or an ended session |
| 401 | `AuthenticationFailure` | `login-failed` | A login name and password that do not match; the answer does not say which is wrong |
| 401 | `WebhookRejection` | `signature-invalid` | Only the webhook receiver: an unknown integration or a missing or failed signature (section 5) |
| 403 | `CsrfRejection` | `csrf-token-invalid` | A session-authenticated mutation without the header or with another session's token; nothing took effect |
| 403 | `AccessDenial` | `role-required` | The principal lacks the role of section 3 |

A mutation's 403 response is one of `AccessDenial` and `CsrfRejection`, which differ by their reason. The other statuses follow the kernel codes as in the execution document: 400 `invalid`, 404 `not-found`, 409 `conflict`, 422 `precondition-failed`, 500 `internal`, and 503 `unavailable`.

## 3. Authorization

The Access module checks the role before any port is called; a port never decides authorization ([product ports](product-ports.md) section 2, rule 1; [account pool contract](account-pool.md) section 2, rule 1). The roles are those of [trust model](../trust-model.md#3-project-scoped-authorization-roles) section 3; each principal has at most one role per project.

| Operations | Role |
| --- | --- |
| `readSession`, `logIn`, `logOut` | None; section 2 |
| `listProjects`, `listScmIntegrations`, `readScmIntegration` | Any authenticated principal; `listProjects` returns the projects on which the caller holds a role, and every project to an `installation-owner` |
| `readProject`, `listProjectMembers`, `readProjectDefaults`, `readAutoMergeSetting`, `readRepositoryBinding`, `listProjectAccountSlots` | `project-viewer` or above on the project, or `installation-owner` |
| `readBoard`, `readTaskDetail`, `readInbox`, `readInboxCounts`, `listAgentSessions`, `readAgentSession`, `listAgentSessionTurns`, `listAgentSessionRequests`, `readAgentSessionOutput`, `streamProjectEvents` | `project-viewer` or above on the project, or `installation-owner` |
| `submitTurn`, `respondToNativeRequest` | `project-operator` or above on the project |
| `answerInboxItem` | `project-operator` or above on the project, and the item's `answerableBy` role or above (section 8) |
| `updateProject`, `updateProjectDefaults`, `updateAutoMergeSetting`, `bindRepository` | `project-maintainer` on the project |
| `createProject`, `assignProjectMember`, `removeProjectMember`, `listWorkers`, enrollment tokens, account slots, `createScmIntegration`, `updateScmIntegration` | `installation-owner` |
| `readInstallationInbox`, `readInstallationInboxCounts`, `answerInstallationInboxItem`, `streamInstallationEvents` | `installation-owner` |
| `receiveScmWebhook` | None; section 5 |

An `installation-owner` manages operator principals, so assigning project roles is its command; a project has no member until one is assigned, and its creator gets no role by creating it. Project roles are ordered `project-viewer`, `project-operator`, `project-maintainer`, each holding the capabilities of the one before it (trust model section 3). An `installation-owner` reads every project's views, as it reads every project, but answers a project's items, submits turns, and responds to native requests only with a project role, because these are project capabilities in the trust model.

## 4. Operations

- **Projects.** A project is created with its name and its defaults; its auto-merge setting starts on ([product ports](product-ports.md) section 6.2). The defaults are the SDLC framework plugin that new runs bind to, the harnesses in the project's order of preference, the first of which is the default implementer and the rest the harnesses tried after a limit ([account pool contract](account-pool.md) sections 4.1 and 4.4), the default reviewer, the spec approver (`SPEC_APPROVERS`), and the policy for no eligible slot (section 4.5 there). A change of the defaults applies to tasks created afterwards and changes no run.
- **Auto-merge.** Its own resource with its own revision, as the `AutoMergeSettings` port keeps it; a change records or revokes the push standing rule in the same transaction ([product ports](product-ports.md) sections 5 and 6.2).
- **Repository binding.** One repository of one SCM integration per project, with the integration branch that merges target and the merge method ([source control contract](source-control.md) section 4; [product ports](product-ports.md) section 6.3). The repository is an opaque external identifier, and the binding also holds its HTTPS remote URL without user information, query, or fragment, which workspaces clone from and push to, and the integration branch is their base branch ([git workspace contract](git-workspace.md) sections 3 and 7). A branch is any name that `git check-ref-format --branch` accepts; Git sets no length limit, so the document's bound of 1024 characters only bounds the request. A first binding has no expected revision; a later change needs one. `bindRepository` answers 422 `precondition-failed` with a `BindingRefusal` reason, checked in this order: a remote URL that is not HTTPS (`remote-not-https`), holds user information (`remote-userinfo`), a query (`remote-query`), or a fragment (`remote-fragment`); a remote URL whose normalized origin is not the integration's allowed origin (`remote-origin-mismatch`, section 4.1); and a merge method that the integration's plugin does not declare in its `SourceControlCapabilities` (`merge-method-undeclared`), because every merge with it would fail with `unavailable` ([source control contract](source-control.md) section 2, rule 5, and section 4). The binding does not check that the plugin can reach the repository: no port operation does that.
- **Compare-and-set.** `updateProject`, `updateProjectDefaults`, `updateAutoMergeSetting`, `bindRepository` on a bound project, the slot commands `updateAccountSlot`, `revokeAccountSlot`, `reinstateAccountSlot`, `rotateSlotCredential`, and `removeAccountSlot`, and `updateScmIntegration` name the revision they read and fail with 409 `conflict` when the revision moved, so of two concurrent updates exactly one wins ([product ports](product-ports.md) section 2, rule 7). The exceptions name no revision: the first binding of a project, which fails with 409 when the project is already bound; a member assignment, which replaces the principal's role, so of two concurrent assignments the one serialized last stays, an explicit exception to rule 7, because only an `installation-owner` assigns and the role it sends is the whole state of the membership; a member removal, which succeeds for a principal that is no member; and the enrollment token commands, which serialize with redemption instead.
- **Workers.** `listWorkers` maps `WorkerAdmissionView.workers()` ([worker admission](worker-admission.md) section 8): every enrolled worker that is not revoked, in identifier order, with no credential or credential hash, every detail redacted again, and 503 with no partial data when a source cannot be read.
- **Enrollment tokens.** `issueEnrollmentToken` takes the host constraints and returns the token's record and its secret, `tken_` and 256 random bits ([installation contract](installation-and-enrollment.md) section 5). `rotateEnrollmentToken` replaces a pending token by a new one with the same constraints and a new TTL in one transaction, and `revokeEnrollmentToken` makes a pending one unusable. Both serialize with a redemption on the token's row lock, so of a rotation or revocation and a concurrent `enrollWorker` exactly one wins. Revocation adds a token state that installation contract section 5, check 1, does not list: a redemption treats a revoked token as `token-invalid`, like an unknown, used, or expired one. Revoking a revoked or expired token answers 204, because neither can be redeemed; revoking a used token answers 422 `token-used`, and revoking a token that a rotation replaced answers 422 `token-rotated` with the replacement's `tokenId` in `details.replacementTokenId`, because the replacement stays redeemable. `listEnrollmentTokens` returns pending tokens: unused, unexpired, and not revoked. Worker credential rotation and worker revocation stay administrative commands (installation contract section 4): a rotated generation's secrets belong to the worker, which G3 item 26 delivers them to.
- **Account slots.** The operations map the commands of the [account pool contract](account-pool.md): adding a slot with its credential (sections 3.1 and 7.1, 400 for a mechanism without an admitted delivery or a slot beyond its pair's limit), changing its allowed projects or concurrency limit, revoking, reinstating, rotating its credential (section 8.1, 409 while the slot is active or a held reservation names it), and removing it (section 8). `listProjectAccountSlots` shows a project member the active slots of the project's pools, with whether each also serves other projects but never their names, as section 2, rule 1 requires of item 9.
- **SCM integrations.** An integration is installation-wide: one SCM plugin with a label, the plugin's non-secret settings, and its write-only secrets, which the plugin defines and checks; the core document names no SCM ([source control contract](source-control.md) section 2, rule 1). It also holds the allowed origin of its remote URLs, which only an `installation-owner` sets (section 4.1).

### 4.1 Remote origin

The architect decided on 2026-10-28 how a remote URL is tied to its integration, because the [git workspace contract](git-workspace.md) section 7 sends the per-run SCM credential to exactly the bound remote URL, and the credential's scope check names only the repository.

- **Allowed origin.** Each SCM integration holds an allowed origin: the scheme https, a host, and an optional port, without user information, path, query, or fragment. Only an `installation-owner` sets it, through `createScmIntegration` or `updateScmIntegration`; a `project-maintainer` cannot. The host is a host name, not an IPv6 literal, which has no single lower-case form to compare, and a port is 1 to 65535.
- **Normalization.** Origins are compared only after normalization: the scheme https only, the host in lower case, and the port explicit, 443 when none is given. The integration stores and returns its origin in that form (`NormalizedOrigin`).
- **Binding.** `bindRepository` normalizes the origin of the remote URL and refuses it with 422 when it is not HTTPS, holds user information, a query, or a fragment, or differs from the integration's allowed origin (section 4, "Repository binding").
- **Credential issue.** Every time the control plane issues or re-delivers a per-run SCM credential for a run, a 9c re-delivery included, it first re-checks the binding's remote URL against the integration's current allowed origin. On a mismatch it issues no credential and records the reason `remote-origin-mismatch`, so narrowing an origin later also covers existing bindings.
- **Worker.** The worker sends the credential only to the remote URL that the control plane sent with the run (git workspace contract section 7); items 16c and 16e owe that obligation.
- **Follow-up.** Item 7's SCM port gains an operation that derives the remote URL from the repository, which item 20 implements; `remoteUrl` then becomes output-only.

## 5. Webhook receiver

`receiveScmWebhook` takes `POST /scm-integrations/{integrationId}/webhooks` with no session, CSRF token, or operator credential: the delivery's signature is its authentication. Its order is therefore its own: the receiver reads at most its limit of raw bytes and answers 413 beyond it, then has the plugin verify the signature over those bytes, and only then parses the payload. It never parses the body before verification, and passes it with the headers in lower case to the integration's plugin, whose `verifyWebhookDelivery` checks the signature over those bytes ([source control contract](source-control.md) section 6). The plugin names its signature and delivery headers, so the document declares none. An unknown integration, also one whose identifier is not an `Identifier`, and a failed verification both answer 401 with the same `WebhookRejection` body, reason `signature-invalid`, so an unauthenticated sender learns nothing. A verified delivery whose payload the plugin cannot parse answers 400 `invalid` and is not recorded ([source control contract](source-control.md) section 2, rule 5). A verified delivery answers 202, also when it repeats one already recorded by its `deliveryId`; 413 answers a body over the receiver's limit, which item 20 sets. The receiver needs an ingress that the SCM can reach, which items 26 and 37 provide.

## 6. Identifiers and pages

- **Minted identifiers.** The control plane mints the identifier of a new project, principal, enrollment token, slot, SCM integration, or turn as `workerId` is minted ([installation contract](installation-and-enrollment.md) section 2): one lowercase letter, `p`, `u`, `e`, `s`, `i`, or `t` respectively, and 32 lowercase hexadecimal digits from 128 random bits, a safe name that can become a NATS subject token. On the wire every identifier is an `Identifier`.
- **Pages.** Every list (`list*`) except `listWorkers` returns at most 100 items in the order of its key and a `next` key while more remain, which the caller passes as `after`. The key is the identifier, in the code-unit order of [account pool contract](account-pool.md) section 2, rule 2, except for `listAgentSessionTurns` and `listAgentSessionRequests`, whose key is the position (section 9); `readAgentSessionOutput` pages output by position the same way. `listWorkers` returns the workers view as one unpaged snapshot, as its port returns it, and so do the views of section 8; the tests `every list but the workers snapshot pages by its key` and `the snapshot reads are unpaged and carry the time of their state` check the document.

## 7. Secrets in requests and responses

- **Write-only.** A password, a slot credential, and an SCM integration's secrets travel only in request bodies and carry `writeOnly`; no response schema reaches them, which a test checks. An SCM integration returns the names of its secrets, never their values.
- **One-time reveal.** The only stored secret that a response carries is a new enrollment token's secret, in the 201 response of `issueEnrollmentToken` or `rotateEnrollmentToken`. Only its hash is stored, so no later response can repeat it.
- **Session values.** The session identifier travels only in the `Set-Cookie` header of `readSession` and `logIn`, never in a body. The CSRF token is in the body of `readSession` and `logIn`; it authenticates nothing without the cookie.
- **No caching.** Each response that carries the token's secret or a CSRF token has `Cache-Control: no-store`.
- **Session text.** Session text is the text of an agent session, whoever wrote it: a person's turns and answers, and the harness's native requests and output. It is shown to the project's members and carried by the event streams (section 10), so the control plane redacts it with `@taskelith/secrets` before it records it, and a read and an event carry the same redacted text ([architecture section 11](../architecture.md#11-spa-authentication-and-live-traffic) keeps secret values out of event payloads and prompts). The harness therefore receives a turn or an answer as recorded, redacted: a secret that a person types never reaches the agent's prompt.
- **Output across chunks.** A harness writes output in chunks, and a secret can span two of them, which redacting each chunk alone would let through. The control plane therefore redacts a generation's output as one text: it holds back the tail of what it received that could still be the start or a part of a secret of a known shape or a credential revealed to the run, and records it only when a later chunk shows it is none, redacted if it is one, or when the generation ends. An output entry, the output read, and the `output-appended` event carry only text released this way, so neither path carries a secret split across chunks. The held tail is kept durably with the generation, never shown; after a restart of the control plane, the next chunk or the generation's end, also one that recovery records, decides it as before, so no tail is lost or released unredacted.
- **Idempotency before redaction.** Redaction loses information: two different inputs can redact to the same text. A repeated command is therefore compared by its input before redaction, never by the recorded text. With the idempotency key of a turn, an inbox answer, or a native response, the control plane records a keyed digest of the unredacted input, HMAC-SHA-256 under a control-plane key that no response or log carries, in the transaction that records the redacted input and the outcome. The key repeated with the same digest returns the first outcome; with another digest it answers 409 `idempotency-key-reused`, also when both inputs redact to the same text. The control plane resolves a repeat before the domain or, for an inbox answer, before `NeedsYouSource`, so these see only new keys ([product ports](product-ports.md) section 4.2).
- **Atomic key check.** The key check, the call of the domain or the source, and the digest write commit in one `SERIALIZABLE` transaction, with the key unique within its scope (section 8, section 9). Two concurrent commands with one key therefore commit at most one effect: both may pass the check and call the domain or the source, but only one commits; the other's transaction conflicts, is rolled back with its effect, and is retried as a whole, and the retry finds the key and answers as a repeat, 200 or 409 `idempotency-key-reused`, never as a second answer.
- **Failures and logs.** A failure names settings and identifiers, never a secret value. `@taskelith/secrets` redacts only known shapes and the credentials revealed to a run ([installation contract](installation-and-enrollment.md) section 8), and the session identifier, the CSRF token, a password, a slot credential, and SCM secrets have none of them. A request log therefore holds only an allowlist of request parts: the method, the operation, its path and query parameters, the status, and the failure. It never holds a request body that reaches a `writeOnly` schema or the `Cookie`, `X-CSRF-Token`, or `Authorization` header, and what it holds is still redacted with `@taskelith/secrets`.

## 8. Board, task detail, and inbox

The views map the ports of the [product ports contract](product-ports.md) one to one:

| Operation | Port |
| --- | --- |
| `readBoard` | `BoardReadModel.board` (section 3.5 there) |
| `readTaskDetail` | `BoardReadModel.taskDetail` (section 3.7) |
| `readInbox`, `readInboxCounts` | `NeedsYouInbox.open` and `counts` for the project scope (section 4.3), with the optional `kind` and `runId` filters |
| `readInstallationInbox`, `readInstallationInboxCounts` | The same for the installation scope, which only an `installation-owner` reads (section 4.1) |
| `answerInboxItem`, `answerInstallationInboxItem` | `NeedsYouSource.answer` of the item's source (section 4.3) |

- **Request items.** A `permission-request`, `input-request`, or `delivery-acknowledgement` item names its native request by `sessionId`, `sessionGeneration`, and `nativeRequestId` (`NativeRequestInboxSubject`), the session and key of `listAgentSessionRequests`, because a later generation can reuse a native request ID ([session timeline](session-timeline.md) section 5.3).
- **Snapshots.** Each view is one snapshot with the time of its state (`asOf`) and the event stream position it reflects (`position`), and never partial: when one of its sources cannot be read, it answers 503 ([product ports](product-ports.md) section 2, rule 2, and section 3.5). The views are not paged, because a page would carry its own stamp and the pages together would show no single state.
- **Cards.** A card is one root run, and `readTaskDetail` answers 404 for a run that is not a card of the project, a delegated child's run included ([product ports](product-ports.md) section 3.3). A change of a card's task detail also sends the card's `card-changed` event (section 10), and a client that shows the detail reads it again.
- **Answering.** The control plane authenticates, checks the CSRF token, and checks that the principal holds `project-operator` or above on the project, or `installation-owner` for the installation inbox, before it reads the body. It then reads the item, still before the body, and refuses with 403 `role-required` a principal below the item's `answerableBy` role; this tells such a principal only that the item exists, which it may read anyway. The item's source consumes the answer once and rechecks the current state in its own transaction ([product ports](product-ports.md) sections 2 and 4.2):

| Status | Body | When |
| --- | --- | --- |
| 200 | `InboxItem` | The answer resolved the item, or repeats with the same idempotency key the answer that resolved it; the first outcome is returned |
| 400 | `Failure`, `invalid` | An answer of another kind than the item, `resolve-execution` for an `unrecorded-process` item or `acknowledge-process` for an `unknown-execution` one, or an input text over `MAX_INPUT_ANSWER_BYTES`, 65,536 bytes in UTF-8, the bound of `respondToNativeRequest` too (section 9) |
| 404 | `Failure`, `not-found` | No such item in the project, or in the installation scope |
| 409 | `CommandConflict` | `already-answered`: another answer resolved the item first; `idempotency-key-reused`: the key resolved the item with another answer |
| 422 | `AnswerRefusal` | `item-closed`: the item is closed; `attempt-not-current`: the item's attempt has a newer generation; `subject-changed`: the subject's state no longer allows the answer, such as an execution that is no longer unknown or a gate that is no longer pending |

An idempotency key is scoped to the item it answers. The repeat check comes before the refusal of a resolved item and compares the answer before redaction (section 7). A schema bound counts Unicode code points, while the byte bound of an input answer and the text bounds of section 9 count what their ports count, so a text within the schema can still answer 400.

### 8.1 Acknowledgement of an uncertain delivery

A consumed response whose delivery became `delivery-uncertain` may have run an action, so it opens one inbox item of kind `delivery-acknowledgement` ([session timeline](session-timeline.md) section 5.5; [product ports](product-ports.md) section 4.1). The native request source of item 13 opens it for each request that `uncertainDeliveries` lists, with the card subject of its task, attempt, attempt generation, and native request, which `sessionId`, `sessionGeneration`, and `nativeRequestId` name, answerable by `project-operator` or above. Its only answer, `acknowledge`, records, audited, that a person has seen the uncertain delivery. It resends nothing, answers no request, and starts no turn, because an uncertain delivery is final (session timeline sections 5.4 and 6; [architecture section 7](../architecture.md#durable-chat-turns-and-provider-approvals)).

## 9. Agent sessions

On the wire the session of the [session timeline](session-timeline.md) is an **agent session**, so that its names (`AgentSessionId`, `listAgentSessions`, `/agent-sessions/`) never meet the login session of section 2. A card's agent sessions are those of every task of its run and of the delegated child tasks of its lineage ([product ports](product-ports.md) section 3.3).

- **Reads.** `readAgentSession` returns one session: its task, card, and harness, its limit stop and handoff when it has them, its active bound attempt and running generation, the last positions of its turns and requests, and its output window. `listAgentSessionTurns` lists turns in position order. `listAgentSessionRequests` lists native requests in recording order: a request's `position` is its place in that order from 1 without gaps, which never changes, because the timeline appends requests and never removes them (session timeline section 5.1). Turns and requests change state after a page is read; the events of section 10 carry each change. Every read carries the stamp of section 8.
- **Turns.** `submitTurn` records a turn of the calling principal with the client's idempotency key and text, and the control plane mints its `TurnId` (section 6); the key is not returned by the reads. The answers follow `submitTurn` of the session timeline section 4.1: 201 with `recorded` for a new turn, queued and delivered one at a time in position order (section 4.2 there); 200 with `duplicate` and the turn unchanged, whatever its state, when the key, author, and text before redaction repeat; 409 `idempotency-key-reused` when the key was used for another author or text, compared by the digest of section 7; 422 `TurnRefusal` `session-stopped` for a stopped session; 400 for text outside 1 to 65,536 characters (`MAX_HARNESS_TEXT_LENGTH`). A host turn that delivers a delegation outcome is the host's (item 38), never the wire's.
- **Responses.** `respondToNativeRequest` consumes a person's permission or input answer, naming the request by its generation and native request ID, and the attempt and ownership generation the person answers for ([architecture section 7](../architecture.md#durable-chat-turns-and-provider-approvals); session timeline section 5.2). The answers follow the checks of `consumeResponse` in their order, with the idempotency check before the refusal of an answered request: 400 for text outside its bound, for an input answer `MAX_INPUT_ANSWER_BYTES`, 65,536 bytes in UTF-8, as through the inbox (section 8), and for a permission message `MAX_HARNESS_TEXT_LENGTH`; 404 for an unknown request; for an answered request, 200 with the answered request when the idempotency key and the response repeat those of the response that answered it (section 7, "Idempotency before redaction"), 409 `idempotency-key-reused` when that key comes with another response, and otherwise 409 `already-answered`, the first response staying; 404 for an `expired` or `unresolved` request, which is never answered; 422 `ResponseRefusal` `attempt-not-current` for an attempt or ownership generation that is not the session's active bound one; and 400 for an answer of the wrong kind, which includes any answer to a delegation request, because only the host answers those and the schema admits no delegation result from a person. The key is scoped to the request. A permission or input request is also an inbox item (section 8), and both operations reach the same source, which consumes one answer: whichever commits first wins, and the other answers 409 `already-answered`. A response resolves the request's inbox item in its transaction, which sends `inbox-item-changed` (section 10). Delivery to the harness is reported once and never resent (session timeline section 5.4).
- **Output.** `readAgentSessionOutput` maps `readOutputAfter` (session timeline section 7): after the cursor `after`, `0` by default, it returns at most 100 retained entries in position order and a `next` position while more remain; a cursor older than the retained window returns `cursor-expired` with the earliest retained position, and a cursor after the last position answers 400. After `cursor-expired` the client reads again after the position before the earliest retained one and shows that older output left the window; a durable snapshot of the older output is item 14's (session timeline section 9).
- **Reused names.** Sub-change 9d defines the worker messages that deliver turns and responses and carry session observations back, and reuses these schemas unchanged, as the generator requires: `AgentSessionId`, `AgentSessionGeneration`, `TurnId`, `TurnText`, `TurnOutcome`, `HarnessFailure`, `NativeRequestId`, `NativeRequestKey`, `NativeRequestKind`, `HarnessText`, `NativeAnswer`, `PermissionDecision`, `DelegationResultOutcome`, and `IdempotencyKey`. They use only keywords that JSON Schema draft-07, the dialect of the message schemas, reads as 2020-12 does, which a test checks.

## 10. Event streams

`streamProjectEvents` streams one project's events to a `project-viewer` or above, or an `installation-owner`, and `streamInstallationEvents` streams the installation-scoped inbox events to an `installation-owner`; a stream never carries another project's events (trust model section 3). Both are server-sent events ([architecture section 11](../architecture.md#11-spa-authentication-and-live-traffic)): a `text/event-stream` response with `Cache-Control: no-store`, in which each event is a frame with `id`, its position, `event`, its type, and one `data` line of JSON that matches its schema, except `resync` and `stream-ended`, whose frames have no `id`; comment lines keep the connection alive. `ProjectEvent` and `InstallationEvent` are the unions of the event schemas, told apart by `type`.

| Type | Stream | Data |
| --- | --- | --- |
| `board-changed` | Project | The board's `workersOnline`, after the number of workers online changed, also on a board with no cards |
| `card-changed` | Project | The card, after any change of the card or its task detail |
| `inbox-item-changed` | Both | The item, after it opened, was resolved, or closed; it moves the inbox counts with it (product ports section 4.2), and for an item that counts toward a card the same change also sends the card's `card-changed` with its new `needsYou` |
| `agent-session-changed` | Project | The session, after it opened, bound an attempt, started or ended a generation, stopped, or wrote or gave its handoff |
| `turn-changed` | Project | The turn, after it was recorded or changed state |
| `native-request-changed` | Project | The request, after it was recorded, answered, expired, or became unresolved, or its delivery was reported |
| `output-appended` | Project | The output entry |
| `resync` | Both | The reason; no position (below) |
| `stream-ended` | Both | The reason, `role-changed`; no position (below) |

- **Commit before display.** An event's position exists only after the change it reports has committed: the control plane assigns positions after the commit, in commit order, from one installation-wide sequence, never reuses one, and sends a stream's events in increasing position order. So no event names an uncommitted change, a native request reaches a read or an event only after its record committed ([session timeline](session-timeline.md) section 5.1; architecture section 7), and no event with a lower position appears after a higher one was sent. A stream's positions are that sequence filtered to its scope, so they have gaps. Positions are decimal integers, `0` before any event, so a client compares them.
- **Cursor as a boundary.** A cursor is a boundary in the installation-wide sequence, not the position of an event of the stream: the stream resumes with its scope's events whose position is greater than the cursor. A cursor is valid from the stream's retention floor, the highest position whose events have left the retention, `0` while none has, to the head of the installation-wide sequence, both included; so `0`, a view's position, and a position between two events of the scope, or of another scope's event, are valid. Item 14 keeps events long enough that a view just read can be resumed from its position, so a view read after a `resync` normally gets no other; a client slower than that retention can get `cursor-expired` again and falls back again.
- **Cursor.** The durable cursor is the `Last-Event-ID` header, which a browser sends with the last `id` it received when it reconnects; it wins over the `after` query parameter, which carries the `position` of a view for the first connection, since a browser cannot set the header then. Without either, the stream starts at its head. After the cursor, the stream sends every retained event of its scope in position order and then the live ones. A client that resumes from a view's position can receive an event that another view it holds already reflects; each event carries its record as of its position, so the client skips an event whose position is not greater than that of the view it took the record from.
- **Resync.** A cursor below the stream's retention floor gets a `resync` event with reason `cursor-expired`, and a cursor beyond the head of the installation-wide sequence, such as one from before a restore that set the sequence back, gets `cursor-unknown`. The frame has no `id`, so it moves no cursor, and the server ends the stream after it. The client then closes its `EventSource`, which would otherwise reconnect with the same `Last-Event-ID` and get the same `resync`, and falls back to snapshots: it reads its views again and opens a new stream after the lowest of their positions. The stream answers 200 with this event rather than an error status, because a browser does not reconnect after any status other than 200; only a malformed cursor answers 400.
- **Slow consumers.** Each stream has a bounded buffer; when it is full the control plane ends that stream rather than wait, so a slow consumer never blocks a command or a cancellation ([architecture section 11](../architecture.md#11-spa-authentication-and-live-traffic), R14). The client reconnects with `Last-Event-ID`.
- **Authorization.** A stream is authorized when it connects, and ends when its login session ends; the next connection is refused with 401.
- **Role change.** A stream also ends on any change of its principal's roles in its project, or of its `installation-owner` role, raised or lowered: the server sends `stream-ended` with reason `role-changed`, whose frame has no `id`, and ends the stream. The client reads its views again, so that it shows the `callerMayAct` of its new roles, and resumes from its durable cursor; the reconnection is authorized anew and refused with 403 when no role lets the principal read. So no stream outlives the roles that it was authorized with.
- **Payloads.** An event's data is the record that the corresponding read returns for the same state, or for `board-changed` the field of `readBoard` it reports, so an event shows nothing that a read does not; session text is redacted before it is recorded (section 7). `board-changed` does not carry `callerMayAct`, which is the caller's own and not the board's.
