# Source control port contract

Date: 2026-10-26. Status: proposed contract for G3 ([G3 work plan](../g3-plan.md) item 7, `define-scm-port`), under independent review. It defines the draft `SourceControlProvider` port, version `0.3.0` since the plan item 20 change `run-github-scm-conformance`, through which an SCM plugin issues, refreshes, and ends per-run credentials, derives a repository's remote URL, hosts change requests, commit statuses, and protected merges, and verifies webhooks, and the SCM-neutral conformance suite that every SCM plugin passes. [ADR 0006](../decisions/0006-github-first-scm.md) makes GitHub.com the first SCM and Forgejo a later second one; the [GitHub qualification](../qualification/github.md#consequences-for-the-scm-port) states the port's needs in SCM-neutral terms. G3 item 20 implements the port for GitHub, and item 9 maps it onto the wire schemas.

## 1. Purpose and parties

| Port | Client | Implemented by |
| --- | --- | --- |
| `RunCredentialIssuer`: per-run credentials, refresh, adoption confirmation, revocation | The launch path, which delivers a credential to one run (item 21, section 10) | SCM plugins |
| `RepositoryRemoteResolver`: a repository's remote URL (section 4.1) | The repository binding and the credential issue of [control-plane wire contracts](control-plane-wire-contracts.md) section 4.1 | SCM plugins |
| `ChangeRequestHost`: merge protection, change requests, commit statuses, merges | The integration and merge flow (items 21 and 23) | SCM plugins |
| `WebhookVerifier`: verification of a delivery on its raw body | The webhook receiver, G3 work of items 9, 20, 26, and 37 (section 6) | SCM plugins |
| `SourceControlProvider`: the four ports with the plugin's capabilities | The plugin registry | SCM plugins |

The ports belong to the Integrations module, the "SCM / Tracker integrations" module of [architecture section 6](../architecture.md#modules), next to the [product ports](product-ports.md) of item 8. They are plugin-facing, so the module exports them through its `./port` entry, which holds only port types and constants, as `@taskelith/sdlc/port` does for the SDLC framework port ([ADR 0009](../decisions/0009-frozen-sdlc-framework-port.md)). Each client depends on the narrowest port it uses ([ADR 0004](../decisions/0004-first-class-engineering-principles.md) principle 2).

## 2. Common rules

1. **No vendor names.** No type, value, or test of the module names an SCM. A plugin maps its service onto the port; section 7 records how GitHub and Forgejo map.
2. **Untrusted plain data.** Requests and results are plain strings and arrays, as in the SDLC framework port and the item 8 `IntakeSource` and `WriteBack` ports. Enumerated values are typed as `string` in results, so that an unknown value is a finding rather than a type lie, and the module checks every result at run time.
3. **Opaque identifiers.** Repositories, change requests, commits, runs, credentials, and deliveries are opaque strings that the module compares exactly and never parses. A service's numeric change request number becomes a string. A run identifier is the module's own and has the kernel identifier syntax (`parseIdentifier`: 1 to 128 printable ASCII characters without whitespace). The other identifiers are external: the service issues them, and each is a non-empty string of at most 1024 characters. The module checks both at run time, and the conformance suite reports any other value.
4. **The plugin's own identity.** Change request, status, and merge operations act as the plugin's own identity. The identity that opens a change cannot approve it, so the port has no approval operation.
5. **Failures.** Every operation returns a kernel `Result`. Callers branch on the kernel failure codes: `invalid` for a malformed request, `not-found`, `forbidden` for a refused credential or signature, `precondition-failed` for a refused merge or a protection that the plugin would weaken, and `unavailable` for an undeclared merge method, a service that cannot be reached, or a refresh for which the service gives no later expiry, which a retry after a second can resolve.
6. **Instants.** Expiries are kernel instants: UTC, `YYYY-MM-DDTHH:mm:ss.sssZ`. A plugin normalizes its service's format.
7. **Draft status.** The port stays a draft until a second SCM maps onto it. The item 20 change `revise-scm-port-refresh-and-authorization` raised it from `0.1.0` to `0.2.0`: a refresh keeps the previous secret until the run confirms adoption of the new one (section 3), a run credential carries its version and its `authorization`, and `resolveRemoteUrl` derives a repository's remote URL (section 4.1). The item 20 change `implement-github-scm-plugin-core` re-exports the port's types from the plugin SDK only in its `draft` namespace, outside the frozen root export, and raises the plugin API to `0.3.0`; the port moves to the root export only when it is frozen. The item 20 change `manage-scm-integrations` adds the draft plugin descriptor `SourceControlPlugin` to that namespace and raises the plugin API to `0.4.0`; the port's operations, and so its version `0.2.0`, stay unchanged (section 6.2). The item 20 change `run-github-scm-conformance` adds the propagation window and its constant `REVOCATION_PROPAGATION_SECONDS` (section 3) and the suite's clock (section 8), and raises the port to `0.3.0`: the operations stay unchanged, but the meaning of an end does, and a changed meaning needs the next version, as a refresh's did for `0.2.0`. The plugin SDK's `draft` namespace carries types only and no constants yet, so the constant is not in it; exposing it there is a follow-up of item 20 in the [G3 work plan](../g3-plan.md). Forgejo's admission may revise the port again.

## 3. Credentials

| Constant | Values |
| --- | --- |
| `SCM_PERMISSIONS` | `read-code`, `write-code`, `write-change-requests`, `write-statuses` |

- `issueRunCredential` takes the run, its repositories, and the permissions it needs, and returns a credential for that run only, limited to those repositories for every permission, reads included, with its effective repositories, permissions, and expiry, at version 1.
- **Version.** A credential's versions share its `credentialId`; a version is the secret that one issue or refresh returned, numbered 1 at issue and one more at each refresh, as the version of [execution wire contracts](execution-wire-contracts.md) section 8.7.
- **Authorization.** Each version also carries `authorization`, the complete value of the HTTP `Authorization` header that sends its secret, which the Git workspace places in `http.extraHeader` ([Git workspace contract](git-workspace.md) section 7). The plugin forms it, because the form belongs to the service (section 7). It is a scheme, one space, and credentials of visible ASCII characters with inner spaces only, so that no line break reaches a header, at most 65536 characters as the wire's `ScmAuthorization`, and it is as secret as the secret itself. The workspace's `WorkspaceCredential` is the part of `RunCredential` it uses, `authorization` included.
- The effective permissions are what the credential can actually do: each one works in the project, and a permission not listed does not.
- Effective permissions cover the request and may exceed it when the service has no narrower permission, and the plugin reports them; a credential requested without `write-code` never has it. A service whose only permission for change request or status writes also writes code therefore cannot serve a request for them without `write-code`, and the conformance suite reports such a grant (section 7 records this gate for Forgejo). The policy that accepts or refuses a wider set belongs to the module's use cases.
- The secret goes only to its run and is never logged or stored. The redaction of log text and of `@taskelith/secrets` matches Taskelith's own secret shapes (`tkop_`, `tken_`, and `tkwk_` tokens, NKey seeds, JWTs, and `.creds` blocks), the GitHub plugin's per-run secret, a GitHub App installation token (`ghs_` and at least 36 characters of `A-Za-z0-9._-`, GitHub's own pattern for its stateful and stateless formats, wherever it starts), through the shared `SECRET_SHAPE_RULES` of `@taskelith/observability`, which both use (item 20, `implement-github-scm-plugin`), and secrets in marked positions (URL user information, and `Basic` credentials after an `Authorization` header name, as Git's `http.extraHeader` carries the GitHub plugin's `authorization`, in both; `Bearer` tokens, `key=value` pairs, and log fields whose names mark a secret in logs). No rule matches a bare token of another SCM service outside these marked positions, and no production path calls `scrubEnvironment` of `@taskelith/secrets` yet: that is a G3 obligation of item 21 (`implement-review-and-verification-stages`), which owns the delivery of the credential to a run (section 10) and scrubs it on that delivery path.
- Credentials of different runs are independent: neither widens the other, and revoking one leaves the other usable.
- `refreshRunCredential` returns the next version of the credential: the same `credentialId`, repositories, and permissions, a new secret and `authorization`, and a later expiry, so that a long run keeps working. It ends no earlier version: each one stays valid, reads included, until an adoption confirmation ends it, a revocation ends the credential, or its own expiry, its deadline, passes. The service enforces that expiry where it can; otherwise the plugin refuses the version from its next operation on. A refresh fails with `not-found` for an unknown or revoked credential.
- `confirmRunCredentialAdoption` (request `RunCredentialAdoption`) names the credential and the version its run adopted, and ends every earlier version, reads included; the adopted version and later ones stay valid. A repeated confirmation, or one of a version at or below one already confirmed, succeeds and ends nothing more. It fails with `not-found` for an unknown or revoked credential and for a version not yet issued. As with item 26's worker credentials, the predecessor stays valid until its successor is confirmed or its deadline passes; the module ends a version without a confirmation by confirming a later one, and the version's own expiry ends it in any case.
- Delivery of a refreshed credential to a running run is open G3 work. Item 9 (`define-g3-wire-contracts`) defines the notice that tells the worker of it, which carries no secret, the HTTPS fetch with which the worker then takes it (`fetchRunScmCredential`, sub-change 9c), and the worker's confirmation that the run adopted it (sub-change 9d, [worker messages and terminal](worker-messages-and-terminal.md) section 6), item 21 delivers it, item 18 (`implement-harness-host-in-worker`) adopts it by passing the run's current credential to the item 16 workspace per operation and sends the confirmation, and item 21 ends the previous version through `confirmRunCredentialAdoption` by the run-wide rule of that section 6. Because a refresh ends no earlier version, a failed delivery leaves the run working with the version it holds.
- `revokeRunCredential` ends the credential, every version of it, reads included, and returns no value. It fails with `not-found` for an unknown or revoked credential.
- **Propagation window.** An adoption confirmation or a revocation requests the end of its versions at the service before it returns. The service may take a while to apply the end everywhere: every surface, Git's smart HTTP included, refuses an ended version within `REVOCATION_PROPAGATION_SECONDS`, 30 seconds, counted from the operation's return. A permission or repository that a version was never granted is refused at once. Section 7 states what each service guarantees.
- **Isolation boundary.** Because of that window, no consumer relies on a revocation or an adoption alone to isolate runs. The fencing of a run's owned state and mediated operations ([architecture](../architecture.md)) and the workspace hand-off and reclaim ([Git workspace contract](git-workspace.md) section 3) stay the isolation boundary.

## 4. Change requests, statuses, and merges

| Constant | Values |
| --- | --- |
| `CHANGE_REQUEST_STATES` | `open`, `closed`, `merged` |
| `COMMIT_STATUS_STATES` | `pending`, `success`, `failure`, `error` |
| `MERGE_METHODS` | `merge-commit`, `squash`, `rebase` |

- `ensureMergeProtection` configures the base branch's required status contexts and reports `bindsProvider`, which is true only when the service enforces the protection against the plugin's own identity. When configuring them would drop or weaken a setting of the branch's current protection, such as a required review, it fails with `precondition-failed`, names those settings in the failure's details, and changes nothing. A protection that already is as requested is not written again. A service without a conditional write, such as GitHub, leaves a window between the read and the write in which an operator's change is overwritten.
- `openChangeRequest` and `readChangeRequest` return the change request with its repository, branches, head commit, state, and link. A merge made outside the port, such as a manual merge, appears as the `merged` state and as a `change-request` webhook event; the module records it through the item 8 `MergeQueue.recordManualMerge`.
- `setCommitStatus` posts a status on one commit in one context.
- `mergeChangeRequest` (request `ChangeRequestMerge`) names the expected head and the project's merge method. It fails with `precondition-failed` while any required status is missing, `pending`, `failure`, or `error`, or when the head differs from the expected one, and with `unavailable` for a method the plugin does not declare. On success it returns the method used and the base branch head after the merge as its merge commit.
- A refused merge leaves the change request open and the base branch unchanged.

### 4.1 Repository remote

- `resolveRemoteUrl` takes a repository and returns it with its remote URL, as the plugin's own identity reads it from the service: an HTTPS URL of at most 2048 characters with a host name, not an IPv6 literal, an optional port from 1 to 65535, and no white space, user information, query, or fragment, the `RemoteUrl` form of the execution wire document and the form that the repository binding requires ([control-plane wire contracts](control-plane-wire-contracts.md) section 4, "Repository binding"). It fails with `not-found` for a repository that the plugin's identity cannot see.
- `bindRepository` resolves a binding's remote URL through this operation, so the binding's `remoteUrl` is output-only since sub-change 11b1 ([control-plane wire contracts](control-plane-wire-contracts.md) sections 4 and 4.1). It maps `not-found` to 422 `repository-not-visible` and `forbidden` to 422 `integration-credential-refused`, and treats a value outside this form as a plugin defect; that mapping belongs to the binding's handlers, not to the port.

## 5. Review identity

By G3 plan decision D8 (a), independent review is Taskelith evidence, posted as a commit status in the project's review context that merge protection requires.

| Constant | Values |
| --- | --- |
| `REVIEW_EVIDENCE_KINDS` | `required-status` (mandatory), `native-approval` (reserved for a separate reviewer identity, D8 (b)) |

A plugin declares its merge methods and review evidence in `SourceControlCapabilities`. A merge is refused while the review context is pending, even after verification has succeeded.

## 6. Webhooks

| Constant | Values |
| --- | --- |
| `WEBHOOK_EVENT_KINDS` | `change-request`, `commit-status`, `push`, `other` |

- `verifyWebhookDelivery` receives the headers, with names in lower case, and the body bytes exactly as received. It verifies the signature over those bytes before it trusts any payload.
- It fails with `forbidden` for a missing signature, a signature made with another secret, or a body that was parsed and serialized again.
- The receiver that calls it needs an ingress that the service can reach, with TLS. The installation has no externally reachable ingress: it publishes the control-plane API on `127.0.0.1` only, over HTTPS on a certificate of the installation CA since G3 sub-change 26a ([local installation](../local-installation.md)). Item 9 (`define-g3-wire-contracts`) defines the receiver's HTTP operation, item 20 builds the receiver (section 6.1), item 26 (`secure-remote-connectivity`) provides the TLS of D11 (b), and item 37 (`extend-installation-for-g3`) the installation that serves it. Until they merge, no service can deliver a webhook to an installation.
- The verified event carries an opaque `deliveryId` that every redelivery of the same delivery repeats and that differs between deliveries; the module deduplicates by it.

### 6.1 Receipt

The module's `ScmWebhookReceiver` serves the receiver of [control-plane wire contracts](control-plane-wire-contracts.md) section 5 (item 20, sub-change `receive-scm-webhooks`) through four ports of its own, outside the plugin-facing port entry, and the installation's SCM plugin identifier (`pluginId`), which names that plugin in each defect record:

| Port | Role | Implemented by |
| --- | --- | --- |
| `ScmIntegrationVerifiers` | The `WebhookVerifier` of an integration by its identifier, or none for an unknown one | The module's `StoredScmIntegrationVerifiers` over the stored integrations (section 6.2): each verifier is built by the integration's plugin and kept per integration and revision, so a changed webhook secret verifies the next delivery |
| `ScmWebhookDeliveries` | Records a verified event once per integration and `deliveryId`, answering `recorded` or `repeated` | The PostgreSQL adapter: the table `scm_webhook_deliveries`, keyed by both, without a foreign key, with the identifiers stored as their UTF-16LE code units so that any port identifier, a NUL included, is kept exactly |
| `EventlessDeliveries` | Tells, by its headers, a verified delivery that its service sends without an event of the port | The plugin descriptor's `isEventless`, which the composition passes on: for GitHub, the events `ping`, `installation`, and `installation_repositories` |
| `ScmPluginDefects` (`defects`) | Reports a plugin defect by integration, plugin, operation, and kind, never with a value | The control plane's log, one `scm.plugin.defect` record per defect |

- **One refusal.** An identifier that is not a kernel `Identifier`, an unknown integration, a `forbidden` verification, a missing signature, and a plugin defect of `verifyWebhookDelivery` or `isEventless` all fail with `forbidden`, reason `signature-invalid`, and one message, and record nothing. A defect is a call that throws or answers outside its contract, such as a verified event of another shape or an eventless answer that is no boolean, and is reported through `ScmPluginDefects`. For an unknown or invalid integration, for a stored one whose plugin is not registered or cannot build it, and after a plugin defect, the receiver first runs a decoy verifier, which the plugin descriptor's `createDecoy` provides with the work of the plugin's verification for the same headers: for GitHub, nothing for a missing or malformed signature, and HMAC-SHA256 over the raw body under a random key with a constant-time comparison for a well-formed one.
- **No event.** A verification that fails with `invalid` comes after a valid signature, since a plugin checks the signature first. The receipt is `no-event`, answered 202 and not recorded, only when `EventlessDeliveries` calls the delivery eventless and its body is a JSON object in strict UTF-8: for GitHub, a `ping`, `installation`, or `installation_repositories` event, which has no repository for the port's `WebhookEvent`. Any other one, such as a `push` without a repository or a `ping` whose body is no JSON object, fails with `invalid`. The headers are not signed: GitHub's signature covers the body only, so the event and delivery headers are trusted only as far as TLS and the secret keep signed bodies from others.
- **Checked events.** The receiver checks a verified event with the module's runtime reader before it records it; an event of another shape is a plugin defect of `verifyWebhookDelivery`, which gets the decoy's verification and the one refusal, and is not recorded.
- **Concurrent redeliveries.** Each record is one SERIALIZABLE transaction that inserts with `ON CONFLICT DO NOTHING` on the key. Of two concurrent identical deliveries one inserts; the other's insert meets a row its snapshot cannot see, fails to serialize, and its retry answers `repeated`.

### 6.2 Integrations and plugin descriptor

SCM integrations are installation-wide records of [control-plane wire contracts](control-plane-wire-contracts.md) section 4, which the module's `ScmIntegrationService` manages over the store port `ScmIntegrations` (item 20, sub-change `manage-scm-integrations`).

- **Plugin descriptor.** An SCM plugin exposes the draft `SourceControlPlugin` of the port entry: its manifest identifier, the secret names every integration must hold, `checkSettings` for the whole set of settings, `checkSecret` for one secret, `createProvider` from an integration's settings and secrets, `createDecoy`, and `isEventless`. A check fails with `invalid` and `details.setting`; the module answers with the name alone, never the value or the plugin's message.
- **GitHub names.** The GitHub plugin's settings are `app-id` and `installation-id`, positive decimal numbers, and `merge-methods`, a comma-separated list of distinct port merge methods; its secrets are `private-key`, an RSA private key that Node.js parses, because App tokens are signed with RS256, and `webhook-secret`, not empty.
- **Changes.** Creation needs a registered plugin, `not-found` otherwise, every setting, and every secret of the descriptor. An update by compare-and-set replaces the settings whole when it names them and only the secrets it names.
- **Secrets at rest.** The PostgreSQL adapter seals each secret with AES-256-GCM under the control-plane key `scm-integration-secrets.key`, never the slot credential key, with the integration, the secret's name, and the integration's revision as authenticated data. An update re-seals every secret under the new revision, so a ciphertext of an earlier revision no longer opens.

## 7. SCM mapping

The GitHub column follows the [GitHub qualification](../qualification/github.md#consequences-for-the-scm-port) record. The Forgejo column is an assumption about Forgejo's model, written without a source consulted for this change and without a pinned version. The Forgejo plugin must confirm each row at its pinned version, with sources, before admission ([ADR 0006](../decisions/0006-github-first-scm.md) decision 4). The unconfirmed conditions are, per row: how a plugin creates a token for the bot user, and with which authentication; the available token scopes; whether a token can expire or only be deleted; the `Authorization` form that Git's HTTP transport accepts for a token; whether branch protection can deny a merge override to the bot user; the merge API's method values and whether it can require the expected head; and the names of the signature and delivery headers.

| Port element | GitHub.com | Forgejo |
| --- | --- | --- |
| Run credential | Installation access token from the installation's App, requested with `repositories` and `permissions` | Access token of a per-project bot user that is a collaborator only on the project's repositories, with token scopes |
| Permissions | `contents` read or write, `pull_requests` write, `statuses` write | Token scopes are coarser (repository read or write, assumed `read:repository` and `write:repository`); the plugin reports the effective set; `write:repository` writes code, so it cannot serve a request without `write-code` (admission gate below) |
| Refresh | A new installation token before the hour expires; the previous token stays valid until its own expiry. GitHub states expiry in whole seconds, so a token from the newest version's second is revoked and minted again after a wait; one still no later fails with `unavailable` | A new token; the old one stays until its revocation, so its deadline is enforced by revocation |
| Adoption confirmation | Revoke every earlier installation token of the credential | Delete every earlier access token of the credential |
| Authorization | `Basic ` followed by the base64 of `x-access-token:<secret>` ([Git workspace contract](git-workspace.md) section 14) | The form of a token in Git's HTTP authentication |
| Remote URL | The repository's HTTPS clone URL | The repository's HTTPS clone URL |
| Revocation | Revoke the installation token. The REST API refuses a revoked token at once; Git's smart HTTP accepts one for a few seconds more: the recorded live runs of `run-github-scm-conformance` saw every ended token refused within the window of section 3 | Delete the access token |
| Merge protection binding the plugin | Protected branch with required status checks and `enforce_admins: true` | Branch protection with required status checks, with the bot user given no merge override |
| Change request | Pull request; number as an opaque string | Pull request; index as an opaque string |
| Commit status | Commit status API with a context | Commit status API with a context |
| Merge with method and expected head | Merge API with `merge_method` and `sha` | Merge API with `Do` (merge, squash, or rebase) and the head commit |
| Review evidence (D8 (a)) | Required commit status posted by the App | Required commit status posted by the bot user |
| Webhook signature | HMAC-SHA256 of the raw body in `X-Hub-Signature-256` | HMAC-SHA256 of the raw body in the signature header |
| Delivery identifier | `X-GitHub-Delivery` | The delivery header's GUID |

The GitHub plugin keeps its credential versions in its process's memory only (`implement-github-scm-plugin-core`). After a restart every earlier credential is unknown, so a refresh, an adoption confirmation, or a revocation of it fails with `not-found` and never succeeds; its installation tokens end at GitHub's own expiry, at most an hour later. An adoption confirmation or a revocation revokes the ended tokens at GitHub, so no token outlives the plugin's record of it beyond that expiry. A version a minute past its expiry ends without a request to GitHub, and a credential whose every version has ended is forgotten, so an operation on it fails with `not-found`. Durable credential state belongs to item 21.

The gaps are recorded, not hidden: Forgejo's coarser token scopes make the effective permissions a superset for some runs, and its credential refresh is a revocation flow rather than a service expiry. A superset is allowed except for `write-code` (section 3). If Forgejo allows change request or status writes only with a scope that also writes code, such as `write:repository`, its plugin cannot serve a request for `write-change-requests` or `write-statuses` without `write-code`, and the suite's credential cases report every such grant. This is a Forgejo admission and compatibility gate: its admission must show a narrower mechanism at its pinned version, or the port must be revised (section 2, rule 7) before Forgejo is admitted.

## 8. Conformance suite

`runSourceControlConformance` runs against a live service with the plugin's own credential. The plugin's test supplies a fixture: the provider, a project repository, a foreign repository outside the project that the plugin's own identity can access, so that a refusal shows the credential's scope, a hidden repository that the plugin's own identity cannot see, the project repository's remote URL as the service names it, the base branch, the merge method, and native helpers to create and advance a head branch, read a branch head, observe a merge's method, attempt with a run credential the action that each permission allows (a code read and a code write, which send the credential's `authorization` as the Git workspace does, a change request write, and a status write), attempt the most privileged native merge, sign a delivery with the plugin's secret or another one, and a clock on which the suite waits for an ended version's refusal, which a test may fake. The report has a finding for each thrown error, malformed or unknown result value, and outcome that differs from this contract. No finding carries a value that the plugin or the fixture supplied. A finding names a thrown value only by a fixed category, one of the built-in error classes, another `Error` class, or a value that is not an `Error`, and never by its message, name, stack, or other payload. It names a malformed, unknown, or mismatched result field, of the plugin or of a fixture `Result`, by its path and the kind of problem, never by its value. It may name the suite's own terms: operations, fixture steps, its contexts and run probes, the port's constants, and values that matched them. A secret in a thrown error, in a result, or in a fixture value therefore never reaches the report. Among others, the suite checks on the service that:

- in the project, every credential, read-only, write, change request, status, and refreshed, can do exactly what its effective permissions allow and nothing else, and outside the project it can do nothing, reads included;
- an issue returns version 1, and a refresh of a read-only credential and of one with every permission keeps the `credentialId` and the effective permissions and returns the next version, a later expiry, and a new secret and `authorization`;
- after a refresh both versions can do exactly what the permissions allow, and after the adoption of the new one the previous one can do nothing, reads included, while the new one still works;
- after an adoption confirmation or a revocation, the suite repeats each attempt with an ended version about once a second on the fixture's clock until it is refused or the window of section 3 has passed, starts and answers every attempt within the window, which the probes of one ending share, bounds an attempt that does not answer by the window, and records the slowest answer of each ending in the report's `endings`; a refusal with another code than `forbidden`, a refusal answered after the window, or a success at the window's end, is a finding;
- an adoption ends only the versions before the adopted one, a repeated or stale adoption ends nothing more and restores nothing, an adoption of a version not yet issued, of an unknown credential, or of a revoked one fails with `not-found`, a credential still refreshes after a confirmed adoption, a revocation ends every version, reads included, and a refresh or a revocation of a revoked or an unknown credential fails with `not-found`;
- `resolveRemoteUrl` returns the requested repository with an HTTPS remote URL without user information, query, or fragment, the fixture's URL for the project repository, and another one for the foreign repository, and fails with `not-found` for the hidden repository;
- two runs' credentials stay independent and have distinct secrets and `authorization` values;
- each required context, including any the service already required, blocks a merge through the port and through the native bypass while it is missing, pending, failed, or in error, for every declared merge method, and a moved head blocks every declared method too;
- the native bypass merges a change request whose statuses all succeed, so that a broken helper cannot pass as protection;
- every declared method merges with that method and reports the base branch head as its merge commit, and every undeclared method fails with `unavailable`;
- a re-serialized body, a foreign signature, and a missing signature fail with `forbidden`, and delivery identifiers are stable per delivery and distinct between deliveries.

## 9. Required tests

- This item: the suite against a test-only in-memory SCM, and against defective variants of it, each of which the suite must report.
