---
name: taskelith-task-protocol
description: The Taskelith agent task protocol for coordinator and worker sessions. Use when starting, reviewing, handing off, assigning, or integrating a Taskelith task, or when told to continue Taskelith work.
---

Read `docs/agent-task-protocol.md` in this repository and follow it step by step for your role:

- As a **worker**, follow "Worker steps" from the worktree through the archive of your change on its own branch to the handoff, then stop and wait for the coordinator; after it reports the merge, clean up and take the next brief in the same session, without a `/clear`.
- As the **coordinator**, follow "Coordinator steps" to assign, integrate each archived change with one pull request, clean up, and release workers; a branch that conflicts with `dev`, whose evidence the merge invalidates, or that lacks its archive commit goes back to its worker. The coordinator merges `dev` only on a local integration branch in its own worktree (`make integrate`), pushes the merge only when it will integrate, and on any return discards that branch and worktree, so a returned branch never carries a coordinator merge. On any return of a branch that carries its archive commit, the worker restores the active change by reverting that commit, merges `dev`, reconciles each restored delta with `dev`'s current requirement text, keeping others' edits, has reviewer A review the resolved diff and the reconciliation, records it, and archives again as the last commit; a branch without an archive commit only needs step 7.

The protocol builds on `AGENTS.md`, `docs/governance.md`, and `docs/releases.md`; read them when the protocol points to them. Never skip the OpenSpec change, `make verify`, or the independent review, and send owner decisions to the coordinator (or, as coordinator, to the owner) with options instead of deciding them.

Since 2026-10-26 (owner rule), develop each task's worktree work in a subagent that you brief and whose result you check; keep messages, owner questions, the review, and the handoff in your own session. Never resume a subagent that has been idle for more than five minutes; for a round of review fixes, start a fresh subagent with a short brief of the findings, files, and checks. `docs/agent-task-protocol.md` "Subagent execution" has the details.

If a review attempt does not run to a report for any reason, do not use that reviewer for any task for 30 minutes. Propose the next reviewer in the rotation that is not paused, meets the task's review requirements, may take the role under `docs/governance.md` "Reviewer assignment", and, for a task with reviewers A and B, has a harness different from the task's other reviewer (a worker proposes it to the coordinator, who assigns it; a coordinator that develops the task itself chooses it and records why), as `docs/governance.md` "Unavailable reviewer" sets out. If no reviewer of another harness is available and allowed in the role, the coordinator may assign a different model of the same harness and records the reason in `verification.md`. Each task has two reviewers, normally of different harnesses, assigned as `docs/governance.md` "Reviewer assignment" sets out (owner, 2026-10-27; normally Codex CLI gpt-6.1-sol as A and Claude Code claude-opus-5-5 as B): reviewer A makes the full pass 1 and confirms the pass 2 fixes in pass 3 when `docs/governance.md` "Conditional third pass" requires it, reviewer B makes the full, independent pass 2 and checks the pass 1 fixes, and a Low-only pass ends the review (`docs/governance.md` "Two alternating reviewers per task"); a replacement takes the role, A or B, of the reviewer it replaces. Run every pass with `make review CHANGE=<change> PASS=<n> ROLE=<A|B> REVIEWER='<reviewer key>' PROMPT=<prompt file> LOG=<log file>`, never a hand-typed reviewer command: it routes a stamped tree before pass 1 or refuses, runs the reviewer's fixed invocation from `scripts/reviewer-invocations.ts` without any secret in its environment, and appends the pass line with counts 0, which you set when you record the findings. The reviewer keys, one per reviewer (a harness may have several reviewers, named by their models), and current pauses are in `docs/agent-task-protocol.md`.

After each pass that runs to a report, record one summary line in the change's `passes.jsonl`, also for a pass without findings, with the role, A or B, reviewer, session, and counts by severity, and every review finding as one line of its `findings.jsonl` (both files empty before the first pass), with the capability of every finding outside `openspec/changes/` (the closest one when the change skips specs) and `missedBy` when an earlier pass or the integration missed it, and check at the archive that both files exist and `make findings ARGS="validate"` passes; `make findings ARGS="reviewers"` prints the statistics per reviewer and role; as coordinator, paste the output of `make findings ARGS="checklist --capability <a,b> --files <globs>"`, with its "Record quality" section and its dev commit line, the exact invocation, and the task's size, into every brief; as worker, save that checklist when you create the change by running the brief's invocation with `--save <change> --at <dev commit>` (and `--size <size>` when the brief gives one), which writes `checklist.json` from the archive as of the brief's dev commit, and never edit it; `make findings ARGS="effect"` compares archived pass-1 findings with their checklists and archived routes with the passes they needed. As worker, once the implementation is committed and before the `make verify` run that `make record` records for pass 1, run `make findings ARGS="route --change <change>"` and commit its `route.json` unedited; it only recommends: review with the brief's reviewers at the effort that `docs/governance.md` "Routed effort" allows, and report a reviewer A in `route.json` other than the brief's to the coordinator. The shadow router reads `JEV_MAF_LAB`, which the owner sets; without it the rule decides alone. `docs/agent-task-protocol.md` "Review findings record" has the details.

Keep your context thin: as coordinator, offload polling to background scripts and notifications and keep briefs in files; as worker, do all task work in subagents. The repository's Claude Code hook warns at an estimated 140,000 tokens. When your context approaches 150,000 tokens, record what a reset would lose, tell the owner, and recommend `/compact` or `/clear` (only `/compact` in the middle of a task); a worker also tells the coordinator. `docs/agent-task-protocol.md` "Context size" has the details.
